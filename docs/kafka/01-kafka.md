# Apache Kafka

## Что это такое

Kafka — распределённый журнал сообщений, а не очередь в привычном смысле.

Различие принципиальное. В классической очереди сообщение удаляется после
получения потребителем. В Kafka сообщение записывается в лог и хранится заданное
время независимо от того, кто и сколько раз его прочитал.

```text
очередь → прочитал, сообщение исчезло
Kafka   → прочитал, сообщение осталось, сдвинулся указатель чтения
```

Отсюда свойства, которых у очередей нет: несколько независимых потребителей читают
одни и те же данные, потребитель может перечитать историю с любого места, а
добавление нового читателя не влияет на существующих.

---

## Устройство

```text
Broker    → узел кластера, хранит данные
Topic     → именованный поток сообщений
Partition → часть топика, упорядоченный лог
Offset    → порядковый номер сообщения внутри партиции
Producer  → пишет сообщения
Consumer  → читает сообщения
Consumer Group → группа потребителей, распределяющих партиции между собой
```

### Партиции

Топик делится на партиции, и каждая — независимый упорядоченный лог.

```text
Topic "orders"

partition 0: [0][1][2][3][4]
partition 1: [0][1][2]
partition 2: [0][1][2][3]
             ↑
          offset
```

Партиции нужны для параллелизма: каждую может обрабатывать отдельный потребитель.
Число партиций — потолок параллелизма внутри одной группы.

Ключевое ограничение: **порядок гарантируется только внутри партиции**. Между
партициями порядка нет.

### Ключ сообщения

Ключ определяет, в какую партицию попадёт сообщение:

```text
partition = hash(key) % количество партиций
```

Сообщения с одинаковым ключом всегда попадают в одну партицию, а значит,
обрабатываются по порядку.

```java
// все события одного заказа попадут в одну партицию
producer.send(new ProducerRecord<>("orders", orderId.toString(), event));
```

Это стандартный приём: если важен порядок событий по сущности, ключом берут её
идентификатор. Глобальный порядок по всему топику возможен только при одной
партиции — то есть ценой полного отказа от параллелизма.

Без ключа сообщения распределяются по партициям равномерно.

Важная деталь: изменение числа партиций ломает соответствие. Ключ, ранее попадавший
в партицию 2, после расширения может попасть в партицию 5, и порядок нарушится.
Поэтому число партиций планируют заранее с запасом.

## Consumer Group

Основной механизм масштабирования потребления.

```text
Topic с 3 партициями, группа из 3 потребителей

partition 0 → consumer A
partition 1 → consumer B
partition 2 → consumer C
```

Правило: внутри одной группы **одна партиция обрабатывается ровно одним
потребителем**. Один потребитель при этом может держать несколько партиций.

```text
потребителей меньше партиций → кто-то держит несколько
потребителей больше партиций → лишние простаивают
```

Последнее часто становится неожиданностью: добавили пятый экземпляр сервиса, а
пропускная способность не выросла, потому что партиций всего четыре.

Разные группы независимы: каждая имеет собственные позиции чтения и получает все
сообщения топика. Так один поток событий обслуживает несколько подсистем.

## Offset и фиксация

Позиция чтения хранится не у потребителя, а в служебном топике
`__consumer_offsets`. Поэтому после перезапуска потребитель продолжает с того же
места.

```java
enable.auto.commit=true      // фиксация по таймеру, по умолчанию
enable.auto.commit=false     // фиксация вручную
```

Автоматическая фиксация удобна, но опасна: позиция может зафиксироваться раньше,
чем сообщение обработано. При падении между этими моментами сообщение потеряется.

```java
// ручная фиксация после обработки
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    for (ConsumerRecord<String, String> record : records) {
        process(record);
    }

    consumer.commitSync();
}
```

```text
commitSync  → блокирует до подтверждения, надёжнее
commitAsync → не блокирует, быстрее, без гарантии
```

## Гарантии доставки

Определяются моментом фиксации относительно обработки.

### At most once

```text
1. прочитали
2. зафиксировали offset
3. обработали   ← падение здесь → сообщение потеряно
```

Потери возможны, дубликатов нет. Подходит для метрик и телеметрии, где потеря
отдельного значения безразлична.

### At least once

```text
1. прочитали
2. обработали
3. зафиксировали offset   ← падение до этого → сообщение прочитается снова
```

Потерь нет, дубликаты возможны. Режим по умолчанию и наиболее употребимый.

### Exactly once

Достигается сочетанием идемпотентного продюсера и транзакций Kafka.

Существенная оговорка, которую стоит проговаривать: гарантия действует **в пределах
Kafka** — при чтении из топика, обработке и записи в другой топик. Если обработка
включает вставку в базу или вызов внешнего API, exactly-once протокол не
охватывает: атомарно зафиксировать транзакцию Kafka и транзакцию базы нельзя.

Поэтому практический ответ на вопрос про exactly-once — **at-least-once плюс
идемпотентный потребитель**. Обработка строится так, чтобы повторное получение
сообщения не меняло результат: проверка по идентификатору события, `UPSERT` вместо
`INSERT`, вставка с уникальным ограничением.

---

## Идемпотентный продюсер

Решает проблему дубликатов при повторных отправках.

```text
продюсер отправил сообщение
брокер записал
подтверждение потерялось в сети
продюсер повторил → дубликат в логе
```

С идемпотентностью каждому продюсеру присваивается идентификатор, а сообщениям —
последовательные номера. Брокер отбрасывает повтор с уже виденным номером.

```properties
enable.idempotence=true
```

Начиная с Kafka 3.0 включено по умолчанию.

Действует в пределах сессии продюсера и одной партиции. Дубликаты, возникшие из-за
повторной обработки на стороне потребителя, это не решает.

## Подтверждения и репликация

### Репликация

Каждая партиция имеет несколько копий на разных брокерах: одна — лидер, остальные —
последователи.

```text
ISR (in-sync replicas) → реплики, не отстающие от лидера
```

При отказе лидера новым становится одна из ISR.

### acks

```text
acks=0   → продюсер не ждёт подтверждения, потери возможны
acks=1   → ждёт запись лидером; при его отказе до репликации данные теряются
acks=all → ждёт запись всеми ISR, надёжно
```

`acks=all` работает только в связке с `min.insync.replicas`:

```properties
acks=all
min.insync.replicas=2
replication.factor=3
```

Иначе при единственной живой реплике `all` вырождается в `acks=1`. Такое сочетание
переживает отказ одного брокера без потерь.

### Повторы и порядок

Тонкость, которую спрашивают у тех, кто уверенно ответил про `acks`.

```text
retries > 0 и max.in.flight.requests.per.connection > 1
→ повторно отправленное сообщение может обогнать следующее
→ порядок в партиции нарушается
```

Идемпотентный продюсер сохраняет порядок при значении до пяти включительно. Без
идемпотентности единственный способ гарантировать порядок — ограничить число
одновременных запросов единицей, что бьёт по пропускной способности.

## Ребалансировка

Перераспределение партиций между потребителями группы. Запускается, когда
потребитель присоединяется, покидает группу или перестаёт отвечать.

Классический вариант останавливает всю группу: партиции отзываются у всех, затем
раздаются заново. Обработка на это время прекращается.

```properties
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

Кооперативная стратегия перераспределяет только затронутые партиции, остальные
продолжают обрабатываться.

### Главная практическая проблема

```properties
max.poll.interval.ms=300000   # 5 минут по умолчанию
max.poll.records=500
```

Если обработка пачки сообщений заняла больше `max.poll.interval.ms`, брокер сочтёт
потребителя мёртвым и исключит из группы. Начнётся ребалансировка, партиция уйдёт
другому потребителю, а сообщения — не зафиксированные — будут обработаны повторно.

```text
долгая обработка
→ исключение из группы
→ ребалансировка
→ повторная обработка тех же сообщений
→ при медленной обработке цикл повторяется бесконечно
```

Симптом узнаваемый: сервис работает, ничего не падает, а одни и те же сообщения
обрабатываются снова и снова.

Решения: уменьшить `max.poll.records`, увеличить `max.poll.interval.ms`, ускорить
обработку или вынести долгие операции в отдельный поток, фиксируя позицию
самостоятельно.

Отдельно существует `session.timeout.ms` — таймаут фоновых heartbeat-ов, который
отвечает за обнаружение полностью упавшего потребителя.

## Обработка ошибок

Сообщение не удалось обработать — что делать.

```text
пропустить и зафиксировать → потеря
повторять бесконечно       → остановка партиции
```

Второй вариант опаснее, чем кажется: «ядовитое» сообщение блокирует всю партицию,
и за ним встают все последующие.

### Retry-топики и DLQ

Стандартная схема:

```text
orders
  ↓ ошибка
orders.retry.1   (задержка 1 с)
  ↓ ошибка
orders.retry.2   (задержка 10 с)
  ↓ ошибка
orders.DLT       (dead letter topic)
```

Сообщение уходит в отдельный топик, а основной продолжает обрабатываться. После
исчерпания попыток — в мёртвую очередь, откуда его разбирают вручную или
переотправляют после исправления.

В Spring Kafka это настраивается декларативно:

```java
@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 2.0)
)
@KafkaListener(topics = "orders")
public void handle(OrderEvent event) {
}

@DltHandler
public void handleDlt(OrderEvent event) {
    log.error("Не удалось обработать: {}", event);
}
```

### Что учитывать

**Порядок теряется.** Сообщение, ушедшее в retry-топик, вернётся позже остальных.
Если порядок по ключу критичен, схема с retry-топиками не подходит — придётся
блокировать партицию.

**Различать типы ошибок.** Повторять имеет смысл временные сбои: недоступность
сервиса, таймаут, блокировка в базе. Повторять некорректное сообщение бессмысленно —
оно должно уходить в DLQ сразу.

```java
new DefaultErrorHandler(recoverer, backOff)
        .addNotRetryableExceptions(ValidationException.class);
```

## Хранение

```text
retention.ms    → сколько хранить, по умолчанию 7 дней
retention.bytes → ограничение по размеру

cleanup.policy=delete  → удалять старое, по умолчанию
cleanup.policy=compact → хранить последнее значение для каждого ключа
```

Уплотнение превращает топик в подобие таблицы: для каждого ключа остаётся последняя
версия. На этом основаны топики состояния и справочники, где нужна не история, а
текущее значение.

## Двойная запись и Outbox

Частая задача: сохранить заказ в базу и отправить событие в Kafka.

```java
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    kafkaTemplate.send("orders", event);   // может не выполниться
}
```

Атомарности здесь нет: транзакция базы и отправка в Kafka — разные системы.
Возможны оба сценария рассогласования — заказ сохранён без события или событие
отправлено, а транзакция откатилась.

Решение — паттерн Outbox: событие записывается в ту же базу в отдельную таблицу
внутри той же транзакции, а отдельный процесс читает её и отправляет в Kafka.

```text
транзакция: INSERT order + INSERT outbox_event
отдельный процесс: читает outbox → отправляет в Kafka → помечает отправленным
```

Атомарность обеспечивается транзакцией базы. Доставка получается at-least-once,
поэтому потребитель должен быть идемпотентным.

Более простой промежуточный вариант — отправлять событие после фиксации транзакции
через `@TransactionalEventListener(AFTER_COMMIT)`. Это убирает случай «событие без
заказа», но не спасает от «заказ без события», если приложение упадёт сразу после
фиксации.

## Типичные ошибки

### Ожидать глобального порядка

Порядок есть только внутри партиции. Для порядка по сущности нужен ключ.

### Добавлять потребителей сверх числа партиций

Лишние простаивают, пропускная способность не растёт.

### Менять число партиций у топика с ключами

Соответствие ключей партициям изменится, порядок нарушится.

### Полагаться на автоматическую фиксацию

Позиция может зафиксироваться до завершения обработки, и сообщение потеряется.

### Считать exactly-once универсальной гарантией

Она действует внутри Kafka. При записи во внешнюю систему нужна идемпотентность
потребителя.

### Использовать acks=all без min.insync.replicas

При одной живой реплике гарантия вырождается в `acks=1`.

### Долго обрабатывать пачку сообщений

Превышение `max.poll.interval.ms` приводит к исключению из группы, ребалансировке
и повторной обработке.

### Повторять обработку некорректного сообщения бесконечно

Партиция блокируется, за «ядовитым» сообщением встают все остальные.

### Считать retry-топики бесплатными

Порядок обработки теряется.

### Записывать в базу и Kafka без Outbox

Атомарности между двумя системами нет.

### Хранить бизнес-состояние только в Kafka

Данные удаляются по истечении срока хранения, если не настроено уплотнение.

Kafka — распределённый лог, а не очередь
сообщение не удаляется при чтении, сдвигается offset
```

topic → partitions → упорядоченный лог с offset
порядок только внутри партиции

consumer group

```

## Краткий ответ для собеседования

Kafka — распределённый журнал, а не очередь: сообщение не удаляется при чтении, а
хранится заданное время, и потребитель лишь сдвигает свою позицию. Поэтому одни и
те же данные могут независимо читать несколько подсистем, а историю можно
перечитать.

Топик делится на партиции — независимые упорядоченные логи. Порядок гарантируется
только внутри партиции, поэтому для упорядоченной обработки событий одной сущности
её идентификатор используют как ключ: он определяет партицию через хеш.

В группе потребителей одна партиция обрабатывается ровно одним потребителем,
поэтому число партиций задаёт потолок параллелизма. Разные группы независимы и
получают все сообщения.

Гарантии доставки определяются моментом фиксации позиции. Фиксация до обработки
даёт at-most-once с риском потери, после — at-least-once с риском дубликатов, и это
режим по умолчанию. Exactly-once достигается транзакциями, но только в пределах
Kafka: при записи во внешнюю систему нужен идемпотентный потребитель.

Надёжность записи задаётся параметром `acks` в связке с `min.insync.replicas`.
Идемпотентный продюсер устраняет дубликаты от повторных отправок и сохраняет
порядок при повторах.

Основная эксплуатационная проблема — ребалансировка из-за долгой обработки:
превышение `max.poll.interval.ms` приводит к исключению потребителя из группы и
повторной обработке тех же сообщений.

Ошибки обрабатывают через retry-топики и dead letter topic, чтобы одно
некорректное сообщение не блокировало партицию. Для согласованности записи в базу и
отправки события применяют паттерн Outbox.

## Вопросы на собеседовании

### 1. Чем Kafka отличается от обычной очереди?

**Ответ:** сообщение не удаляется при чтении, а хранится заданное время. Потребитель
сдвигает собственную позицию, поэтому данные могут независимо читать несколько
групп, а историю — перечитывать.

### 2. Зачем нужны партиции?

**Ответ:** для параллелизма. Каждую партицию обрабатывает отдельный потребитель, и
их число задаёт потолок параллельной обработки.

### 3. Гарантируется ли порядок сообщений?

**Ответ:** только внутри партиции. Глобального порядка по топику нет, если партиций
больше одной.

### 4. Как обеспечить порядок для событий одной сущности?

**Ответ:** использовать её идентификатор как ключ сообщения. Ключ определяет
партицию через хеш, поэтому все события попадут в одну партицию.

### 5. Что произойдёт при изменении числа партиций?

**Ответ:** соответствие ключей партициям изменится, и порядок для существующих
ключей нарушится. Число партиций планируют заранее.

### 6. Сколько потребителей может читать одну партицию?

**Ответ:** внутри одной группы — ровно один. Потребители из разных групп читают
независимо.

### 7. Что будет, если потребителей больше, чем партиций?

**Ответ:** лишние будут простаивать, пропускная способность не вырастет.

### 8. Где хранится offset?

**Ответ:** в служебном топике `__consumer_offsets`, поэтому после перезапуска
потребитель продолжает с прежней позиции.

### 9. Какие есть гарантии доставки?

**Ответ:** at-most-once с возможной потерей, at-least-once с возможными дубликатами
и exactly-once. По умолчанию используется at-least-once.

### 10. Как получить at-least-once?

**Ответ:** отключить автоматическую фиксацию и фиксировать позицию после успешной
обработки.

### 11. Работает ли exactly-once при записи в базу?

**Ответ:** нет. Гарантия действует внутри Kafka. Для внешних систем нужен
идемпотентный потребитель, поскольку атомарно зафиксировать транзакцию Kafka и базы
нельзя.

### 12. Как сделать потребителя идемпотентным?

**Ответ:** проверять идентификатор события перед обработкой, использовать `UPSERT`
или уникальные ограничения — чтобы повторная обработка не меняла результат.

### 13. Что делает идемпотентный продюсер?

**Ответ:** брокер отбрасывает повторную отправку с уже виденным порядковым номером
от того же продюсера. Устраняет дубликаты от повторов, но не от повторной обработки
потребителем.

### 14. Что означают значения acks?

**Ответ:** `0` — не ждать подтверждения, `1` — дождаться записи лидером, `all` —
дождаться записи всеми синхронными репликами.

### 15. Почему acks=all нужен вместе с min.insync.replicas?

**Ответ:** иначе при единственной живой реплике гарантия сводится к `acks=1`, и
отказ брокера приведёт к потере данных.

### 16. Могут ли повторы нарушить порядок?

**Ответ:** да, если число одновременных запросов больше одного и идемпотентность
отключена. Повторно отправленное сообщение способно обогнать следующее.

### 17. Когда происходит ребалансировка?

**Ответ:** при входе или выходе потребителя, а также когда он перестаёт отвечать в
отведённое время.

### 18. Почему сообщения обрабатываются повторно без видимых ошибок?

**Ответ:** обработка пачки заняла больше `max.poll.interval.ms`, потребитель
исключён из группы, позиция не зафиксирована, и после ребалансировки те же
сообщения читаются снова.

### 19. Как обрабатывать ошибки?

**Ответ:** через retry-топики с нарастающей задержкой и dead letter topic.
Бесконечные повторы в основном топике блокируют партицию.

### 20. Что теряется при использовании retry-топиков?

**Ответ:** порядок обработки: сообщение вернётся позже остальных.

### 21. Что такое compaction?

**Ответ:** политика хранения, при которой для каждого ключа остаётся последнее
значение. Превращает топик в подобие таблицы состояния.

### 22. Как согласовать запись в базу и отправку в Kafka?

**Ответ:** через паттерн Outbox: событие пишется в ту же базу в одной транзакции с
данными, а отдельный процесс читает таблицу и отправляет в Kafka. Доставка при этом
at-least-once, поэтому потребитель должен быть идемпотентным.
