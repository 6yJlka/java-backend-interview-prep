# Spring Kafka

Обвязка над клиентом Apache Kafka: отправка через `KafkaTemplate`, приём через
`@KafkaListener`, управление смещениями, обработка ошибок и повторы.

Сам брокер, партиции, группы потребителей и семантика доставки разобраны в
отдельном конспекте. Здесь — то, что пишет разработчик, и места, где обвязка ведёт
себя не так, как ожидается.

```text
Kafka        → брокер, партиции, смещения, гарантии
Spring Kafka → контейнеры слушателей, шаблон отправки, обработчики ошибок
```

Важная оговорка: Spring Kafka не меняет гарантий брокера. Доставка остаётся
минимум однократной, дубликаты остаются возможными, порядок сохраняется только
внутри партиции.

## Отправка

### KafkaTemplate

```java
@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void publish(OrderEvent event) {
        kafkaTemplate.send("orders", event.orderId().toString(), event);
    }
}
```

Второй аргумент — ключ. От него зависит партиция, а значит и порядок: сообщения с
одним ключом всегда попадают в одну партицию и обрабатываются последовательно.
Отправка без ключа распределяет сообщения по партициям и порядок между ними не
сохраняет.

Практическое следствие: ключом выбирают идентификатор сущности, по которой важен
порядок событий. Для заказа — его идентификатор, тогда `OrderCreated` гарантированно
обработается раньше `OrderPaid`.

### Асинхронность

```java
CompletableFuture<SendResult<String, OrderEvent>> future =
        kafkaTemplate.send("orders", key, event);

future.whenComplete((result, exception) -> {
    if (exception != null) {
        log.error("Send failed for key {}", key, exception);
    }
});
```

`send()` возвращает управление сразу: сообщение складывается в буфер продюсера и
отправляется батчем. Ошибка приходит асинхронно, и без обработчика она уйдёт только
в лог самого клиента.

Синхронная отправка возможна, но замедляет всё:

```java
kafkaTemplate.send("orders", key, event).get();
```

Каждое сообщение отправляется отдельно, батчинг не работает. Оправдано только
там, где нужно точно знать результат до продолжения.

### Настройки продюсера

```yaml
spring:
  kafka:
    producer:
      acks: all
      properties:
        enable.idempotence: true
        max.in.flight.requests.per.connection: 5
      retries: 3
```

```text
acks=0   → не ждём подтверждения, потеря возможна
acks=1   → ждём лидера, потеря при его падении до репликации
acks=all → ждём все синхронизированные реплики
```

`enable.idempotence` включает нумерацию сообщений на стороне брокера, благодаря
чему повтор при сетевом сбое не создаёт дубликат. Это защита от дублирования
именно при повторной отправке, а не от логических дубликатов в приложении.

## Приём

### @KafkaListener

```java
@Component
public class OrderEventListener {

    @KafkaListener(topics = "orders", groupId = "order-processor")
    public void handle(OrderEvent event) {
        orderService.process(event);
    }
}
```

Метод может принимать не только полезную нагрузку:

```java
@KafkaListener(topics = "orders", groupId = "order-processor")
public void handle(
        @Payload OrderEvent event,
        @Header(KafkaHeaders.RECEIVED_KEY) String key,
        @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
        @Header(KafkaHeaders.OFFSET) long offset,
        Acknowledgment acknowledgment
) {
}
```

### Контейнеры и параллелизм

За `@KafkaListener` стоит контейнер — по умолчанию
`ConcurrentMessageListenerContainer`. Он создаёт указанное число потребителей,
каждый в своём потоке.

```java
@KafkaListener(topics = "orders", groupId = "order-processor", concurrency = "3")
```

```text
concurrency = 3 → три потребителя в одном приложении
```

Ключевое ограничение: число одновременно работающих потребителей в группе не может
превышать число партиций. Если партиций две, а `concurrency = 5`, три потребителя
будут простаивать. Параллелизм в Kafka ограничен партиционированием, и никакая
настройка приложения это не обходит.

## Смещения

### Почему автоматическое подтверждение выключают

```yaml
spring:
  kafka:
    consumer:
      enable-auto-commit: false
```

Spring Kafka по умолчанию выставляет это в `false` и управляет смещениями сам. С
включённым автоподтверждением клиент отправляет смещения по таймеру, независимо от
того, успешно ли обработано сообщение.

```text
получили сообщение
→ таймер сработал, смещение подтверждено
→ обработка упала
→ сообщение потеряно: при перезапуске начнём со следующего
```

Это превращает доставку в at-most-once, чего почти никогда не хотят.

### AckMode

```yaml
spring:
  kafka:
    listener:
      ack-mode: batch
```

```text
BATCH            → после обработки всей пачки из poll, по умолчанию
RECORD           → после каждого сообщения, надёжнее и медленнее
MANUAL           → подтверждает код, фактически при следующем poll
MANUAL_IMMEDIATE → подтверждает код, немедленно
TIME / COUNT     → по таймеру или счётчику
```

Ручное подтверждение:

```java
@KafkaListener(topics = "orders", groupId = "order-processor")
public void handle(OrderEvent event, Acknowledgment acknowledgment) {
    orderService.process(event);
    acknowledgment.acknowledge();
}
```

Смысл в том, чтобы смещение подтверждалось после успешной обработки, а не после
получения. Тогда при падении сообщение придёт снова — это и есть at-least-once,
из которого следует обязательная идемпотентность обработчика.

## Сериализация

### JSON

```yaml
spring:
  kafka:
    producer:
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
    consumer:
      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      properties:
        spring.json.trusted.packages: "com.example.events"
```

Список доверенных пакетов обязателен: по умолчанию десериализатор отказывается
создавать объекты произвольных классов, и это защита, а не придирка — тип берётся
из заголовка сообщения, то есть из внешних данных.

### Poison pill

Самая неприятная ситуация в теме. В топик попало сообщение, которое не
десериализуется — сломанный JSON, несовместимая схема, чужой формат.

```text
потребитель читает сообщение
→ ошибка десериализации до вызова слушателя
→ смещение не подтверждено
→ при следующем poll то же сообщение
→ бесконечный цикл, обработка встала
```

Обработчик ошибок здесь не поможет: исключение возникает раньше, чем управление
дойдёт до слушателя.

Решение — обернуть десериализатор:

```yaml
spring:
  kafka:
    consumer:
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer
```

`ErrorHandlingDeserializer` перехватывает ошибку и передаёт её дальше как обычное
исключение обработки, которое уже можно отправить в мёртвую очередь.

Про схемы: в зрелых системах ту же проблему решают реестром схем и форматом вроде
Avro, где совместимость проверяется на стороне брокера. Для Junior-уровня
достаточно знать, что такой подход существует.

## Обработка ошибок

### DefaultErrorHandler

```java
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template);

    DefaultErrorHandler handler = new DefaultErrorHandler(
            recoverer,
            new FixedBackOff(1000L, 3)
    );

    handler.addNotRetryableExceptions(ValidationException.class);

    return handler;
}
```

Логика простая: при исключении из слушателя сообщение повторяется по заданному
расписанию, а после исчерпания попыток передаётся восстановителю — обычно в
мёртвую очередь.

Разделение исключений на повторяемые и неповторяемые существенно. Недоступность
базы — повторять имеет смысл. Некорректные данные в сообщении — нет, повтор даст
тот же результат и лишь задержит очередь.

### Куда попадает сообщение

`DeadLetterPublishingRecoverer` по умолчанию пишет в топик с суффиксом `.DLT`, в
партицию с тем же номером. В заголовки добавляется причина: исходный топик,
смещение, класс исключения, сообщение и трассировка.

Без разбора мёртвой очереди она бесполезна. Минимум — оповещение о появлении
сообщений в ней и возможность переотправить их после исправления причины.

### Блокирующие повторы и их цена

Главная проблема схемы выше: повторы **блокируют партицию**.

```text
сообщение упало
→ повтор через 1 секунду, ещё раз, ещё раз
→ всё это время следующие сообщения этой партиции не обрабатываются
```

При трёх попытках с интервалом в секунду задержка невелика. При экспоненциальном
backoff с максимумом в минуту одно проблемное сообщение останавливает партицию на
минуты.

### Неблокирующие повторы

```java
@RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 2),
        dltStrategy = DltStrategy.FAIL_ON_ERROR
)
@KafkaListener(topics = "orders", groupId = "order-processor")
public void handle(OrderEvent event) {
}
```

Здесь Spring создаёт отдельные топики повторов:

```text
orders
orders-retry-0   → задержка 1 с
orders-retry-1   → задержка 2 с
orders-retry-2   → задержка 4 с
orders-dlt
```

Упавшее сообщение отправляется в топик повтора, а основная партиция продолжает
работать. Цена — порядок сообщений нарушается: повторённое придёт позже тех, что
шли за ним.

```text
блокирующие повторы    → порядок сохраняется, партиция стоит
неблокирующие повторы  → партиция работает, порядок нарушается
```

Выбор зависит от того, что важнее. Для обработки событий одного заказа порядок
обычно критичен, для рассылки уведомлений — нет.

## Транзакции и согласованность

### Транзакции Kafka

```yaml
spring:
  kafka:
    producer:
      transaction-id-prefix: order-service-
```

```java
@Transactional("kafkaTransactionManager")
public void publishAll(List<OrderEvent> events) {
    events.forEach(event -> kafkaTemplate.send("orders", event.orderId().toString(), event));
}
```

Транзакция даёт атомарность **внутри Kafka**: либо все сообщения станут видимыми
потребителям с `isolation.level=read_committed`, либо ни одно.

### Чего транзакции не дают

Атомарности между базой и брокером не существует. Это две разные системы, и общей
транзакции у них нет.

```java
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    kafkaTemplate.send("orders", event);   // а если упадёт здесь?
}
```

Варианта отказа два, и оба плохие: транзакция откатилась, а сообщение уже ушло —
или наоборот, сообщение не ушло, а заказ сохранён.

Стандартное решение — Outbox: событие пишется в ту же базу в одной транзакции с
бизнес-данными, а отдельный процесс читает таблицу и отправляет в брокер.

```sql
CREATE TABLE outbox_events (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id BIGINT NOT NULL,
    type         VARCHAR(50) NOT NULL,
    payload      JSONB NOT NULL,
    sent_at      TIMESTAMPTZ
);
```

Отправка при этом остаётся минимум однократной: процесс может упасть после
отправки, но до отметки о ней. Дубликаты неизбежны, и снова нужна идемпотентность
на стороне потребителя.

Более простой вариант для некритичных событий — отправлять после фиксации
транзакции:

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    kafkaTemplate.send("orders", event);
}
```

Тогда сообщение точно не уйдёт при откате. Но если приложение упадёт между
фиксацией и отправкой, событие потеряется — гарантии слабее, чем у Outbox.

## Ребалансировка и долгая обработка

Потребитель обязан регулярно вызывать `poll()`. Если между вызовами прошло больше
`max.poll.interval.ms`, брокер считает его умершим и запускает перераспределение
партиций.

```yaml
spring:
  kafka:
    consumer:
      properties:
        max.poll.interval.ms: 300000
      max-poll-records: 500
```

Отсюда сценарий, который ловят на собеседовании:

```text
обработка одного сообщения занимает 2 секунды
за один poll пришло 500 сообщений
500 × 2 = 1000 секунд
max.poll.interval.ms = 300 секунд

→ потребитель исключён из группы
→ ребалансировка
→ смещения не подтверждены
→ те же сообщения достаются другому потребителю
→ он тоже не успевает
→ бесконечная ребалансировка
```

Лечится уменьшением `max-poll-records`, увеличением интервала или выносом долгой
работы за пределы обработчика.

Отдельно стоит знать про `CooperativeStickyAssignor`: он перераспределяет только
затронутые партиции вместо полной остановки всех потребителей. В новых версиях
клиента это поведение по умолчанию.

## Идемпотентность потребителя

Поскольку доставка минимум однократная, обработчик обязан переносить повтор.
Способы те же, что везде:

```text
уникальное ограничение на идентификатор события в базе
проверка текущего состояния перед изменением
UPSERT вместо слепой вставки
таблица обработанных идентификаторов
```

```java
@Transactional
public void process(OrderEvent event) {
    if (processedEventRepository.existsById(event.eventId())) {
        return;
    }

    orderService.apply(event);
    processedEventRepository.save(new ProcessedEvent(event.eventId()));
}
```

Проверка и запись должны идти в одной транзакции, иначе между ними вклинится
повтор.

## Тестирование

```java
@SpringBootTest
@EmbeddedKafka(partitions = 1, topics = "orders")
class OrderEventListenerTest {
}
```

`@EmbeddedKafka` поднимает брокер в том же процессе — быстро, но это не настоящая
Kafka, и некоторые сценарии воспроизводятся неточно.

```java
@SpringBootTest
@Testcontainers
class OrderEventListenerTest {

    @Container
    @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer(
            DockerImageName.parse("confluentinc/cp-kafka:7.6.0")
    );
}
```

Testcontainers запускает настоящий брокер той же версии, что в продакшене. Медленнее,
зато проверяет реальное поведение — ребалансировку, мёртвые очереди, транзакции.

Главная сложность тестов на Kafka — асинхронность. Проверять результат нужно с
ожиданием, а не сразу:

```java
await().atMost(Duration.ofSeconds(10))
        .untilAsserted(() -> assertThat(orderRepository.findById(id)).isPresent());
```

## Типичные ошибки

### Игнорировать результат отправки

`send()` асинхронен. Без обработки ошибки потеря сообщения останется незамеченной.

### Отправлять синхронно без нужды

Вызов `get()` на каждом сообщении отключает батчинг и резко снижает пропускную
способность.

### Отправлять без ключа там, где важен порядок

Без ключа сообщения расходятся по партициям, и порядок между ними не гарантируется.

### Включать автоподтверждение смещений

Смещение подтверждается по таймеру независимо от результата обработки, и при
падении сообщение теряется.

### Считать, что concurrency увеличит параллелизм сверх числа партиций

Лишние потребители будут простаивать. Параллелизм ограничен партиционированием.

### Не защищаться от poison pill

Сообщение, которое не десериализуется, останавливает партицию навсегда. Нужен
`ErrorHandlingDeserializer`.

### Не указывать доверенные пакеты

Тип берётся из заголовка сообщения, то есть из внешних данных. Без ограничения это
дыра в безопасности.

### Повторять неповторяемые ошибки

Некорректные данные не исправятся от повтора, а очередь будет стоять. Такие
исключения регистрируют как неповторяемые.

### Не учитывать, что блокирующие повторы останавливают партицию

Одно проблемное сообщение с экспоненциальной задержкой блокирует обработку на
минуты.

### Забывать, что неблокирующие повторы ломают порядок

Повторённое сообщение придёт позже тех, что шли за ним в партиции.

### Ожидать атомарности базы и брокера

Общей транзакции не существует. Нужен Outbox или отправка после фиксации.

### Обрабатывать сообщение неидемпотентно

Доставка минимум однократная, дубликаты неизбежны по построению.

### Делать долгую обработку внутри слушателя

Превышение `max.poll.interval.ms` исключает потребителя из группы и запускает
бесконечную ребалансировку.

### Заводить DLQ и не смотреть в неё

Мёртвая очередь без оповещения и разбора — просто место, куда молча уходят
потерянные сообщения.

```text
проверять с ожиданием, а не сразу
```

## Краткий ответ для собеседования

Spring Kafka даёт две основные абстракции: `KafkaTemplate` для отправки и
`@KafkaListener` для приёма. За слушателем стоит контейнер, создающий указанное
число потребителей, но их число имеет смысл только до числа партиций — параллелизм
в Kafka задаётся партиционированием.

Отправка асинхронна: метод возвращает future, и без обработки результата ошибка
останется незамеченной. Ключ сообщения определяет партицию, а значит и порядок:
события одной сущности отправляют с одним ключом, иначе порядок между ними не
гарантирован.

Смещения Spring подтверждает сам, автоподтверждение по умолчанию выключено — иначе
смещение фиксировалось бы по таймеру независимо от результата обработки, и при
падении сообщение терялось бы. Подтверждение после успешной обработки даёт
at-least-once, из чего прямо следует обязательная идемпотентность обработчика.

Отдельная ловушка — сообщение, которое не десериализуется. Ошибка возникает до
вызова слушателя, смещение не подтверждается, и потребитель бесконечно читает одно
и то же сообщение. Лечится обёрткой `ErrorHandlingDeserializer`.

Ошибки обработки закрывает `DefaultErrorHandler`: повторы по заданному расписанию,
после исчерпания — отправка в мёртвую очередь через
`DeadLetterPublishingRecoverer`. Важно разделять повторяемые и неповторяемые
исключения и понимать, что обычные повторы блокируют партицию. Неблокирующая
альтернатива — `@RetryableTopic` с отдельными топиками повторов, но она нарушает
порядок.

Транзакции Kafka обеспечивают атомарность только внутри брокера. Атомарности между
базой и Kafka не существует, поэтому применяют Outbox: событие пишется в ту же
базу в одной транзакции, а отправляет его отдельный процесс.

Наконец, долгая обработка опасна: если между вызовами `poll` прошло больше
`max.poll.interval.ms`, потребителя исключают из группы, начинается
перераспределение, и при неудачном сочетании настроек это превращается в
бесконечный цикл ребалансировок.

## Вопросы на собеседовании

### 1. Что Spring Kafka добавляет поверх клиента?

**Ответ:** контейнеры слушателей, шаблон отправки, декларативное объявление
обработчиков, управление смещениями, обработчики ошибок и интеграцию с
транзакциями. Гарантии самого брокера при этом не меняются.

### 2. Синхронна ли отправка через KafkaTemplate?

**Ответ:** нет, метод возвращает future, а сообщение попадает в буфер продюсера.
Ошибка приходит асинхронно, и её нужно обрабатывать явно.

### 3. Что даёт ключ сообщения?

**Ответ:** он определяет партицию. Сообщения с одним ключом попадают в одну
партицию и обрабатываются последовательно, что и обеспечивает порядок для одной
сущности.

### 4. Чем плоха синхронная отправка?

**Ответ:** каждое сообщение отправляется отдельно, батчинг не работает, и
пропускная способность резко падает.

### 5. Что означает acks=all?

**Ответ:** продюсер ждёт подтверждения от всех синхронизированных реплик. Это самая
надёжная настройка и самая медленная.

### 6. Что даёт enable.idempotence?

**Ответ:** брокер нумерует сообщения продюсера и отбрасывает повторы, возникшие при
сетевых сбоях. От логических дубликатов в приложении это не защищает.

### 7. Что стоит за @KafkaListener?

**Ответ:** контейнер слушателя, по умолчанию `ConcurrentMessageListenerContainer`,
создающий потребителей в отдельных потоках.

### 8. Имеет ли смысл concurrency больше числа партиций?

**Ответ:** нет. Партиция закрепляется за одним потребителем в группе, поэтому
лишние будут простаивать.

### 9. Почему автоподтверждение смещений выключают?

**Ответ:** оно фиксирует смещение по таймеру независимо от результата обработки.
Падение после подтверждения означает потерю сообщения, то есть at-most-once.

### 10. Какие режимы подтверждения существуют?

**Ответ:** `BATCH` по умолчанию, `RECORD` после каждого сообщения, `MANUAL` и
`MANUAL_IMMEDIATE` для ручного подтверждения, а также варианты по времени и
счётчику.

### 11. Когда нужно подтверждать смещение?

**Ответ:** после успешной обработки. Тогда при падении сообщение придёт снова, что
и даёт at-least-once.

### 12. Зачем нужен список доверенных пакетов?

**Ответ:** тип для десериализации берётся из заголовка сообщения, то есть из
внешних данных. Без ограничения это возможность создать произвольный объект.

### 13. Что такое poison pill?

**Ответ:** сообщение, которое не удаётся десериализовать. Ошибка возникает до
вызова слушателя, смещение не подтверждается, и потребитель бесконечно читает одно
и то же.

### 14. Почему обработчик ошибок не спасает от poison pill?

**Ответ:** исключение происходит раньше, чем управление доходит до слушателя.
Нужен `ErrorHandlingDeserializer`, превращающий ошибку в обычное исключение
обработки.

### 15. Что делает DefaultErrorHandler?

**Ответ:** повторяет обработку по заданному расписанию, а после исчерпания попыток
передаёт сообщение восстановителю — обычно в мёртвую очередь.

### 16. Зачем разделять повторяемые и неповторяемые исключения?

**Ответ:** повтор имеет смысл при временной ошибке вроде недоступности базы.
Некорректные данные не исправятся, и повторы лишь задержат очередь.

### 17. Куда попадает сообщение после исчерпания попыток?

**Ответ:** в топик с суффиксом `.DLT`, с заголовками о причине: исходный топик,
смещение, класс исключения и трассировка.

### 18. Чем опасны блокирующие повторы?

**Ответ:** на время повторов партиция не обрабатывается. При экспоненциальной
задержке одно сообщение останавливает поток на минуты.

### 19. Как устроены неблокирующие повторы?

**Ответ:** `@RetryableTopic` создаёт отдельные топики повторов с возрастающей
задержкой. Основная партиция продолжает работать, но порядок сообщений нарушается.

### 20. Что выбрать между блокирующими и неблокирующими повторами?

**Ответ:** блокирующие, когда критичен порядок событий одной сущности.
Неблокирующие, когда важнее не останавливать обработку остальных сообщений.

### 21. Что дают транзакции Kafka?

**Ответ:** атомарность внутри брокера: набор сообщений становится видимым
потребителям с уровнем `read_committed` либо целиком, либо никак.

### 22. Можно ли сделать атомарными запись в базу и отправку в Kafka?

**Ответ:** нет, это две разные системы без общей транзакции. Применяют Outbox либо
отправку после фиксации транзакции.

### 23. Как работает Outbox?

**Ответ:** событие пишется в ту же базу в одной транзакции с бизнес-данными, а
отдельный процесс читает таблицу и публикует сообщения. Доставка остаётся минимум
однократной.

### 24. Чем отправка после фиксации хуже Outbox?

**Ответ:** если приложение упадёт между фиксацией и отправкой, событие потеряется.
Outbox переживает такое падение, потому что запись уже в базе.

### 25. Почему долгая обработка приводит к ребалансировке?

**Ответ:** потребитель обязан вызывать `poll` не реже `max.poll.interval.ms`.
Превышение означает для брокера, что потребитель умер, и партиции
перераспределяются.

### 26. Как возникает бесконечная ребалансировка?

**Ответ:** потребитель не успевает обработать пачку, его исключают, смещения не
подтверждены, те же сообщения достаются другому потребителю, который тоже не
успевает.

### 27. Как это лечится?

**Ответ:** уменьшением `max-poll-records`, увеличением интервала или выносом долгой
работы за пределы обработчика.

### 28. Что даёт CooperativeStickyAssignor?

**Ответ:** перераспределение только затронутых партиций вместо полной остановки
всех потребителей группы.

### 29. Почему обработчик обязан быть идемпотентным?

**Ответ:** доставка гарантируется минимум однократная, поэтому дубликаты неизбежны
по построению, а не из-за ошибки.

### 30. Как обеспечить идемпотентность обработки?

**Ответ:** уникальным ограничением на идентификатор события, проверкой текущего
состояния, `UPSERT` или таблицей обработанных идентификаторов. Проверка и запись
должны выполняться в одной транзакции.

### 31. Чем @EmbeddedKafka отличается от Testcontainers?

**Ответ:** встроенный брокер быстрее, но это не настоящая Kafka. Testcontainers
поднимает реальный брокер нужной версии и позволяет проверить ребалансировку,
мёртвые очереди и транзакции.

### 32. В чём главная сложность тестов на Kafka?

**Ответ:** в асинхронности. Результат нужно проверять с ожиданием, иначе тест будет
падать случайным образом.
