# Тестирование: JUnit 5, Mockito и Spring

## Пирамида тестов

```text
        ╱ E2E ╲            мало, медленные, хрупкие
      ╱─────────╲
    ╱ интеграция ╲         средне, проверяют связки
  ╱───────────────╲
╱  модульные тесты  ╲      много, быстрые, изолированные
```

Смысл в стоимости обратной связи. Модульный тест выполняется за миллисекунды и
точно указывает на сломанное место. Интеграционный поднимает контекст и базу,
занимает секунды и говорит лишь, что где-то в цепочке проблема.

Из этого следует практическое правило: логику проверяют модульными тестами, а
интеграционными — то, что модульными проверить нельзя: SQL-запросы, сериализацию,
конфигурацию, взаимодействие слоёв.

## JUnit 5

### Устройство

```text
JUnit Platform → запуск тестов, интеграция со сборщиками и IDE
JUnit Jupiter  → API для написания тестов, то что видит разработчик
JUnit Vintage  → запуск тестов JUnit 4
```

Разделение появилось в пятой версии, чтобы платформа могла запускать и другие
фреймворки.

### Базовый тест

```java
class OrderCalculatorTest {

    @Test
    void appliesDiscountForLargeOrder() {
        OrderCalculator calculator = new OrderCalculator();

        BigDecimal total = calculator.calculate(items, DiscountType.LARGE_ORDER);

        assertThat(total).isEqualByComparingTo("900.00");
    }
}
```

Класс и метод не обязаны быть публичными — это отличие от JUnit 4.

Структура теста обычно трёхчастная: подготовка, действие, проверка. Разделять их
пустой строкой достаточно, комментарии вроде `// given` избыточны.

### Жизненный цикл

```java
@BeforeAll   static void setUpAll() {}     // один раз до всех
@BeforeEach  void setUp() {}               // перед каждым
@AfterEach   void tearDown() {}            // после каждого
@AfterAll    static void tearDownAll() {}  // один раз после всех
```

Важная деталь: по умолчанию **на каждый тестовый метод создаётся новый экземпляр
класса**. Поля не разделяются между тестами, поэтому состояние не протекает.

Отсюда требование `static` у `@BeforeAll` — метод вызывается до создания
экземпляров. Изменить поведение можно:

```java
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
```

Тогда экземпляр один на класс, а `@BeforeAll` может быть нестатическим. Но
изоляция теряется, и порядок тестов начинает иметь значение.

### Проверки

```java
assertEquals(expected, actual);
assertTrue(condition);
assertNull(value);

assertThrows(OrderNotFoundException.class, () -> service.get(999L));

assertAll(
    () -> assertEquals("NEW", order.getStatus()),
    () -> assertEquals(2, order.getItems().size())
);
```

`assertAll` выполняет все проверки и сообщает обо всех неудачах сразу, а не
останавливается на первой.

На практике вместо встроенных проверок чаще используют AssertJ — он читается лучше
и даёт более информативные сообщения:

```java
assertThat(orders)
        .hasSize(2)
        .extracting(Order::getStatus)
        .containsExactly("NEW", "PAID");

assertThatThrownBy(() -> service.get(999L))
        .isInstanceOf(OrderNotFoundException.class)
        .hasMessageContaining("999");
```

AssertJ входит в `spring-boot-starter-test`, отдельно подключать не нужно.

### Параметризованные тесты

```java
@ParameterizedTest
@ValueSource(strings = {"", " ", "   "})
void rejectsBlankName(String name) {
    assertThatThrownBy(() -> new Customer(name))
            .isInstanceOf(IllegalArgumentException.class);
}
```

```java
@ParameterizedTest
@CsvSource({
    "100, 0,   100",
    "100, 10,   90",
    "100, 100,   0"
})
void appliesDiscount(BigDecimal price, int percent, BigDecimal expected) {
    assertThat(calculator.apply(price, percent)).isEqualByComparingTo(expected);
}
```

```java
@ParameterizedTest
@MethodSource("invalidOrders")
void rejectsInvalidOrder(Order order, String expectedMessage) {
}

static Stream<Arguments> invalidOrders() {
    return Stream.of(
        Arguments.of(new Order(null), "customer required"),
        Arguments.of(new Order(emptyItems), "items required")
    );
}
```

`@MethodSource` нужен, когда параметры — объекты, а не константы.

### Прочее

```java
@DisplayName("Заказ не создаётся без позиций")
@Disabled("Ожидает исправления в SPR-1234")
@Tag("slow")

@Nested
class WhenOrderIsPaid {
    // группировка тестов по состоянию
}
```

`@Nested` полезен для структурирования: внешний класс задаёт общую подготовку,
вложенные — конкретные сценарии.

## Mockito

### Тестовые двойники

```text
dummy → объект-заглушка, передаётся, но не используется
stub  → возвращает заранее заданные значения
mock  → stub + проверка того, как с ним взаимодействовали
spy   → обёртка над реальным объектом, часть вызовов настраивается
fake  → упрощённая рабочая реализация, например Map вместо базы
```

Различие между stub и mock спрашивают часто. Stub нужен, чтобы тест мог выполниться;
mock дополнительно участвует в проверке — важно не только что вернулось, но и что
метод был вызван.

### Настройка

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @Mock
    private PaymentClient paymentClient;

    @InjectMocks
    private OrderService orderService;

    @Test
    void createsOrder() {
        when(orderRepository.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));

        Order result = orderService.create(request);

        assertThat(result.getStatus()).isEqualTo("NEW");
        verify(paymentClient).charge(any());
    }
}
```

`@InjectMocks` создаёт объект и подставляет моки — предпочтительно через
конструктор. Это ещё один аргумент в пользу внедрения через конструктор: с полями
пришлось бы полагаться на рефлексию.

### Настройка поведения

```java
when(repository.findById(1L)).thenReturn(Optional.of(order));
when(repository.findById(999L)).thenReturn(Optional.empty());
when(client.charge(any())).thenThrow(new PaymentException());

// для void-методов синтаксис другой
doThrow(new IllegalStateException()).when(client).notify(any());
doNothing().when(client).notify(any());
```

`when(...)` не работает с методами, возвращающими `void` — для них существуют
формы `doThrow`, `doNothing`, `doAnswer`.

### Проверка вызовов

```java
verify(paymentClient).charge(order);              // ровно один раз
verify(paymentClient, times(2)).charge(any());
verify(paymentClient, never()).refund(any());
verify(paymentClient, atLeastOnce()).charge(any());

verifyNoInteractions(notificationClient);
```

### ArgumentCaptor

Когда нужно проверить, что именно передали:

```java
ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);

verify(orderRepository).save(captor.capture());

assertThat(captor.getValue().getStatus()).isEqualTo("NEW");
```

Полезно для объектов, создаваемых внутри тестируемого метода и наружу не
возвращаемых.

### Матчеры

```java
when(repository.find(any(), eq("NEW"))).thenReturn(orders);
```

Правило, о котором спотыкаются: если хотя бы один аргумент задан матчером, **все
остальные тоже должны быть матчерами**. Обычное значение нужно обернуть в `eq()`,
иначе будет `InvalidUseOfMatchersException`.

### Строгие заглушки

По умолчанию `MockitoExtension` работает в строгом режиме и падает с
`UnnecessaryStubbingException`, если настроенная заглушка не была использована.

Это не придирка: неиспользуемая заглушка обычно означает, что тест проверяет не то,
что задумывалось, либо код изменился, а тест этого не заметил.

### Чего не стоит мокать

```text
не мокать типы, которых не контролируете
→ поведение чужой библиотеки может отличаться от вашего представления о нём

не мокать значения и простые объекты
→ проще создать настоящие

не мокать всё подряд
→ тест начинает проверять собственные заглушки, а не код
```

Признак проблемы: тест, где половина строк — настройка моков. Обычно это говорит не
о сложности теста, а о том, что у класса слишком много зависимостей.

`static`- и `final`-методы Mockito по умолчанию не мокает — по той же причине, что
и прокси в Spring: их нельзя переопределить. Существует `mockito-inline`, но
необходимость в нём чаще указывает на проблему в дизайне.

## Тестирование Spring

### @SpringBootTest

Поднимает полный контекст приложения.

```java
@SpringBootTest
class OrderServiceIntegrationTest {

    @Autowired
    private OrderService orderService;
}
```

```java
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class OrderApiTest {

    @Autowired
    private TestRestTemplate restTemplate;
}
```

Медленно: запускается всё приложение. Использовать стоит там, где действительно
нужна проверка сквозного сценария.

### Срезы контекста

Поднимают только нужную часть.

```java
@WebMvcTest(OrderController.class)
class OrderControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private OrderService orderService;

    @Test
    void returnsOrder() throws Exception {
        when(orderService.get(1L)).thenReturn(new OrderResponse(1L, "NEW"));

        mockMvc.perform(get("/api/orders/1"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.status").value("NEW"));
    }
}
```

`@WebMvcTest` поднимает веб-слой: контроллеры, конвертеры, обработчики исключений,
валидацию. Сервисы и репозитории не создаются, их заменяют заглушками.

Аннотация `@MockitoBean` появилась в Spring Boot 3.4 вместо `@MockBean`, которая
теперь считается устаревшей.

```java
@DataJpaTest
class OrderRepositoryTest {

    @Autowired
    private OrderRepository orderRepository;

    @Autowired
    private TestEntityManager entityManager;
}
```

`@DataJpaTest` поднимает слой доступа к данным. Особенности: каждый тест
выполняется в транзакции с откатом, а база по умолчанию подменяется встроенной.

Последнее — источник ложной уверенности: запрос, работающий на H2, может не
работать на PostgreSQL из-за различий в диалектах. Отключается так:

```java
@AutoConfigureTestDatabase(replace = Replace.NONE)
```

Другие срезы: `@JsonTest` для сериализации, `@RestClientTest` для клиентов,
`@WebFluxTest` для реактивного стека.

### Кеширование контекста

Spring кеширует контекст между тестовыми классами и переиспользует, если
конфигурация совпадает.

```text
одинаковая конфигурация → контекст поднимается один раз
любое отличие          → новый контекст
```

Отличием считается всё: другой срез, другие свойства, другой набор заглушек,
`@DirtiesContext`. Поэтому сборка, где каждый тестовый класс имеет свою
конфигурацию, поднимает контекст десятки раз и выполняется минутами.

Практический вывод: держать число различных конфигураций небольшим и не
злоупотреблять `@DirtiesContext`.

### Testcontainers

Запускает настоящую базу в контейнере на время тестов.

```java
@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");
}
```

Аннотация `@ServiceConnection` из Spring Boot 3.1 сама настраивает подключение —
раньше это делалось через `@DynamicPropertySource`.

Плюс очевиден: проверяется тот же PostgreSQL, что и в продакшене, с его типами,
диалектом и поведением. Минус — требуется Docker и время на запуск, поэтому
контейнер объявляют статическим и переиспользуют между тестами.

### @Transactional в тестах

```java
@SpringBootTest
@Transactional
class OrderServiceTest {
}
```

Транзакция откатывается после каждого теста, база остаётся чистой. Удобно, но
следует помнить о двух вещах.

Тест выполняется **внутри той же транзакции**, что и проверяемый код. Поэтому не
проверяется реальная фиксация, а `LazyInitializationException`, который возникнет в
проде, в тесте не воспроизведётся — контекст всё ещё открыт.

Для проверки поведения на границах транзакций нужен тест без этой аннотации, с
очисткой данных вручную.

## Что и как тестировать

**Проверять поведение, а не реализацию.** Тест, ломающийся при переименовании
приватного метода, мешает рефакторингу вместо того, чтобы его защищать.

**Один тест — один сценарий.** Название должно говорить, что проверяется:
`throwsWhenOrderNotFound` лучше, чем `testGetOrder`.

**Граничные случаи важнее основного пути.** Пустая коллекция, `null`, ноль,
отрицательное значение, максимальное значение — там и живут ошибки.

**Тест должен падать по одной причине.** Если он проверяет пять вещей сразу,
причина падения неочевидна.

**Тесты не должны зависеть от порядка.** Общее изменяемое состояние между
тестами — источник плавающих падений.

## Типичные ошибки

### Смешивать матчеры и обычные значения

Если один аргумент — матчер, остальные тоже должны быть матчерами, обычное значение
оборачивается в `eq()`.

### Использовать when для void-метода

Для них существуют `doThrow`, `doNothing`, `doAnswer`.

### Мокать всё подряд

Тест начинает проверять настроенные заглушки, а не поведение кода.

### Мокать типы из чужих библиотек

Заглушка отражает представление о поведении, а не само поведение.

### Оставлять неиспользуемые заглушки

Строгий режим Mockito сообщит об этом — и обычно он прав.

### Использовать @SpringBootTest везде

Полный контекст поднимается для проверки одного контроллера. Есть срезы.

### Плодить разные конфигурации контекста

Кеш перестаёт работать, сборка замедляется в разы.

### Полагаться на H2 вместо реальной базы

Диалекты различаются, и запрос, прошедший тест, может не работать в проде.

### Считать, что @Transactional в тесте проверяет фиксацию

Тест выполняется внутри той же транзакции, реальный commit не происходит.

### Проверять приватные методы

Тестируется публичное поведение. Если приватный метод хочется проверить отдельно,
возможно, он должен быть отдельным классом.

### Писать тесты, зависящие от порядка выполнения

По умолчанию на каждый метод создаётся новый экземпляр класса, но общее статическое
состояние это не защищает.

## Краткий ответ для собеседования

Тесты выстраивают пирамидой: много быстрых модульных, меньше интеграционных,
минимум сквозных. Модульные проверяют логику, интеграционные — то, что нельзя
проверить в изоляции: запросы, сериализацию, конфигурацию.

В JUnit 5 на каждый тестовый метод создаётся новый экземпляр класса, поэтому
состояние между тестами не протекает, а `@BeforeAll` должен быть статическим.
Параметризованные тесты позволяют прогнать один сценарий на наборе данных.

Mockito различает виды тестовых двойников: stub возвращает заданные значения, mock
дополнительно участвует в проверке вызовов, spy оборачивает реальный объект.
Настройка выполняется через `when` и `thenReturn`, для методов без возвращаемого
значения — через `doThrow` и `doNothing`. Если один аргумент задан матчером,
остальные тоже должны быть матчерами.

В Spring помимо `@SpringBootTest`, поднимающего весь контекст, есть срезы:
`@WebMvcTest` для веб-слоя с `MockMvc` и `@DataJpaTest` для слоя данных. Контекст
кешируется между классами, поэтому большое число различных конфигураций резко
замедляет сборку.

`@DataJpaTest` по умолчанию подменяет базу встроенной, что может скрыть различия
диалектов. Надёжнее использовать Testcontainers с настоящей базой.

`@Transactional` в тесте откатывает изменения, но тест выполняется внутри той же
транзакции, поэтому реальная фиксация не проверяется и
`LazyInitializationException` не воспроизводится.

## Вопросы на собеседовании

### 1. Из чего состоит JUnit 5?

**Ответ:** из Platform для запуска, Jupiter с API для написания тестов и Vintage для
совместимости с JUnit 4.

### 2. Создаётся ли новый экземпляр тестового класса для каждого теста?

**Ответ:** да, по умолчанию. Поэтому поля не разделяются между тестами, а
`@BeforeAll` должен быть статическим. Поведение меняется через `@TestInstance`.

### 3. Что делает assertAll?

**Ответ:** выполняет все переданные проверки и сообщает обо всех неудачах, а не
останавливается на первой.

### 4. Как проверить, что метод бросает исключение?

**Ответ:** через `assertThrows` или `assertThatThrownBy` в AssertJ, где можно
дополнительно проверить сообщение.

### 5. Зачем нужны параметризованные тесты?

**Ответ:** чтобы прогнать один сценарий на наборе данных без дублирования кода.
Источники — `@ValueSource`, `@CsvSource`, `@MethodSource` и другие.

### 6. Чем stub отличается от mock?

**Ответ:** stub только возвращает заданные значения, чтобы тест мог выполниться.
Mock дополнительно участвует в проверке — важно, что метод был вызван и с какими
аргументами.

### 7. Что такое spy?

**Ответ:** обёртка над реальным объектом, где часть методов настраивается, а
остальные выполняются по-настоящему.

### 8. Как настроить поведение void-метода?

**Ответ:** через `doThrow`, `doNothing` или `doAnswer` — конструкция `when` для них
не работает.

### 9. Что делает ArgumentCaptor?

**Ответ:** перехватывает аргумент, переданный в мок, чтобы его можно было
проверить. Полезен для объектов, создаваемых внутри тестируемого метода.

### 10. Какое правило действует для матчеров?

**Ответ:** если хотя бы один аргумент задан матчером, все остальные тоже должны
быть матчерами; обычное значение оборачивается в `eq()`.

### 11. Что такое UnnecessaryStubbingException?

**Ответ:** ошибка строгого режима Mockito о том, что настроенная заглушка не
использовалась. Обычно означает, что тест проверяет не то, что задумывалось.

### 12. Можно ли мокать static и final?

**Ответ:** по умолчанию нет — их нельзя переопределить. Существует
`mockito-inline`, но потребность в нём обычно указывает на проблему в дизайне.

### 13. Чего не стоит мокать?

**Ответ:** типы из чужих библиотек, поскольку заглушка отражает представление о
поведении, а не само поведение, а также простые объекты, которые проще создать
настоящими.

### 14. Чем @WebMvcTest отличается от @SpringBootTest?

**Ответ:** поднимает только веб-слой — контроллеры, конвертеры, обработчики
исключений. Сервисы и репозитории заменяются заглушками, поэтому тест быстрее.

### 15. Что делает @DataJpaTest?

**Ответ:** поднимает слой доступа к данным, выполняет каждый тест в транзакции с
откатом и по умолчанию подменяет базу встроенной.

### 16. Чем опасна подмена базы на H2?

**Ответ:** диалекты различаются, и запрос, прошедший тест, может не работать на
реальной СУБД.

### 17. Почему тесты Spring могут работать медленно?

**Ответ:** контекст кешируется только при совпадении конфигурации. Разные срезы,
свойства и наборы заглушек порождают новые контексты, каждый из которых поднимается
заново.

### 18. Что такое @MockitoBean?

**Ответ:** замена бина в контексте заглушкой. Появилась в Spring Boot 3.4 вместо
устаревшей `@MockBean`.

### 19. Зачем нужны Testcontainers?

**Ответ:** чтобы тестировать на настоящей базе в контейнере, а не на встроенной
замене, и получить совпадение с продакшеном по диалекту и поведению.

### 20. Чем плох @Transactional в тестах?

**Ответ:** тест выполняется внутри той же транзакции, что и код, поэтому реальная
фиксация не проверяется, а `LazyInitializationException` не воспроизводится.
