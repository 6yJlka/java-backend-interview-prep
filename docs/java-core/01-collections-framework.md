# Java Collections Framework

Набор интерфейсов, реализаций и алгоритмов для хранения и обработки групп
объектов. Тема почти всегда открывает техническую часть собеседования, и
спрашивают не перечисление классов, а умение объяснить, почему выбрана конкретная
реализация.

Фреймворк даёт:

- общие интерфейсы для разных типов коллекций;
- готовые реализации структур данных;
- единый набор методов для работы с элементами;
- алгоритмы сортировки, поиска, перемешивания и других операций.

```java
List<String> names = new ArrayList<>();
Set<Integer> uniqueNumbers = new HashSet<>();
Queue<String> tasks = new ArrayDeque<>();
Map<Long, String> users = new HashMap<>();
```

---

## Основные понятия

Три похожих названия, которые нужно различать:

```text
Collection  → интерфейс группы элементов
Collections → утилитный класс со статическими методами
Map         → отдельная структура ключ → значение
```

### Collection

`Collection<E>` — базовый интерфейс для большинства коллекций. Он описывает группу
отдельных элементов типа `E`.

```java
Collection<String> values = new ArrayList<>();
```

Основные методы:

```text
add(element)
remove(element)
contains(element)
size()
isEmpty()
clear()
iterator()
```

### Collections

`Collections` — утилитный класс со статическими методами:

```java
Collections.sort(list);
Collections.reverse(list);
Collections.shuffle(list);
Collections.min(list);
Collections.max(list);
```

Экземпляр создавать не нужно и нельзя — конструктор закрыт.

### Map

`Map<K, V>` хранит пары «ключ — значение» и не наследуется от `Collection`.

```java
Map<Long, String> users = new HashMap<>();

users.put(1L, "Alice");
users.put(2L, "Bob");
```

Разница в природе хранимого:

```text
Collection        Map
element           key → value
element           key → value
element
```

При этом `Map` предоставляет представления своих данных в виде коллекций:

```java
map.keySet();    // Set<K>
map.values();    // Collection<V>
map.entrySet();  // Set<Map.Entry<K, V>>
```

Подробный разбор реализаций `Map` — в отдельном конспекте.

## Упрощённая иерархия

```text
Iterable<E>
    │
    └── Collection<E>
            │
            ├── List<E>
            │
            ├── Set<E>
            │
            └── Queue<E>
                    │
                    └── Deque<E>

Map<K, V> — отдельная иерархия
```

Схема упрощена: некоторые интерфейсы наследуют сразу несколько других.

---

## Iterable

`Iterable<E>` — базовый интерфейс объектов, элементы которых можно последовательно
обходить. Единственный обязательный метод:

```java
Iterator<E> iterator();
```

Благодаря ему коллекцию можно использовать в цикле `for-each`:

```java
List<String> names = List.of("Alice", "Bob", "Charlie");

for (String name : names) {
    System.out.println(name);
}
```

Под капотом это итератор:

```java
Iterator<String> iterator = names.iterator();

while (iterator.hasNext()) {
    String name = iterator.next();
    System.out.println(name);
}
```

## List

`List<E>` — упорядоченная последовательность элементов.

Основные свойства:

- сохраняет порядок добавления;
- допускает дубликаты;
- поддерживает доступ по индексу;
- обычно допускает `null`, но это зависит от реализации.

```java
List<String> values = new ArrayList<>();

values.add("A");
values.add("B");
values.add("A");
```

Результат:

```text
[A, B, A]
```

### Основные методы

```java
list.add(element);
list.add(index, element);

list.get(index);
list.set(index, element);

list.remove(index);
list.remove(element);

list.indexOf(element);
list.lastIndexOf(element);

list.subList(fromIndex, toIndex);
```

У `remove()` две перегрузки:

```text
remove(int index)     → удаляет по позиции
remove(Object element) → удаляет по значению
```

Это ловушка для `List<Integer>`:

```java
List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30));

numbers.remove(1);
```

Удалится элемент по индексу `1`, то есть число `20`. Чтобы удалить само число `1`:

```java
numbers.remove(Integer.valueOf(1));
```

### ArrayList

Основан на динамическом массиве. Упрощённо внутри лежит:

```java
Object[] elementData;
```

Когда массив заполняется, создаётся новый большего размера, а элементы копируются.

```text
старый массив
    ↓
создание нового массива
    ↓
копирование элементов
```

| Операция | Сложность |
|---|---:|
| Получение по индексу | `O(1)` |
| Изменение по индексу | `O(1)` |
| Добавление в конец | `O(1)` амортизированно |
| Вставка в начало или середину | `O(n)` |
| Удаление из начала или середины | `O(n)` |
| Поиск по значению | `O(n)` |
| Проверка `contains()` | `O(n)` |

Доступ по индексу выполняется за константу, потому что адрес элемента вычисляется
арифметически и обходить предшествующие элементы не нужно.

Вставка в середину стоит `O(n)`, потому что всё, что правее, сдвигается:

```text
[A, B, C, D]
       ↑ вставляем X

[A, B, X, C, D]
```

### Амортизированное добавление

Добавление в конец выполняется за `O(1)`, пока во внутреннем массиве есть место.
При заполнении требуется создать новый массив, скопировать старые элементы и
добавить новый. Отдельное расширение стоит `O(n)`, но происходит не при каждом
добавлении, поэтому средняя стоимость последовательности добавлений —
амортизированное `O(1)`.

### Capacity и size

```text
size     → количество фактически хранимых элементов
capacity → размер внутреннего массива
```

```java
List<String> values = new ArrayList<>(100);

values.size(); // 0
```

Начальная ёмкость равна `100`, но список пуст. Указывать её полезно, когда
количество элементов известно заранее:

```java
List<Order> orders = new ArrayList<>(expectedCount);
```

Это сокращает число расширений и копирований.

### LinkedList

Основан на двусвязном списке. Каждый узел содержит ссылку на предыдущий, значение
и ссылку на следующий:

```text
null ← [A] ⇄ [B] ⇄ [C] → null
```

`LinkedList` реализует не только `List`, но и `Deque`, поэтому может работать как
список, очередь, двусторонняя очередь и стек.

| Операция | Сложность |
|---|---:|
| Получение по индексу | `O(n)` |
| Поиск по значению | `O(n)` |
| Добавление в начало | `O(1)` |
| Добавление в конец | `O(1)` |
| Удаление первого элемента | `O(1)` |
| Удаление последнего элемента | `O(1)` |
| Вставка по индексу | `O(n)` |
| Удаление по индексу | `O(n)` |

Изменение ссылок занимает `O(1)`, но перед этим узел нужно найти:

```text
поиск узла:        O(n)
изменение ссылок:  O(1)
итого:             O(n)
```

Вставка будет `O(1)` только тогда, когда ссылка на узел уже есть, — например при
работе через `ListIterator`.

### ArrayList и LinkedList

| Критерий | ArrayList | LinkedList |
|---|---|---|
| Внутренняя структура | Динамический массив | Двусвязный список |
| Доступ по индексу | `O(1)` | `O(n)` |
| Добавление в конец | `O(1)` амортизированно | `O(1)` |
| Вставка по индексу | `O(n)` | `O(n)` |
| Удаление по индексу | `O(n)` | `O(n)` |
| Дополнительная память | Меньше | Больше из-за ссылок |
| Локальность данных | Хорошая | Хуже |
| Реализует Deque | Нет | Да |

По умолчанию берут `ArrayList`. Он лучше, когда нужен доступ по индексу, элементы
добавляются преимущественно в конец, важна скорость последовательного обхода и
меньший расход памяти.

`LinkedList` оправдан, когда активно используются операции с началом и концом,
нужна реализация `Deque` или вставка идёт через уже найденный итератор. На
практике для очереди и стека лучше `ArrayDeque`: у него та же семантика без
накладных расходов на узлы и с хорошей локальностью данных.

## Set

`Set<E>` — коллекция уникальных элементов.

Основные свойства:

- не допускает логических дубликатов;
- не предоставляет доступ по индексу;
- порядок хранения зависит от реализации;
- повторное добавление равного элемента не изменяет множество.

```java
Set<String> names = new HashSet<>();

names.add("Alice");
names.add("Bob");
names.add("Alice");
```

Останутся два элемента:

```text
Alice
Bob
```

Метод `add()` возвращает `true`, если элемент добавлен, и `false`, если равный уже
присутствовал:

```java
boolean first = names.add("Alice");  // true
boolean second = names.add("Alice"); // false
```

Три основные реализации отличаются порядком хранения, внутренней структурой и
сложностью операций.

### HashSet

Основан на хешировании.

- не сохраняет порядок вставки;
- поиск, добавление и удаление — `O(1)` в среднем;
- уникальность определяется через `hashCode()` и `equals()`;
- допускает один `null`;
- внутри использует `HashMap`.

```java
Set<Integer> numbers = new HashSet<>();

numbers.add(30);
numbers.add(10);
numbers.add(20);
```

Рассчитывать на порядок `30, 10, 20` нельзя: порядок не входит в контракт.

Элементы хранятся как ключи внутреннего `HashMap`, а значением для всех служит
одна и та же заглушка:

```text
элемент → PRESENT
```

Отсюда прямая зависимость корректности от `equals()` и `hashCode()`. Худший случай
операций хуже среднего при большом числе коллизий.

### LinkedHashSet

Хеш-таблица плюс связная структура, сохраняющая порядок вставки.

- сохраняет порядок первого появления элемента;
- операции — `O(1)` в среднем;
- требует больше памяти, чем `HashSet`;
- допускает один `null`.

```java
Set<Integer> numbers = new LinkedHashSet<>();

numbers.add(30);
numbers.add(10);
numbers.add(20);
```

Обход гарантированно даст `30, 10, 20`.

Типичное применение — удаление дубликатов с сохранением порядка:

```java
List<Integer> values = List.of(3, 1, 3, 2, 1);

Set<Integer> unique = new LinkedHashSet<>(values);
```

Результат:

```text
[3, 1, 2]
```

### TreeSet

Хранит элементы отсортированными, внутри — сбалансированное дерево. Реализует
`SortedSet<E>` и `NavigableSet<E>`.

- элементы сортируются автоматически;
- операции — `O(log n)`;
- уникальность определяется сравнением, а не `equals()`;
- порядок задаётся `Comparable` или `Comparator`;
- `null`, как правило, не поддерживается.

```java
Set<Integer> numbers = new TreeSet<>();

numbers.add(30);
numbers.add(10);
numbers.add(20);
```

Порядок обхода: `10, 20, 30`.

Без переданного компаратора элементы обязаны реализовывать `Comparable`.
Пользовательский порядок задаётся явно:

```java
Set<String> names = new TreeSet<>(
        Comparator.comparingInt(String::length)
                .thenComparing(Comparator.naturalOrder())
);
```

### Уникальность в TreeSet

Ключевое отличие, которое спрашивают:

```text
HashSet, LinkedHashSet → equals() + hashCode()
TreeSet                → compare(a, b) == 0 или a.compareTo(b) == 0
```

Компаратор может признать два объекта одинаковыми, даже если `equals()` возвращает
`false`:

```java
Set<String> values =
        new TreeSet<>(Comparator.comparingInt(String::length));

values.add("cat");
values.add("dog");
```

Обе строки длиной `3`, сравнение возвращает `0`, поэтому останется только одна.
Чтобы сохранить обе, нужен дополнительный критерий:

```java
Comparator.comparingInt(String::length)
          .thenComparing(Comparator.naturalOrder())
```

### NavigableSet

`TreeSet` даёт методы навигации по отсортированным данным:

```java
NavigableSet<Integer> numbers =
        new TreeSet<>(List.of(10, 20, 30, 40));

numbers.lower(30);   // 20 — строго меньше
numbers.floor(30);   // 30 — меньше или равно
numbers.higher(30);  // 40 — строго больше
numbers.ceiling(30); // 30 — больше или равно
```

Также доступны:

```java
numbers.first();
numbers.last();

numbers.pollFirst();
numbers.pollLast();

numbers.headSet(30);
numbers.tailSet(30);
numbers.subSet(20, true, 40, false);
```

### Сравнение реализаций

| Критерий | HashSet | LinkedHashSet | TreeSet |
|---|---|---|---|
| Порядок вставки | Нет | Да | Нет |
| Сортировка | Нет | Нет | Да |
| `add()` | `O(1)` в среднем | `O(1)` в среднем | `O(log n)` |
| `contains()` | `O(1)` в среднем | `O(1)` в среднем | `O(log n)` |
| `remove()` | `O(1)` в среднем | `O(1)` в среднем | `O(log n)` |
| Дополнительная память | Средняя | Больше | Больше |
| Механизм уникальности | `equals/hashCode` | `equals/hashCode` | `compareTo/Comparator` |
| `null` | Один | Один | Обычно нельзя |

```text
нужна только уникальность            → HashSet
уникальность и порядок вставки       → LinkedHashSet
уникальность и сортировка            → TreeSet
```

## Queue и Deque

`Queue<E>` представляет коллекцию элементов, ожидающих обработки. Чаще всего это
FIFO — first in, first out, — но интерфейс сам по себе такого не гарантирует:
`PriorityQueue` извлекает элементы по приоритету.

Методы идут парами, различаясь поведением при неудаче:

| Операция | Исключение при неудаче | Специальное значение |
|---|---|---|
| Добавление | `add()` | `offer()` |
| Получение с удалением | `remove()` | `poll()` |
| Просмотр без удаления | `element()` | `peek()` |

Для обычной очереди используют вторую колонку.

```java
Queue<String> tasks = new ArrayDeque<>();

tasks.offer("first");
tasks.offer("second");
tasks.offer("third");

String next = tasks.poll();   // first
```

### Deque

`Deque<E>` — двусторонняя очередь, double ended queue. Позволяет добавлять,
удалять и просматривать элементы с обоих концов.

| Операция | Начало | Конец |
|---|---|---|
| Добавление | `offerFirst()` | `offerLast()` |
| Удаление | `pollFirst()` | `pollLast()` |
| Просмотр | `peekFirst()` | `peekLast()` |

```java
Deque<Integer> deque = new ArrayDeque<>();

deque.offerFirst(10);
deque.offerLast(20);

int first = deque.pollFirst();
int last = deque.pollLast();
```

`Deque` используется как обычная очередь FIFO, как стек LIFO и как двусторонняя
очередь:

```java
Deque<Integer> stack = new ArrayDeque<>();

stack.push(10);
stack.push(20);

int value = stack.pop();   // 20
```

### PriorityQueue

Очередь с приоритетом, внутри — двоичная куча. По умолчанию первым извлекается
минимальный элемент в естественном порядке.

```java
PriorityQueue<Integer> queue = new PriorityQueue<>();

queue.offer(10);
queue.offer(3);
queue.offer(7);

queue.poll();   // 3
```

Для обратного порядка передаётся компаратор:

```java
PriorityQueue<Integer> maxHeap =
        new PriorityQueue<>(Comparator.reverseOrder());

maxHeap.offer(10);
maxHeap.offer(3);
maxHeap.offer(7);

maxHeap.poll();   // 10
```

Для пользовательского типа:

```java
PriorityQueue<User> queue = new PriorityQueue<>(
        Comparator.comparingInt(User::getPriority).reversed()
);
```

| Операция | Сложность |
|---|---:|
| `offer()` и `add()` | `O(log n)` |
| `poll()` и `remove()` первого элемента | `O(log n)` |
| `peek()` и `element()` | `O(1)` |
| поиск произвольного элемента | `O(n)` |

Внутренний массив не обязан быть полностью отсортирован: гарантируется только то,
что элемент с наивысшим приоритетом доступен через `peek()` и `poll()`. Поэтому
обход итератором порядка не даёт, упорядоченную последовательность получают
последовательным извлечением.

```text
получение минимума или максимума
Top K
планировщик по приоритету
алгоритм Дейкстры
```

## Map

`Map<K, V>` связывает уникальный ключ со значением.

```java
Map<String, Integer> ages = new HashMap<>();

ages.put("Alice", 25);
ages.put("Bob", 30);
```

Основные свойства:

- ключи уникальны, значения могут повторяться;
- `put()` по существующему ключу заменяет прежнее значение;
- доступ выполняется по ключу.

```java
ages.put("Alice", 26);
```

После этого:

```text
Alice → 26
Bob   → 30
```

Основные реализации — `HashMap`, `LinkedHashMap` и `TreeMap`; они соотносятся с
реализациями `Set` ровно так же, как описано выше, поскольку множества построены
на картах. Устройство бакетов, разрешение коллизий и переход к дереву разбираются
в отдельном конспекте.

## Comparable и Comparator

Оба задают порядок объектов, но по-разному.

### Comparable

`Comparable<T>` задаёт естественный порядок самого класса, и потому такой порядок
может быть только один.

```java
public class User implements Comparable<User> {

    private final long id;

    @Override
    public int compareTo(User other) {
        return Long.compare(this.id, other.id);
    }
}
```

Результат сравнения:

```text
< 0 → текущий объект меньше
= 0 → объекты равны с точки зрения порядка
> 0 → текущий объект больше
```

Естественный порядок используется там, где компаратор не передан:

```java
Collections.sort(users);
```

### Comparator

`Comparator<T>` — внешняя стратегия сравнения, и их может быть сколько угодно для
одного класса.

```java
Comparator<User> byAge =
        Comparator.comparingInt(User::getAge);

Comparator<User> byName =
        Comparator.comparing(User::getName);

Comparator<User> bySalary =
        Comparator.comparing(User::getSalary);
```

Компараторы комбинируются и разворачиваются:

```java
Comparator<User> comparator =
        Comparator.comparingInt(User::getAge)
                .thenComparing(User::getName);

Comparator<User> byAgeDescending =
        Comparator.comparingInt(User::getAge).reversed();
```

```text
Comparable            Comparator
естественный порядок  внешний или альтернативный порядок
логика внутри класса  логика отдельно
compareTo()           compare()
```

### Collections.sort и List.sort

Оба варианта сортируют список на месте и нового списка не создают.

```java
Collections.sort(list);   // естественный порядок
list.sort(comparator);    // переданный порядок
```

`Collections.sort()` внутри делегирует вызов `list.sort()`, появившемуся в Java 8,
поэтому в новом коде используют второй вариант.

## Iterator и ListIterator

`Iterator<E>` — интерфейс последовательного обхода:

```java
Iterator<String> iterator = list.iterator();
```

```text
hasNext()
next()
remove()
```

Цикл `for-each` использует его под капотом:

```java
for (String value : list) {
    System.out.println(value);
}
```

Эквивалентно:

```java
Iterator<String> iterator = list.iterator();

while (iterator.hasNext()) {
    String value = iterator.next();
    System.out.println(value);
}
```

### ListIterator

`ListIterator<E>` расширяет `Iterator<E>` и предназначен только для `List`. Умеет
двигаться в обе стороны, знает индексы и позволяет изменять список:

```text
hasNext() / next()
hasPrevious() / previous()
nextIndex() / previousIndex()
set(element) / add(element) / remove()
```

```java
ListIterator<String> iterator = list.listIterator();

while (iterator.hasNext()) {
    String value = iterator.next();

    if (value.equals("old")) {
        iterator.set("new");
    }
}
```

## Fail-fast

Итераторы обычных коллекций пытаются обнаружить структурное изменение коллекции,
выполненное в обход итератора во время обхода.

```java
for (String value : list) {
    if (value.equals("delete")) {
        list.remove(value);
    }
}
```

`for-each` работает через `Iterator`, а изменение идёт напрямую через `list`.
Упрощённо реализации сравнивают два счётчика:

```text
modCount         → число структурных изменений коллекции
expectedModCount → значение, которое запомнил Iterator
```

При расхождении выбрасывается `ConcurrentModificationException`.

> Это исключение не означает, что участвовало несколько потоков. Его легко
> получить и в одном.

### Безопасное изменение при обходе

```java
Iterator<String> iterator = list.iterator();

while (iterator.hasNext()) {
    String value = iterator.next();

    if (value.equals("delete")) {
        iterator.remove();
    }
}
```

Изменение выполняется через сам итератор, поэтому его состояние остаётся
согласованным. Для удаления по условию чаще подходит:

```java
list.removeIf(value -> value.equals("delete"));
```

### Границы механизма

`fail-fast` — попытка раннего обнаружения, best effort, а не строгая гарантия.

```text
fail-fast
→ пытается быстро обнаружить неожиданное изменение
→ может выбросить ConcurrentModificationException

fail-fast
≠ механизм потокобезопасности
≠ гарантия исключения при любом неправильном изменении
```

## Immutable и Unmodifiable

Важно различать неизменяемую коллекцию и неизменяемое представление другой
коллекции.

### Immutable collection

Структурно изменить нельзя:

```java
List<String> list = List.of("A", "B");

list.add("C");     // UnsupportedOperationException
```

То же касается `remove()` и `set()`.

### Unmodifiable view

```java
List<String> original = new ArrayList<>();
original.add("A");

List<String> view = Collections.unmodifiableList(original);

view.add("B");     // UnsupportedOperationException
```

Но исходная коллекция остаётся изменяемой, и изменения видны через представление:

```java
original.add("B");
```

```text
original → [A, B]
view     → [A, B]
```

```text
immutable collection → сама коллекция не изменяется
unmodifiable view    → через эту ссылку менять нельзя,
                       но исходная коллекция может измениться
```

### copyOf

`copyOf()` возвращает неизменяемый снимок текущего содержимого.

```java
List<String> original = new ArrayList<>();
original.add("A");

List<String> copy = List.copyOf(original);

original.add("B");
```

```text
original → [A, B]
copy     → [A]
```

В отличие от `unmodifiableList()`, дальнейшие изменения оригинала на результат не
влияют. При этом новый объект создаётся не всегда:

```java
List<String> original = List.of("A", "B");
List<String> copy = List.copyOf(original);

// original == copy может быть true
```

Гарантируется неизменяемость результата, а не новая идентичность объекта.

### Фабричные методы

```java
List<String> values = List.of("A", "B");
Set<String> unique = Set.of("A", "B");

Map<String, Integer> map = Map.of(
        "A", 1,
        "B", 2
);
```

Ограничения:

```text
List.of → null запрещён, изменения запрещены
Set.of  → null и дубликаты запрещены (IllegalArgumentException)
Map.of  → null в ключах и значениях запрещён,
          повторяющиеся ключи запрещены,
          не более десяти пар — дальше Map.ofEntries()
```

### Поверхностная неизменяемость

Неизменяемость коллекции не делает неизменяемыми объекты внутри неё.

```java
User user = new User("Dima");
List<User> users = List.of(user);

user.setName("Alex");
```

Состав списка не изменился, состояние объекта — изменилось.

```text
immutable collection ≠ глубокая неизменяемость содержимого
```

## Sequenced Collections

В Java 21 появились интерфейсы для коллекций с определённым порядком обхода:

```text
SequencedCollection<E>
SequencedSet<E>
SequencedMap<K, V>
```

У таких коллекций есть понятие первого и последнего элемента:

```text
getFirst() / getLast()
addFirst(element) / addLast(element)
removeFirst() / removeLast()
reversed()
```

`List` и `Deque` являются `SequencedCollection`:

```java
List<String> names = new ArrayList<>();

names.add("Bob");
names.addFirst("Alice");
names.addLast("Charlie");

String first = names.getFirst();   // Alice
String last = names.getLast();     // Charlie
```

Метод `reversed()` возвращает представление в обратном порядке:

```java
SequencedCollection<String> reversed = names.reversed();
```

Главная ценность в том, что операции с концами получили единые имена: раньше у
`List` и `Deque` они назывались по-разному.

## Необязательные операции

Часть операций интерфейса `Collection` объявлена необязательной для конкретной
реализации:

```java
List<String> names = List.of("Alice", "Bob");

names.add("Charlie");   // UnsupportedOperationException
```

Наличие метода в интерфейсе не гарантирует, что реализация разрешает изменение.

## Программирование через интерфейс

Переменную объявляют через интерфейс, а не через конкретный класс:

```java
List<String> names = new ArrayList<>();
Set<Integer> numbers = new HashSet<>();
Map<Long, String> users = new HashMap<>();
```

Так реализацию можно заменить, не трогая остальной код:

```java
List<String> names = new LinkedList<>();
```

## Stack в современном коде

Класс `java.util.Stack` — legacy API, наследующий `Vector`. Формально он не
помечен `@Deprecated`, но для нового кода предпочтителен `Deque`:

```java
Deque<Integer> stack = new ArrayDeque<>();

stack.push(10);
stack.push(20);

stack.pop();    // 20
stack.peek();   // 10
```

Причины две: `Vector` синхронизирован, что даёт лишние накладные расходы, и
наследование от него открывает доступ по индексу, нарушающий семантику стека.

## Типичные ошибки

### Считать вставку в LinkedList по индексу операцией O(1)

Изменение ссылок действительно константно, но поиск нужного узла занимает `O(n)`.

### Выбирать LinkedList из-за частых вставок

Стоимость поиска позиции обычно перевешивает выигрыш от перестановки ссылок.

### Удалять с начала ArrayList

```java
arrayList.remove(0);
```

Это `O(n)`: оставшиеся элементы сдвигаются. Для очереди нужен `ArrayDeque`.

### Путать size и capacity

Начальная ёмкость не создаёт элементы и не влияет на `size()`.

### Вызывать remove(int) вместо remove(Object)

Для `List<Integer>` вызов `remove(1)` удаляет элемент с индексом `1`, а не число
`1`. Нужен `remove(Integer.valueOf(1))`.

### Ожидать порядок от HashSet

Порядок обхода не входит в контракт и может измениться между запусками.

### Использовать TreeSet только для удаления дубликатов

Если сортировка не нужна, `HashSet` быстрее: `O(1)` в среднем против `O(log n)`.

### Забыть про equals и hashCode

Для пользовательских объектов в `HashSet` и ключей `HashMap` оба метода должны
быть переопределены согласованно.

### Писать компаратор, возвращающий 0 для разных объектов

`TreeSet` считает такие элементы дубликатами и молча теряет один из них.

### Изменять поля объекта, лежащего в HashSet

Если изменить поле, участвующее в `hashCode()`, объект окажется не в той корзине,
и `contains()` перестанет его находить.

### Изменять коллекцию напрямую во время обхода

Даёт `ConcurrentModificationException` даже в одном потоке. Нужен
`iterator.remove()` или `removeIf()`.

### Считать fail-fast гарантией

Это обнаружение по возможности, а не строгая проверка и тем более не
потокобезопасность.

### Путать unmodifiable view и immutable collection

Представление запрещает изменения только через себя; исходная коллекция может
измениться, и это будет видно.

### Считать неизменяемую коллекцию глубоко неизменяемой

Состав менять нельзя, состояние объектов внутри — можно.

### Использовать Stack в новом коде

Наследник `Vector` с лишней синхронизацией и доступом по индексу. Нужен
`ArrayDeque`.

## Краткая памятка

```text
Collection  → интерфейс группы элементов
Collections → утилитный класс
Map         → отдельная иерархия ключ → значение
```

```text
нужен порядок и индексы       → List
нужны уникальные элементы     → Set
нужна очередь обработки       → Queue
нужна работа с обоими концами → Deque
нужно соответствие ключу      → Map
```

```text
ArrayList
→ динамический массив
→ get O(1)
→ add в конец O(1) амортизированно
→ вставка и удаление в середине O(n)

LinkedList
→ двусвязный список
→ get O(n)
→ работа с уже найденным узлом O(1)
→ вставка по индексу O(n) из-за поиска
```

```text
HashSet       → хеш-таблица, equals + hashCode, O(1) в среднем
LinkedHashSet → то же плюс порядок вставки
TreeSet       → красно-чёрное дерево, O(log n),
                compare(...) == 0 означает дубликат
```

```text
ArrayDeque    → FIFO и LIFO, современный выбор для Queue и Stack
PriorityQueue → куча, offer и poll O(log n), peek O(1),
                полный порядок обхода не гарантирован
```

```text
Comparable → естественный порядок, compareTo(), один на класс
Comparator → внешняя стратегия, compare(), сколько угодно
```

```text
Iterator     → последовательный обход вперёд
ListIterator → только List, обе стороны, индексы, add и set
```

```text
fail-fast
→ попытка обнаружить неожиданное структурное изменение
→ ConcurrentModificationException
→ не гарантия и не потокобезопасность
```

```text
Collections.unmodifiableList(original)
→ представление, изменения original видны

List.copyOf(original)
→ неизменяемый снимок, изменения original не видны

List.of / Set.of / Map.of
→ неизменяемы, null запрещён
→ Set.of: дубликаты запрещены
→ Map.of: повторные ключи запрещены
```

---

## Краткий ответ для собеседования

Collections Framework строится на интерфейсе `Collection`, от которого наследуются
`List`, `Set` и `Queue`. `Map` в эту иерархию не входит, потому что хранит не
элементы, а соответствия ключей значениям, хотя и предоставляет представления в
виде коллекций.

`List` упорядочен, допускает дубликаты и доступ по индексу. `ArrayList` основан на
динамическом массиве: доступ по индексу за константу, добавление в конец
амортизированно за константу, вставка и удаление в середине за линейное время.
`LinkedList` — двусвязный список: перестановка ссылок дёшева, но узел сначала
нужно найти, поэтому вставка по индексу всё равно линейна. По умолчанию берут
`ArrayList`, а для очереди и стека — `ArrayDeque`.

`Set` хранит уникальные элементы. `HashSet` построен на `HashMap` и определяет
уникальность через `hashCode()` и `equals()`, давая константное время в среднем.
`LinkedHashSet` добавляет порядок вставки. `TreeSet` держит элементы
отсортированными за логарифмическое время, но уникальность определяет сравнением:
если компаратор вернул ноль, элемент считается дубликатом, даже когда `equals()`
говорит обратное.

Порядок задаётся двумя способами: `Comparable` описывает единственный естественный
порядок внутри класса, `Comparator` — внешняя стратегия, которых может быть
сколько угодно.

Обход выполняется итератором, и итераторы обычных коллекций работают в режиме
fail-fast: при изменении коллекции в обход итератора они выбрасывают
`ConcurrentModificationException`. Это механизм обнаружения ошибок, а не
потокобезопасность, и сработать он может в одном потоке.

Наконец, стоит различать неизменяемую коллекцию и неизменяемое представление:
первое нельзя изменить вообще, второе лишь запрещает изменения через себя, оставляя
исходную коллекцию изменяемой. И в обоих случаях неизменяемость поверхностна —
объекты внутри остаются изменяемыми.

## Вопросы на собеседовании

### 1. Чем Collection отличается от Collections?

**Ответ:** первое — интерфейс группы элементов, второе — утилитный класс со
статическими методами вроде `sort()` и `shuffle()`.

### 2. Почему Map не наследует Collection?

**Ответ:** коллекция хранит отдельные элементы, а карта — соответствия ключей
значениям. Методы `Collection` для неё не имеют смысла, поэтому иерархии разные.

### 3. Что даёт интерфейс Iterable?

**Ответ:** метод `iterator()`, благодаря которому объект можно обходить циклом
`for-each`.

### 4. Чем ArrayList отличается от LinkedList?

**Ответ:** первый основан на динамическом массиве и даёт доступ по индексу за
константу, второй — двусвязный список с линейным доступом, но дешёвыми операциями
с концами. `LinkedList` дополнительно реализует `Deque`.

### 5. Почему добавление в конец ArrayList считается амортизированным O(1)?

**Ответ:** пока в массиве есть место, операция константна. Расширение с
копированием стоит `O(n)`, но происходит редко, поэтому средняя стоимость на
длинной последовательности добавлений остаётся константной.

### 6. Чем size отличается от capacity?

**Ответ:** `size` — количество фактически хранимых элементов, `capacity` — размер
внутреннего массива. Указание начальной ёмкости не создаёт элементов.

### 7. Почему вставка по индексу в LinkedList не O(1)?

**Ответ:** перестановка ссылок константна, но узел сначала нужно найти, а это
`O(n)`. Константной вставка будет только через уже полученный `ListIterator`.

### 8. Что выбрать по умолчанию?

**Ответ:** `ArrayList` для списка и `ArrayDeque` для очереди или стека.
`LinkedList` оправдан редко.

### 9. Почему numbers.remove(1) для List<Integer> удаляет не то, что ожидается?

**Ответ:** выбирается перегрузка `remove(int index)`, то есть удаление по позиции.
Чтобы удалить значение, нужно `remove(Integer.valueOf(1))`.

### 10. Как HashSet обеспечивает уникальность?

**Ответ:** он построен на `HashMap`, где элементы выступают ключами, а значением
служит одна заглушка. Уникальность определяется связкой `hashCode()` и `equals()`.

### 11. Что возвращает add() при повторном добавлении?

**Ответ:** `false` — множество не изменилось.

### 12. Чем LinkedHashSet отличается от HashSet?

**Ответ:** дополнительной связной структурой, которая сохраняет порядок первого
появления элементов. Цена — больший расход памяти.

### 13. Как TreeSet определяет дубликат?

**Ответ:** сравнением: если `compare()` или `compareTo()` вернули ноль, элемент
считается уже присутствующим. `equals()` при этом не используется.

### 14. Почему опасно менять поля объекта, лежащего в HashSet?

**Ответ:** изменение поля, участвующего в `hashCode()`, меняет корзину, в которой
объект должен искаться. Сам объект остаётся в прежней, и `contains()` его не
находит.

### 15. Чем Comparable отличается от Comparator?

**Ответ:** `Comparable` реализуется самим классом и задаёт его единственный
естественный порядок через `compareTo()`. `Comparator` — внешний объект с методом
`compare()`, описывающий произвольный порядок, и таких может быть много.

### 16. Чем Iterator отличается от ListIterator?

**Ответ:** `Iterator` идёт только вперёд и умеет удалять. `ListIterator` доступен
для списков, ходит в обе стороны, знает индексы и позволяет вставлять и заменять
элементы.

### 17. Почему ConcurrentModificationException можно получить в одном потоке?

**Ответ:** исключение сигнализирует не о конкуренции потоков, а о структурном
изменении коллекции во время обхода. Удаление элемента внутри цикла `for-each`
даёт его в одном потоке.

### 18. Что означает fail-fast?

**Ответ:** итератор отслеживает счётчик модификаций коллекции и при расхождении
немедленно выбрасывает исключение вместо того, чтобы продолжать работу с
неопределённым результатом.

### 19. Почему iterator.remove() допустим во время обхода?

**Ответ:** он изменяет коллекцию через сам итератор и синхронизирует счётчик
модификаций, поэтому расхождения не возникает.

### 20. Чем immutable collection отличается от unmodifiable view?

**Ответ:** неизменяемая коллекция не может быть изменена вообще. Неизменяемое
представление запрещает изменения только через себя и остаётся связанным с
исходной коллекцией: её изменения в нём видны.

### 21. Чем List.copyOf() отличается от Collections.unmodifiableList()?

**Ответ:** `copyOf()` создаёт независимый неизменяемый снимок,
`unmodifiableList()` возвращает представление исходного списка.

### 22. Обязана ли List.copyOf() создавать новый объект?

**Ответ:** нет. Если аргумент уже является подходящим неизменяемым списком,
реализация вправе вернуть его же.

### 23. Можно ли передать null в List.of()?

**Ответ:** нет, будет `NullPointerException`. Фабричные методы Java 9 запрещают
`null` как элемент.

### 24. Что произойдёт при дубликате в Set.of()?

**Ответ:** `IllegalArgumentException`. В отличие от `HashSet`, где дубликат просто
игнорируется, фабричный метод считает его ошибкой вызывающего кода.

### 25. Какие ограничения есть у Map.of()?

**Ответ:** запрет на `null` в ключах и значениях, запрет на дублирующиеся ключи и
ограничение в десять пар. Для большего числа существует `Map.ofEntries()`.

### 26. Делает ли immutable collection неизменяемыми свои элементы?

**Ответ:** нет, неизменяемость поверхностная. Изменить состав нельзя, а состояние
объектов внутри — можно.

### 27. Как устроена PriorityQueue?

**Ответ:** это двоичная куча в массиве. Элемент с наивысшим приоритетом всегда в
корне, поэтому его извлечение дёшево, а вставка и удаление стоят `O(log n)`.

### 28. Как сделать max-heap?

**Ответ:** передать компаратор с обратным порядком, например
`Comparator.reverseOrder()`.

### 29. Почему обход PriorityQueue не даёт отсортированную последовательность?

**Ответ:** куча упорядочена лишь частично — гарантируется только положение корня.
Итератор идёт по внутреннему массиву; упорядоченный результат даёт только
последовательный `poll()`.

### 30. Чем отличаются offer() и add() у очереди?

**Ответ:** поведением при неудаче. `add()` бросает исключение, `offer()` возвращает
специальное значение. Аналогично различаются `remove()` и `poll()`, `element()` и
`peek()`.

### 31. Почему для стека предпочтительнее ArrayDeque, а не Stack?

**Ответ:** `Stack` наследует `Vector` и потому синхронизирован, что даёт лишние
накладные расходы, а наследование открывает доступ по индексу, нарушающий
семантику стека.

### 32. Чем Collections.sort(list) отличается от list.sort(comparator)?

**Ответ:** это статический метод-утилита и метод самого списка, появившийся в
Java 8. Внутри `Collections.sort()` делегирует вызов `list.sort()`, поэтому
разницы в поведении нет.

### 33. Что дали Sequenced Collections в Java 21?

**Ответ:** единые имена операций с первым и последним элементом для всех
упорядоченных коллекций и метод `reversed()`, возвращающий представление в
обратном порядке.
