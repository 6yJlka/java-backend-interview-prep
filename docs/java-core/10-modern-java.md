# Modern Java: Enum, Record и Sealed Classes

## Enum

### Enum — это класс

`enum` не является отдельным примитивом языка. Компилятор превращает его в класс,
неявно наследующий `java.lang.Enum`, а каждая константа становится статическим
экземпляром этого класса.

```java
enum IncidentStatus {
    OPEN,
    IN_PROGRESS,
    CLOSED
}
```

Отсюда следуют важные свойства:

- наследование от другого класса невозможно, поскольку место в иерархии уже занято;
- реализовать интерфейсы можно;
- конструктор всегда `private` и не может быть вызван извне;
- константы создаются JVM при инициализации класса, поэтому создание потокобезопасно;
- экземпляр каждой константы существует в единственном числе.

### Поля, конструктор и методы

Enum может нести состояние и поведение:

```java
enum IncidentPriority {

    LOW(1, "Низкий"),
    MEDIUM(2, "Средний"),
    HIGH(3, "Высокий"),
    CRITICAL(4, "Критический");

    private final int weight;
    private final String title;

    IncidentPriority(int weight, String title) {
        this.weight = weight;
        this.title = title;
    }

    public int getWeight() {
        return weight;
    }

    public boolean requiresImmediateResponse() {
        return weight >= HIGH.weight;
    }
}
```

Список констант идёт первым, после него ставится точка с запятой, и только затем
объявляются поля и методы.

Модификатор `private` у конструктора писать не нужно — он подразумевается, а
`public` или `protected` вызовут ошибку компиляции.

### Стандартные методы

```java
IncidentStatus.values();          // массив всех констант
IncidentStatus.valueOf("OPEN");   // константа по имени
status.name();                    // "OPEN"
status.ordinal();                 // порядковый номер, начиная с 0
```

`valueOf()` бросает `IllegalArgumentException`, если константы с таким именем нет.
Имя чувствительно к регистру.

`values()` возвращает **новый массив при каждом вызове**. Это защита от изменения
внутреннего состояния: если бы возвращался один и тот же массив, любой код мог бы
перезаписать его элемент. Практическое следствие — не стоит вызывать `values()`
внутри цикла:

```java
for (int i = 0; i < IncidentStatus.values().length; i++) { // копия на каждой итерации
}
```

```java
IncidentStatus[] statuses = IncidentStatus.values();       // одна копия
for (int i = 0; i < statuses.length; i++) {
}
```

`name()` возвращает имя константы точно так, как оно объявлено, и переопределить
его нельзя — метод `final`. `toString()` по умолчанию возвращает то же самое, но
его переопределить можно.

### Сравнение

Константы enum сравнивают через `==`:

```java
if (status == IncidentStatus.OPEN) {
}
```

Это безопасно, потому что экземпляр каждой константы единственный, и в отличие от
`equals()` не бросает `NullPointerException` при `null` слева.

`equals()` у `Enum` объявлен `final` и сводится к сравнению ссылок, так что разницы
в поведении нет — только в устойчивости к `null` и в читаемости.

### Enum в switch

Внутри `switch` квалификатор не пишется:

```java
switch (status) {
    case OPEN -> notifyAssignee();
    case IN_PROGRESS -> updateSla();
    case CLOSED -> archive();
}
```

Начиная с Java 14 `switch` может быть выражением, и для enum он проверяется на
полноту: если перечислены все константы, ветка `default` не требуется.

```java
String label = switch (status) {
    case OPEN -> "Открыт";
    case IN_PROGRESS -> "В работе";
    case CLOSED -> "Закрыт";
};
```

Здесь есть тонкость, которую полезно понимать. Отсутствие `default` — не только
краткость: при добавлении новой константы компилятор укажет на все такие `switch`.
С веткой `default` новая константа молча попадёт в неё, и ошибка проявится уже во
время выполнения.

### Constant-specific behaviour

Каждая константа может иметь собственную реализацию метода:

```java
enum Operation {

    PLUS {
        @Override
        public int apply(int a, int b) {
            return a + b;
        }
    },

    MINUS {
        @Override
        public int apply(int a, int b) {
            return a - b;
        }
    };

    public abstract int apply(int a, int b);
}
```

Технически каждая такая константа — экземпляр анонимного подкласса. Поэтому
`Operation.PLUS.getClass()` вернёт не `Operation`, а сгенерированный класс вида
`Operation$1`. Enum без таких тел неявно `final`; с ними — нет.

### Enum и интерфейсы

```java
interface Describable {
    String description();
}

enum IncidentStatus implements Describable {

    OPEN,
    CLOSED;

    @Override
    public String description() {
        return name().toLowerCase();
    }
}
```

Это стандартный способ дать enum общий контракт с другими типами.

### EnumSet и EnumMap

Для enum существуют специализированные коллекции, и они заметно эффективнее общих.

```java
EnumSet<IncidentStatus> active = EnumSet.of(
        IncidentStatus.OPEN,
        IncidentStatus.IN_PROGRESS
);

EnumMap<IncidentStatus, Integer> counters =
        new EnumMap<>(IncidentStatus.class);
```

`EnumSet` внутри представлен битовой маской: для перечисления не более чем из 64
констант — одним `long`. Проверка вхождения сводится к битовой операции, хеширование
не выполняется вовсе.

`EnumMap` использует обычный массив, индексируемый по `ordinal()`. Коллизий нет,
хеш не считается, порядок обхода совпадает с порядком объявления констант.

```text
HashSet<Enum>  → хеширование, bucket, объекты-обёртки
EnumSet        → битовая маска

HashMap<Enum, V> → хеширование, bucket, Node
EnumMap          → массив по ordinal
```

Оба не допускают `null` в качестве элемента или ключа.

Полезная деталь: `EnumSet` — абстрактный класс, экземпляры создаются только через
фабрики `of()`, `noneOf()`, `allOf()`, `range()`, `complementOf()`.

### Enum как singleton

Enum с единственной константой — самый надёжный способ реализовать singleton:

```java
enum ConfigHolder {

    INSTANCE;

    private final Properties properties = load();

    public Properties get() {
        return properties;
    }
}
```

Причины: инициализация выполняется JVM и потокобезопасна без двойной проверки,
рефлексия не может создать второй экземпляр, десериализация не порождает дубликат.

### ordinal и хранение в базе

`ordinal()` возвращает позицию константы в объявлении. Опираться на это значение
опасно: вставка новой константы в середину сдвигает номера всех последующих.

Отсюда правило для JPA:

```java
@Enumerated(EnumType.STRING)
private IncidentStatus status;
```

`EnumType.ORDINAL` — вариант по умолчанию, и он хранит именно порядковый номер.
Любая перестановка констант тихо повредит уже сохранённые данные. `STRING` хранит
имя, поэтому переупорядочивание безопасно, а вот переименование константы — нет.

Тот же принцип касается сериализации и внешних API: наружу отдают `name()`, а не
`ordinal()`.

## Record

### Зачем нужен

Класс, единственная задача которого — переносить данные, требовал много
однообразного кода: поля, конструктор, геттеры, `equals()`, `hashCode()`,
`toString()`. Этот код не выражает намерения и легко расходится с полями при
изменениях.

```java
record UserView(long id, String email, String displayName) {
}
```

Одна строка заменяет несколько десятков.

### Что генерирует компилятор

Для объявления выше создаются:

- `private final` поля для каждого компонента;
- канонический конструктор со всеми компонентами в порядке объявления;
- методы доступа с именами компонентов: `id()`, `email()`, `displayName()`;
- `equals()`, сравнивающий все компоненты;
- `hashCode()`, согласованный с `equals()`;
- `toString()` вида `UserView[id=1, email=a@b.c, displayName=Dima]`.

Важно: методы доступа называются `id()`, а не `getId()`. Соглашение JavaBeans здесь
не действует, что иногда требует настройки библиотек, ожидающих геттеры.

### Свойства

- record неявно `final`, наследоваться от него нельзя;
- он неявно наследует `java.lang.Record`, поэтому расширить другой класс нельзя;
- реализовывать интерфейсы можно;
- компоненты всегда `final`;
- объявлять дополнительные поля экземпляра нельзя;
- статические поля и методы объявлять можно;
- record может быть объявлен внутри метода как локальный тип.

Запрет на дополнительные поля принципиален: состояние record полностью описывается
списком компонентов, и на этом строятся сгенерированные `equals()` и `hashCode()`.

### Compact constructor

Для валидации и нормализации служит компактная форма — без списка параметров и без
явных присваиваний:

```java
record Money(BigDecimal amount, String currency) {

    Money {
        Objects.requireNonNull(amount, "amount must not be null");
        Objects.requireNonNull(currency, "currency must not be null");

        if (amount.signum() < 0) {
            throw new IllegalArgumentException("amount must not be negative");
        }

        currency = currency.toUpperCase();
    }
}
```

Присваивание полям компилятор добавляет сам, в самом конце. Внутри тела работают с
параметрами, а не с полями: `currency = currency.toUpperCase()` меняет параметр, и
уже нормализованное значение попадёт в поле. Обращение к `this.currency` здесь
приведёт к ошибке компиляции.

Можно объявить и полный канонический конструктор, но тогда присваивать поля
придётся вручную.

### Дополнительные конструкторы

```java
record Money(BigDecimal amount, String currency) {

    Money(BigDecimal amount) {
        this(amount, "RUB");
    }
}
```

Любой неканонический конструктор обязан делегировать каноническому через `this(...)`.

### Переопределение методов

Сгенерированные методы можно заменить своими:

```java
record UserView(long id, String email) {

    @Override
    public String toString() {
        return "UserView[id=" + id + "]"; // не раскрываем email в логах
    }
}
```

С `equals()` и `hashCode()` так делать стоит осторожно: их согласованность —
единственная причина, по которой record безопасно класть в `HashSet` или
использовать как ключ `Map`.

### Immutability поверхностная

Это самая частая ловушка.

```java
record Team(String name, List<String> members) {
}
```

```java
List<String> members = new ArrayList<>(List.of("Dima"));
Team team = new Team("Backend", members);

members.add("Alex"); // состояние team изменилось
```

Поле `members` — `final`, но список за ссылкой изменяемый. Та же история, что с
`final`-ссылкой в JMM и с захватом объекта лямбдой.

Защита — копирование в compact constructor и в методе доступа:

```java
record Team(String name, List<String> members) {

    Team {
        members = List.copyOf(members);
    }
}
```

`List.copyOf()` создаёт неизменяемую копию, поэтому дополнительная защита в геттере
уже не нужна. Если бы копия была изменяемой, потребовалось бы и переопределение
метода доступа.

### Где применяются

- DTO для API и ответы контроллеров;
- value objects: деньги, координаты, диапазоны дат;
- ключи `Map` — сгенерированные `equals()` и `hashCode()` корректны по построению;
- возврат нескольких значений из метода вместо массива или `Map`;
- локальные record внутри метода для промежуточных группировок в стримах;
- проекции результатов запросов.

### Где не применяются

**JPA Entity.** Hibernate требует конструктор без аргументов и изменяемые поля,
создаёт прокси через наследование и полагается на dirty checking. Record не
удовлетворяет ни одному из этих требований. При этом как **проекция** результата
запроса record подходит отлично:

```java
record UserSummary(long id, String email) {
}
```

```java
@Query("select new com.example.UserSummary(u.id, u.email) from User u")
List<UserSummary> findSummaries();
```

**Изменяемое состояние.** Если объекту нужно менять поля в течение жизни, record —
неподходящий инструмент.

**Классы с поведением.** Record описывает данные. Класс, чья суть — операции, а не
набор значений, лучше оставить обычным.

### Record patterns

С Java 21 record можно разбирать на компоненты прямо в сопоставлении:

```java
if (shape instanceof Circle(double radius)) {
    return Math.PI * radius * radius;
}
```

Работает и вложенно, и в `switch`. Это не отдельная возможность record, а часть
общего pattern matching, но именно с record она раскрывается полнее всего.

## Sealed Classes

### Задача

Обычная иерархия открыта: любой класс может унаследоваться от вашего. Иногда это
нежелательно — набор вариантов известен заранее и должен оставаться закрытым.

До Java 17 закрыть иерархию можно было только `final`, что запрещает наследование
вовсе, или package-private конструктором, что ограничивает грубо и неявно.

```java
public sealed interface PaymentMethod
        permits Card, BankTransfer, Cash {
}

public record Card(String number, String holder) implements PaymentMethod {
}

public record BankTransfer(String iban) implements PaymentMethod {
}

public record Cash() implements PaymentMethod {
}
```

Теперь список реализаций фиксирован и виден в объявлении.

### Правила

Каждый наследник обязан объявить один из трёх модификаторов:

```text
final      → иерархия на нём заканчивается
sealed     → продолжается, но тоже ограниченным списком
non-sealed → снова открывается для произвольного наследования
```

Пропустить модификатор нельзя — это ошибка компиляции. Record и enum подходят
сразу, поскольку неявно `final`.

Дополнительные требования:

- наследники должны находиться в том же модуле, а без модулей — в том же пакете;
- если все наследники объявлены в одном файле с базовым типом, `permits` можно
  опустить, компилятор выведет список сам;
- каждый перечисленный в `permits` тип обязан действительно наследовать базовый.

`non-sealed` существует ради компромисса: часть ветвей иерархии можно оставить
закрытой, а конкретную ветку намеренно открыть для расширения.

### Исчерпывающий switch

Главная практическая выгода. Компилятор знает полный список вариантов, поэтому
`default` не нужен:

```java
String describe(PaymentMethod method) {
    return switch (method) {
        case Card card -> "Карта " + card.number();
        case BankTransfer transfer -> "Перевод на " + transfer.iban();
        case Cash cash -> "Наличные";
    };
}
```

Добавление нового варианта в `permits` сделает такой `switch` ошибкой компиляции —
ровно то поведение, которое нужно, чтобы не забыть обработать новый случай.

### Sealed вместе с record

Связка «sealed-интерфейс плюс record-реализации» описывает замкнутый набор
вариантов, каждый со своим набором данных. Вместе с pattern matching получается
компактная и проверяемая компилятором обработка:

```java
sealed interface Result permits Success, Failure {
}

record Success(String value) implements Result {
}

record Failure(String message, int code) implements Result {
}
```

```java
String render(Result result) {
    return switch (result) {
        case Success(String value) -> "OK: " + value;
        case Failure(String message, int code) -> "Ошибка " + code + ": " + message;
    };
}
```

## Типичные ошибки

### Хранить ordinal в базе или во внешнем API

Вставка константы в середину списка сдвигает номера. В JPA нужен
`@Enumerated(EnumType.STRING)`.

### Вызывать values() в цикле

Метод создаёт новый массив при каждом вызове.

### Ожидать, что valueOf вернёт null

При отсутствии константы бросается `IllegalArgumentException`.

### Использовать HashMap вместо EnumMap

`EnumMap` работает через массив по `ordinal()` и не хеширует ключи.

### Добавлять default в switch по enum

Ветка `default` скрывает появление новой константы. Без неё компилятор укажет на
неполный `switch`.

### Считать record полностью неизменяемым

Неизменяемы ссылки, а не объекты за ними. Изменяемые коллекции и даты нужно
копировать в компактном конструкторе.

### Присваивать this.field в compact constructor

Внутри компактной формы работают с параметрами. Присваивание полей добавляет
компилятор.

### Пытаться использовать record как JPA Entity

Отсутствуют конструктор без аргументов, изменяемые поля и возможность создать
прокси наследованием. Для проекций record при этом подходит.

### Ожидать геттеры вида getId у record

Методы доступа называются по именам компонентов: `id()`, а не `getId()`.

### Забыть модификатор у наследника sealed-типа

Каждый наследник обязан быть `final`, `sealed` или `non-sealed`.

### Считать sealed заменой final

`final` запрещает наследование целиком. `sealed` разрешает его ограниченному
списку типов.

## Краткая памятка

```text
Enum

наследует java.lang.Enum → extends другого класса невозможен
implements интерфейсов    → возможен
конструктор               → всегда private
константы                 → единственные экземпляры, сравнение через ==

values()  → новая копия массива при каждом вызове
valueOf() → IllegalArgumentException, если имени нет
name()    → final, переопределить нельзя
ordinal() → позиция; не хранить снаружи

EnumSet → битовая маска
EnumMap → массив по ordinal

JPA → @Enumerated(EnumType.STRING)
```

```text
Record

неявно final, наследует java.lang.Record
extends невозможен, implements возможен

генерируются:
  private final поля
  канонический конструктор
  accessors по именам компонентов
  equals, hashCode, toString

нельзя: поля экземпляра сверх компонентов
можно:  статические поля и методы, свои конструкторы, переопределение методов

compact constructor
→ без параметров
→ работа с параметрами, не с полями
→ присваивание добавляет компилятор

immutability поверхностная
→ изменяемые компоненты копировать
```

```text
Sealed

sealed + permits → закрытый список наследников
наследник обязан быть final | sealed | non-sealed
тот же модуль или тот же пакет
permits можно опустить, если всё в одном файле

выгода → исчерпывающий switch без default
```

## Краткий ответ для собеседования

`enum` — это класс, неявно наследующий `java.lang.Enum`, поэтому расширять другой
класс он не может, а реализовывать интерфейсы может. Каждая константа — единственный
экземпляр, созданный JVM при инициализации класса, поэтому сравнение выполняется
через `==`, а enum с одной константой является надёжной реализацией singleton.
`values()` возвращает новую копию массива при каждом вызове, `valueOf()` бросает
`IllegalArgumentException` для неизвестного имени. Для enum существуют `EnumSet`
на битовой маске и `EnumMap` на массиве по `ordinal()`, которые эффективнее общих
коллекций. Опираться на `ordinal()` при хранении данных нельзя, поэтому в JPA
используют `@Enumerated(EnumType.STRING)`.

`record` — компактное объявление неизменяемого носителя данных. Компилятор
генерирует `final`-поля, канонический конструктор, методы доступа по именам
компонентов, `equals()`, `hashCode()` и `toString()`. Record неявно `final`,
наследует `java.lang.Record`, дополнительных полей экземпляра иметь не может, но
может реализовывать интерфейсы и объявлять статические члены. Валидация и
нормализация выполняются в компактном конструкторе. Неизменяемость поверхностная:
изменяемые компоненты нужно копировать. Record подходит для DTO, value objects,
ключей `Map` и проекций запросов, но не годится на роль JPA Entity.

`sealed` ограничивает список наследников через `permits`. Каждый наследник обязан
быть `final`, `sealed` или `non-sealed` и находиться в том же модуле или пакете.
Главная выгода — исчерпывающий `switch` без ветки `default`: при добавлении нового
варианта компилятор укажет на все места, где его не обработали.

## Вопросы на собеседовании

### 1. Enum — это класс?

**Ответ:** да. Компилятор создаёт класс, неявно наследующий `java.lang.Enum`, а
каждая константа становится его статическим экземпляром.

### 2. Может ли enum наследовать класс или реализовывать интерфейс?

**Ответ:** наследовать класс нельзя, место в иерархии занято `java.lang.Enum`.
Реализовывать интерфейсы можно.

### 3. Почему конструктор enum всегда private?

**Ответ:** набор экземпляров фиксирован списком констант, и создание новых извне
нарушило бы эту гарантию. Явные `public` и `protected` вызовут ошибку компиляции.

### 4. Почему константы enum сравнивают через ==?

**Ответ:** экземпляр каждой константы единственный, поэтому сравнение ссылок
корректно. Дополнительно оно не бросает `NullPointerException` при `null`.

### 5. Что возвращает values() и в чём подвох?

**Ответ:** массив всех констант, причём новую копию при каждом вызове — чтобы
внутреннее состояние нельзя было испортить. Поэтому вызывать его в цикле не стоит.

### 6. Что делает valueOf при неизвестном имени?

**Ответ:** бросает `IllegalArgumentException`. Имя чувствительно к регистру.

### 7. Почему нельзя опираться на ordinal?

**Ответ:** это позиция в объявлении. Вставка константы в середину сдвигает номера
последующих и портит уже сохранённые данные. В JPA используют
`@Enumerated(EnumType.STRING)`.

### 8. Чем EnumSet и EnumMap лучше HashSet и HashMap?

**Ответ:** `EnumSet` представлен битовой маской, `EnumMap` — массивом по
`ordinal()`. Хеширование не выполняется, коллизий нет, расход памяти меньше.

### 9. Почему enum считается лучшим способом реализовать singleton?

**Ответ:** инициализация выполняется JVM и потокобезопасна, рефлексия не может
создать второй экземпляр, десериализация не порождает дубликат.

### 10. Нужен ли default в switch по enum?

**Ответ:** если перечислены все константы — нет, и лучше его не добавлять. Тогда
при появлении новой константы компилятор укажет на неполный `switch`, а с `default`
ошибка проявилась бы только во время выполнения.

### 11. Что генерирует компилятор для record?

**Ответ:** `private final` поля, канонический конструктор, методы доступа по именам
компонентов, `equals()`, `hashCode()` и `toString()`.

### 12. Как называются методы доступа у record?

**Ответ:** по именам компонентов — `id()`, а не `getId()`. Соглашение JavaBeans не
применяется.

### 13. Может ли record иметь дополнительные поля?

**Ответ:** поля экземпляра — нет, состояние полностью описывается компонентами.
Статические поля и методы объявлять можно.

### 14. Что такое compact constructor?

**Ответ:** конструктор без списка параметров, предназначенный для валидации и
нормализации. Внутри работают с параметрами, присваивание полям добавляет
компилятор в конце.

### 15. Является ли record полностью неизменяемым?

**Ответ:** нет, неизменяемость поверхностная. Ссылки `final`, но объекты за ними
могут меняться. Изменяемые компоненты нужно копировать в компактном конструкторе.

### 16. Можно ли использовать record как JPA Entity?

**Ответ:** нет. Hibernate требует конструктор без аргументов и изменяемые поля,
создаёт прокси наследованием и полагается на dirty checking. Как проекция
результата запроса record подходит.

### 17. Что даёт sealed по сравнению с final?

**Ответ:** `final` запрещает наследование полностью, `sealed` разрешает его
ограниченному списку типов, перечисленному в `permits`.

### 18. Какие модификаторы обязан иметь наследник sealed-типа?

**Ответ:** один из трёх — `final`, `sealed` или `non-sealed`. Пропуск является
ошибкой компиляции.

### 19. Зачем нужен non-sealed?

**Ответ:** чтобы намеренно открыть отдельную ветвь иерархии для произвольного
наследования, оставив остальные закрытыми.

### 20. В чём главная практическая польза sealed?

**Ответ:** исчерпывающий `switch` без `default`. Добавление нового варианта делает
неполные `switch` ошибкой компиляции.
