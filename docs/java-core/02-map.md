# Map в Java

`Map<K, V>` хранит пары «ключ — значение», где ключи уникальны, а значения могут
повторяться.

```java
Map<Long, String> users = new HashMap<>();

users.put(1L, "Alice");
users.put(2L, "Bob");
```

```text
1 → Alice
2 → Bob
```

Тема тесно связана с контрактом `equals` и `hashCode`: без него `HashMap` просто
не находит записи. Сам контракт разбирается отдельно, здесь — устройство карты и
последствия его нарушения.

---

## Map и Collection

`Map` не наследует `Collection`.

```text
Iterable
└── Collection
    ├── List
    ├── Set
    └── Queue

Map
```

`Collection` представляет набор отдельных элементов, `Map` — соответствия. Методы
вроде `add(E)` для карты бессмысленны, поэтому у неё собственный набор операций:

```java
put(key, value);
get(key);
remove(key);
containsKey(key);
```

### Основные свойства

Ключи уникальны: повторный `put()` заменяет значение, а не добавляет запись.

```java
Map<String, Integer> ages = new HashMap<>();

ages.put("Dmitry", 22);
ages.put("Dmitry", 23);

ages.size();   // 1
```

```text
Dmitry → 23
```

Значения повторяться могут:

```java
cities.put(1L, "Moscow");
cities.put(2L, "Moscow");
```

## Основные методы

### put

```java
V put(K key, V value);
```

Добавляет пару или заменяет значение существующего ключа, возвращая предыдущее:

```java
Integer previous = scores.put("Alice", 15);   // 10
Integer absent = scores.put("Charlie", 5);    // null
```

### get и getOrDefault

```java
Integer score = scores.get("Alice");
scores.get("Unknown");   // null
```

Здесь возникает неоднозначность:

```java
map.put("existing", null);

map.get("existing");   // null
map.get("missing");    // null
```

По результату нельзя понять, отсутствует ключ или он связан с `null`. Различает
только `containsKey()`.

```java
int count = map.getOrDefault("java", 0);
```

Метод возвращает значение по умолчанию при отсутствии ключа. Но если ключ есть и
связан с `null`, вернётся именно `null`, а не значение по умолчанию.

Классическое применение — подсчёт частот:

```java
Map<Character, Integer> frequencies = new HashMap<>();

for (char character : text.toCharArray()) {
    frequencies.put(
            character,
            frequencies.getOrDefault(character, 0) + 1
    );
}
```

Для строки `banana` получится:

```text
b → 1
a → 3
n → 2
```

### putIfAbsent

```java
map.put("java", 5);
map.putIfAbsent("java", 10);
```

```text
java → 5
```

Старое значение не заменяется.

### containsKey и containsValue

```java
map.containsKey("java");     // O(1) в среднем
map.containsValue(10);       // O(n)
```

Поиск по значению требует просмотра всех записей: по значению нельзя вычислить
бакет, карта индексирована по ключам.

### remove и replace

```java
Integer removed = map.remove("java");
map.remove("java", 10);
```

Вторая форма удалит запись только при совпадении и ключа, и значения.

```java
map.replace("java", 20);
map.replace("java", 10, 20);
```

В отличие от `put()`, `replace()` новый ключ не создаёт: если ключа нет, ничего не
происходит. Трёхаргументная форма меняет значение только тогда, когда текущим
является указанное.

### Размер и очистка

```java
map.size();      // число пар, а не уникальных значений
map.isEmpty();
map.clear();
```

## Представления

Карта даёт три представления своего содержимого. Они связаны с исходной картой и
копиями не являются.

```java
Set<K> keySet();
Collection<V> values();
Set<Map.Entry<K, V>> entrySet();
```

`keySet()` возвращает `Set`, потому что ключи уникальны, а `values()` —
`Collection`, потому что значения могут повторяться.

Удаление через представление меняет саму карту:

```java
map.keySet().remove("java");
```

`entrySet()` — стандартный способ обхода, когда нужны и ключ, и значение:

```java
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    String key = entry.getKey();
    Integer value = entry.getValue();

    System.out.println(key + " = " + value);
}
```

Запись можно изменить прямо во время обхода:

```java
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    if (entry.getValue() < 0) {
        entry.setValue(0);
    }
}
```

Обход через `keySet()` с последующим `get()` хуже:

```java
for (String key : map.keySet()) {
    Integer value = map.get(key);
}
```

Для каждого ключа выполняется повторный поиск, а намерение выражено менее точно.

## Методы вычисления значений

```text
computeIfAbsent
computeIfPresent
compute
merge
replaceAll
```

### computeIfAbsent

Возвращает существующее значение или создаёт новое при отсутствии ключа.

```java
Map<String, List<String>> groups = new HashMap<>();

groups.computeIfAbsent("backend", ignored -> new ArrayList<>())
      .add("Java");
```

Заменяет связку «проверить, создать, положить»:

```java
if (!groups.containsKey("backend")) {
    groups.put("backend", new ArrayList<>());
}

groups.get("backend").add("Java");
```

Если функция вернёт `null`, запись не добавляется.

### computeIfPresent и compute

```java
map.computeIfPresent("java", (key, value) -> value + 1);
```

Срабатывает только для существующего ключа.

```java
map.compute("java", (key, value) -> value == null ? 1 : value + 1);
```

Вызывается всегда и получает `null`, если значения нет. В обоих случаях возврат
`null` из функции удаляет запись.

### merge

```java
frequencies.merge("java", 1, Integer::sum);
frequencies.merge("java", 1, Integer::sum);
```

```text
java → 2
```

Если ключа нет, записывается переданное значение; если есть — старое и новое
объединяются функцией. Для счётчиков это короче и надёжнее варианта с
`getOrDefault()`.

## Реализации

```text
HashMap
LinkedHashMap
TreeMap
```

| Характеристика | HashMap | LinkedHashMap | TreeMap |
|---|---|---|---|
| Внутренняя структура | хеш-таблица | хеш-таблица и связный список | красно-чёрное дерево |
| Порядок | не гарантирован | вставки или доступа | сортировка ключей |
| `get`, `put`, `remove` | `O(1)` в среднем | `O(1)` в среднем | `O(log n)` |
| `containsKey` | `O(1)` в среднем | `O(1)` в среднем | `O(log n)` |
| `containsValue` | `O(n)` | `O(n)` | `O(n)` |
| Обход | `O(n)` | `O(n)` | `O(n)` |
| `null`-ключ | один | один | обычно запрещён |
| `null`-значения | разрешены | разрешены | разрешены |
| Требования к ключам | `equals` и `hashCode` | `equals` и `hashCode` | `Comparable` или `Comparator` |
| Расход памяти | базовый | больше из-за ссылок | больше из-за узлов |

## HashMap

Основная реализация. Подходит, когда нужен быстрый поиск по ключу, порядок не
важен, а ключи имеют корректные `equals()` и `hashCode()`.

### Внутреннее устройство

Упрощённо карта содержит массив бакетов:

```text
index 0 → null
index 1 → Entry
index 2 → Entry → Entry
index 3 → null
index 4 → Entry
```

Каждая запись хранит примерно следующее:

```text
hash
key
value
next
```

Поле `next` связывает записи, попавшие в один бакет.

### Что происходит при put

```java
map.put("java", 10);
```

```text
hashCode
→ смешивание битов хеша
→ индекс бакета
→ поиск через hash и equals
→ добавление или замена
→ возможный resize
```

Индекс вычисляется битовой операцией:

```text
index = hash & (capacity - 1)
```

Вместимость всегда является степенью двойки, поэтому `capacity - 1` даёт маску из
единиц:

```text
capacity = 16
capacity - 1 = 15 = 00001111
```

Это заметно дешевле деления с остатком.

### hashCode и equals

```text
hashCode → определяет бакет
equals   → находит точный ключ внутри бакета
```

Ключи считаются совпавшими при подходящем хеше и `equals()`, вернувшем `true`.

> Если два объекта равны по `equals()`, их `hashCode()` обязан совпадать.

Обратное неверно: одинаковый хеш равенства не означает. Подробный разбор контракта
— в отдельном конспекте.

### Коллизии

Коллизия — попадание разных ключей в один бакет. Она неизбежна, поскольку хеш
отображает бесконечное множество значений в ограниченное число бакетов.

```text
key A → bucket 5
key B → bucket 5
```

В бакете образуется цепочка, и поиск идёт по ней через сравнение хешей и
`equals()`. Большое число коллизий ухудшает производительность.

При длинной цепочке список превращается в красно-чёрное дерево:

```text
связный список       → O(n)
красно-чёрное дерево → O(log n)
```

```text
TREEIFY_THRESHOLD = 8
MIN_TREEIFY_CAPACITY = 64
```

Если таблица ещё маленькая, вместо превращения в дерево сначала выполняется
расширение.

### Capacity, load factor и resize

```text
capacity    → количество бакетов, по умолчанию 16
load factor → коэффициент заполнения, по умолчанию 0.75
threshold   → capacity × loadFactor, порог в штуках
resize      → процесс расширения
```

Для вместимости 16 порог равен 12. После его превышения таблица увеличивается
вдвое, и все записи распределяются заново — индекс зависит от размера таблицы.

```text
16 → 32 → 64 → 128
```

Операция дорогая, но выполняется не при каждом `put()`, поэтому средняя стоимость
добавления остаётся амортизированной `O(1)`. Если количество записей известно
заранее, ёмкость задают сразу:

```java
Map<Long, User> users = new HashMap<>(100);
```

Внутренний массив у пустой карты может быть выделен только при первом добавлении.

### Почему O(1) только в среднем

При хорошем распределении ключей бакеты короткие и доступ константный. В плохом
случае большинство ключей попадает в один бакет, и сложность вырождается до
`O(log n)` благодаря деревьям — а без них была бы `O(n)`.

Поэтому корректная формулировка: `HashMap` выполняет поиск, добавление и удаление
за `O(1)` **в среднем**.

### null

Допускается один `null`-ключ и сколько угодно `null`-значений.

```java
map.put(null, "value");
map.put("first", null);
map.put("second", null);
```

Ключ один, потому что ключи уникальны, а все попытки положить `null` используют
один и тот же ключ. Для него применяется отдельная обработка: запись обычно
попадает в нулевой бакет без вычисления хеша.

### Изменяемые ключи

Ключи желательно делать неизменяемыми. Пусть `equals()` и `hashCode()` зависят от
email:

```java
UserKey key = new UserKey("old@example.com");

map.put(key, "value");

key.changeEmail("new@example.com");
```

Запись физически осталась в бакете, вычисленном по старому хешу, а поиск идёт по
новому:

```java
map.get(key);      // может вернуть null
map.remove(key);   // может вернуть null
```

> Поля, участвующие в `equals()` и `hashCode()`, не должны изменяться, пока объект
> используется как ключ хешированной коллекции.

Подходящие ключи:

```text
String
Integer
Long
UUID
record
неизменяемый value object
```

## LinkedHashMap

Построен на `HashMap`, но дополнительно поддерживает двусвязный список записей и
потому гарантирует порядок обхода.

```java
Map<String, Integer> map = new LinkedHashMap<>();

map.put("B", 2);
map.put("A", 1);
map.put("C", 3);
```

```text
B
A
C
```

По умолчанию сохраняется порядок вставки. Операции остаются `O(1)` в среднем,
плата — дополнительная память на ссылки.

### Порядок доступа и LRU

```java
Map<String, Integer> map = new LinkedHashMap<>(16, 0.75f, true);
```

Третий параметр — `accessOrder`. При нём обращение к записи перемещает её в конец:

```java
map.put("A", 1);
map.put("B", 2);
map.put("C", 3);

map.get("A");
```

```text
B
C
A
```

На этом строится LRU-кеш — вытеснение элемента, к которому дольше всего не
обращались:

```java
public class LruCache<K, V> extends LinkedHashMap<K, V> {

    private final int capacity;

    public LruCache(int capacity) {
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

## TreeMap

Хранит ключи отсортированными в красно-чёрном дереве, все основные операции — за
`O(log n)`.

```java
Map<Integer, String> map = new TreeMap<>();

map.put(3, "C");
map.put(1, "A");
map.put(2, "B");
```

```text
1
2
3
```

### Сравнение ключей

Используется естественный порядок либо переданный компаратор:

```java
Map<Integer, String> natural = new TreeMap<>();

Map<String, Integer> reversed = new TreeMap<>(Comparator.reverseOrder());
```

Равенство ключей определяется результатом сравнения:

```java
compare(first, second) == 0
```

Это верно даже тогда, когда `first.equals(second)` возвращает `false`. Хеш-код не
используется вовсе. Отсюда следствие: несогласованный компаратор приводит к
неожиданной замене записей.

### null

При естественном порядке `null`-ключ даёт `NullPointerException`: его не с чем
сравнить. `null`-значения допускаются. Пользовательский компаратор технически
может поддерживать `null`, но в стандартном ответе считается, что `TreeMap`
`null`-ключи не допускает.

### NavigableMap

```java
TreeMap<Integer, String> map = new TreeMap<>();

map.put(10, "A");
map.put(20, "B");
map.put(30, "C");
```

```java
map.lowerKey(20);     // 10
map.floorKey(20);     // 20
map.ceilingKey(25);   // 30
map.higherKey(20);    // 30
```

```text
lower   → строго меньше
floor   → меньше или равно
ceiling → больше или равно
higher  → строго больше
```

Также доступны диапазоны:

```java
map.headMap(20);
map.tailMap(20);
map.subMap(10, 30);
```

## Неизменяемые карты

```java
Map<String, Integer> priorities = Map.of(
        "LOW", 1,
        "HIGH", 2
);

priorities.put("CRITICAL", 3);   // UnsupportedOperationException
```

`Map.of()` не допускает `null`-ключи, `null`-значения и повторяющиеся ключи. Для
большего числа записей существует `Map.ofEntries()`:

```java
Map<String, Integer> map = Map.ofEntries(
        Map.entry("A", 1),
        Map.entry("B", 2),
        Map.entry("C", 3)
);
```

Важно различать представление и копию:

```java
Map<String, Integer> view = Collections.unmodifiableMap(source);
Map<String, Integer> copy = Map.copyOf(source);
```

Через представление менять нельзя, но изменения исходной карты в нём видны. Копия
независима: последующие изменения оригинала на неё не влияют. `Map.copyOf()` тоже
запрещает `null`.

```text
Collections.unmodifiableMap → представление
Map.copyOf                  → неизменяемая копия
```

## ConcurrentHashMap

Обычный `HashMap` потокобезопасным не является. При конкурентном доступе
используют `ConcurrentHashMap`:

```text
поддерживает конкурентный доступ
не блокирует всю карту одной общей блокировкой
не допускает null-ключи и null-значения
предоставляет атомарные putIfAbsent(), compute(), merge()
```

Запрет `null` связан с однозначностью: в конкурентной карте результат
`map.get(key) == null` должен означать именно отсутствие значения, а проверить
через `containsKey()` в конкурентной среде ненадёжно.

Подробно разбирается в теме многопоточности.

## Типичные ошибки

### Использовать изменяемый ключ

Если поле, участвующее в `hashCode()`, меняется после вставки, запись остаётся в
старом бакете и перестаёт находиться.

### Рассчитывать на порядок HashMap

Порядок не входит в контракт и может измениться между запусками и версиями. Для
порядка вставки есть `LinkedHashMap`.

### Использовать containsValue для частого поиска

Операция линейная. Если нужен быстрый поиск и по ключам, и по значениям, нужна
дополнительная структура.

### Обходить карту через keySet с последующим get

Для каждого ключа выполняется повторный поиск. Нужен `entrySet()`.

### Нарушать контракт equals и hashCode

Равные по `equals()` ключи с разными хешами попадут в разные бакеты, и запись не
найдётся.

### Писать несогласованный Comparator для TreeMap

Нулевой результат сравнения означает для карты одинаковые ключи, поэтому запись
может неожиданно замениться.

### Различать отсутствие ключа и null-значение по результату get

`null` возвращается в обоих случаях. Нужен `containsKey()`.

### Брать TreeMap ради разовой сортировки

Каждая операция стоит `O(log n)`. Если порядок нужен только при выводе, дешевле
держать данные в `HashMap` и отсортировать список записей один раз.

### Класть null в ConcurrentHashMap

Запрещено и для ключей, и для значений — в отличие от `HashMap`.

## Краткая памятка

```text
Map не наследует Collection: хранит соответствия, а не элементы
ключи уникальны, значения повторяются
keySet   → Set ключей
values   → Collection значений
entrySet → Set пар, стандартный способ обхода
представления связаны с картой, удаление через них меняет карту
```

```text
put → возвращает предыдущее значение
get → null и при отсутствии ключа, и при null-значении
      различает только containsKey
getOrDefault → значение по умолчанию только при отсутствии ключа
replace → не создаёт новый ключ
containsKey O(1), containsValue O(n)
```

```text
computeIfAbsent → создать при отсутствии
computeIfPresent → пересчитать при наличии
compute → всегда, value может быть null
merge → счётчики: merge(key, 1, Integer::sum)
возврат null из функции удаляет запись
```

```text
HashMap       → хеш-таблица, O(1) в среднем, порядок не гарантирован
LinkedHashMap → плюс порядок вставки или доступа
TreeMap       → красно-чёрное дерево, O(log n), сортировка и диапазоны
```

```text
hashCode → бакет
equals   → точный ключ внутри бакета
index = hash & (capacity - 1), capacity — степень двойки

capacity    → число бакетов, по умолчанию 16
load factor → 0.75
threshold   → capacity × loadFactor
resize      → удвоение и перераспределение
```

## Краткий ответ для собеседования

`Map` хранит соответствия ключей значениям и в иерархию `Collection` не входит,
потому что оперирует парами, а не элементами. Доступ к содержимому как к коллекции
дают три представления: `keySet()`, `values()` и `entrySet()`. Они связаны с
картой, а не копируют её, поэтому удаление через представление меняет саму карту.
Обходить карту следует через `entrySet()`: вариант с `keySet()` и `get()` выполняет
повторный поиск на каждой итерации.

Основная реализация — `HashMap`. Внутри массив бакетов; при вставке вычисляется
хеш ключа, из него — индекс бакета битовой операцией по маске, что возможно
благодаря тому, что ёмкость всегда является степенью двойки. Внутри бакета точный
ключ находится через `equals()`. Отсюда роль контракта: `hashCode()` определяет,
где искать, `equals()` — что именно найдено.

Коллизии неизбежны, и при длинной цепочке в одном бакете список превращается в
красно-чёрное дерево, что даёт логарифмический поиск вместо линейного. Когда число
записей превышает произведение ёмкости на коэффициент заполнения, таблица
удваивается и все записи распределяются заново — операция дорогая, но редкая,
поэтому средняя стоимость вставки остаётся константной. Именно поэтому про
`HashMap` говорят «`O(1)` в среднем», а не просто `O(1)`.

Ключ обязан быть фактически неизменяемым: изменение поля, участвующего в хеше,
после вставки делает запись недостижимой — она останется в старом бакете, а искать
её карта будет в новом.

`LinkedHashMap` добавляет двусвязный список и потому гарантирует порядок обхода —
вставки либо последнего доступа. Второй режим вместе с переопределённым
`removeEldestEntry()` даёт готовый LRU-кеш. `TreeMap` держит ключи
отсортированными в красно-чёрном дереве, работает за `O(log n)` и определяет
равенство ключей результатом сравнения, а не `equals()`, — зато умеет диапазонные
и навигационные запросы.

Из мелочей, на которых ловят: `get()` возвращает `null` и когда ключа нет, и когда
он связан с `null`, различает только `containsKey()`. `HashMap` допускает один
`null`-ключ, `TreeMap` при естественном порядке — нет, `ConcurrentHashMap`
запрещает `null` и в ключах, и в значениях.

## Вопросы на собеседовании

### 1. Почему Map не наследует Collection?

**Ответ:** `Collection` описывает набор отдельных элементов, а `Map` хранит пары
«ключ — значение». Методы вроде `add(E)` для неё бессмысленны. Доступ к содержимому
как к коллекции дают `keySet()`, `values()` и `entrySet()`.

### 2. Чем ключ отличается от значения?

**Ответ:** ключ уникален, участвует в вычислении бакета и требует корректных
`equals` и `hashCode`. Значения могут повторяться, и требований к ним нет.

### 3. Что возвращает put()?

**Ответ:** предыдущее значение по этому ключу либо `null`, если ключа не было.
`null` может означать и отсутствие ключа, и хранившееся `null`-значение —
различить помогает `containsKey()`.

### 4. Чем get() отличается от getOrDefault()?

**Ответ:** `get()` возвращает `null` при отсутствии ключа, `getOrDefault()` —
указанное значение по умолчанию.

### 5. Что вернёт getOrDefault, если ключ есть и связан с null?

**Ответ:** `null`, а не значение по умолчанию. Метод смотрит на наличие значения,
а не на его содержимое.

### 6. Чем replace() отличается от put()?

**Ответ:** `replace()` меняет значение только существующего ключа и нового не
создаёт. Трёхаргументная форма дополнительно проверяет текущее значение.

### 7. Почему containsValue() работает за O(n)?

**Ответ:** по значению нельзя вычислить бакет — карта индексирована по ключам,
поэтому приходится просматривать все записи.

### 8. Какие типы возвращают keySet(), values() и entrySet()?

**Ответ:** `Set` ключей, `Collection` значений и `Set` пар `Map.Entry`. Это
представления, а не копии: изменения карты в них видны, а удаление через них
изменяет саму карту.

### 9. Почему обходить карту лучше через entrySet()?

**Ответ:** он сразу отдаёт пару, тогда как обход по `keySet()` требует повторного
поиска значения для каждого ключа.

### 10. Для чего используется computeIfAbsent()?

**Ответ:** чтобы получить значение по ключу, создав его при отсутствии. Заменяет
связку «проверить, создать, положить». Типичный случай — карта списков.

### 11. Чем compute() отличается от computeIfPresent()?

**Ответ:** `compute()` вызывается независимо от наличия ключа и получает `null`
при его отсутствии. `computeIfPresent()` срабатывает только для существующего
ключа. Возврат `null` из функции в обоих случаях удаляет запись.

### 12. Для чего используется merge()?

**Ответ:** для объединения нового значения с существующим. Если ключа нет,
записывается переданное значение, иначе вызывается функция слияния. Удобно для
счётчиков: `merge(key, 1, Integer::sum)`.

### 13. Что происходит внутри HashMap при put()?

**Ответ:** вычисляется хеш ключа и по нему индекс бакета. Если бакет пуст,
создаётся запись. Если занят, элементы сравниваются через `equals`: при совпадении
значение заменяется, иначе запись добавляется в цепочку. После этого проверяется
необходимость расширения.

### 14. Какую роль выполняет hashCode()?

**Ответ:** определяет бакет. От него зависит скорость: плохой хеш собирает все
ключи в одном бакете и превращает поиск в перебор.

### 15. Какую роль выполняет equals()?

**Ответ:** находит точный ключ внутри бакета. Совпадение хешей равенства ключей не
означает.

### 16. Почему индекс бакета вычисляется битовой операцией?

**Ответ:** ёмкость всегда является степенью двойки, поэтому `capacity - 1` даёт
маску из единиц, и `hash & (capacity - 1)` заменяет деление с остатком.

### 17. Что такое коллизия?

**Ответ:** попадание разных ключей в один бакет. Неизбежна, поскольку хеш
отображает бесконечное множество значений в ограниченное число бакетов.

### 18. Как HashMap обрабатывает длинные цепочки коллизий?

**Ответ:** при достижении восьми элементов в бакете и достаточном размере таблицы
цепочка превращается в сбалансированное дерево, и поиск внутри бакета становится
логарифмическим. При уменьшении числа элементов дерево разворачивается обратно.

### 19. Что такое capacity?

**Ответ:** текущее число бакетов во внутреннем массиве. Всегда степень двойки.

### 20. Что такое load factor?

**Ответ:** коэффициент заполнения, по умолчанию 0,75. Определяет, при какой доле
занятости таблица расширяется. Компромисс между расходом памяти и вероятностью
коллизий.

### 21. Что такое threshold?

**Ответ:** произведение ёмкости на коэффициент заполнения — число записей, после
которого запускается расширение.

### 22. Что происходит при resize?

**Ответ:** создаётся массив вдвое большего размера, и все записи распределяются
заново, поскольку индекс зависит от размера таблицы. Операция дорогая, поэтому при
известном количестве элементов начальную ёмкость задают заранее.

### 23. Почему операции HashMap работают за O(1) только в среднем?

**Ответ:** при равномерном распределении хешей бакеты короткие, и доступ
константный. При плохом хеше все ключи попадают в один бакет, и сложность
вырождается — до `O(log n)` благодаря деревьям, а без них была бы `O(n)`.

### 24. Почему ключи желательно делать неизменяемыми?

**Ответ:** изменение поля, участвующего в `hashCode()`, меняет бакет, в котором
карта будет искать ключ. Запись остаётся в старом бакете и становится
недостижимой — её не найти ни через `get()`, ни через `containsKey()`.

### 25. Какие null допускает HashMap?

**Ответ:** один `null`-ключ и произвольное количество `null`-значений.
`null`-ключ помещается в нулевой бакет без вычисления хеша.

### 26. Чем LinkedHashMap отличается от HashMap?

**Ответ:** поддерживает двусвязный список записей и потому гарантирует порядок
обхода — вставки либо доступа. Расплата — дополнительная память на ссылки.

### 27. Для чего используется accessOrder = true?

**Ответ:** чтобы записи хранились в порядке последнего обращения. При каждом
`get()` запись перемещается в конец, что даёт основу для LRU-кеша.

### 28. Что такое LRU?

**Ответ:** стратегия вытеснения, при которой удаляется дольше всех не
использовавшийся элемент. Реализуется на `LinkedHashMap` с `accessOrder = true` и
переопределённым `removeEldestEntry()`.

### 29. Чем TreeMap отличается от HashMap?

**Ответ:** хранит ключи отсортированными в красно-чёрном дереве, все операции
работают за `O(log n)`. Хеш-код не используется, зато доступны диапазонные и
навигационные запросы.

### 30. Как TreeMap сравнивает ключи?

**Ответ:** через `compareTo()` ключа либо через переданный `Comparator`. Ключи
считаются одинаковыми при нулевом результате сравнения — `equals` не вызывается
вовсе. Несогласованность `compareTo` и `equals` приводит к неожиданному поведению.

### 31. Какие навигационные методы предоставляет TreeMap?

**Ответ:** `firstKey`, `lastKey`, `floorKey`, `ceilingKey`, `higherKey`,
`lowerKey`, а также диапазонные представления `headMap`, `tailMap` и `subMap`.

### 32. Чем Collections.unmodifiableMap() отличается от Map.copyOf()?

**Ответ:** первый возвращает неизменяемое представление исходной карты — изменения
оригинала в нём видны. `Map.copyOf()` создаёт независимую неизменяемую копию.

### 33. Почему ConcurrentHashMap запрещает null?

**Ответ:** чтобы результат `get()`, равный `null`, однозначно означал отсутствие
значения. Проверить наличие через `containsKey()` в конкурентной среде ненадёжно:
между двумя вызовами состояние может измениться.

### 34. Когда выбирать HashMap, LinkedHashMap и TreeMap?

**Ответ:** `HashMap` по умолчанию, когда порядок не важен. `LinkedHashMap` — когда
нужен предсказуемый порядок обхода или LRU-кеш. `TreeMap` — когда ключи должны
храниться отсортированными или нужны диапазонные и навигационные операции.
