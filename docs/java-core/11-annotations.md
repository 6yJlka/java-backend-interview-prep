# Annotations

## Что такое аннотация

Аннотация — это метаданные, прикреплённые к элементу кода. Сама по себе она ничего
не делает.

```java
@Override
public String toString() {
    return "User";
}
```

Это важнейшая мысль всей темы, и её стоит проговорить первой. Аннотация не
исполняется, не перехватывает вызовы и не меняет поведение метода. Она лишь
помечает элемент, а всю работу выполняет кто-то другой: компилятор, обработчик
аннотаций на этапе сборки или фреймворк во время выполнения.

```text
аннотация      → пассивная пометка
кто-то читает  → компилятор, annotation processor, фреймворк
поведение      → создаётся читающей стороной
```

Без понимания этой связки невозможно объяснить, почему `@Transactional` перестаёт
работать при вызове метода изнутри того же класса, — а этот вопрос задают почти
всегда.

Технически аннотация является особой формой интерфейса, неявно наследующей
`java.lang.annotation.Annotation`.

---

## Встроенные аннотации

### @Override

Сообщает компилятору, что метод переопределяет метод суперкласса или реализует
метод интерфейса. Если это не так, будет ошибка компиляции.

```java
class User {

    @Override
    public boolean equals(Object other) {
        return super.equals(other);
    }
}
```

Аннотация не обязательна, но защищает от опечаток в сигнатуре. Классический случай:

```java
class User {

    public boolean equals(User other) { // перегрузка, а не переопределение
        return false;
    }
}
```

Без `@Override` такой код компилируется и молча ломает работу `HashSet` и `HashMap`.
С `@Override` компилятор укажет на ошибку.

### @Deprecated

Помечает элемент как устаревший. Использование вызывает предупреждение компилятора.

```java
@Deprecated(since = "2.1", forRemoval = true)
public void oldMethod() {
}
```

Параметр `forRemoval` сообщает, что элемент планируется удалить, и усиливает
предупреждение.

Отдельно существует тег `@deprecated` в Javadoc — он описывает причину и
альтернативу. Аннотация нужна компилятору, тег — человеку, и обычно пишут оба.

### @SuppressWarnings

Подавляет предупреждения компилятора.

```java
@SuppressWarnings("unchecked")
List<User> users = (List<User>) rawList;
```

Распространённые значения: `unchecked`, `rawtypes`, `deprecation`, `serial`,
`unused`.

Аннотацию следует размещать на минимально возможной области — на локальной
переменной, а не на классе целиком, иначе она скроет и те предупреждения, которые
появятся позже.

### @FunctionalInterface

Проверяет, что интерфейс содержит ровно один абстрактный метод. Подробно разобрана
в конспекте по лямбдам.

### @SafeVarargs

Подавляет предупреждение о heap pollution для методов с параметризованным varargs.

```java
@SafeVarargs
static <T> List<T> listOf(T... elements) {
    return List.of(elements);
}
```

Применима к `static`, `final` и `private`-методам, а также к конструкторам.
Ответственность за корректность лежит на авторе: аннотация подавляет
предупреждение, а не проверяет безопасность.

## Собственные аннотации

Объявление использует ключевое слово `@interface`:

```java
public @interface Audited {
}
```

### Элементы

Аннотация может нести параметры. Они объявляются как методы без тела:

```java
public @interface Audited {

    String value();

    String category() default "general";

    int priority() default 0;
}
```

Использование:

```java
@Audited(value = "user-creation", priority = 5)
public void createUser(String email) {
}
```

Элемент с именем `value` можно указывать без имени, если он единственный
задаваемый:

```java
@Audited("user-creation")
```

Элементы без `default` обязательны при использовании.

### Допустимые типы элементов

Список ограничен:

```text
примитивы
String
Class и Class<?>
enum
другая аннотация
массив любого из перечисленного
```

Произвольный объект в качестве значения использовать нельзя. Причина в том, что
значения аннотаций должны быть константами времени компиляции и попадать в
constant pool класса. `null` в качестве значения по умолчанию тоже недопустим —
для «отсутствия» используют пустую строку или специальную константу enum.

## Мета-аннотации

Это аннотации, применяемые к другим аннотациям. Их четыре основные.

### @Target

Задаёт, к каким элементам кода аннотация применима.

```java
@Target({ElementType.METHOD, ElementType.TYPE})
public @interface Audited {
}
```

Основные значения `ElementType`:

```text
TYPE             → класс, интерфейс, enum, record, аннотация
FIELD            → поле
METHOD           → метод
PARAMETER        → параметр метода
CONSTRUCTOR      → конструктор
LOCAL_VARIABLE   → локальная переменная
ANNOTATION_TYPE  → другая аннотация
PACKAGE          → пакет
TYPE_PARAMETER   → параметр обобщённого типа, с Java 8
TYPE_USE         → любое использование типа, с Java 8
MODULE           → модуль, с Java 9
```

Без `@Target` аннотация применима почти везде. Явное ограничение полезно: попытка
поставить её не туда станет ошибкой компиляции.

`TYPE_USE` стоит особняком — он позволяет аннотировать типы в любых позициях,
включая приведение и generics, и на нём построены библиотеки статического анализа:

```java
List<@NonNull String> names;
```

### @Retention

Определяет, до какого этапа аннотация доживает. Самая важная мета-аннотация с
практической точки зрения.

```java
@Retention(RetentionPolicy.RUNTIME)
public @interface Audited {
}
```

Три политики:

```text
SOURCE
→ существует только в исходном коде
→ отбрасывается компилятором
→ в .class не попадает
→ пример: @Override, @SuppressWarnings

CLASS
→ попадает в .class
→ недоступна через рефлексию во время выполнения
→ политика по умолчанию
→ пример: аннотации для инструментов анализа байт-кода

RUNTIME
→ попадает в .class
→ доступна через рефлексию
→ пример: @Component, @Transactional, @Entity, @Test
```

Значение по умолчанию — `CLASS`, и это регулярный источник ошибок. Собственная
аннотация без явного `@Retention(RUNTIME)` просто не будет видна фреймворку, при
этом код скомпилируется и никакой ошибки не возникнет — обработчик её молча не
найдёт.

```text
фреймворк читает аннотацию во время выполнения
→ обязательно RUNTIME
```

### @Documented

Включает аннотацию в сгенерированный Javadoc. По умолчанию аннотации в документацию
не попадают.

### @Inherited

Позволяет наследовать аннотацию от суперкласса.

```java
@Inherited
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Audited {
}
```

```java
@Audited
class BaseService {
}

class UserService extends BaseService {
}
```

С `@Inherited` запрос аннотации у `UserService` вернёт её, унаследованную от
`BaseService`. Без неё — нет.

Ограничения существенные:

- работает только для аннотаций на классах, но не на методах и полях;
- не распространяется на реализованные интерфейсы — только на суперкласс.

Именно поэтому Spring не полагается на `@Inherited`, а использует собственный поиск
через `AnnotatedElementUtils`, который умеет обходить и интерфейсы, и мета-аннотации.

### @Repeatable

С Java 8 одну аннотацию можно применить несколько раз:

```java
@Repeatable(Schedules.class)
public @interface Schedule {
    String cron();
}

public @interface Schedules {
    Schedule[] value();
}
```

```java
@Schedule(cron = "0 0 * * *")
@Schedule(cron = "0 12 * * *")
public void report() {
}
```

Компилятор оборачивает повторения в контейнер, поэтому при чтении через рефлексию
нужен `getAnnotationsByType()`, а не `getAnnotation()`.

## Чтение аннотаций через рефлексию

Аннотация с политикой `RUNTIME` читается так:

```java
Class<?> type = UserService.class;

if (type.isAnnotationPresent(Audited.class)) {
    Audited audited = type.getAnnotation(Audited.class);
    String category = audited.category();
}
```

Для методов:

```java
for (Method method : type.getDeclaredMethods()) {
    Audited audited = method.getAnnotation(Audited.class);

    if (audited != null) {
        register(method, audited.value());
    }
}
```

Основные методы:

```text
isAnnotationPresent(Class)   → есть ли аннотация
getAnnotation(Class)         → аннотация или null
getAnnotations()             → все, включая унаследованные
getDeclaredAnnotations()     → только объявленные на самом элементе
getAnnotationsByType(Class)  → для @Repeatable
```

Эти методы есть у `Class`, `Method`, `Field`, `Constructor` и `Parameter` — все они
реализуют `AnnotatedElement`.

Минимальный пример собственного обработчика:

```java
public void process(Object target) {
    Class<?> type = target.getClass();

    for (Method method : type.getDeclaredMethods()) {
        if (method.isAnnotationPresent(Audited.class)) {
            Audited audited = method.getAnnotation(Audited.class);
            auditLog.register(type.getSimpleName(), method.getName(), audited.value());
        }
    }
}
```

Это и есть весь принцип работы аннотаций во фреймворках, только в реальных
библиотеках сканирование, кэширование и создание прокси устроены сложнее.

## Как это работает в Spring

Понимание предыдущего раздела позволяет объяснить вещи, которые иначе выглядят
магией.

### Аннотация ничего не делает сама

```java
@Service
public class UserService {
}
```

`@Service` не создаёт бин. Она лишь помечает класс, а во время старта приложения
компонентное сканирование обходит классы, находит эту пометку через рефлексию и
регистрирует определение бина. Убрать сканирование — и аннотация станет
бесполезным комментарием.

### Мета-аннотации и композиция

Spring активно использует аннотации, помеченные другими аннотациями:

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component
public @interface Service {
}
```

`@Service` сама помечена `@Component`, поэтому всё, что реагирует на `@Component`,
реагирует и на `@Service`. Так же устроены `@Repository`, `@Controller` и
`@RestController`, а `@SpringBootApplication` объединяет `@Configuration`,
`@ComponentScan` и `@EnableAutoConfiguration`.

Обычная рефлексия такую вложенность не раскрывает — это делает поиск Spring.

### Почему @Transactional не работает при self-invocation

`@Transactional` обрабатывается через прокси: Spring оборачивает бин объектом,
который перед вызовом метода открывает транзакцию, а после — фиксирует или
откатывает её.

```java
@Service
public class OrderService {

    public void process(Order order) {
        save(order); // вызов через this, прокси не участвует
    }

    @Transactional
    public void save(Order order) {
    }
}
```

Внешний вызов `orderService.process()` идёт через прокси, но внутренний вызов
`save()` выполняется напрямую через `this`. Прокси в этой цепочке отсутствует,
аннотацию читать некому, транзакция не начинается.

```text
внешний вызов  → прокси → перехватчик → целевой метод
self-invocation → this → целевой метод
```

Ошибки при этом не будет — код просто выполнится вне транзакции. Это прямое
следствие того, что аннотация пассивна: работает не она, а инфраструктура вокруг
вызова.

По той же причине `@Transactional` на `private`-методе не даёт эффекта: прокси не
может его перехватить.

## Обработка на этапе компиляции

Помимо рефлексии существует второй механизм — annotation processing. Обработчик
подключается к компилятору и может генерировать новый исходный код.

Так работают Lombok, MapStruct и генераторы метамодели JPA. Аннотациям для этого
достаточно политики `SOURCE`: до времени выполнения они доживать не обязаны.

```text
runtime-обработка (рефлексия)
→ RUNTIME
→ поведение определяется при старте или при вызове
→ Spring, JPA, JUnit

compile-time обработка (annotation processor)
→ SOURCE достаточно
→ генерируется код, который затем компилируется обычным образом
→ Lombok, MapStruct
```

Практическое различие: сгенерированный код видно в собранных классах и он не стоит
ничего во время выполнения, тогда как рефлексия работает при каждом запуске.

## Типичные ошибки

### Забыть @Retention(RUNTIME)

Политика по умолчанию — `CLASS`. Собственная аннотация без явного указания не будет
видна через рефлексию, и фреймворк её не найдёт. Ошибки компиляции при этом нет.

### Считать, что аннотация выполняет действие

Аннотация пассивна. Всё поведение создаёт читающая сторона.

### Ожидать, что @Inherited работает всегда

Только для аннотаций на классах и только по линии суперкласса. На методы, поля и
интерфейсы не распространяется.

### Ставить @SuppressWarnings на класс целиком

Скрывает и те предупреждения, которые появятся позже. Область должна быть
минимальной.

### Использовать null как значение по умолчанию

Недопустимо. Применяют пустую строку или константу enum.

### Пытаться передать произвольный объект в элемент аннотации

Допустимы только примитивы, `String`, `Class`, enum, аннотации и их массивы.

### Ожидать работы @Transactional при self-invocation

Прокси не участвует во внутреннем вызове через `this`.

### Читать @Repeatable через getAnnotation

Повторяющиеся аннотации оборачиваются в контейнер, нужен
`getAnnotationsByType()`.

### Забывать про стоимость рефлексии

Сканирование аннотаций на горячем пути дорого. Результат кэшируют — так поступают
и фреймворки.

## Краткий ответ для собеседования

Аннотация — это метаданные, прикреплённые к элементу кода, и сама по себе она
ничего не делает. Поведение создаёт тот, кто её читает: компилятор, обработчик
аннотаций на этапе сборки или фреймворк во время выполнения через рефлексию.

Собственная аннотация объявляется через `@interface`, её элементы описываются как
методы без тела и могут иметь значения по умолчанию. Допустимы только примитивы,
`String`, `Class`, enum, другие аннотации и массивы из них, поскольку значения
должны быть константами времени компиляции.

Поведение аннотации настраивают мета-аннотации. `@Target` задаёт допустимые места
применения, `@Retention` — до какого этапа аннотация доживает, `@Documented`
включает её в Javadoc, `@Inherited` разрешает наследование от суперкласса,
`@Repeatable` — повторное применение.

Практически важнее всего `@Retention`. По умолчанию действует `CLASS`, то есть
аннотация попадает в байт-код, но недоступна рефлексии. Чтобы фреймворк смог её
прочитать, нужен `RUNTIME`.

На этом механизме построен Spring: `@Service` не создаёт бин сама, её находит
компонентное сканирование. `@Transactional` обрабатывается прокси, который
оборачивает бин, — поэтому при вызове метода изнутри того же класса через `this`
прокси не участвует и транзакция не открывается.

## Вопросы на собеседовании

### 1. Что такое аннотация и что она делает?

**Ответ:** метаданные, прикреплённые к элементу кода. Сама по себе она ничего не
делает — поведение создаёт читающая сторона: компилятор, annotation processor или
фреймворк через рефлексию.

### 2. Как объявить собственную аннотацию?

**Ответ:** через `@interface`. Элементы описываются как методы без тела и могут
иметь `default`-значения.

### 3. Какие типы допустимы для элементов аннотации?

**Ответ:** примитивы, `String`, `Class`, enum, другие аннотации и массивы из них.
Значения должны быть константами времени компиляции.

### 4. Можно ли задать null значением по умолчанию?

**Ответ:** нет. Используют пустую строку или специальную константу enum.

### 5. Какие существуют политики удержания?

**Ответ:** `SOURCE` — отбрасывается компилятором, `CLASS` — попадает в байт-код, но
недоступна рефлексии, `RUNTIME` — доступна рефлексии.

### 6. Какая политика действует по умолчанию?

**Ответ:** `CLASS`. Это частая причина, по которой собственная аннотация не видна
фреймворку, — при этом код компилируется без ошибок.

### 7. Что делает @Target?

**Ответ:** ограничивает элементы кода, к которым аннотация применима. Нарушение
даёт ошибку компиляции.

### 8. Как работает @Inherited и каковы ограничения?

**Ответ:** позволяет наследовать аннотацию от суперкласса. Работает только для
аннотаций на классах и не распространяется на методы, поля и интерфейсы.

### 9. Как прочитать аннотацию во время выполнения?

**Ответ:** через рефлексию — `isAnnotationPresent()`, `getAnnotation()`,
`getDeclaredAnnotations()`. Для повторяющихся аннотаций нужен
`getAnnotationsByType()`.

### 10. Что даёт @Override, если она необязательна?

**Ответ:** проверку компилятором. Опечатка в сигнатуре превращает переопределение в
перегрузку, и без аннотации это компилируется молча.

### 11. Как @Service создаёт бин?

**Ответ:** сама она бин не создаёт. Компонентное сканирование при старте находит
помеченные классы через рефлексию и регистрирует определения бинов.

### 12. Что такое мета-аннотация в Spring?

**Ответ:** аннотация, помеченная другой аннотацией. `@Service` помечена
`@Component`, поэтому обрабатывается всем, что реагирует на `@Component`. Обычная
рефлексия такую вложенность не раскрывает, это делает поиск Spring.

### 13. Почему @Transactional не работает при вызове метода изнутри класса?

**Ответ:** аннотацию обрабатывает прокси, оборачивающий бин. Внутренний вызов идёт
через `this`, минуя прокси, поэтому перехватчик не срабатывает и транзакция не
открывается. Ошибки при этом не возникает.

### 14. Чем annotation processing отличается от рефлексии?

**Ответ:** обработчик подключается к компилятору и генерирует код на этапе сборки,
поэтому ему достаточно политики `SOURCE`. Рефлексия читает аннотации во время
выполнения и требует `RUNTIME`.

### 15. Есть ли у аннотаций стоимость во время выполнения?

**Ответ:** у самих аннотаций нет, но чтение через рефлексию стоит дорого, поэтому
результаты сканирования кэшируют.
