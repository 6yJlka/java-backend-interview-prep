# equals и hashCode в Java

Методы `equals()` и `hashCode()` определены в `Object`, поэтому есть у каждого
объекта.

```java
public class Object {

    public boolean equals(Object object) {
        return this == object;
    }

    public native int hashCode();
}
```

По умолчанию равенство — это тождество ссылок. От их корректной реализации зависит
работа всех хешированных коллекций, поэтому тема разбирается сразу после карт и
множеств.

---

## Оператор == и метод equals

Для ссылочных типов `==` проверяет, указывают ли переменные на один объект.

```java
String first = new String("Java");
String second = new String("Java");

first == second;        // false
first.equals(second);   // true
```

Ссылки разные, но `String` переопределяет `equals()` и сравнивает содержимое.

```text
==       → сравнение ссылок
equals() → логическое равенство объектов
```

Для примитивов `==` сравнивает значения.

---

## Зачем переопределять equals

```java
public final class UserKey {

    private final Long id;

    public UserKey(Long id) {
        this.id = id;
    }
}
```

```java
UserKey first = new UserKey(10L);
UserKey second = new UserKey(10L);

first.equals(second);   // false
```

Логически это один и тот же идентификатор, но стандартный метод сравнивает
ссылки. Нужна собственная реализация:

```java
@Override
public boolean equals(Object object) {
    if (this == object) {
        return true;
    }

    if (!(object instanceof UserKey other)) {
        return false;
    }

    return id.equals(other.id);
}
```

### Контракт

Корректный `equals()` обязан соблюдать пять требований.

```text
рефлексивность  → x.equals(x) == true
симметричность  → x.equals(y) == y.equals(x)
транзитивность  → x=y и y=z ⇒ x=z
согласованность → результат не меняется, пока не менялись объекты
сравнение с null → x.equals(null) == false, без исключения
```

### Структура метода

```java
@Override
public boolean equals(Object object) {
    if (this == object) {
        return true;
    }

    if (!(object instanceof UserKey other)) {
        return false;
    }

    return id.equals(other.id);
}
```

Первая проверка — быстрый выход при совпадении ссылок. Вторая одновременно
проверяет `null`, проверяет тип и приводит объект. Дальше сравниваются поля,
определяющие логическое равенство.

## Метод hashCode

Возвращает число типа `int` и используется хешированными структурами:
`HashMap`, `HashSet`, `Hashtable`, `ConcurrentHashMap`.

```text
объект
→ hashCode
→ бакет
→ equals
→ точный объект
```

`hashCode()` выбирает бакет, `equals()` находит нужный объект внутри него.

### Контракт

> Если два объекта равны по `equals()`, их `hashCode()` обязан совпадать.

Обратное неверно: одинаковый хеш равенства не означает. Разные объекты с
совпадающим хешем — это коллизия, и она неизбежна.

```text
значений int:  от -2 147 483 648 до 2 147 483 647
возможных объектов: несравнимо больше
```

После попадания в один бакет объекты различаются через `equals()`.

### Почему нужно переопределять оба метода

```java
@Override
public boolean equals(Object object) {
    if (!(object instanceof UserKey other)) {
        return false;
    }

    return id.equals(other.id);
}
```

Здесь `equals()` переопределён, а `hashCode()` остался стандартным.

```java
UserKey first = new UserKey(10L);
UserKey second = new UserKey(10L);

first.equals(second);   // true
```

Но хеши различаются:

```java
Map<UserKey, String> map = new HashMap<>();

map.put(first, "User");

String value = map.get(second);   // может вернуть null
```

Причина:

```text
1. first добавляется в бакет по своему хешу
2. для second вычисляется другой хеш
3. поиск выполняется в другом бакете
4. до сравнения через equals карта не доходит
```

> При переопределении `equals()` необходимо переопределить `hashCode()`.

## Корректная реализация

```java
public final class UserKey {

    private final Long id;

    public UserKey(Long id) {
        this.id = Objects.requireNonNull(id);
    }

    @Override
    public boolean equals(Object object) {
        if (this == object) {
            return true;
        }

        if (!(object instanceof UserKey other)) {
            return false;
        }

        return id.equals(other.id);
    }

    @Override
    public int hashCode() {
        return id.hashCode();
    }
}
```

Оба метода используют одно и то же значимое поле — это ключевое условие.

### Несколько полей

```java
public final class OrderKey {

    private final String category;
    private final OrderPriority priority;

    public OrderKey(String category, OrderPriority priority) {
        this.category = category;
        this.priority = priority;
    }

    @Override
    public boolean equals(Object object) {
        if (this == object) {
            return true;
        }

        if (!(object instanceof OrderKey other)) {
            return false;
        }

        return Objects.equals(category, other.category)
                && priority == other.priority;
    }

    @Override
    public int hashCode() {
        return Objects.hash(category, priority);
    }
}
```

Перечисления сравниваются через `==`, потому что каждая константа существует в
единственном экземпляре.

### Objects.equals и Objects.hash

```java
Objects.equals(first, second);
```

Безопасно работает с `null`:

```text
оба null      → true
одно null     → false
оба не null   → first.equals(second)
```

```java
return Objects.hash(category, priority);
```

Вычисляет общий хеш нескольких полей. Читаемо и удобно, хотя чуть менее эффективно
ручного вычисления — в горячем коде это иногда имеет значение.

## Какие поля включать

Вопрос сводится к тому, что означает логическое равенство объектов.

**Объект-значение** сравнивается по всем значимым полям:

```java
public record Money(BigDecimal amount, Currency currency) {
}
```

Два объекта равны, если совпадают сумма и валюта.

**Сущность** обладает идентичностью: изменение имени пользователя не делает его
другим пользователем.

```text
одинаковый идентификатор → та же сущность
```

Для JPA-сущностей у этого подхода есть отдельные сложности, разобранные ниже.

### Изменяемые поля

Поля, участвующие в обоих методах, желательно делать неизменяемыми.

```java
public class UserKey {

    private String email;

    @Override
    public int hashCode() {
        return email.hashCode();
    }
}
```

```java
UserKey key = new UserKey("old@example.com");

Map<UserKey, String> map = new HashMap<>();
map.put(key, "value");

key.changeEmail("new@example.com");
```

Хеш изменился, объект физически остался в старом бакете, а поиск идёт в новом:

```java
map.get(key);      // может вернуть null
map.remove(key);   // может вернуть null
```

> Не изменять поля ключа, участвующие в `equals()` и `hashCode()`, пока объект
> находится в `HashMap` или `HashSet`.

## HashSet и hashCode

`HashSet` внутри использует `HashMap`:

```java
private HashMap<E, Object> map;

private static final Object PRESENT = new Object();
```

```java
map.put(element, PRESENT);
```

```text
элемент HashSet → ключ HashMap
PRESENT         → служебное значение
```

Поэтому множество зависит от той же пары методов, что и карта.

## instanceof и getClass

Два способа проверки типа, и выбор между ними — это выбор компромисса.

```java
if (!(object instanceof UserKey other)) {
    return false;
}
```

Принимает объект указанного класса и его наследников.

```java
if (object == null || getClass() != object.getClass()) {
    return false;
}
```

Требует точного совпадения классов. Для `final`-классов практической разницы нет.

### Наследование и симметричность

```java
class Point {

    private int x;
    private int y;
}

class ColoredPoint extends Point {

    private String color;
}
```

```java
Point point = new Point(1, 2);
ColoredPoint coloredPoint = new ColoredPoint(1, 2, "red");

point.equals(coloredPoint);   // true, сравниваются координаты
coloredPoint.equals(point);   // false, учитывается цвет
```

Симметричность нарушена. Добавление поля в наследник делает корректное сравнение с
родителем невозможным без нарушения контракта, поэтому классы-значения обычно
объявляют `final` либо используют композицию.

## JPA-сущности

Самый сложный случай.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

До сохранения идентификатор равен `null`, после — присвоен базой. Если
`hashCode()` зависит от него, значение меняется прямо во время жизни объекта:

```java
Set<Order> orders = new HashSet<>();

Order order = new Order(...);

orders.add(order);

entityManager.persist(order);
```

После появления идентификатора множество может перестать находить объект.

Отдельная сложность — прокси. Для ленивых связей Hibernate подставляет
сгенерированный подкласс:

```text
Order
→ Order$HibernateProxy
```

Проверка через `getClass() != object.getClass()` сочтёт сущность и её прокси
разными объектами.

При реализации равенства сущностей приходится учитывать transient- и
managed-состояние, отсоединённые экземпляры, генерируемый идентификатор, прокси и
использование в хешированных коллекциях.

Простого универсально верного варианта здесь нет: сравнение по ссылке работает
только внутри одного контекста персистентности, а сравнение по генерируемому `id`
нарушает контракт. Рабочие подходы — бизнес-ключ, известный при создании,
идентификатор, присвоенный приложением, и константный `hashCode()` — разобраны в
конспекте по практическим проблемам Hibernate.

## record как ключ

Для составных неизменяемых ключей удобен `record`:

```java
public record OrderKey(String category, OrderPriority priority) {
}
```

Компилятор генерирует конструктор, методы доступа, `equals()`, `hashCode()` и
`toString()` по всем компонентам, поэтому контракт соблюдается по построению.

```java
Map<OrderKey, Integer> statistics = new HashMap<>();

OrderKey key = new OrderKey("Infrastructure", OrderPriority.CRITICAL);

statistics.put(key, 5);
```

Но глубокой неизменяемости `record` не даёт:

```java
public record MutableKey(List<String> values) {
}
```

Ссылку изменить нельзя, содержимое списка — можно. Изменяемую коллекцию внутри
нужно копировать в компактном конструкторе.

## Типичные ошибки

### Переопределён только equals

Хеши равных объектов различаются, и запись не находится в хешированной коллекции.

### Переопределён только hashCode

`equals()` продолжает сравнивать ссылки, и логически равные объекты остаются
разными.

### Методы используют разные поля

Например, `equals()` по идентификатору, а `hashCode()` по почте. Контракт
нарушен.

### Используются изменяемые поля

Объект перестаёт находиться в коллекции после изменения значимого поля.

### Строки сравниваются через ==

Нужен `Objects.equals(email, other.email)`.

### Не учитывается null

Вызов `object.getClass()` при `object == null` даст `NullPointerException`.
Проверка через `instanceof` закрывает этот случай сама.

### Требование уникального hashCode

Он не обязан быть уникальным: коллизии допустимы. Требуется согласованность с
`equals()`, стабильность при неизменных полях и достаточно равномерное
распределение.

### Сравнение JPA-сущностей по generated ID

До сохранения идентификатор `null`, после — присвоен, и хеш меняется. Объект
теряется в собственном множестве.

## Краткий ответ для собеседования

`equals()` задаёт логическое равенство, `hashCode()` — числовой отпечаток,
используемый хеш-структурами для выбора бакета. Контракт связывает их
односторонне: равные объекты обязаны иметь одинаковый хеш, а одинаковый хеш
равенства не гарантирует, потому что коллизии неизбежны — множество возможных
объектов больше диапазона `int`. Переопределять методы нужно только вместе и по
одному и тому же набору полей.

`HashMap` сначала вычисляет бакет по хешу, затем внутри бакета находит нужный ключ
сравнением через `equals()`. Отсюда два практических правила: поля, участвующие в
хеше, не должны меняться, пока объект лежит в коллекции, иначе запись станет
недостижимой; и ключом лучше делать неизменяемый объект — `String`, `record` или
класс, объявленный `final`. `HashSet` построен на `HashMap` и зависит от той же
пары методов.

Сам `equals()` пишется по одной схеме: быстрая проверка на совпадение ссылок,
затем `instanceof` с приведением, который заодно закрывает случай `null`, затем
сравнение значимых полей. Для полей удобны `Objects.equals()` и `Objects.hash()`,
а перечисления сравниваются через `==`.

Выбор между `getClass()` и `instanceof` — это выбор между строгой
симметричностью и возможностью сравнивать с наследником. Добавление поля в
наследник делает корректное сравнение с родителем невозможным без нарушения
контракта, поэтому классы-значения обычно объявляют `final`.

Отдельный случай — JPA-сущности. Сравнение по ссылке работает только внутри одного
контекста персистентности, а сравнение по генерируемому идентификатору нарушает
контракт: до сохранения он `null`, после — присвоен базой, и объект теряется в
собственном `HashSet`. Дополнительно мешают ленивые прокси, из-за которых проверка
через `getClass()` возвращает `false` для одной и той же строки. Рабочие варианты
— бизнес-ключ, известный при создании, идентификатор, присвоенный приложением, или
константный `hashCode()` при сравнении по `id`.

## Вопросы на собеседовании

### 1. Чем == отличается от equals()?

**Ответ:** `==` сравнивает ссылки, то есть отвечает на вопрос, один ли это объект.
`equals()` сравнивает содержимое по правилам, заданным классом. Для примитивов
`==` сравнивает значения.

### 2. Какие требования входят в контракт equals()?

**Ответ:** рефлексивность, симметричность, транзитивность, согласованность при
неизменном состоянии и то, что сравнение с `null` всегда даёт `false`.

### 3. Какое правило связывает equals() и hashCode()?

**Ответ:** равные объекты обязаны иметь одинаковый хеш-код. Обратное не требуется:
разные объекты могут иметь совпадающий хеш.

### 4. Означает ли одинаковый хеш равенство объектов?

**Ответ:** нет. Хеш отображает бесконечное множество значений в ограниченный
диапазон, поэтому совпадения неизбежны. Окончательное решение принимает
`equals()`.

### 5. Что произойдёт, если переопределить только equals()?

**Ответ:** хеш-коды равных объектов окажутся разными, и они попадут в разные
бакеты. `HashMap` не найдёт запись по равному ключу, а `HashSet` примет дубликат.

### 6. Из каких шагов состоит корректная реализация equals()?

**Ответ:** проверка на совпадение ссылок, проверка типа через `instanceof` с
приведением, которая заодно обрабатывает `null`, и сравнение значимых полей.

### 7. Почему изменяемый ключ опасен?

**Ответ:** изменение поля, участвующего в `hashCode()`, меняет бакет, где карта
будет искать ключ. Запись остаётся в прежнем бакете и становится недостижимой.

### 8. Как HashMap использует hashCode() и equals()?

**Ответ:** по хешу вычисляется бакет, а внутри бакета нужный ключ находится
сравнением через `equals()`.

### 9. Почему HashSet зависит от этих методов?

**Ответ:** он построен на `HashMap`, где элементы выступают ключами. Уникальность
проверяется той же связкой хеша и равенства.

### 10. Чем instanceof отличается от getClass() в equals()?

**Ответ:** `getClass()` требует точного совпадения типов, поэтому объекты родителя
и наследника никогда не равны — зато симметричность соблюдается всегда.
`instanceof` допускает сравнение с наследником, но легко нарушает симметричность,
если наследник переопределит `equals()` по-своему.

### 11. Какие проблемы возникают при наследовании?

**Ответ:** добавление поля в наследник делает корректное сравнение с родителем
невозможным без нарушения контракта. Общая рекомендация — предпочитать композицию
либо делать класс `final`.

### 12. Зачем нужны Objects.equals() и Objects.hash()?

**Ответ:** первый безопасно сравнивает значения, которые могут быть `null`, второй
вычисляет общий хеш нескольких полей. Оба делают реализацию короче и читаемее.

### 13. Почему JPA-сущности сложно сравнивать?

**Ответ:** гарантия единственности экземпляра действует только внутри контекста
персистентности. Для отсоединённых сущностей и разных транзакций одна строка базы
представлена разными объектами, поэтому сравнение по ссылке не работает.

### 14. Как generated ID влияет на hashCode()?

**Ответ:** до сохранения идентификатор `null`, после — присвоен базой. Значение
`hashCode()` изменится, и объект, добавленный в `HashSet` до сохранения, в нём
потеряется.

### 15. Почему Hibernate-прокси нужно учитывать?

**Ответ:** ленивая связь подставляет прокси — сгенерированный подкласс. Сравнение
через `getClass()` вернёт `false` для одной и той же строки, поэтому используют
`instanceof` или `Hibernate.getClass()`.

### 16. Почему record подходит для ключа?

**Ответ:** компилятор генерирует `equals()` и `hashCode()` по всем компонентам, а
компоненты неизменяемы. Контракт соблюдается по построению, и хеш не меняется в
течение жизни объекта.

### 17. Гарантирует ли record глубокую неизменяемость?

**Ответ:** нет. Неизменяемы ссылки на компоненты, но объекты за ними могут
меняться. Изменяемую коллекцию внутри record нужно копировать в компактном
конструкторе.
