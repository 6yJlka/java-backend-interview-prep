# Git

## Модель данных

Понимание устройства Git избавляет от заучивания команд: почти всё выводится из
того, как хранятся данные.

### Коммит

Коммит — это снимок всего дерева файлов, а не набор изменений.

```text
коммит содержит
├── ссылку на дерево файлов
├── ссылку на родительский коммит (или несколько при слиянии)
├── автора и время
└── сообщение
```

Различия между коммитами Git вычисляет на лету, сравнивая снимки. Одинаковые файлы
между коммитами не дублируются — они хранятся один раз по хешу содержимого.

Идентификатор коммита — хеш от его содержимого вместе с родителем. Отсюда важное
следствие: **изменить коммит невозможно**. Любая правка порождает новый коммит с
новым хешем, а все потомки тоже получают новые хеши.

### Ветка

Ветка — это указатель на коммит. Не копия файлов, не отдельная папка, а файл с
сорока символами хеша.

```text
main    → c3
feature → c5

c1 ← c2 ← c3          (main)
       ↖ c4 ← c5      (feature)
```

Поэтому создание ветки мгновенно и ничего не стоит.

`HEAD` — указатель на текущую позицию, обычно на ветку. Состояние detached HEAD
означает, что он указывает прямо на коммит, минуя ветку: новые коммиты в этом
случае не принадлежат ни одной ветке и легко теряются.

### Три области

```text
рабочий каталог → файлы, которые вы редактируете
индекс (stage)  → то, что войдёт в следующий коммит
репозиторий     → зафиксированная история
```

```text
git add    рабочий каталог → индекс
git commit индекс → репозиторий
git restore --staged  индекс → обратно
```

Индекс существует, чтобы коммит можно было собрать выборочно — например,
зафиксировать исправление отдельно от незаконченной правки в том же файле.

## Слияние и перебазирование

Две операции с одинаковым результатом по содержимому и разным по форме истории.

### Merge

```text
до:
c1 ← c2 ← c3            (main)
       ↖ c4 ← c5        (feature)

после git merge feature:
c1 ← c2 ← c3 ← c6       (main)
       ↖ c4 ← c5 ↗
```

Создаётся коммит слияния с двумя родителями. История сохраняется как есть: видно,
что ветка существовала и когда её влили.

Если основная ветка не двигалась, слияние выполняется перемоткой — указатель просто
сдвигается вперёд, нового коммита не появляется.

```bash
git merge --no-ff feature   # принудительно создать коммит слияния
```

### Rebase

```text
до:
c1 ← c2 ← c3            (main)
       ↖ c4 ← c5        (feature)

после git rebase main:
c1 ← c2 ← c3 ← c4' ← c5'  (feature)
```

Коммиты ветки применяются заново поверх основной. История становится линейной.

Ключевой момент: `c4'` и `c5'` — **новые коммиты** с новыми хешами. Исходные
остаются в репозитории до сборки мусора, но ветка на них больше не указывает.

### Золотое правило

```text
не перебазировать ветки, опубликованные и используемые другими
```

Причина прямо следует из смены хешей. Коллега работал поверх `c5`, а после
перебазирования его больше нет — есть `c5'` с другим идентификатором. При следующей
синхронизации Git попытается совместить обе истории, и получится дублирование
коммитов.

Для личных веток перебазирование безопасно и полезно: перед вливанием оно убирает
лишние коммиты слияния.

```text
merge  → история как было, ветвления видны, больше шума
rebase → линейная история, читается легче, переписывает коммиты
```

### Squash

```bash
git merge --squash feature
```

Все изменения ветки складываются в один коммит. Часто применяется при вливании
запроса на слияние: в основной ветке остаётся один осмысленный коммит вместо
двадцати вида «фикс», «ещё фикс», «точно фикс».

## Отмена изменений

Три команды, которые путают чаще всего.

### reset

Сдвигает указатель ветки назад.

```bash
git reset --soft HEAD~1    # коммит отменён, изменения в индексе
git reset --mixed HEAD~1   # коммит отменён, изменения в рабочем каталоге (по умолчанию)
git reset --hard HEAD~1    # коммит отменён, изменения уничтожены
```

```text
--soft  → трогает только историю
--mixed → историю и индекс
--hard  → историю, индекс и файлы
```

`--hard` — единственная команда в этом списке, которая безвозвратно теряет
незафиксированную работу.

Переписывает историю, поэтому применима только к неопубликованным коммитам.

### revert

Создаёт новый коммит, отменяющий изменения указанного.

```bash
git revert c3
```

История не переписывается — она дополняется. Это единственный безопасный способ
отменить изменения в общей ветке.

```text
reset  → как будто коммита не было, история переписана
revert → коммит остался, добавлен обратный
```

### cherry-pick

Переносит отдельный коммит в текущую ветку.

```bash
git cherry-pick c4
```

Создаётся новый коммит с тем же содержимым, но другим хешем. Применяется, когда
исправление нужно и в основной ветке, и в релизной, а вливать всю ветку целиком
незачем.

Злоупотребление приводит к дублированию изменений в истории и конфликтам при
последующем слиянии.

### stash

Временно убирает незафиксированные изменения.

```bash
git stash               # спрятать
git stash pop           # вернуть и удалить из хранилища
git stash list
git stash -u            # включая неотслеживаемые файлы
```

Нужен, когда надо срочно переключиться на другую задачу, а текущая работа не готова
к коммиту. По умолчанию неотслеживаемые файлы не сохраняются — отсюда флаг.

## Конфликты

Возникают, когда две ветки изменили одни и те же строки, и Git не может выбрать
версию сам.

```text
<<<<<<< HEAD
    return calculateTotal(items);
=======
    return calculateTotalWithDiscount(items, discount);
>>>>>>> feature
```

```text
HEAD      → текущая ветка
после === → входящие изменения
```

Порядок разрешения:

```bash
# отредактировать файл, убрав маркеры
git add file.java
git merge --continue     # или git rebase --continue
```

```bash
git merge --abort        # отказаться и вернуться к исходному состоянию
```

Тонкость при перебазировании: там `HEAD` — это ветка, поверх которой перебазируем,
а «входящие» — ваши собственные коммиты. Стороны меняются местами по сравнению со
слиянием, и на этом регулярно ошибаются.

Лучшая профилактика — чаще синхронизироваться с основной веткой и держать ветки
короткоживущими. Конфликты в ветке двухнедельной давности разрешать заметно
тяжелее.

## Работа с удалённым репозиторием

### fetch и pull

```text
git fetch → загрузить изменения, ничего не менять в рабочих ветках
git pull  → fetch + merge (или rebase)
```

`fetch` безопасен всегда: он обновляет только удалённые ветки вида `origin/main`,
позволяя посмотреть, что появилось, до того как что-либо объединять.

`pull` делает то же самое и сразу вливает. По умолчанию через слияние, из-за чего в
истории появляются коммиты вида «Merge branch main of...».

```bash
git pull --rebase
git config --global pull.rebase true
```

Перебазирование при получении обычно предпочтительнее: ваши локальные коммиты
переносятся поверх свежих, и лишний коммит слияния не создаётся.

### push и принудительная отправка

После перебазирования локальная история расходится с удалённой, и обычная отправка
отклоняется.

```bash
git push --force              # опасно
git push --force-with-lease   # безопаснее
```

Различие существенное. Обычная принудительная отправка перезаписывает удалённую
ветку безусловно и может уничтожить чужие коммиты, появившиеся после вашей
последней синхронизации. Вариант `--force-with-lease` проверяет, что удалённая ветка
находится там, где вы её видели в последний раз, и отказывается, если кто-то успел
что-то отправить.

Правило: в общие ветки принудительно не отправляют вовсе, в собственные — только с
проверкой.

## Reflog

Журнал перемещений `HEAD`. Страховка почти от любой ошибки.

```bash
git reflog
```

```text
c5a1b2c HEAD@{0}: reset: moving to HEAD~3
f8e9d10 HEAD@{1}: commit: добавлена валидация
```

```bash
git reset --hard f8e9d10    # вернуться к состоянию до сброса
```

Коммиты не удаляются сразу после того, как на них перестали ссылаться — они живут
до сборки мусора, обычно около месяца. Поэтому «удалённые» `reset --hard` коммиты
почти всегда восстановимы.

Это первое, что стоит вспомнить, когда кажется, что работа потеряна.

## Модели ветвления

```text
trunk-based
→ короткоживущие ветки от main, вливание за часы или дни
→ требует хорошего покрытия тестами
→ сейчас распространён шире всего

git flow
→ ветки develop, release, hotfix, feature
→ подходит при редких релизах по расписанию
→ для непрерывной поставки избыточен
```

В обоих случаях работа обычно идёт через запросы на слияние с проверкой кода
коллегами и автоматическим прогоном тестов.

### Сообщения коммитов

```text
плохо: fix, wip, изменения, фикс2
хорошо: Исправлена гонка при резервировании остатков
```

Распространённое соглашение — Conventional Commits:

```text
feat: добавлена пагинация в списке заказов
fix: исправлен расчёт скидки при нулевом количестве
refactor: вынесено маппирование в отдельный класс
```

Формат позволяет автоматически генерировать список изменений и определять версию.

## Типичные ошибки

### Перебазировать общую ветку

Хеши меняются, история коллег расходится с вашей.

### Использовать push --force в общей ветке

Может уничтожить чужие коммиты. Как минимум нужен `--force-with-lease`.

### Отменять опубликованный коммит через reset

История переписывается. Для общих веток существует `revert`.

### Не глядя выполнять reset --hard

Единственная из команд отмены, теряющая незафиксированную работу.

### Считать, что после reset --hard всё потеряно

Коммиты доступны через `reflog` до сборки мусора.

### Держать долгоживущие ветки

Чем дольше ветка живёт, тем тяжелее конфликты при вливании.

### Использовать pull без rebase

История засоряется коммитами слияния при каждой синхронизации.

### Коммитить всё подряд через add .

В коммит попадают отладочные правки, файлы IDE и локальные конфигурации.

### Класть секреты в репозиторий

Удаление в следующем коммите не помогает — значение остаётся в истории. Требуется
переписывание истории и смена скомпрометированного ключа.

### Писать неинформативные сообщения

История коммитов — это документация о том, зачем менялся код.

## Краткий ответ для собеседования

Коммит в Git — это снимок всего дерева файлов вместе со ссылкой на родителя, а его
идентификатор является хешем от содержимого. Поэтому коммит нельзя изменить: любая
правка создаёт новый коммит с новым хешем, и все потомки тоже пересоздаются. Ветка
— всего лишь указатель на коммит, поэтому её создание мгновенно.

Слияние и перебазирование дают одинаковый результат по содержимому, но разный по
форме истории. Слияние создаёт коммит с двумя родителями и сохраняет структуру
ветвлений. Перебазирование применяет коммиты заново поверх другой ветки, делая
историю линейной, но порождая новые хеши. Отсюда правило: опубликованные ветки, с
которыми работают другие, перебазировать нельзя.

Для отмены изменений есть три команды. `reset` сдвигает указатель ветки назад и
переписывает историю, поэтому применим только к неопубликованным коммитам. `revert`
создаёт новый коммит с обратными изменениями и безопасен для общих веток.
`cherry-pick` переносит отдельный коммит в текущую ветку.

`fetch` загружает изменения, не трогая рабочие ветки, `pull` дополнительно их
вливает. Перебазирование при получении обычно предпочтительнее, чтобы не плодить
коммиты слияния.

Практически любая ошибка обратима через `reflog` — журнал перемещений `HEAD`, где
сохраняются коммиты, на которые больше никто не ссылается.

## Вопросы на собеседовании

### 1. Что такое коммит?

**Ответ:** снимок всего дерева файлов со ссылкой на родительский коммит. Различия
вычисляются на лету, а идентификатором служит хеш от содержимого.

### 2. Что такое ветка?

**Ответ:** указатель на коммит. Файл с хешем, поэтому создание ветки ничего не
стоит.

### 3. Можно ли изменить существующий коммит?

**Ответ:** нет. Любая правка создаёт новый коммит с новым хешем, и все его потомки
тоже пересоздаются.

### 4. Зачем нужен индекс?

**Ответ:** чтобы собирать коммит выборочно, включая в него только часть изменений
рабочего каталога.

### 5. Чем merge отличается от rebase?

**Ответ:** слияние создаёт коммит с двумя родителями и сохраняет ветвление.
Перебазирование применяет коммиты заново поверх другой ветки, делая историю
линейной, но меняя хеши.

### 6. Почему нельзя перебазировать общую ветку?

**Ответ:** коммиты получают новые хеши, и история коллег, работавших поверх старых,
расходится с новой. При синхронизации возникает дублирование.

### 7. Что такое fast-forward?

**Ответ:** слияние без создания коммита, когда целевая ветка не двигалась и
указатель просто сдвигается вперёд.

### 8. Чем reset отличается от revert?

**Ответ:** `reset` сдвигает указатель назад и переписывает историю. `revert`
добавляет новый коммит с обратными изменениями, ничего не переписывая, и потому
безопасен для общих веток.

### 9. Чем различаются режимы reset?

**Ответ:** `--soft` меняет только историю, `--mixed` дополнительно сбрасывает
индекс, `--hard` затрагивает и рабочий каталог, теряя незафиксированные изменения.

### 10. Можно ли восстановить данные после reset --hard?

**Ответ:** обычно да, через `reflog`. Коммиты хранятся до сборки мусора даже без
ссылок на них.

### 11. Что делает cherry-pick?

**Ответ:** переносит содержимое отдельного коммита в текущую ветку, создавая новый
коммит с другим хешем.

### 12. Для чего нужен stash?

**Ответ:** временно убрать незафиксированные изменения, чтобы переключиться на
другую задачу. Неотслеживаемые файлы сохраняются только с флагом `-u`.

### 13. Чем fetch отличается от pull?

**Ответ:** `fetch` только загружает изменения и обновляет удалённые ветки, `pull`
дополнительно вливает их в текущую.

### 14. Почему предпочитают pull --rebase?

**Ответ:** локальные коммиты переносятся поверх свежих, и не создаётся лишний
коммит слияния при каждой синхронизации.

### 15. Чем force-with-lease лучше force?

**Ответ:** он проверяет, что удалённая ветка не изменилась с момента последней
синхронизации, и отказывается перезаписывать чужие коммиты.

### 16. Как разрешать конфликты?

**Ответ:** отредактировать файл, убрав маркеры, добавить его в индекс и продолжить
операцию. Можно также прервать её и вернуться к исходному состоянию.

### 17. Чем отличаются стороны конфликта при merge и rebase?

**Ответ:** при слиянии `HEAD` — ваша ветка, при перебазировании — та, поверх которой
переносятся коммиты, а вашими оказываются входящие изменения.

### 18. Что такое reflog?

**Ответ:** журнал перемещений `HEAD`, позволяющий вернуться к состоянию до почти
любой операции, включая сброс и перебазирование.

### 19. Что делать, если секрет попал в репозиторий?

**Ответ:** удаления в новом коммите недостаточно — значение остаётся в истории.
Нужно переписать историю и обязательно сменить скомпрометированный ключ.

### 20. Чем trunk-based отличается от git flow?

**Ответ:** первый использует короткоживущие ветки от основной и подходит для частых
релизов, второй заводит отдельные ветки разработки и релизов и оправдан при
релизах по расписанию.
