# Java Memory Model

Java Memory Model, или JMM, — это набор правил, отвечающих на один вопрос: при
каких условиях изменение, сделанное одним потоком, обязано стать видимым другому
и в каком порядке эти изменения наблюдаются.

Тема кажется сугубо теоретической ровно до первого бага, который её требует.
Выглядит он так: поток крутит цикл ожидания по обычному `boolean`-флагу, другой
поток флаг выставляет, а цикл не заканчивается никогда. В отладчике всё
правильно, под нагрузкой воспроизводится через раз, на другой машине не
воспроизводится вовсе. Объяснить и починить это можно только через JMM.

---

## JMM и JVM Runtime Data Areas

Эти две вещи описывают разные стороны выполнения программы и постоянно
смешиваются.

Runtime Data Areas отвечают на вопрос, какие логические области памяти существуют
во время работы JVM: Heap, JVM Stack, Method Area, PC Register, Native Method
Stack.

JMM отвечает на другой вопрос — какие гарантии существуют при взаимодействии
нескольких потоков с общей памятью. Её предмет:

```text
visibility → когда один поток обязан увидеть запись другого
atomicity  → может ли операция наблюдаться как неделимое действие
ordering   → какие отношения порядка обязаны соблюдать потоки
```

```text
JVM Runtime Data Areas
→ логическая организация памяти во время выполнения

Java Memory Model
→ правила наблюдения действий между потоками
```

JMM не определяет, где физически лежит конкретная переменная. Она задаёт
допустимое поведение программы и гарантии, которые получают корректно
синхронизированные потоки.

Отсюда следует, что фраза «у каждого потока своя копия Heap» моделью не является.
Куча — общая область в терминах Runtime Data Areas. Расхождения между потоками
возникают из-за кешей процессора, буферов записи и переупорядочивания инструкций,
а модель описывает эти эффекты абстрактно, не привязываясь к железу.

---

## Visibility

Видимость отвечает на вопрос, когда запись одного потока обязана стать
наблюдаемой другим.

```java
private boolean ready = false;

void writer() {
    ready = true;
}

void reader() {
    while (!ready) {
    }
}
```

Между записью `ready = true` и чтением этого поля другим потоком нет
синхронизации, поэтому JMM не даёт читающему потоку никакой гарантии. Из
исходного кода нельзя заключить:

```text
writer записал true
→ reader обязательно немедленно увидит true
→ цикл обязательно завершится
```

Это и есть тот самый зависающий цикл. Обычное чтение общей переменной не является
механизмом межпоточной синхронизации.

Решить можно объявлением поля `volatile`:

```java
private volatile boolean ready;
```

Запись и последующее чтение такого поля образуют нужное отношение happens-before.

Либо работать с состоянием под одним монитором:

```java
private boolean ready;

synchronized void markReady() {
    ready = true;
}

synchronized boolean isReady() {
    return ready;
}
```

Освобождение монитора пишущим потоком связано с последующим захватом того же
монитора читающим. Поэтому `synchronized` даёт не только взаимное исключение, но
и видимость с упорядочиванием.

## Atomicity

Атомарность означает, что действие наблюдается как неделимое: другой поток не
может вклиниться внутрь и увидеть промежуточные шаги.

```java
count++;
```

Логически это три действия:

```text
read count
→ modify: прибавить 1
→ write count
```

Нужно различать атомарность отдельного чтения или записи и атомарность составной
операции. Даже если каждое обращение атомарно, `count++` целиком таковым не
становится.

```text
count = 0

Thread 1             Thread 2

read 0               read 0
+1                   +1
write 1              write 1

итог: count == 1
ожидалось: count == 2
```

Одна запись потеряна, потому что оба потока вычислили новое значение из одного
старого состояния. Это lost update.

Ключевой момент: `volatile` здесь не помогает.

```java
private volatile int count;

void increment() {
    count++;
}
```

`volatile` применяется к отдельным чтениям и записям поля и даёт видимость и
порядок. Он не объединяет последовательность read-modify-write в одну атомарную
операцию.

```text
volatile int count + count++  ≠  thread-safe increment
```

Нужна либо единая критическая секция, либо специализированная атомарная операция
вроде `AtomicInteger.incrementAndGet()`.

## Ordering и reordering

Порядок строк исходного кода не становится автоматически порядком, который смогут
наблюдать другие потоки. Компилятор, JIT и процессор применяют допустимые
оптимизации.

Описывать это как «JVM случайно переставляет строки» неправильно. Это
преобразования, которым разрешено менять внутренний способ выполнения при
сохранении требуемого поведения, и подчиняются они правилам, а не случайности:
зависимые операции переставлены не будут.

As-if-serial semantics означает, что внутри одного потока оптимизация не должна
менять допустимое однопоточное поведение программы. Если поток выполняется без
наблюдения со стороны других, результат обязан выглядеть так, будто действия
соблюдают семантику исходной программы.

Само по себе это правило межпоточных гарантий не создаёт.

```java
private int value;
private boolean ready;

void writer() {
    value = 42;
    ready = true;
}

void reader() {
    if (ready) {
        System.out.println(value);
    }
}
```

Внутри пишущего потока запись `value` расположена раньше записи `ready`. Но
обычное чтение `ready` в другом потоке синхронизирующим действием не является,
поэтому порядок строк не гарантирует читающему потоку увидеть `value == 42`.

Межпоточный наблюдаемый порядок задаётся правилами JMM, прежде всего
happens-before. Правильное решение создаёт такое отношение, а не рассчитывает на
конкретный компилятор, JIT или процессор.

---

## Happens-before

Центральное отношение порядка в модели. Если

```text
A happens-before B
```

то результаты действия `A` должны быть доступны действию `B`, а допустимые
переупорядочивания не могут нарушить эту гарантию.

Важно, что это логическое отношение, а не физическое время. Два действия могут
идти одно за другим по часам, но без правила JMM между ними отношения не будет. И
наоборот: связь может существовать между действиями, чей физический порядок на
конкретном железе иной.

```text
раньше по настенным часам ≠ автоматически happens-before
```

### Program order

В одном потоке каждое действие happens-before последующему по тексту программы.

```java
int value = 40;      // A
value = value + 2;   // B
print(value);        // C
```

```text
A HB B
B HB C
```

Порядок программы задаёт отношения внутри потока. Чтобы перенести гарантию в
другой поток, нужна межпоточная синхронизирующая связь.

### Монитор

Освобождение монитора happens-before каждому последующему успешному захвату того
же монитора.

```java
private int value;

synchronized void write() {
    value = 42;
}

synchronized int read() {
    return value;
}
```

Если оба метода вызваны на одном объекте, они используют один монитор `this`:

```text
Thread 1: value = 42
→ unlock this
→ HB
→ lock this
→ Thread 2: read value
```

Слово «того же» принципиально. Синхронизация на разных объектах этого отношения
не создаёт.

### volatile

Запись в `volatile`-переменную synchronizes-with последующим чтением той же
переменной, и эта связь создаёт happens-before.

```java
private int value;
private volatile boolean ready;

void write() {
    value = 42;
    ready = true;
}

void read() {
    if (ready) {
        System.out.println(value);
    }
}
```

```text
volatile write ready = true
HB
volatile read ready == true
```

### Thread.start()

Действия потока до вызова `thread.start()` happen-before всем действиям
запущенного потока.

```java
private int value;

void example() {
    value = 42;

    Thread thread = new Thread(() -> System.out.println(value));

    thread.start();
}
```

```text
write value = 42
→ thread.start()
→ HB
→ действия нового потока
```

Новый поток гарантированно увидит `42`, хотя поле не объявлено `volatile`.
Гарантию создаёт сам `start()`.

Обратной гарантии правило не даёт:

```java
Thread worker = new Thread(() -> value = 42);

worker.start();

System.out.println(value);
```

После `start()` оба потока выполняются конкурентно. Запускающий может прочитать
`value` до записи, и отношения от записи worker к этому чтению нет.

```text
start
├── worker:  write value = 42
└── starter: read value

порядок этих двух действий правилом start не задан
```

### Thread.join()

Все действия завершившегося потока happen-before успешному возврату из
`thread.join()` в ожидающем потоке.

```java
int[] result = new int[1];

Thread worker = new Thread(() -> result[0] = 42);

worker.start();
worker.join();

System.out.println(result[0]);
```

```text
worker: write result[0] = 42
→ worker завершается
→ HB
→ join успешно возвращается
→ read result[0]
```

Поле здесь не обязано быть `volatile`: нужное отношение уже создаёт `join()`.

Оговорка существенная: правило работает для **успешного** ожидания. Если `join()`
был прерван или ожидание с таймаутом вернулось только из-за истечения времени,
использовать это правило как доказательство видимости нельзя.

### Транзитивность

```text
A HB B
B HB C

=>

A HB C
```

Это и делает модель работоспособной: пишущий поток записывает обычное поле, затем
volatile-флаг, а читающий читает флаг и после него поле.

```java
value = 42;         // A
ready = true;       // B, volatile write

if (ready) {        // C, volatile read
    print(value);   // D
}
```

```text
A HB B     program order
B HB C     volatile rule
C HB D     program order

=>

A HB D
```

Транзитивность связывает локальный порядок обоих потоков с межпоточной
синхронизацией.

## volatile

Подходит для состояния, где нужны видимость и упорядочивание, но не нужна
взаимная блокировка составной модификации.

```text
volatile обеспечивает:
→ visibility
→ ordering вокруг volatile-доступов

volatile не обеспечивает:
→ mutual exclusion
→ атомарность составных операций
→ атомарность count++
→ согласованное изменение нескольких независимых полей
```

Публикация данных через флаг:

```java
private volatile boolean ready;
private int value;

void writer() {
    value = 42;
    ready = true;
}

void reader() {
    if (ready) {
        System.out.println(value);
    }
}
```

Если читающий поток увидел `ready == true`, записанное пишущим, он гарантированно
увидит и `value == 42`:

```text
value = 42
HB
volatile write ready = true
HB
volatile read ready == true
HB
read value
```

Первая и последняя связи — порядок программы, средняя — правило `volatile`,
итоговая гарантия получается транзитивностью.

При этом `volatile` не блокирует другие потоки: несколько потоков могут
одновременно читать и записывать поле.

### Порядок операций относительно volatile-записи

Расположение обычной записи относительно volatile-записи принципиально.

```java
void writer() {
    value = 42;      // до volatile write
    ready = true;
}
```

Читающий поток, увидевший `ready == true`, получает видимость записи `value`.

```java
void writer() {
    ready = true;
    value = 42;      // после volatile write
}
```

Теперь запись `value` следует после публикации. Volatile-связь не переносит назад
то, что пишущий поток сделает позже.

```text
volatile write ready = true
→ volatile read ready == true
→ reader может прочитать value

writer: value = 42 выполняется после публикации
→ нужной HB-цепочки к read value нет
```

Правило, которое стоит запомнить дословно:

> volatile write публикует то, что было сделано до него, а не то, что будет
> сделано после него.

## synchronized

Работает через монитор объекта или класса и даёт сразу три вещи: взаимное
исключение, видимость и упорядочивание.

```java
private int count;

public synchronized void increment() {
    count++;
}
```

Метод экземпляра захватывает монитор `this`. Только один поток может одновременно
выполнять код, защищённый этим монитором.

```text
Thread 1

lock this
read → modify → write
unlock this

        HB

Thread 2

lock this
read → modify → write
unlock this
```

`count++` остаётся составной операцией, но вся последовательность выполняется в
одной критической секции, и другой поток на том же мониторе не может вклиниться
между чтением и записью. Кроме того, освобождение монитора первым потоком
happens-before последующему захвату вторым, поэтому второй видит изменения
первого.

Для `static synchronized` используется монитор объекта `Class`, и он не совпадает
с монитором `this` конкретного экземпляра.

### Синхронизированный writer и обычный reader

Частая и неочевидная ошибка:

```java
private int count;

public synchronized void increment() {
    count++;
}

public int getCount() {
    return count;
}
```

Пишущий поток освобождает монитор `this`, но читающий его не захватывает. Пары
«освобождение — захват» нет, значит нет и гарантии.

```text
writer: unlock this
reader: обычный read count
нет парного lock того же монитора
→ нет monitor HB-гарантии
```

Корректный вариант синхронизирует и чтение:

```java
public synchronized int getCount() {
    return count;
}
```

Для простого независимо читаемого значения альтернативой иногда служит
`volatile`, но выбор должен учитывать инварианты класса: если несколько полей
образуют связанное состояние, одного volatile-поля недостаточно.

### volatile и synchronized

| Свойство | `volatile` | `synchronized` |
|---|---|---|
| Visibility | Да | Да |
| Ordering | Да | Да |
| Mutual exclusion | Нет | Да |
| Делает `count++` атомарным | Нет | Да, если операция целиком внутри критической секции |

`volatile` подходит для флага остановки, флага публикации, ссылки на безопасно
публикуемый снимок состояния и простого значения без составной модификации:

```java
private volatile boolean stopped;

void stop() {
    stopped = true;
}

void work() {
    while (!stopped) {
        doOneIteration();
    }
}
```

`synchronized` нужен для read-modify-write, check-then-act, нескольких связанных
изменений и любой критической секции:

```java
public synchronized boolean withdraw(int amount) {
    if (balance < amount) {
        return false;
    }

    balance -= amount;
    return true;
}
```

Выбор определяется требуемым набором гарантий, а не удобством синтаксиса.

## Data race и race condition

Два разных понятия, которые постоянно путают.

**Data race** возникает, когда несколько потоков обращаются к одной переменной
общей памяти, обращения конфликтуют, хотя бы одно из них является записью, и они
не упорядочены отношением happens-before. Конфликтуют обращения, если относятся к
одной переменной и хотя бы одно — запись.

```text
int value;

Thread 1: value = 42;
Thread 2: System.out.println(value);
```

Без синхронизации запись и чтение не упорядочены — это гонка данных. Определение
не содержит слов «когда нам важно значение переменной»: важность для
бизнес-логики в него не входит.

**Race condition** — более широкое логическое понятие: корректность результата
зависит от непредсказуемого порядка выполнения конкурентных операций.

```java
if (balance >= amount) {
    balance -= amount;
}
```

Оба потока могут проверить одно исходное значение, оба пройти условие и оба
выполнить списание. Операция check-then-act должна быть защищена как единое
целое.

```text
Thread 1: check true
Thread 2: check true
Thread 1: subtract
Thread 2: subtract
```

```text
Data race       → конфликтующий доступ к памяти без HB
Race condition  → логическая корректность зависит от порядка выполнения
```

Практический вывод: устранение гонки данных не устраняет состояние гонки. Два
вызова потокобезопасного API по отдельности корректны, а их композиция —
check-then-act — нет.

## Safe publication

Публикация объекта — передача ссылки так, чтобы другой поток получил к ней
доступ. Опубликовать нужно не только значение ссылки, но и корректно
сконструированное состояние объекта.

Небезопасная публикация:

```java
class Config {
    int timeout;
    String url;
}

private Config config;
```

```java
Config c = new Config();
c.timeout = 5000;
c.url = "localhost";

config = c;
```

```java
if (config != null) {
    System.out.println(config.timeout);
    System.out.println(config.url);
}
```

Между обычной записью ссылки и обычным чтением ссылки нет happens-before связи,
поэтому читающий поток может увидеть ненулевую ссылку на объект с ещё не
записанными полями.

Безопасный вариант через volatile-ссылку:

```java
private volatile Config config;
```

```java
Config local = config;

if (local != null) {
    System.out.println(local.timeout);
    System.out.println(local.url);
}
```

```text
write c.timeout = 5000
write c.url = "localhost"
HB
volatile write config = c
HB
volatile read config into local
HB
read local.timeout and local.url
```

Локальная переменная здесь фиксирует одну прочитанную ссылку: если `config` позже
заменит другой поток, оба чтения всё равно относятся к одному объекту.

Другие стандартные способы — публикация под тем же монитором и передача состояния
через механизмы, контракты которых создают нужные отношения.

### volatile-ссылка не делает поля volatile

```java
private volatile User user;
```

Volatile-семантика применяется к чтению и записи самой ссылки. Она не означает,
что `user.name` и `user.age` стали volatile.

Публикация видимость даёт:

```java
User created = new User();
created.name = "Dima";
created.age = 22;

user = created;   // volatile write
```

Поток, прочитавший эту ссылку, увидит предшествующие записи. Но последующая
конкурентная мутация:

```java
user.age = 23;
```

volatile-записью поля `age` не становится. Для неё нужно отдельное решение:
синхронизация, атомарная семантика самого изменяемого состояния или отказ от
мутации в пользу неизменяемого снимка.

```text
volatile reference
→ гарантии для доступа к ссылке и для предшествующей публикации

volatile reference
≠ транзитивно volatile граф объектов
```

## final и JMM

Модель даёт специальные гарантии для `final`-полей после корректного завершения
конструктора.

```java
final class Config {

    private final String host;
    private final int timeout;

    Config(String host, int timeout) {
        this.host = host;
        this.timeout = timeout;
    }
}
```

Если объект корректно сконструирован и ссылка `this` не утекла из конструктора,
любой поток, получивший ссылку, увидит корректно инициализированные `final`-поля
без дополнительной синхронизации.

Опасная утечка:

```java
class Listener {

    private final int threshold;

    Listener(Registry registry) {
        registry.register(this);
        threshold = 10;
    }
}
```

`registry.register(this)` может сделать объект доступным другому потоку до
присваивания `threshold`, и рассуждать о безопасно завершённом конструировании
уже нельзя.

Неизменяемые объекты проще в многопоточном коде: после создания состояние не
меняется, и целый класс гонок исчезает. Но способ передачи ссылки всё равно нужно
оценивать по контракту публикации. Final-field guarantees относятся к корректно
установленным `final`-полям и не превращают произвольную небезопасную публикацию
в безопасную для всего изменяемого состояния объекта.

Отдельно: `final` у ссылки запрещает переназначение, но не делает объект по
ссылке неизменяемым.

```java
final List<String> values = new ArrayList<>();

values.add("Java");          // допустимо
values = new ArrayList<>();  // не компилируется
```

```text
final reference  → ссылку нельзя переназначить
immutable object → состояние объекта нельзя изменить
```

`final` не делает список ни неизменяемым, ни потокобезопасным.

## Типичные ошибки

### Считать volatile count++ потокобезопасным

`count++` состоит из чтения, изменения и записи. `volatile` не объединяет их в
одну атомарную операцию, поэтому возможен lost update.

### Синхронизировать writer, но оставить reader обычным

Правило монитора связывает освобождение с последующим захватом того же монитора.
Обычное чтение такого захвата не выполняет и гарантии не получает.

### Считать поля объекта volatile из-за volatile-ссылки

Семантика применяется к ссылке. Изменения `user.name` или `user.age` требуют
собственного решения.

### Считать порядок строк межпоточной гарантией

Порядок программы важен внутри потока, но сам по себе результат другому потоку не
передаёт. Нужна синхронизирующая связь и цепочка happens-before.

### Использовать Thread.sleep() как синхронизацию

```java
worker.start();
Thread.sleep(1000);
System.out.println(value);
```

`sleep()` не создаёт happens-before. Задержка не доказывает ни завершения worker,
ни видимости записи. Для ожидания завершения существует `join()`.

### Говорить, что у каждого потока своя копия Heap

Куча — общая область в терминах Runtime Data Areas. JMM описывает гарантии
наблюдения, а не физическое копирование памяти.

### Считать data race и race condition синонимами

Первое — конфликтующие доступы без happens-before, второе — зависимость
логической корректности от порядка событий. Второе шире.

### Считать, что JMM описывает Heap, Stack и Metaspace

Это Runtime Data Areas. JMM отвечает за видимость, атомарность, упорядочивание и
правила межпоточного наблюдения.

### Считать, что volatile всегда заменяет synchronized

`volatile` не даёт взаимного исключения и не защищает составные операции и
инварианты нескольких полей.

### Считать synchronized механизмом только атомарности

Он даёт взаимное исключение, видимость и упорядочивание одновременно. Освобождение
и последующий захват того же монитора создают happens-before.

### Полагаться на join() с таймаутом как на доказательство видимости

Ожидание могло завершиться по истечении времени, а не по завершении потока. Тогда
правила happens-before для `join()` не применяются.

## Краткая памятка

```text
JVM Runtime Data Areas → где логически лежат данные
Java Memory Model      → правила наблюдения между потоками

предмет JMM:
visibility → увидит ли другой поток запись
atomicity  → наблюдается ли операция как неделимая
ordering   → в каком порядке другой поток видит операции
```

```text
happens-before — логическое отношение, не физическое время

правила:
program order    → внутри потока по тексту программы
monitor          → unlock HB последующему lock того же монитора
volatile         → запись HB последующему чтению того же поля
Thread.start()   → всё до start() HB действиям нового потока
Thread.join()    → всё в завершившемся потоке HB успешному возврату
транзитивность   → A HB B, B HB C ⇒ A HB C
```

```text
volatile
→ visibility и ordering
→ НЕ mutual exclusion
→ НЕ атомарность count++
→ публикует сделанное ДО записи, не после

synchronized
→ mutual exclusion + visibility + ordering
→ монитор должны захватывать обе стороны
→ instance: this, static: Class
```

```text
data race       → конфликтующие доступы, хотя бы один — запись, нет HB
race condition  → корректность зависит от порядка; check-then-act
устранение data race не устраняет race condition
```

```text
safe publication
небезопасно: обычная запись ссылки + обычное чтение
безопасно:   volatile-ссылка, публикация под монитором,
             корректно сконструированные final-поля

volatile-ссылка ≠ volatile поля объекта
final-поле ≠ immutable объект по ссылке
утечка this из конструктора ломает final-гарантии
```

## Краткий ответ для собеседования

Java Memory Model определяет гарантии взаимодействия потоков с общей памятью. Её
предмет — три свойства: видимость изменений, атомарность операций и
упорядочивание действий. Важно не путать её с Runtime Data Areas: куча, стеки и
Method Area описывают логические области памяти, а модель памяти — правила
межпоточного наблюдения.

Центральный инструмент рассуждения — happens-before. Если действие A
happens-before действия B, результаты A должны быть доступны B, и допустимые
переупорядочивания не могут это нарушить. Это логическое отношение, а не
физический порядок по времени: операция может произойти раньше по часам, но без
правила модели её результат видеть никто не обязан.

Основных правил пять. Внутри потока действует порядок программы. Освобождение
монитора happens-before последующему захвату того же монитора — и слово «того же»
принципиально. Запись в volatile-поле happens-before последующему чтению этого
поля. Всё, сделанное до `Thread.start()`, видно запущенному потоку. Всё, сделанное
завершившимся потоком, видно после успешного `join()`. Отношение транзитивно, и
именно транзитивность позволяет опубликовать обычное поле через volatile-флаг.

`volatile` даёт видимость и упорядочивание, но не взаимное исключение и не
атомарность: `volatile count++` по-прежнему допускает потерю обновления, потому
что это три отдельных действия. `synchronized` через один монитор даёт всё три
гарантии сразу, но только если монитор захватывают обе стороны — синхронизировать
запись и оставить чтение обычным бессмысленно.

Отдельно стоит различать гонку данных и состояние гонки. Первое — свойство
доступа к памяти: конфликтующие обращения без happens-before. Второе — свойство
логики: корректность зависит от порядка, как в check-then-act. Устранение первого
не устраняет второго.

И последнее, что часто спрашивают, — безопасная публикация. Обычная запись ссылки
на объект не гарантирует, что другой поток увидит его инициализированные поля.
Нужна volatile-ссылка, публикация под монитором или корректно установленные
final-поля, причём последняя гарантия теряется при утечке `this` из конструктора.

## Вопросы на собеседовании

### 1. На какой вопрос отвечает Java Memory Model?

**Ответ:** при каких условиях изменение, сделанное одним потоком, гарантированно
становится видно другому и в каком порядке эти изменения наблюдаются. Это набор
правил, а не описание физического устройства памяти.

### 2. Чем JMM отличается от JVM Runtime Data Areas?

**Ответ:** области памяти описывают, где хранятся данные: куча, стеки, Metaspace.
JMM описывает правила видимости и упорядочивания между потоками. Это ортогональные
вопросы.

### 3. Почему неверно говорить, что у каждого потока есть собственная копия Heap?

**Ответ:** куча одна на всю JVM. Расхождения возникают из-за кешей процессора,
буферов записи и переупорядочивания инструкций, а не из-за копии кучи. Модель
описывает эти эффекты абстрактно, не привязываясь к железу.

### 4. Что означают visibility, atomicity и ordering?

**Ответ:** видимость — станет ли запись одного потока заметна другому. Атомарность
— выполняется ли операция целиком, без промежуточных наблюдаемых состояний.
Упорядочивание — в каком порядке другой поток может увидеть операции.

### 5. Почему обычный boolean ready не является надёжным механизмом передачи сигнала?

**Ответ:** без happens-before связи компилятор и процессор вправе кешировать
значение в регистре или переупорядочить обращения. Читающий поток может
неограниченно долго видеть старое значение, и цикл ожидания не завершится.

### 6. Из каких логических шагов состоит count++?

**Ответ:** чтение текущего значения, увеличение на единицу и запись результата.
Три отдельных действия, между которыми возможно вмешательство другого потока.

### 7. Как возникает lost update при двух конкурентных инкрементах?

**Ответ:** оба потока читают одно и то же значение, каждый увеличивает свою копию
и записывает результат. Вторая запись затирает первую, и вместо двух инкрементов
получается один.

### 8. Почему volatile int count не делает count++ потокобезопасным?

**Ответ:** `volatile` обеспечивает видимость и упорядочивание, но не атомарность
составной операции. Между чтением и записью по-прежнему может вклиниться другой
поток. Нужен `AtomicInteger` или синхронизация.

### 9. Что означает as-if-serial semantics?

**Ответ:** оптимизации обязаны сохранять результат, наблюдаемый в пределах одного
потока. Внутри потока программа ведёт себя так, будто инструкции выполнялись в
исходном порядке.

### 10. Почему as-if-serial semantics не создаёт межпоточных гарантий?

**Ответ:** правило говорит только о том, что видит сам поток. Другой поток может
наблюдать переупорядоченные операции, поскольку для него результат первого потока
не является наблюдаемым результатом в смысле этого правила.

### 11. Почему reordering нельзя описывать как случайную перестановку строк?

**Ответ:** переупорядочивание происходит на нескольких уровнях — компилятор,
процессор, буферы записи — и подчиняется правилам, а не случайности. Зависимые
операции переставлены не будут. Правильнее говорить, что порядок наблюдения не
гарантирован без happens-before связи.

### 12. Что означает отношение happens-before?

**Ответ:** если действие A happens-before действия B, то результаты A
гарантированно видны при выполнении B, и порядок между ними соблюдён.

### 13. Почему happens-before не равно физическому порядку по времени?

**Ответ:** это логическое отношение, устанавливаемое правилами модели. Операция
может произойти раньше по часам, но без happens-before связи её результат не
обязан быть виден. Верно и обратное: связь может существовать между действиями,
физический порядок которых на конкретном железе иной.

### 14. Какое happens-before правило задаёт program order?

**Ответ:** в пределах одного потока каждое действие happens-before следующего по
тексту программы.

### 15. Какое отношение возникает между unlock и последующим lock того же монитора?

**Ответ:** освобождение монитора happens-before последующего его захвата. Всё, что
поток сделал внутри синхронизированного блока, видно потоку, который затем вошёл в
блок на том же мониторе.

### 16. Что изменится, если writer и reader синхронизируются на разных объектах?

**Ответ:** связь не возникнет. Правило действует только для одного и того же
монитора, поэтому гарантий видимости не будет, а взаимного исключения — тем более.

### 17. Какое happens-before правило связано с volatile?

**Ответ:** запись в `volatile`-поле happens-before последующего чтения того же
поля.

### 18. Как транзитивность связывает обычную запись, volatile-флаг и обычное чтение?

**Ответ:** обычная запись happens-before записи флага по правилу порядка
программы, запись флага happens-before его чтения по правилу `volatile`, а чтение
флага happens-before последующего обычного чтения. Отношение транзитивно, поэтому
первая запись видна последнему чтению.

### 19. Почему в коде `value = 42; ready = true;` volatile-поле ready публикует value?

**Ответ:** обычная запись предшествует записи флага в порядке программы, а флаг
создаёт связь с читающим потоком. Увидев `ready == true`, он гарантированно
увидит и `value == 42`.

### 20. Почему порядок `ready = true; value = 42;` не даёт той же гарантии?

**Ответ:** запись `value` идёт после установки флага, поэтому в цепочку
happens-before не попадает. Читающий поток может увидеть флаг, но ещё не увидеть
значение.

### 21. Какие гарантии даёт synchronized помимо взаимного исключения?

**Ответ:** видимость и упорядочивание. При входе в блок поток видит все изменения,
сделанные до выхода из блока на том же мониторе.

### 22. Почему synchronized writer и обычный reader не образуют happens-before связь?

**Ответ:** правило требует пары «освобождение — захват» одного монитора. Если
читающий поток не входит в синхронизированный блок, второй половины пары нет, и
гарантий не возникает.

### 23. Какой монитор используют два instance synchronized-метода одного объекта?

**Ответ:** один и тот же — сам объект. Поэтому два таких метода не могут
выполняться параллельно на одном экземпляре.

### 24. Почему новый поток видит данные, записанные до thread.start()?

**Ответ:** действует отдельное правило: всё, выполненное до вызова `start()`,
happens-before любого действия в запущенном потоке.

### 25. Почему следующий код не гарантирует чтение 42 запускающим потоком?

```java
Thread worker = new Thread(() -> value = 42);
worker.start();
System.out.println(value);
```

**Ответ:** правило `start()` работает в одну сторону — от запускающего потока к
запущенному. Обратной гарантии нет, и печать может произойти до записи либо не
увидеть её результат. Нужен `join()` или иная синхронизация.

### 26. Почему после успешного worker.join() поле value не обязано быть volatile?

**Ответ:** действует правило: все действия завершившегося потока happens-before
успешного возврата из `join()`. Этого достаточно для видимости без дополнительных
средств.

### 27. Почему join с таймаутом не даёт той же гарантии?

**Ответ:** ожидание могло завершиться по истечении времени, а не по завершении
потока. Правило применяется только к успешному ожиданию, поэтому факт завершения
нужно проверять отдельно.

### 28. По каким признакам определяется data race?

**Ответ:** несколько потоков обращаются к одной переменной, обращения
конфликтуют, хотя бы одно из них является записью, и они не упорядочены
отношением happens-before. Важность переменной для бизнес-логики в определение не
входит.

### 29. Чем race condition отличается от data race на примере check-then-act?

**Ответ:** гонка данных — свойство доступа к памяти, состояние гонки — свойство
логики. Проверка наличия ключа и последующая вставка могут быть корректны с точки
зрения модели памяти, если каждая операция атомарна, но между ними вклинивается
другой поток, и результат оказывается неверным. Отсюда следствие: устранение
гонки данных не устраняет состояние гонки.

### 30. Почему следующая публикация небезопасна и как исправить её через volatile?

```java
Config created = new Config();
created.timeout = 5000;
config = created;
```

**Ответ:** запись поля `timeout` и запись ссылки `config` могут быть
переупорядочены, поэтому другой поток способен увидеть ненулевую ссылку на объект
с неинициализированным полем. Если объявить `config` как `volatile`, запись ссылки
создаст happens-before связь, и все предшествующие записи станут видны вместе с
ней.

### 31. Делает ли volatile-ссылка volatile поля объекта?

**Ответ:** нет. Семантика применяется к самой ссылке и к тому, что было записано
до её публикации. Последующая мутация полей объекта требует отдельной защиты.

### 32. Какие гарантии даёт корректное конструирование final-полей?

**Ответ:** если объект правильно сконструирован, любой поток, получивший на него
ссылку, увидит корректно инициализированные `final`-поля без дополнительной
синхронизации. Гарантия теряется при утечке `this` из конструктора — например,
регистрации объекта в слушателях до его завершения: другой поток получит ссылку
на недостроенный объект. Кроме того, `final ArrayList` означает лишь
неизменяемость ссылки: сам список остаётся изменяемым и не является
потокобезопасным.
