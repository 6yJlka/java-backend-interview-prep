# Locks, Atomics и Executors в Java

Следующий уровень после `synchronized` и `wait/notify`: явные блокировки с
дополнительными возможностями, атомарные операции без блокировок и пулы потоков,
отделяющие задачу от исполнителя. Это же самый частый источник вопросов на
собеседовании из всей многопоточности после модели памяти.

---

## Lock и ReentrantLock

`synchronized` и `Lock` решают одну базовую задачу — взаимное исключение: не
позволяют нескольким потокам одновременно выполнять критическую секцию,
защищённую одним и тем же механизмом.

```java
synchronized (monitor) {
    updateSharedState();
}
```

`synchronized` работает с intrinsic monitor объекта. Захват и освобождение
встроены в конструкцию языка: и при нормальном выходе из блока, и при выходе
из-за исключения JVM освобождает монитор сама.

Интерфейс `Lock` из `java.util.concurrent.locks` представляет явную блокировку.
Чаще всего используется `ReentrantLock`:

```java
Lock lock = new ReentrantLock();

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();
}
```

Освобождение обязательно помещают в `finally`: этот блок выполнится и при
нормальном завершении, и при `return`, и при исключении. Забытый `unlock()`
оставит остальные потоки в вечном ожидании.

```text
synchronized  → монитор освобождается автоматически при выходе из блока
ReentrantLock → код обязан вызвать unlock()
```

Из этого не следует, что `ReentrantLock` «безопаснее при исключениях» — наоборот,
безопасность целиком зависит от правильного шаблона `try-finally`. Оба механизма
дают взаимное исключение и необходимые гарантии видимости. `ReentrantLock`
выбирают ради дополнительных возможностей: неблокирующая попытка захвата,
ожидание с таймаутом, прерываемое ожидание, справедливость и несколько
`Condition`.

Вызов `lock()` должен находиться **до** `try`. Если захват прошёл успешно, поток
обязан освободить блокировку; если сам захват завершился исключением, вызывать
`unlock()` для незахваченной блокировки нельзя.

### Способы захвата

```java
lock.lock();
```

Если блокировка свободна, поток захватывает её и продолжает. Если занята — ждёт.
Занятость сама по себе исключения не вызывает. Обычный `lock()` не позволяет
выйти из ожидания по прерыванию: флаг может быть установлен, но захват
продолжает ожидаться.

```java
if (lock.tryLock()) {
    try {
        updateSharedState();
    } finally {
        lock.unlock();
    }
} else {
    doAlternativeWork();
}
```

`tryLock()` пытается захватить блокировку немедленно и возвращает `true` или
`false`, не ожидая освобождения. `unlock()` вызывают только после успешного
захвата.

```java
boolean acquired = lock.tryLock(500, TimeUnit.MILLISECONDS);

if (acquired) {
    try {
        updateSharedState();
    } finally {
        lock.unlock();
    }
}
```

Перегрузка с таймаутом ждёт не дольше указанного времени. Ожидание прерываемо,
поэтому метод может выбросить `InterruptedException`.

```java
try {
    lock.lockInterruptibly();
    try {
        updateSharedState();
    } finally {
        lock.unlock();
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

`lockInterruptibly()` ждёт блокировку, но позволяет прервать ожидание. В этом
случае метод выбрасывает исключение, не захватив её. Полезно, когда длительное
ожидание должно отменяться — при остановке сервиса или отмене задачи. При
выбрасывании исключения флаг прерывания очищается, поэтому его восстанавливают.

| Метод | Ждёт занятую | Таймаут | Реагирует на прерывание | Результат |
|---|---:|---:|---:|---|
| `lock()` | да | нет | не выходом через исключение | после возврата блокировка захвачена |
| `tryLock()` | нет | нет | ожидания нет | `true` или `false` сразу |
| `tryLock(timeout, unit)` | ограниченно | да | да | `true`, `false` или исключение |
| `lockInterruptibly()` | да | нет | да | захват или исключение |

### Повторный захват

Reentrant означает повторно входимый: поток, уже владеющий блокировкой, может
захватить её ещё раз и не заблокируется на самом себе.

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    System.out.println(lock.getHoldCount());   // 1

    lock.lock();
    try {
        System.out.println(lock.getHoldCount());   // 2
    } finally {
        lock.unlock();
    }

    System.out.println(lock.getHoldCount());   // 1
} finally {
    lock.unlock();
}
```

Блокировка хранит счётчик захватов для владеющего потока.

```text
lock()   → hold count 1
lock()   → hold count 2
unlock() → hold count 1, блокировка ещё занята
unlock() → hold count 0, блокировка свободна
```

Число `unlock()` должно совпадать с числом успешных захватов. Лишний вызов
потоком, который не владеет блокировкой, даёт `IllegalMonitorStateException`, а
недостающий оставляет её захваченной.

Intrinsic monitor тоже повторно входим: `synchronized`-метод может вызвать другой
`synchronized`-метод того же объекта без самоблокировки.

### Fairness

```java
ReentrantLock unfairLock = new ReentrantLock();
ReentrantLock fairLock = new ReentrantLock(true);
```

По умолчанию блокировка несправедливая. Освободившуюся может получить поток,
который только что начал захват, даже если другие уже ждут; такое опережение
очереди называют barging. Оно часто повышает пропускную способность, поскольку
готовый поток захватывает блокировку без лишних переключений.

Справедливая блокировка старается отдавать её наиболее долго ожидающим потокам.
Это уменьшает риск голодания, но дополнительные ограничения порядка обычно
снижают пропускную способность.

Справедливость относится к политике получения конкретной блокировки, а не к
управлению планировщиком процессора: она не гарантирует, что разблокированный
поток немедленно получит процессорное время. Кроме того, `tryLock()` без таймаута
может захватить доступную справедливую блокировку, не соблюдая очередь.

## Condition

`Condition` связывается с конкретным `Lock` и позволяет ожидать изменения
логического условия:

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();
```

Аналогия с monitor API помогает при первом знакомстве:

```text
wait()      → await()
notify()    → signal()
notifyAll() → signalAll()
```

Это не одинаковые API: `wait/notify` принадлежат `Object` и работают с intrinsic
monitor, а `await/signal` принадлежат `Condition`, связанному с явной
блокировкой. У одной блокировки может быть несколько отдельных условий.

### Поведение await()

Вызывающий поток должен владеть блокировкой. Затем `await()`:

1. атомарно освобождает связанную блокировку;
2. переводит поток в ожидание сигнала, прерывания или другого допустимого
   события;
3. после пробуждения заставляет снова конкурировать за блокировку;
4. возвращает управление только после повторного успешного захвата.

```text
владение lock
→ await()
→ освобождение lock и ожидание
→ signal()
→ ожидание повторного захвата lock
→ lock снова захвачен
→ await() возвращает управление
```

`signal()` не передаёт блокировку немедленно: сигналящий поток владеет ею до
`unlock()`. Вызов `await()`, `signal()` или `signalAll()` без владения приводит к
`IllegalMonitorStateException`.

Условие всегда проверяют в `while`:

```java
lock.lock();
try {
    while (queue.isEmpty()) {
        notEmpty.await();
    }

    Task task = queue.remove();
} finally {
    lock.unlock();
}
```

Причин две: возможно ложное пробуждение без нужного события, и после сигнала, до
повторного захвата блокировки, другой поток может снова изменить условие —
например, забрать последний элемент очереди. `if` проверил бы условие только до
ожидания и позволил бы продолжить с ложным предположением.

### Несколько условий на одну блокировку

Ограниченная очередь имеет как минимум два разных условия, и это главный аргумент
в пользу `Condition` перед `wait/notify`.

```java
class BoundedQueue<T> {
    private final Queue<T> queue = new ArrayDeque<>();
    private final int capacity;
    private final Lock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    BoundedQueue(int capacity) {
        this.capacity = capacity;
    }

    void put(T element) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) {
                notFull.await();
            }
            queue.add(element);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) {
                notEmpty.await();
            }
            T element = queue.remove();
            notFull.signal();
            return element;
        } finally {
            lock.unlock();
        }
    }
}
```

Производители ожидают `notFull`, потребители — `notEmpty`, и сигнал адресуется
нужной группе. С одним набором ожидающих на мониторе такое разделение
невозможно: `notify()` не различает причины ожидания.

## Atomic-классы

Пакет `java.util.concurrent.atomic` содержит классы для атомарной работы с
отдельным значением без явной критической секции: `AtomicInteger`, `AtomicLong`,
`AtomicBoolean`, `AtomicReference<T>`.

```java
AtomicInteger counter = new AtomicInteger(10);

int current = counter.get();              // прочитать 10
counter.set(20);                          // записать 20
int after = counter.incrementAndGet();    // записать 21, вернуть 21
int before = counter.getAndIncrement();   // вернуть 21, записать 22
int total = counter.addAndGet(5);         // записать 27, вернуть 27
boolean changed = counter.compareAndSet(27, 30);   // true, значение 30
```

Различие двух форм инкремента — только в возвращаемом значении:

```text
исходное значение: 10

incrementAndGet() → сначала увеличить до 11, затем вернуть 11
getAndIncrement() → сначала вернуть 10, затем увеличить до 11
```

Обе выполняют инкремент атомарно; отличается не итоговое состояние, а то, что
получает вызывающий код.

```java
AtomicLong sequence = new AtomicLong();
long id = sequence.incrementAndGet();

AtomicBoolean initialized = new AtomicBoolean();
if (initialized.compareAndSet(false, true)) {
    initializeOnce();
}

AtomicReference<String> state = new AtomicReference<>("NEW");
state.compareAndSet("NEW", "RUNNING");
```

Atomic-класс не делает атомарным произвольный алгоритм вокруг нескольких
переменных. Если инвариант охватывает несколько значений, нужна блокировка,
неизменяемый holder внутри `AtomicReference` или другой механизм.

### Почему volatile count++ не потокобезопасен

```java
private volatile int count;

void increment() {
    count++;
}
```

`count++` — составная операция чтения, изменения и записи:

```text
count = 0

Thread 1             Thread 2
read 0               read 0
increment to 1       increment to 1
write 1              write 1

итог: 1
ожидалось: 2
```

Один инкремент потерян. `volatile` даёт видимость и упорядочивание для чтений и
записей поля, но не объединяет три шага в одну атомарную операцию.

```java
private final AtomicInteger count = new AtomicInteger();

void increment() {
    count.incrementAndGet();
}
```

## CAS

Compare-And-Set — атомарная условная операция обновления:

```java
boolean result = value.compareAndSet(expected, update);
```

Семантика:

1. прочитать текущее значение;
2. атомарно сравнить его с `expected`;
3. при совпадении записать `update` и вернуть `true`;
4. при несовпадении ничего не менять и вернуть `false`.

Сравнение и условная запись наблюдаются как единое атомарное действие. Это не
просто «проверить значение и увеличить»: новое значение может быть любым, а
вычисляет его обычно пользовательский код.

### CAS loop

Атомарный инкремент можно представить циклом:

```java
int current;
int next;

do {
    current = value.get();
    next = current + 1;
} while (!value.compareAndSet(current, next));
```

Если другой поток изменил значение между `get()` и `compareAndSet()`, операция
вернёт `false`. После неудачи нужно **заново прочитать актуальное значение и
пересчитать** результат: повтор со старым `expected` либо никогда не пройдёт, либо
запишет значение, рассчитанное из устаревшего состояния.

```text
T1 читает 10 и вычисляет 11
T2 успешно меняет 10 → 11
T1: CAS(10, 11) → false
T1 снова читает 11, вычисляет 12 и повторяет CAS
```

### CAS и блокировки

```text
lock-based
lock → один владелец → критическая секция → unlock

CAS-based
read → calculate → CAS
                  ├→ success
                  └→ failure → read again → recalculate → CAS
```

CAS тоже является механизмом синхронизации: атомарные операции имеют определённые
гарантии видимости и порядка, и отсутствие явной блокировки не означает
отсутствия синхронизации. Он хорошо подходит для коротких обновлений отдельного
состояния, но при высокой конкуренции повторные попытки расходуют процессор, а
сложные инварианты проще и надёжнее выразить блокировкой.

### ABA

Обычный CAS проверяет текущее значение, но не историю изменений:

```text
T1 прочитал A

T2: A → B → A

T1 снова видит A
CAS с expected A может пройти
```

Хотя значение снова равно `A`, состояние успело измениться, и T1 может ошибочно
решить, что ничего не происходило. Особенно важно для lock-free структур данных,
где промежуточные изменения ссылки могут означать удаление узла, повторную
вставку или изменение связей.

Один из способов обнаружить историю — хранить версию вместе со значением:

```text
A, stamp=1
→ B, stamp=2
→ A, stamp=3
```

```java
AtomicStampedReference<String> reference =
        new AtomicStampedReference<>("A", 1);

int[] stampHolder = new int[1];
String current = reference.get(stampHolder);
int currentStamp = stampHolder[0];

boolean changed = reference.compareAndSet(
        current,
        "B",
        currentStamp,
        currentStamp + 1
);
```

CAS, ожидающий `A` со `stamp=1`, не пройдёт для `A` со `stamp=3`.

Для обычного монотонного счётчика ABA проблемой обычно не является: важно
актуальное числовое значение, а возврат к старому в алгоритм не входит. Но
анализировать её нужно, если смысл операции зависит от того, менялось ли
состояние между чтением и обновлением.

## ExecutorService

Создание потока на каждую задачу через `new Thread(...).start()` связывает каждую
задачу с новым системным потоком: это память под стек, время на запуск и работа
планировщика. При большом потоке задач их число легко становится
неконтролируемым.

Пул потоков содержит набор рабочих потоков и принимает отдельные задачи:

```java
ExecutorService executor = Executors.newFixedThreadPool(4);
```

```text
task          → описание работы
worker thread → поток, который берёт и выполняет задачи
```

Один worker последовательно выполняет много задач, поэтому потоки
переиспользуются. Executor также централизует очередь, ограничение параллелизма,
остановку и обработку перегрузки.

Завершив работу, executor нужно корректно остановить: иначе не-daemon рабочие
потоки могут продолжать удерживать JVM живой.

### execute и submit

```java
executor.execute(() -> processEvent());

Future<Integer> future = executor.submit(() -> 42);
```

`execute(Runnable)` принимает задачу и не возвращает объект результата.
`submit(...)` возвращает `Future`, через который можно дождаться завершения,
получить результат, узнать состояние или запросить отмену.

Контракты задач различаются:

```text
Runnable.run()    → не возвращает результат, не объявляет checked exceptions
Callable<T>.call() → возвращает T, может бросать checked exceptions
```

`submit(Runnable)` тоже допустим: его `Future<?>` сообщает о завершении, но
успешный `get()` обычно возвращает `null`.

Важное различие в обработке неперехваченных исключений. Исключение из задачи,
переданной через `submit`, сохраняется в `Future` и проявляется при `get()` как
`ExecutionException`. У `execute` никакого `Future` нет: исключение покидает
`run()` рабочего потока и попадает в его обработчик неперехваченных исключений —
то есть по умолчанию в лог и больше никуда.

## Future

`Future<T>` представляет результат, который может появиться позже.

### get()

```java
T result = future.get();
```

Если задача не завершена, `get()` блокирует вызывающий поток. Это не делает
задачу синхронной: она выполняется рабочим потоком, а ждёт её тот, кто вызвал
`get()`.

```java
Future<Integer> future = executor.submit(() -> {
    Thread.sleep(3000);
    return 42;
});

System.out.println("A");
System.out.println(future.get());
System.out.println("B");
```

```text
A
ожидание примерно до завершения задачи
42
B
```

`sleep()` здесь выполняет worker, а блокируется поток, вызвавший `get()`, —
например `main`.

### get с таймаутом

```java
Integer result = future.get(2, TimeUnit.SECONDS);
```

Метод ждёт не дольше таймаута и при его истечении бросает `TimeoutException`.
Таймаут ожидания **не отменяет задачу**: worker может продолжать работу. Для
отмены нужен отдельный вызов `cancel(...)`.

### Состояние и отмена

```java
boolean done = future.isDone();
boolean cancelled = future.isCancelled();
boolean accepted = future.cancel(true);
```

`isDone()` возвращает `true` при завершении любым способом — результатом,
исключением или отменой, — и успешного результата не означает. `isCancelled()`
истинен, если отмена произошла до нормального завершения.

```java
future.cancel(false);   // не разрешает прерывать выполняющийся worker
future.cancel(true);    // пытается прервать его
```

Отмена может быть принята и для уже запущенной задачи: `Future` станет
отменённым, но её код сможет продолжить выполнение. `cancel(true)` — не
принудительное убийство потока: прерывание кооперативно, и задача, игнорирующая
флаг и не вызывающая прерываемых методов, продолжит работать.

```java
Future<?> future = executor.submit(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        doOneUnitOfWork();
    }
});

future.cancel(true);
```

Если внутри цикла есть `sleep`, `wait`, `join` или другая прерываемая операция,
она выбросит `InterruptedException` и очистит флаг — задача обязана корректно это
обработать.

Независимо от того, как быстро отреагировал worker, после успешной отмены
`Future` остаётся отменённым, и `get()` бросит `CancellationException` вместо
возврата значения.

### Четыре исключения

**`ExecutionException`.** Если задача завершилась исключением, `get()` бросает не
его, а обёртку; исходная причина доступна через `getCause()`.

```java
Future<Integer> future = executor.submit(() -> {
    throw new IllegalStateException("boom");
});

try {
    future.get();
} catch (ExecutionException e) {
    Throwable cause = e.getCause();
    System.out.println(cause.getClass());     // IllegalStateException
    System.out.println(cause.getMessage());   // boom
}
```

Обёртка нужна потому, что `Future.get()` имеет единый контракт и заранее не знает,
какое исключение выбросит произвольная задача.

**`InterruptedException`.** Означает, что прерван поток, ожидающий в `get()`, а не
обязательно worker. Прерывание ожидающего само по себе задачу не отменяет.

**`TimeoutException`.** Означает только, что ожидающий не дождался за отведённое
время. Задача продолжает работу.

**`CancellationException`.** Непроверяемое исключение после успешной отмены. Это
верно, даже если код worker после запроса успел вычислить и вернуть значение:
контракт уже зафиксировал отменённое состояние.

## Остановка executor

### shutdown()

```java
executor.shutdown();
```

Executor перестаёт принимать новые задачи, продолжает выполнять уже принятые и
находящиеся в очереди, а затем завершает рабочие потоки. Попытка передать новую
задачу приводит к `RejectedExecutionException`.

Метод не ждёт завершения и обычно возвращается сразу. Для ожидания используют
`awaitTermination`:

```java
executor.shutdown();

if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
    executor.shutdownNow();
}
```

### shutdownNow()

```java
List<Runnable> notStarted = executor.shutdownNow();
```

Перестаёт принимать задачи, пытается прервать выполняющиеся и возвращает те, что
ещё не начали выполняться. Это попытка остановки по возможности, а не
гарантированное мгновенное завершение: игнорирующий прерывание код продолжит
работу. Возвращённый список — объекты задач, а не результаты.

## Типы пулов через Executors

Фабричные методы `Executors` удобно создают распространённые конфигурации. Они не
запрещены и не всегда плохи, но важно понимать скрытые параметры очереди и числа
потоков.

**`newFixedThreadPool(n)`** держит фиксированное число workers, а лишние задачи
ждут в практически неограниченной `LinkedBlockingQueue`. Из-за этого
`maximumPoolSize` фактически не помогает при перегрузке: очередь продолжает
принимать задачи, и при устойчивом превышении скорости поступления она может
сильно вырасти и съесть память.

**`newSingleThreadExecutor()`** — один worker, последовательное выполнение. Удобно,
когда важен порядок и нельзя выполнять более одной задачи одновременно. При
аварийном завершении worker executor создаст замену. Очередь здесь тоже может
неограниченно расти.

**`newCachedThreadPool()`** переиспользует свободные workers, а при их отсутствии
создаёт новые. Внутри `SynchronousQueue`, у которой нет буфера: передача требует
непосредственной встречи производителя и потребителя. Поэтому число потоков может
очень сильно вырасти, а вместе с ним — память под стеки, число переключений
контекста, нагрузка на планировщик и конкуренция за нижележащие ресурсы.

В продакшене часто предпочитают явно настроенный `ThreadPoolExecutor`, чтобы
сделать видимыми и ограничить число потоков, ёмкость очереди, именование потоков
и политику отказа. Выбор зависит от нагрузки, а не от универсального запрета на
`Executors`.

## ThreadPoolExecutor

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        2,
        4,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(10),
        threadFactory,
        new ThreadPoolExecutor.AbortPolicy()
);
```

### Параметры

`corePoolSize` — целевое базовое число workers. По умолчанию они создаются по
мере поступления задач, а не все сразу; `prestartAllCoreThreads()` позволяет
запустить их заранее.

`maximumPoolSize` — верхняя граница, до которой пул может вырасти, когда очередь
больше не принимает задачи.

`keepAliveTime` — сколько простаивающий worker сверх core может ждать новую
работу до удаления.

`workQueue` — очередь принятых, но ещё не начатых задач. Её тип и ёмкость
принципиально влияют на рост пула и на перегрузку.

`ThreadFactory` создаёт workers. Через неё задают понятные имена потоков,
daemon-флаг, приоритет и обработчик неперехваченных исключений.

`RejectedExecutionHandler` определяет, что делать с задачей, которую executor не
может принять из-за перегрузки или остановки.

### Алгоритм приёма задачи

Самая важная часть темы.

1. Если workers меньше `corePoolSize`, создать worker для новой задачи.
2. Иначе попытаться положить задачу в `workQueue`.
3. Если очередь не приняла и workers меньше `maximumPoolSize`, создать
   дополнительный worker.
4. Если очередь не приняла и workers достигли `maximumPoolSize`, применить
   политику отказа.

```text
new task
  ↓
workers < core? ── да → create worker
  │ нет
  ↓
queue accepts? ─── да → enqueue
  │ нет
  ↓
workers < max? ─── да → create extra worker
  │ нет
  ↓
reject
```

`maximumPoolSize` начинает играть роль **только после** того, как очередь
перестала принимать задачи. Это одна из самых частых ошибок при настройке пула:
с неограниченной очередью максимум недостижим в принципе.

Пример при `core=2`, `max=4`, `queue=10` и пятнадцати долгих задачах:

```text
задачи 1–2   → создаются 2 core workers
задачи 3–12  → 10 задач помещаются в queue
задачи 13–14 → queue заполнена, создаются 2 extra workers
задача 15    → workers == max и queue заполнена, rejection
```

Итог: четыре выполняются, десять ждут, одна отклонена.

Расчёт предполагает, что задачи достаточно долгие и во время отправки ни один
worker не успел освободиться. В реальной системе результат зависит от времени
выполнения и конкуренции между отправителем и workers.

### keepAliveTime

```text
core = 2
max = 4
keepAlive = 60 секунд
```

Под нагрузкой пул вырос до четырёх workers. После спада два дополнительных
простаивающих worker будут удалены примерно через заданное время, и пул вернётся
к двум.

Core-потоки по умолчанию от простоя не завершаются. Сделать их чувствительными
можно через `allowCoreThreadTimeOut(true)` — тогда время жизни должно быть больше
нуля, и число workers может опускаться ниже core.

### Политики отказа

Отказ происходит, когда работающий пул исчерпал и workers, и ёмкость очереди, а
также при отправке задачи после остановки.

| Политика | Поведение |
|---|---|
| `AbortPolicy` | бросить `RejectedExecutionException` — по умолчанию |
| `CallerRunsPolicy` | выполнить задачу в вызывающем потоке, если executor не остановлен |
| `DiscardPolicy` | молча отбросить новую задачу |
| `DiscardOldestPolicy` | убрать старую ожидающую и повторить приём новой |

`CallerRunsPolicy` заслуживает отдельного внимания:

```java
executor.execute(longTask);
System.out.println("after");
```

Если пул переполнен, `longTask.run()` выполняется прямо в вызывающем потоке, и
`execute` вернёт управление только после завершения задачи — строка `after`
напечатается позже. Если задача бросит неперехваченное исключение, оно пойдёт
через вызывающий поток, и до `after` выполнение может не дойти.

Это создаёт простую форму backpressure: перегруженный потребитель заставляет
производителя тратить время на обработку, и тот временно перестаёт отправлять
новые задачи. При остановке executor задача не выполняется, а молча
отбрасывается.

`DiscardOldestPolicy` удаляет одну из старых ожидающих задач из головы очереди;
уже выполняющиеся не вытесняются. Политика может нарушить ожидания порядка и тоже
теряет работу.

## Размер пула

### CPU-bound

Задачи большую часть времени считают: математика, компрессия, обработка
изображений, некоторые виды парсинга.

```java
int processors = Runtime.getRuntime().availableProcessors();
```

Размер обычно выбирают около числа доступных процессоров, а затем проверяют
измерениями. JVM физически может создать гораздо больше потоков, но двести
вычисляющих потоков на восьмиядерной машине не считают быстрее разумного малого
пула: они конкурируют за тот же процессор и добавляют переключения контекста,
нагрузку на планировщик и ухудшение локальности кеша.

### I/O-bound

Задачи значительную часть времени ждут: HTTP, база, файлы, внешние сервисы. Пока
один worker ждёт, другой может использовать процессор, поэтому пул может быть
больше числа ядер.

Универсальной формулы нет: конфигурацию выбирают по реальной доле ожидания и
проверяют по задержке, пропускной способности, загрузке процессора, памяти,
ограничениям нижележащих систем, пулам соединений и метрикам отказов.

И главное ограничение, о котором забывают:

```text
DB connection pool = 20
Thread pool = 200
```

Это не двести одновременных SQL-запросов. Обращаться к базе смогут не больше, чем
есть соединений, а остальные workers будут ждать. Такое ожидание потребляет
память, увеличивает задержку и может перенести перегрузку на весь сервис.

## Задачи на понимание

### Расчёт заполнения пула

```text
core = 2
max = 4
queue capacity = 5
10 долгих задач
```

**Ответ:** две задачи запускают core workers, пять попадают в очередь, две
запускают дополнительные workers, одна отклоняется. Итого четыре выполняются,
пять ждут, одна отклонена.

### Неограниченная очередь

```text
core = 2
max = 100
unbounded queue
50 долгих задач
```

Сколько workers будет создано?

**Ответ:** два. После достижения core остальные задачи принимает неограниченная
очередь, поэтому условие роста до максимума не наступает никогда.

### Исключение из Callable

Задача бросает `IllegalStateException`. Что произойдёт при `get()`?

**Ответ:** будет выброшено `ExecutionException`, а исходное исключение доступно
через `getCause()`.

### Таймаут ожидания

`get(timeout)` получил `TimeoutException`. Остановилась ли задача?

**Ответ:** нет. Истёк только лимит ожидания вызывающего потока. Worker может
продолжить работу, для отмены нужен отдельный вызов.

### Отмена и прерывание

Future отменили через `cancel(true)`, задача проверяет `isInterrupted()`.

**Ответ:** executor попытается прервать worker, задача может заметить флаг и
завершиться. Но `Future` уже отменён, поэтому `get()` бросит
`CancellationException`, а не вернёт значение.

### shutdownNow и вычислительный цикл

Задача выполняет бесконечный вычислительный цикл и не проверяет флаг прерывания.
Гарантирует ли `shutdownNow()` её остановку?

**Ответ:** нет. Метод запросит прерывание, но задача его игнорирует и может
продолжать работу.

### CallerRunsPolicy

Пул переполнен, политика — `CallerRunsPolicy`, `execute` вызывает `main`. Кто
выполняет задачу?

**Ответ:** `main`. Вызов `execute` вернётся только после завершения задачи.

### CallerRunsPolicy и исключение

Отклонённая задача выполняется в вызывающем потоке и бросает неперехваченное
`RuntimeException`. Выполнится ли следующая строка?

**Ответ:** нет. Исключение выйдет в вызывающий поток и может прервать его обычный
поток управления.

### Повторный захват

Поток трижды вызвал `lock.lock()`, затем дважды `unlock()`. Доступна ли
блокировка другому потоку?

**Ответ:** нет. Счётчик захватов равен единице, нужен ещё один `unlock()`.

### Сигнал Condition

Производитель вызвал `notEmpty.signal()`, но ещё не вышел из защищённого блока.
Может ли потребитель продолжить после `await()`?

**Ответ:** нет. Он должен повторно захватить блокировку, которую пока удерживает
производитель.

### Lost update

Два потока одновременно выполнили `count++` для `volatile int count = 0`. Обязан
ли итог равняться двум?

**Ответ:** нет. Оба могут прочитать ноль и записать единицу. `volatile` не делает
read-modify-write атомарным.

### Stamped CAS

T1 ожидает ссылку `A` со stamp 4. T2 меняет её на `B` со stamp 5, затем на `A` со
stamp 6. Пройдёт ли CAS T1 с ожиданием `A` и stamp 4?

**Ответ:** нет. Ссылка совпала, но версия изменилась — ровно для этого версия и
нужна.

## Типичные ошибки

### Забывать unlock()

Успешный захват требует соответствующего освобождения. Иначе блокировка навсегда
останется недоступной другим потокам.

### Вызывать unlock() не в finally

Исключение или ранний `return` пропустят обычную строку. Освобождение помещают в
`finally` после успешного захвата.

### Считать, что tryLock() ждёт

Без аргументов он возвращает `true` или `false` сразу. Ограниченно ждёт только
перегрузка с таймаутом.

### Ожидать исключения при занятой блокировке

Занятость — нормальная причина ожидания в `lock()`, а не ошибка.

### Оборачивать Condition.await() в if

После ложного пробуждения или изменения условия до повторного захвата блокировки
условие может оказаться ложным. Его проверяют в `while`.

### Считать volatile count++ атомарным

Это по-прежнему read-modify-write, и потеря обновления возможна.

### Понимать CAS как обычную проверку

Сравнение с ожидаемым значением и условная запись выполняются атомарно. Отдельные
`if` и присваивание не эквивалентны.

### Повторять CAS со старым expected

После неудачи нужно снова прочитать актуальное состояние и пересчитать результат,
иначе попытка опирается на устаревшие предположения.

### Забывать про ABA

Совпадение текущего значения с ожидаемым не доказывает, что оно не менялось по
пути `A → B → A`. Для чувствительных алгоритмов применяют версию.

### Считать Future.get() неблокирующим

Если задача не завершена, он блокирует вызывающий поток.

### Считать TimeoutException автоматической отменой

Таймаут ограничивает ожидание, но worker продолжает задачу. Отмена — отдельное
решение и отдельный вызов.

### Считать shutdownNow() принудительным убийством потоков

Метод лишь пытается прервать workers, а задачи должны реагировать кооперативно.

### Считать maximumPoolSize числом сразу создаваемых потоков

Сначала пул растёт до core, затем заполняет очередь и только после её отказа
создаёт workers сверх core.

### Забывать, что очередь заполняется раньше дополнительных workers

При стандартном алгоритме дополнительный worker появляется лишь тогда, когда
очередь больше не принимает задачу. С неограниченной очередью это не наступает
никогда.

### Считать 200 вычислительных потоков быстрее восьми на восьмиядерной машине

JVM их создаст, но они конкурируют за те же восемь процессоров и добавляют
накладные расходы без роста вычислительной мощности.

### Забывать ограничения нижележащих систем

Большой executor не расширяет пул соединений к базе, лимиты внешнего API или
пропускную способность сети. Он лишь увеличивает число ожидающих задач.

```text

lock()                    → ждёт, прерыванием не выходит
tryLock()                 → сразу true/false
tryLock(timeout, unit)    → ждёт ограниченно, прерываемо
lockInterruptibly()       → ждёт, прерываемо

reentrant: hold count, число unlock() = числу захватов
unfair по умолчанию — быстрее; fair снижает риск голодания
fairness ≠ управление планировщиком CPU
```

```text

AtomicInteger / AtomicLong / AtomicBoolean / AtomicReference
```

## Краткий ответ для собеседования

`ReentrantLock` решает ту же задачу взаимного исключения, что и `synchronized`, но
делает захват явным. Освобождение обязательно в `finally`, а сам захват — до
`try`. Брать его стоит ради возможностей, которых у монитора нет: `tryLock()` без
ожидания, ожидание с таймаутом, прерываемое ожидание, настройка справедливости и
несколько условий на одну блокировку. Повторный захват тем же потоком
увеличивает счётчик, и число освобождений должно ему соответствовать.

`Condition` — это `wait/notify` для явной блокировки, но с важным преимуществом:
на одну блокировку можно завести несколько наборов ожидающих. В ограниченной
очереди производители ждут «не полна», потребители — «не пуста», и сигнал
адресуется нужной группе. `await()` освобождает блокировку, ждёт, снова
захватывает её и только потом возвращает управление, а условие проверяют в цикле
из-за ложных пробуждений и возможного изменения состояния до повторного захвата.

Атомарные классы дают обновление отдельного значения без блокировки. В их основе
CAS: атомарно сравнить с ожидаемым значением и при совпадении записать новое. Если
не совпало, нужно перечитать актуальное состояние и пересчитать результат —
повторять со старым ожиданием бессмысленно. Именно поэтому `volatile count++`
небезопасен: видимость он даёт, атомарности трёх шагов — нет. Отдельная тонкость
— ABA: значение вернулось к прежнему, а состояние успело измениться; лечится
версией, например `AtomicStampedReference`.

Пул потоков отделяет задачу от исполнителя. `execute` не возвращает ничего, а
исключение уходит в обработчик потока; `submit` возвращает `Future`, и исключение
приходит через `get()` как `ExecutionException` с исходной причиной внутри.
Таймаут ожидания задачу не отменяет, а `cancel(true)` лишь запрашивает
прерывание — принудительно остановить поток нельзя.

Самое важное про `ThreadPoolExecutor` — порядок приёма задачи: сначала потоки до
core, затем очередь, и только когда очередь отказала — рост до максимума, а после
него отказ. Отсюда главная ошибка настройки: с неограниченной очередью
`maximumPoolSize` недостижим, и пул навсегда остаётся размером с core. Из политик
отказа отдельно стоит `CallerRunsPolicy` — она выполняет задачу в вызывающем
потоке и тем самым создаёт естественный backpressure.

Размер пула выбирают по характеру нагрузки: для вычислительной — около числа ядер,
для ожидающей — больше, но по измерениям. И в любом случае пул не снимает
ограничений нижележащих систем: двести рабочих потоков при двадцати соединениях к
базе дают двадцать запросов и сто восемьдесят ожидающих.

## Вопросы на собеседовании

### 1. Чем synchronized отличается от ReentrantLock?

**Ответ:** `synchronized` работает с intrinsic monitor и освобождает его
автоматически. `ReentrantLock` — явная блокировка с ручным `unlock()` и
дополнительными возможностями: `tryLock`, таймаут, прерываемый захват,
справедливость и несколько условий. Взаимное исключение дают оба.

### 2. Почему unlock() помещают в finally?

**Ответ:** чтобы освободить успешно захваченную блокировку при нормальном выходе,
`return` и исключении. Иначе можно навсегда заблокировать конкурентов.

### 3. Чем lock() отличается от tryLock()?

**Ответ:** `lock()` ждёт освобождения. `tryLock()` без аргументов немедленно
возвращает `true` или `false`.

### 4. Как ведёт себя tryLock(timeout, unit)?

**Ответ:** ждёт захват не дольше таймаута, возвращает `false` при его истечении и
может выбросить `InterruptedException` при прерывании ожидания.

### 5. Для чего нужен lockInterruptibly()?

**Ответ:** он позволяет прекратить ожидание занятой блокировки через прерывание,
выбросив `InterruptedException` и не захватив её.

### 6. Что означает reentrant?

**Ответ:** владеющий поток может повторно захватить ту же блокировку. Каждый
успешный захват увеличивает счётчик и требует своего освобождения.

### 7. Является ли synchronized reentrant?

**Ответ:** да, поток может повторно войти в код, защищённый тем же монитором.

### 8. Чем fair ReentrantLock отличается от unfair?

**Ответ:** справедливая старается обслуживать давно ожидающие потоки, уменьшая
риск голодания, но обычно снижает пропускную способность. По умолчанию
используется несправедливая.

### 9. Гарантирует ли fair lock немедленное получение процессора?

**Ответ:** нет. Она влияет на порядок захвата блокировки, но не управляет
планировщиком.

### 10. Что такое Condition?

**Ответ:** связанный с блокировкой объект ожидания логического условия с методами
`await`, `signal` и `signalAll`. У одной блокировки может быть несколько условий.

### 11. Что делает await()?

**Ответ:** требует владения блокировкой, освобождает её, ждёт, затем повторно
захватывает и только после этого возвращает управление.

### 12. Почему await() окружают while, а не if?

**Ответ:** из-за возможного ложного пробуждения и из-за того, что условие может
измениться другим потоком между сигналом и повторным захватом.

### 13. Зачем нужны несколько Condition у одной блокировки?

**Ответ:** чтобы разделить группы ожидающих по логическим условиям, например
«не пуста» и «не полна», и сигнализировать нужной группе.

### 14. Для чего нужен AtomicInteger?

**Ответ:** для атомарных операций над отдельным `int` — инкремента, сложения,
compare-and-set — без явной блокировки в пользовательском коде.

### 15. Чем incrementAndGet() отличается от getAndIncrement()?

**Ответ:** первый возвращает значение после увеличения, второй — до. Сам инкремент
атомарен в обоих случаях.

### 16. Почему volatile count++ не потокобезопасен?

**Ответ:** операция состоит из чтения, увеличения и записи. `volatile`
обеспечивает видимость и упорядочивание отдельных обращений, но не атомарность
всей последовательности.

### 17. Что такое CAS?

**Ответ:** атомарная операция: если текущее значение равно ожидаемому, записать
новое и вернуть `true`, иначе ничего не менять и вернуть `false`.

### 18. Почему после неудачного CAS нужно перечитать значение?

**Ответ:** другой поток изменил состояние. Новое значение нужно вычислять из
актуального, а не повторять устаревшую попытку.

### 19. Чем CAS-подход отличается от блокировки?

**Ответ:** блокировка даёт одному потоку эксклюзивную критическую секцию,
остальные ждут. При CAS несколько потоков конкурируют попытками, проигравшие
перечитывают состояние и повторяют.

### 20. Является ли CAS синхронизацией?

**Ответ:** да. Это атомарный механизм с гарантиями памяти, хотя явной блокировки
нет.

### 21. Что такое проблема ABA?

**Ответ:** значение прошло путь `A → B → A`, поэтому CAS, ожидающий `A`, не
замечает промежуточного изменения, хотя история состояния могла быть важна.

### 22. Как помогает AtomicStampedReference?

**Ответ:** он сравнивает и меняет ссылку вместе с версией, поэтому `A` со stamp 1
отличается от того же `A` со stamp 3.

### 23. Зачем нужен ExecutorService?

**Ответ:** он отделяет задачи от рабочих потоков, переиспользует потоки и
управляет очередью, параллелизмом, остановкой и перегрузкой.

### 24. Чем execute отличается от submit?

**Ответ:** `execute(Runnable)` не возвращает результат задачи. `submit` возвращает
`Future`, через который получают результат, исключение, состояние и отмену.

### 25. Чем Runnable отличается от Callable?

**Ответ:** `run()` не возвращает результат и не объявляет проверяемых исключений.
`call()` возвращает значение и может их бросать.

### 26. Куда попадёт исключение из задачи, отправленной через execute?

**Ответ:** оно покинет `run()` рабочего потока и попадёт в его обработчик
неперехваченных исключений. В отличие от `submit`, узнать о нём через `Future`
нельзя.

### 27. Что представляет Future?

**Ответ:** результат асинхронной задачи, который может появиться позже,
завершиться исключением или быть отменён.

### 28. Блокирует ли Future.get()?

**Ответ:** да, вызывающий поток ждёт, если задача ещё не завершена.

### 29. Что произойдёт, если Callable бросит исключение?

**Ответ:** `get()` бросит `ExecutionException`, а исходное исключение будет в
`getCause()`.

### 30. Почему исходное исключение оборачивается?

**Ответ:** у `Future.get()` единый контракт, и он заранее не знает, какое
исключение выбросит произвольная задача.

### 31. Что означает TimeoutException из get с таймаутом?

**Ответ:** результат не получен за время ожидания. Задача автоматически не
отменяется и может продолжать работу.

### 32. Что делает cancel(true)?

**Ответ:** переводит `Future` в отменённое состояние, если отмена принята, и
пытается прервать выполняющийся worker. Это не принудительное завершение потока.

### 33. Что вернёт get() после успешной отмены?

**Ответ:** ничего — он бросит `CancellationException`, даже если задача успела
вычислить значение.

### 34. Что означает isDone()?

**Ответ:** что задача завершена любым способом — результатом, исключением или
отменой. Успеха это не означает.

### 35. Чем shutdown() отличается от shutdownNow()?

**Ответ:** `shutdown()` доделывает уже принятые задачи. `shutdownNow()` пытается
прервать выполняющиеся и возвращает ещё не начатые, но мгновенной остановки не
гарантирует.

### 36. Что происходит с новой задачей после shutdown()?

**Ответ:** она отклоняется, и по умолчанию вызывающий получает
`RejectedExecutionException`.

### 37. Как устроен newFixedThreadPool(n)?

**Ответ:** фиксированное число workers и практически неограниченная очередь. При
длительной перегрузке очередь может сильно вырасти.

### 38. Как устроен newCachedThreadPool()?

**Ответ:** он переиспользует простаивающие workers, использует `SynchronousQueue`
и при отсутствии свободного worker создаёт новый, поэтому число потоков может
резко вырасти.

### 39. Как ThreadPoolExecutor принимает новую задачу?

**Ответ:** сначала создаёт workers до core, затем кладёт задачи в очередь, после
её заполнения растёт до максимума, а затем применяет политику отказа.

### 40. Что означает corePoolSize?

**Ответ:** базовое число workers, до которого пул предпочитает создавать потоки
раньше, чем ставить задачи в очередь.

### 41. Когда начинает влиять maximumPoolSize?

**Ответ:** только когда число workers не меньше core и очередь больше не принимает
новую задачу.

### 42. Как workQueue влияет на пул?

**Ответ:** её ёмкость определяет, когда начнётся рост сверх core и когда наступит
отказ. Неограниченная очередь делает максимум практически недостижимым.

### 43. Что делает keepAliveTime?

**Ответ:** позволяет удалить простаивающие workers сверх core после заданного
времени. Core-потоки по умолчанию от него не завершаются.

### 44. Какие стандартные политики отказа существуют?

**Ответ:** `AbortPolicy`, `CallerRunsPolicy`, `DiscardPolicy` и
`DiscardOldestPolicy`.

### 45. Как работает CallerRunsPolicy?

**Ответ:** если executor перегружен и не остановлен, отклонённую задачу синхронно
выполняет вызывающий поток. Это замедляет производителя и создаёт backpressure.

### 46. Почему CPU-bound пул обычно близок к числу ядер?

**Ответ:** задачи постоянно используют процессор, а лишние потоки добавляют
переключения контекста и накладные расходы планировщика, не добавляя ядер.

### 47. Почему I/O-bound пул может быть больше?

**Ответ:** workers часто ждут ввод-вывод, поэтому другие потоки могут использовать
процессор. Размер всё равно ограничивают по измерениям и возможностям нижележащих
систем.

### 48. Почему пул на 200 потоков не обходит пул соединений на 20?

**Ответ:** одновременно работать с базой смогут примерно столько задач, сколько
есть соединений. Остальные будут ждать, увеличивая задержку и потребление
ресурсов.
