# Базовая многопоточность в Java

Практические механизмы работы с потоками: запуск, состояния, ожидание,
синхронизация через мониторы и классические проблемы конкурентного выполнения.
Гарантии видимости и упорядочивания, стоящие за `synchronized`, разбираются в
конспекте по модели памяти; здесь основное внимание — поведению.

---

## Thread и Runnable

Базовая модель состоит из двух сущностей: `Thread` представляет поток
выполнения, `Runnable` — задачу, которую нужно выполнить.

```java
Runnable task = () -> System.out.println("Work");

Thread thread = new Thread(task);
thread.start();
```

`Runnable` содержит единственный абстрактный метод `run()`, поэтому задачу удобно
описывать лямбдой.

```text
создать Runnable
→ передать его в Thread
→ вызвать start()
→ JVM запускает новый поток
→ новый поток выполняет run()
```

Разделение ролей полезно даже в простом коде:

```text
Thread   → где выполняется работа
Runnable → какая работа выполняется
```

Именно поэтому реализуют `Runnable`, а не наследуют `Thread`: задачу можно
передать любому исполнителю, в том числе пулу потоков.

### start() и run()

Разница принципиальная и часто проверяется.

```java
thread.start();
```

`start()` просит JVM запустить новый поток выполнения. После запуска новый поток
вызывает `run()`, а вызвавший поток продолжает работу конкурентно.

```java
thread.run();
```

Прямой вызов `run()` — обычный вызов метода. Новый поток не создаётся, тело
выполняется текущим потоком.

```java
Runnable task = () -> System.out.println(
        "Task: " + Thread.currentThread().getName()
);

Thread thread = new Thread(task, "worker");

System.out.println("Caller: " + Thread.currentThread().getName());
thread.start();
```

Типичный результат при запуске из main:

```text
Caller: main
Task: worker
```

Если заменить `start()` на `run()`, задачу выполнит main:

```text
Caller: main
Task: main
```

Ошибка коварна тем, что код продолжает работать — просто однопоточно. Имя потока
в логе — самый быстрый способ её обнаружить.

Порядок вывода разных потоков детерминированным считать нельзя: какой из готовых
потоков получит процессор, решает планировщик.

## Состояния Thread

Метод `thread.getState()` возвращает одно из значений `Thread.State`:

| Состояние | Смысл |
|---|---|
| `NEW` | объект `Thread` создан, но `start()` ещё не вызван |
| `RUNNABLE` | поток выполняется либо готов выполняться и ожидает процессор |
| `BLOCKED` | поток ждёт захвата занятого intrinsic monitor |
| `WAITING` | поток ожидает события без таймаута |
| `TIMED_WAITING` | поток ожидает события или истечения времени |
| `TERMINATED` | выполнение `run()` завершилось |

Состояние — моментальный снимок. Оно может измениться сразу после вызова
`getState()`, поэтому результат используют для диагностики, а не для построения
логики синхронизации.

### NEW

После конструктора объект существует, но отдельный поток ещё не запущен:

```java
Thread worker = new Thread(() -> doWork());

System.out.println(worker.getState());   // NEW
```

Прямой вызов `run()` запуском не является: объект `Thread` нормального жизненного
цикла при этом не проходит.

### RUNNABLE

После успешного `start()` поток обычно переходит в `RUNNABLE`. В Java это
состояние объединяет два случая:

```text
выполняется на CPU ┐
                   ├→ RUNNABLE
готов получить CPU ┘
```

Отдельного состояния `RUNNING` в `Thread.State` нет, потому что различать
готовность и фактическое исполнение — дело планировщика операционной системы, а
не JVM. Следовательно, `getState() == RUNNABLE` не доказывает, что поток
выполняет инструкцию именно в момент проверки.

### BLOCKED

Смысл узкий: поток пытается получить intrinsic monitor для входа в
`synchronized`, но монитор удерживает другой поток.

```java
synchronized (lock) {
    doWork();
}
```

Если первый поток уже внутри, второй становится `BLOCKED` до освобождения
монитора.

`BLOCKED` не означает произвольное ожидание чего-либо. Спящий поток и поток,
вызвавший `wait()`, находятся в других состояниях — это частая ошибка в ответах.

### WAITING

Ожидание без заданного таймаута:

```java
lock.wait();
thread.join();
```

В первом случае требуется пробуждение и повторный захват монитора, во втором —
завершение ожидаемого потока.

### TIMED_WAITING

Ожидание с ограничением по времени:

```java
Thread.sleep(1000);
thread.join(1000);
lock.wait(1000);
```

Продолжение становится возможным после события, прерывания либо истечения
времени — в зависимости от операции.

### TERMINATED

Поток переходит сюда, когда `run()` завершился нормально либо из-за
необработанного исключения. Объект `Thread` одноразовый:

```java
Thread worker = new Thread(() -> doWork());

worker.start();
worker.join();
worker.start();   // IllegalThreadStateException
```

Повторный `start()` недопустим и после завершения, и пока поток уже запущен.

### Схема переходов

```text
NEW
  │ start()
  ▼
RUNNABLE ◄────────────────────────────────────────────┐
  │                                                   │
  ├─ попытка войти в занятый synchronized ─→ BLOCKED ─┤ monitor получен
  │                                                   │
  ├─ wait() / join() без таймаута ─────────→ WAITING ─┤ событие + готовность
  │                                                   │
  ├─ sleep(t) / wait(t) / join(t) ─→ TIMED_WAITING ───┘ событие или таймаут
  │
  └─ run() завершился ─────────────────────→ TERMINATED
```

После пробуждения из `wait()` поток должен снова захватить монитор. Если монитор
занят, он станет `BLOCKED`, а не продолжит выполнение сразу. Схема упрощена:
реальный момент перехода зависит от операции, владения монитором и планирования.

### Три вида ожидания

```text
BLOCKED       → ждёт захвата intrinsic monitor
WAITING       → ждёт события без таймаута
TIMED_WAITING → ждёт события или времени
```

| Состояние | Чего ждёт поток | Пример | Как продолжится |
|---|---|---|---|
| `BLOCKED` | освобождения занятого монитора | вход в `synchronized (lock)` | после получения монитора |
| `WAITING` | события без ограничения времени | `lock.wait()`, `worker.join()` | после события и выполнения условий операции |
| `TIMED_WAITING` | события или окончания времени | `sleep(1000)`, `wait(1000)`, `join(1000)` | после события, таймаута либо прерывания |

```java
synchronized (lock) {
    lock.wait();        // WAITING, монитор lock освобождён
}

Thread.sleep(1000);     // TIMED_WAITING

synchronized (lock) {   // BLOCKED, если lock удерживает другой поток
    doWork();
}
```

`sleep()` не переводит поток в `WAITING`: вызов с положительной длительностью даёт
`TIMED_WAITING`.

## Thread.sleep()

```java
Thread.sleep(1000);
```

Приостанавливает текущий поток — тот, который вызвал статический метод. В течение
указанного времени поток находится в `TIMED_WAITING`.

```text
RUNNABLE
→ sleep(1000)
→ TIMED_WAITING
→ прошёл таймаут
→ RUNNABLE
→ планировщик когда-нибудь выделяет CPU
```

Указанное время — минимальная задержка до готовности продолжить, а не обещание
возобновить выполнение ровно через заданное число миллисекунд.

Самое важное правило:

> `sleep()` не освобождает ни один монитор, которым владеет поток.

```java
synchronized (lock) {
    Thread.sleep(5000);
}
```

Во время сна поток продолжает владеть монитором `lock`, и любой другой поток,
пытающийся войти в тот же блок, будет `BLOCKED` все пять секунд. Истечение
времени сна монитор не освобождает: освобождение произойдёт при выходе из блока,
в том числе при раскрутке стека из-за исключения.

`sleep()` не является механизмом ожидания результата другого потока и не создаёт
между потоками happens-before связь. Для ожидания завершения существует `join()`.

## Thread.join()

```java
worker.start();
worker.join();
```

Вызывается текущим потоком на объекте другого потока: текущий ждёт завершения
`worker`.

```text
main: worker.start()
main: worker.join() ────── ждёт

worker: выполняет run()
worker: завершает run()

main: join() возвращается
main: продолжает работу
```

Обычный `join()` переводит ожидающий поток в `WAITING`, вариант с таймаутом — в
`TIMED_WAITING`.

```java
worker.join(1000);
```

Возврат из `join()` с таймаутом сам по себе завершения worker не доказывает:
таймаут мог истечь раньше. Проверять нужно через `isAlive()`.

`join()` связан и с моделью памяти: все действия завершившегося worker
happens-before успешному возврату из ожидания.

```java
int[] result = new int[1];

Thread worker = new Thread(() -> result[0] = 42);

worker.start();
worker.join();

System.out.println(result[0]);
```

```text
worker записывает result[0] = 42
→ worker завершается
→ join() успешно возвращается
→ main читает result[0]
```

Поэтому main гарантированно увидит `42`, хотя элемент массива не объявлен
`volatile`. Если ожидание было прервано или вернулось только из-за таймаута, эту
цепочку считать доказанной нельзя.

## Interrupt

Прерывание — кооперативный механизм запроса на остановку:

```java
thread.interrupt();
```

Это не «немедленно уничтожить поток». Поток должен отреагировать сам: проверить
флаг прерывания либо находиться в операции, которая умеет завершать ожидание
через `InterruptedException`.

Если поток не находится в такой операции, `interrupt()` просто устанавливает флаг.
Прочитать его без сброса можно так:

```java
boolean interrupted = Thread.currentThread().isInterrupted();
```

Классический вариант кооперативной отмены:

```java
while (!Thread.currentThread().isInterrupted()) {
    doWork();
}
```

```text
другой поток вызывает interrupt()
→ у worker появляется запрос на прерывание
→ worker замечает флаг
→ worker корректно завершает цикл и освобождает ресурсы
```

Это протокол сотрудничества. Если код никогда не проверяет флаг и не вызывает
прерываемых операций, один вызов `interrupt()` его не остановит.

Два способа проверки различаются существенно:

| Вызов | Что проверяет | Сбрасывает флаг |
|---|---|---|
| `thread.isInterrupted()` | флаг указанного потока | нет |
| `Thread.interrupted()` | флаг текущего потока | да |

Случайный вызов статического метода теряет сигнал для вышестоящего кода, поэтому
сбрасывающую семантику нужно учитывать явно.

### InterruptedException

Прерываемые блокирующие операции: `Thread.sleep()`, `Object.wait()`,
`Thread.join()`.

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    // выбрать корректную реакцию на запрос
}
```

Если спящий поток прервали, `sleep()` завершается раньше и выбрасывает
исключение. **При выбрасывании флаг прерывания очищается** — это ключевая деталь.

Отсюда типичная ошибка:

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
}
```

Такой код проглатывает прерывание: операция уже завершилась досрочно, флаг сброшен
при выбрасывании, обработчик работу не завершил и флаг не восстановил, а
вышестоящий код больше не видит запроса на остановку.

Если метод не может пробросить исключение, флаг восстанавливают вручную:

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

Повторный `interrupt()` не повторяет исключение — он возвращает флаг, чтобы
вышестоящий код узнал о запросе.

Если контракт метода допускает `throws InterruptedException`, часто лучше не
перехватывать исключение, а дать вызывающему уровню выбрать политику остановки.
Конкретная реакция зависит от контракта: завершить операцию, пробросить исключение
или восстановить флаг. Опасно только одно — молча потерять сигнал.

## synchronized и монитор

Каждый объект может использоваться как intrinsic monitor:

```java
synchronized (lock) {
    // критическая секция
}
```

Перед входом поток должен захватить монитор. Владеть им одновременно может только
один поток; претендент становится `BLOCKED`.

```text
Thread 1: захватил monitor lock
Thread 1: выполняет критическую секцию

Thread 2: пытается захватить тот же monitor
Thread 2: BLOCKED

Thread 1: выходит из synchronized и освобождает monitor
Thread 2: получает возможность захватить monitor
```

Выход из блока освобождает монитор — и при нормальном завершении, и при выходе
из-за исключения.

Синхронизироваться нужно именно на одном объекте: два блока на разных объектах
используют разные мониторы и взаимного исключения друг с другом не дают.

Синхронизированные методы выбирают монитор неявно:

```java
public synchronized void update() {
    // monitor: this
}

public static synchronized void reset() {
    // monitor: CurrentClass.class
}
```

Монитор экземпляра и монитор объекта класса — разные мониторы, поэтому метод
экземпляра и статический метод сами по себе друг друга не блокируют.

## wait, notify и notifyAll

### wait()

Используется для ожидания изменения общего состояния, защищённого монитором:

```java
synchronized (lock) {
    lock.wait();
}
```

Главное отличие от `sleep()`:

> `wait()` освобождает монитор объекта, на котором вызван.

```text
поток владеет monitor lock
→ вызывает lock.wait()
→ освобождает monitor lock
→ переходит в WAITING
→ получает сигнал, прерывание или иное допустимое пробуждение
→ снова пытается получить monitor lock
→ после успешного захвата продолжает работу после wait()
```

Вариант с таймаутом даёт `TIMED_WAITING`:

```java
synchronized (lock) {
    lock.wait(1000);
}
```

Вызвать `wait()` можно только владея монитором именно того объекта, у которого
метод вызывается:

```java
lock.wait();               // IllegalMonitorStateException

synchronized (otherLock) {
    lock.wait();           // IllegalMonitorStateException
}
```

Освобождается только монитор объекта вызова. Если поток владеет и другими
мониторами, они остаются захваченными — частая причина взаимоблокировки. Перед
возвратом из `wait()` поток обязан снова захватить освобождённый монитор; это
верно и при выходе через `InterruptedException`.

### sleep() и wait()

```text
sleep() → TIMED_WAITING → monitor НЕ освобождает
wait()  → WAITING или TIMED_WAITING → monitor освобождает
```

| Свойство | `Thread.sleep()` | `Object.wait()` |
|---|---|---|
| Где объявлен | `Thread` | `Object` |
| На кого действует | на текущий поток | на текущий поток, ожидающий на мониторе объекта |
| Назначение | временно приостановить выполнение | координировать потоки через условие под монитором |
| Типичное состояние | `TIMED_WAITING` | `WAITING` или `TIMED_WAITING` |
| Освобождает монитор | нет | да, монитор объекта вызова |
| Требует владения монитором | нет | да |
| Прерывается | да | да |

`sleep()` можно вызвать внутри `synchronized`, но монитор останется у спящего
потока. `wait()` имеет смысл именно внутри синхронизированного протокола:
проверить условие, освободить монитор на время ожидания, после пробуждения снова
получить монитор и повторно проверить условие.

### notify() и notifyAll()

```java
synchronized (lock) {
    lock.notify();
}
```

```java
synchronized (lock) {
    lock.notifyAll();
}
```

`notify()` выбирает один поток из набора ожидающих на этом мониторе, и полагаться
на то, какой именно, нельзя. `notifyAll()` пробуждает всех ожидающих, но войти в
защищённую секцию одновременно они не смогут: каждый должен конкурировать за тот
же монитор и заново проверить своё условие.

Ключевое правило:

> `notify()` и `notifyAll()` не освобождают монитор.

```text
producer владеет monitor lock
→ меняет общее состояние
→ вызывает lock.notifyAll()
→ всё ещё владеет monitor lock
→ выходит из synchronized
→ освобождает monitor lock
→ пробуждённые потоки конкурируют за monitor
→ один захватывает monitor и проверяет условие
```

Оба метода, как и `wait()`, требуют владения монитором объекта вызова, иначе
выбрасывается `IllegalMonitorStateException`.

### Почему wait() вызывают в while

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }

    // работа, для которой condition должна быть true
}
```

Возврат из `wait()` не является гарантией истинности условия, и причин тому две.

**Ложное пробуждение.** Спецификация допускает spurious wakeup: поток может выйти
из ожидания без ожидаемого изменения условия. Код должен оставаться корректным.

**Условие изменилось снова.** После сигнала поток не получает монитор мгновенно.
Пока он конкурирует за монитор, другой поток может захватить его раньше и снова
изменить состояние.

```java
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();
    }

    queue.remove();
}
```

```text
очередь пуста
→ Consumer 1 и Consumer 2 ждут
→ producer добавляет один элемент и пробуждает consumers
→ Consumer 1 первым получает monitor и забирает элемент
→ Consumer 1 освобождает monitor
→ Consumer 2 получает monitor, но очередь снова пуста
```

С `if` второй потребитель пошёл бы дальше с ложным предположением и попытался
удалить несуществующий элемент. `while` отправит его ждать снова.

> `notify()` означает «состояние могло измениться», а не «нужное условие
> гарантированно выполнено».

Условие читают и изменяют под тем же монитором, а после каждого возврата из
`wait()` проверяют заново.

## Deadlock, livelock и starvation

### Deadlock

Состояние взаимного ожидания, при котором участвующие потоки не могут
продолжить. Классический случай — разный порядок захвата двух мониторов:

```text
Thread 1: lockA → lockB
Thread 2: lockB → lockA
```

```text
T1 захватил A
T2 захватил B
T1 пытается захватить B → BLOCKED
T2 пытается захватить A → BLOCKED

T1 держит A и ждёт B
T2 держит B и ждёт A
```

Никто не может продолжить и освободить удерживаемый монитор — образовался цикл
ожидания ресурсов. Взаимоблокировка не завершает JVM и не выбрасывает исключение:
приложение просто перестаёт продвигаться в затронутой части.

### Как предотвращать

Главный способ — установить единый глобальный порядок захвата мониторов и
соблюдать его во всём коде.

```text
было:  T1: A → B,  T2: B → A
стало: T1: A → B,  T2: A → B
```

Если `A` занят, второй поток ждёт `A`, ещё не удерживая `B`, и ситуация «держит B,
ожидая A» становится невозможной.

```text
запрещено брать B раньше A
→ невозможно одновременно получить:
  T1 держит A и ждёт B
  T2 держит B и ждёт A
→ цикл ожидания не формируется
```

Причина именно в устранении циклического ожидания ресурсов — это не объяснение
через happens-before.

Порядок должен определяться стабильным правилом и соблюдаться везде, где
захватываются несколько мониторов: локальная договорённость в одном методе не
поможет, если другой код берёт те же мониторы наоборот. Дополнительно полезно
сокращать время владения монитором и не выполнять внутри критической секции
долгие внешние вызовы, но единый порядок это не заменяет.

### Livelock

Потоки не заблокированы и продолжают изменять состояние, но полезного прогресса
нет. Например, оба видят конфликт, оба уступают ресурс друг другу и сразу
повторяют попытку.

```text
Thread 1: вижу Thread 2 → уступаю → повторяю
Thread 2: вижу Thread 1 → уступаю → повторяю
```

### Starvation

Система работает, но конкретный поток очень долго не получает нужный ресурс.
Например, после каждого освобождения монитора другие потоки успевают захватить
его раньше одного и того же потока.

```text
monitor освобождён
→ его получает T2
→ затем T3
→ затем снова T2
→ T1 продолжает ждать
```

Взаимного циклического ожидания здесь нет: остальные потоки продолжают полезную
работу.

### Сравнение

| Проблема | Потоки активны | Система делает прогресс | Конкретный поток | Причина |
|---|---|---|---|---|
| Deadlock | заблокированы | в затронутой цепочке нет | нет | цикл взаимного ожидания ресурсов |
| Livelock | да | полезного прогресса нет | нет | потоки постоянно реагируют друг на друга |
| Starvation | другие активны | обычно да | очень долго нет | ресурс систематически достаётся другим |

```text
deadlock   → ждут друг друга и стоят
livelock   → действуют, но результат не приближается
starvation → другие продвигаются, один остаётся без ресурса
```

## Типичные ошибки

### Считать, что run() создаёт новый поток

Прямой вызов выполняет обычный метод в текущем потоке. Новый поток запускает
`start()`.

### Добавлять отдельный RUNNING в Thread.State

Такого значения нет. `RUNNABLE` включает и фактическое выполнение на процессоре,
и готовность его получить.

### Определять BLOCKED как любое ожидание

`BLOCKED` — только ожидание захвата занятого монитора. Ожидание в `wait()`,
`join()` или `sleep()` представлено другими состояниями.

### Считать, что sleep() освобождает монитор

Он приостанавливает поток, но оставляет за ним все удерживаемые мониторы.

### Считать, что notify() освобождает монитор

Он только выбирает поток для пробуждения. Монитор освобождается при выходе из
`synchronized`.

### Ожидать немедленного продолжения после notify()

Пробуждённый поток должен снова получить монитор, а до этого уведомивший поток
продолжает работу внутри блока.

### Вызывать wait() вне synchronized

Поток должен владеть монитором объекта вызова, иначе будет
`IllegalMonitorStateException`.

### Оборачивать wait() в if

После ложного пробуждения или изменения условия другим потоком предположение может
оказаться ложным. Условие проверяют в цикле `while`.

### Считать, что interrupt() насильно уничтожает поток

Это запрос. Поток завершается кооперативно, если его код корректно обрабатывает
флаг или `InterruptedException`.

### Оставлять пустой catch (InterruptedException e)

При выбрасывании флаг сбрасывается. Пустой блок теряет сигнал и лишает
вызывающий код возможности отреагировать.

### Полагаться на join с таймаутом как на факт завершения

Метод возвращает управление и по истечении времени. Завершение проверяют через
`isAlive()`.

### Считать deadlock и starvation одним явлением

При взаимоблокировке есть цикл взаимного ожидания. При голодании система работает,
но один поток долго не получает ресурс.

### Объяснять единый порядок захвата через happens-before

Он предотвращает взаимоблокировку тем, что не позволяет сформировать цикл
ожидания ресурсов. Happens-before описывает гарантии видимости и порядка, а не
устраняет этот цикл.

## Краткий ответ для собеседования

`Thread` представляет поток выполнения, `Runnable` — задачу. `start()` запускает
новый поток, после чего JVM вызывает в нём `run()`; прямой вызов `run()` остаётся
обычным вызовом в текущем потоке, и код при этом работает, просто однопоточно.

`Thread.State` содержит `NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`,
`TIMED_WAITING` и `TERMINATED`. Отдельного `RUNNING` нет: различать готовность и
исполнение — дело планировщика. `BLOCKED` означает строго одно — ожидание захвата
занятого монитора, все остальные виды ожидания представлены другими состояниями.

`sleep()` переводит поток в `TIMED_WAITING` и не освобождает мониторы, поэтому сон
внутри `synchronized` блокирует всех остальных на всё время. `wait()`, наоборот,
освобождает монитор объекта, на котором вызван, — и только его. Вызывать `wait()`,
`notify()` и `notifyAll()` можно лишь владея этим монитором, а условие вокруг
`wait()` проверяют в цикле `while`: возможно ложное пробуждение, и условие может
измениться между сигналом и повторным захватом монитора. Ни `notify()`, ни
`notifyAll()` монитор не освобождают, поэтому разбуженные потоки сразу переходят в
`BLOCKED`.

Прерывание — кооперативный запрос, а не принудительная остановка. `interrupt()`
устанавливает флаг, и поток должен либо сам его проверять, либо находиться в
прерываемой операции. При выбрасывании `InterruptedException` флаг сбрасывается,
поэтому пустой блок `catch` теряет сигнал; если исключение нельзя пробросить, флаг
восстанавливают вручную.

`join()` ожидает завершения другого потока и после успешного ожидания даёт
видимость всех его действий без дополнительной синхронизации. Вариант с таймаутом
такой гарантии не даёт, потому что мог вернуться просто по истечении времени.

Из классических проблем: взаимоблокировка — это цикл взаимного ожидания ресурсов,
и лечится он единым порядком захвата мониторов во всём коде. Активная блокировка —
потоки работают, но не продвигаются. Голодание — система работает, но конкретный
поток систематически не получает ресурс.

## Вопросы на собеседовании

### 1. Чем роль Thread отличается от роли Runnable?

**Ответ:** `Thread` — это сам поток выполнения, механизм. `Runnable` — задача,
которую нужно выполнить. Разделение позволяет передавать одну задачу разным
исполнителям, поэтому реализуют обычно `Runnable`, а не наследуют `Thread`.

### 2. Что JVM делает после успешного Thread.start()?

**Ответ:** создаёт новый поток операционной системы и вызывает в нём метод
`run()`. Вызывающий поток продолжает работу, не дожидаясь завершения.

### 3. Чем прямой вызов thread.run() отличается от thread.start()?

**Ответ:** `run()` — обычный вызов метода в текущем потоке, новый поток не
создаётся. Параллелизма нет, а ошибка выглядит как работающий, но однопоточный
код.

### 4. Что выведет имя текущего потока при вызове run() вместо start()?

**Ответ:** имя вызывающего потока, обычно `main`. Это простой способ обнаружить
такую ошибку.

### 5. Какие значения входят в Thread.State?

**Ответ:** `NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`,
`TERMINATED`.

### 6. В каком состоянии находится созданный, но ещё не запущенный Thread?

**Ответ:** в `NEW`. Объект существует, поток операционной системы ещё не создан.

### 7. Почему в Thread.State нет отдельного состояния RUNNING?

**Ответ:** JVM не различает готовность к выполнению и фактическое исполнение на
процессоре — это решает планировщик операционной системы. Оба случая объединены в
`RUNNABLE`.

### 8. Какие два случая объединяет состояние RUNNABLE?

**Ответ:** поток выполняется на процессоре и поток готов выполняться, но ожидает
своей очереди. Сюда же попадает ожидание завершения операции ввода-вывода.

### 9. Что именно должен ожидать поток, чтобы его состояние называлось BLOCKED?

**Ответ:** только освобождение монитора при входе в `synchronized`. Любое другое
ожидание таким состоянием не является — это частая ошибка в ответах.

### 10. Чем BLOCKED отличается от WAITING?

**Ответ:** `BLOCKED` — ожидание монитора, поток вернётся в работу автоматически
при его освобождении. `WAITING` — добровольное ожидание события, из него выводит
только явное уведомление или завершение ожидаемого потока.

### 11. Какие вызовы могут перевести поток в WAITING?

**Ответ:** `Object.wait()` без таймаута, `Thread.join()` без таймаута,
`LockSupport.park()`.

### 12. Какие вызовы могут перевести поток в TIMED_WAITING?

**Ответ:** те же вызовы с таймаутом, а также `Thread.sleep()`.

### 13. В каком состоянии находится поток во время Thread.sleep(1000)?

**Ответ:** в `TIMED_WAITING`.

### 14. Когда поток переходит в TERMINATED и можно ли повторить start()?

**Ответ:** после завершения `run()` — нормального или из-за исключения. Повторный
запуск невозможен: объект `Thread` одноразовый.

### 15. Какое исключение возникает при повторном вызове start()?

**Ответ:** `IllegalThreadStateException`.

### 16. Почему следующий код не освобождает lock на время сна?

```java
synchronized (lock) {
    Thread.sleep(1000);
}
```

**Ответ:** `sleep()` приостанавливает поток, но не освобождает мониторы, которыми
он владеет. Остальные потоки будут ждать всю секунду. Освобождает монитор только
`wait()`.

### 17. Гарантирует ли окончание sleep() немедленное выполнение на CPU?

**Ответ:** нет. Поток переходит в `RUNNABLE` и встаёт в очередь планировщика.
Указанное время — минимальная задержка, а не точная.

### 18. Что делает worker.join() с вызвавшим его потоком?

**Ответ:** переводит его в ожидание до завершения потока `worker`.

### 19. Чем состояние при join() отличается от состояния при join(1000)?

**Ответ:** без таймаута это `WAITING`, с таймаутом — `TIMED_WAITING`.

### 20. Почему после успешного join() следующий код гарантированно печатает 42?

```java
int[] result = new int[1];
Thread worker = new Thread(() -> result[0] = 42);
worker.start();
worker.join();
System.out.println(result[0]);
```

**Ответ:** действует правило happens-before: все действия завершившегося потока
предшествуют успешному возврату из `join()`. Поэтому запись видна без `volatile` и
синхронизации.

### 21. Почему возврат join(1000) не всегда доказывает завершение worker?

**Ответ:** метод возвращает управление и по истечении таймаута, независимо от
того, завершился ли поток. Проверять нужно через `isAlive()`, иначе гарантии
видимости тоже не будет.

### 22. Почему thread.interrupt() обычно не уничтожает поток немедленно?

**Ответ:** это не остановка, а установка флага-запроса. Поток сам решает, как
реагировать. Если код не проверяет флаг и не вызывает прерываемых методов,
выполнение продолжится.

### 23. Чем isInterrupted() отличается от Thread.interrupted()?

**Ответ:** первый только читает флаг, второй читает и сбрасывает его. Случайный
вызов статического метода приводит к потере признака прерывания.

### 24. Что происходит с флагом прерывания при InterruptedException из sleep()?

**Ответ:** он сбрасывается. Именно поэтому при перехвате исключения его часто
восстанавливают вручную.

### 25. Почему пустой catch (InterruptedException e) проглатывает прерывание?

**Ответ:** исключение перехвачено, флаг уже сброшен, и вышестоящий код не узнает о
запросе на завершение. Поток продолжит работу, хотя его просили остановиться.

### 26. Зачем вызывают Thread.currentThread().interrupt() перед return?

**Ответ:** чтобы восстановить сброшенный флаг и передать признак прерывания
вызывающему коду, который сможет корректно завершить работу.

### 27. Какой монитор использует instance synchronized method, а какой — static?

**Ответ:** метод экземпляра синхронизируется на самом объекте, статический — на
объекте `Class` данного класса. Это разные мониторы, и они не блокируют друг
друга.

### 28. В какое состояние попадёт второй поток при входе в занятый synchronized?

**Ответ:** в `BLOCKED` — единственный случай, когда используется это состояние.

### 29. Почему lock.wait() требует владения монитором и что произойдёт без него?

**Ответ:** метод освобождает монитор, а освободить можно только то, чем владеешь.
Без владения будет `IllegalMonitorStateException`.

### 30. Какой монитор освобождает wait(), если поток владеет несколькими?

**Ответ:** только тот, на котором вызван. Остальные остаются захваченными — частая
причина взаимоблокировки.

### 31. Чем sleep() отличается от wait()?

**Ответ:** `sleep()` — статический метод `Thread` для паузы на время, монитор не
освобождается, пробуждение по таймеру. `wait()` — метод `Object` для ожидания
условия, монитор освобождается, пробуждение по уведомлению. Первый не требует
синхронизации, второй требует владения монитором.

### 32. Чем notify() отличается от notifyAll() и почему они не освобождают монитор?

**Ответ:** `notify()` будит один произвольный ожидающий поток, `notifyAll()` — все.
Ни тот ни другой не освобождают монитор: он отпускается только при выходе из
синхронизированного блока. Поэтому разбуженные потоки сразу переходят в `BLOCKED`
и ждут освобождения.

### 33. Почему после следующего кода пробуждённый поток не продолжит работу немедленно?

```java
synchronized (lock) {
    condition = true;
    lock.notifyAll();
    doMoreWork();
}
```

**Ответ:** монитор остаётся у уведомляющего потока до конца блока, включая
`doMoreWork()`. Разбуженные потоки ожидают его освобождения в состоянии `BLOCKED`.

### 34. Какие две причины требуют while, а не if, вокруг wait()?

**Ответ:** во-первых, возможны ложные пробуждения без уведомления. Во-вторых,
между пробуждением и фактическим захватом монитора условие мог изменить другой
поток. Проверка в цикле покрывает оба случая.

### 35. Чем deadlock, livelock и starvation отличаются друг от друга?

**Ответ:** при взаимоблокировке потоки бездействуют, ожидая ресурсы друг друга, и
цикл ожидания не разрывается сам. При активной блокировке потоки работают, но
взаимно уступают и не продвигаются. При голодании поток работоспособен, но
систематически не получает ресурс.

### 36. Почему единый порядок захвата мониторов устраняет deadlock?

**Ответ:** он делает невозможным замкнутый цикл ожидания: поток не может
удерживать второй ресурс, ожидая первый, если брать их разрешено только в одной
последовательности. Это объяснение через ресурсы, а не через happens-before.
