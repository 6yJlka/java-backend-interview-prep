# Базовая многопоточность в Java — Part 1

## Thread и Runnable

Базовая модель запуска работы в отдельном потоке состоит из двух сущностей:

- `Thread` представляет поток выполнения;
- `Runnable` представляет задачу, которую нужно выполнить.

```java
Runnable task = () -> {
    System.out.println("Work");
};

Thread thread = new Thread(task);
thread.start();
```

`Runnable` содержит единственный абстрактный метод `run()`, поэтому задачу удобно
описывать lambda-выражением. Объект `Thread` получает эту задачу, а успешный вызов
`start()` запускает новый поток выполнения. Затем JVM вызывает `run()` в этом
новом потоке.

```text
создать Runnable
→ передать его в Thread
→ вызвать start()
→ JVM запускает новый поток
→ новый поток выполняет run()
```

Разделение роли потока и роли задачи полезно даже в самом простом коде:

```text
Thread   → где и независимо от какого caller выполняется работа
Runnable → какая работа выполняется
```

### start() и run()

Эти два вызова имеют принципиально разную семантику:

```java
thread.start();
```

`start()` просит JVM запустить новый поток выполнения. После успешного запуска
новый поток вызывает `run()`, а вызвавший `start()` поток может продолжить работу
конкурентно с ним.

```java
thread.run();
```

Прямой вызов `run()` — обычный вызов метода. Новый поток не создаётся: тело
`run()` синхронно выполняется текущим потоком, как тело любого другого метода.

```java
Runnable task = () -> System.out.println(
        "Task: " + Thread.currentThread().getName()
);

Thread thread = new Thread(task, "worker");

System.out.println("Caller: " + Thread.currentThread().getName());
thread.start();
```

Типичный результат при запуске из main-потока:

```text
Caller: main
Task: worker
```

Если заменить `thread.start()` на `thread.run()`, задача будет выполнена
main-потоком:

```text
Caller: main
Task: main
```

Порядок вывода разных потоков в общем случае не следует считать
детерминированным: решение о том, какой готовый поток получит процессор, принимает
планировщик.

## Состояния Thread

Метод `thread.getState()` возвращает одно из значений `Thread.State`:

| Состояние | Смысл |
|---|---|
| `NEW` | объект `Thread` создан, но `start()` ещё не вызван |
| `RUNNABLE` | поток выполняется либо готов выполняться и ожидает процессор |
| `BLOCKED` | поток ждёт захвата занятого intrinsic monitor |
| `WAITING` | поток ожидает определённого события без таймаута |
| `TIMED_WAITING` | поток ожидает события или истечения времени с таймаутом |
| `TERMINATED` | выполнение `run()` завершилось |

Состояние — моментальный снимок. Оно может измениться сразу после вызова
`getState()`, поэтому результат обычно используют для диагностики, а не для
построения логики синхронизации.

### NEW

После конструктора объект `Thread` существует, но отдельный поток выполнения ещё
не запущен:

```java
Thread worker = new Thread(() -> doWork());

System.out.println(worker.getState()); // NEW
```

Вызов `run()` напрямую не является запуском этого объекта `Thread`: его состояние
из-за обычного вызова метода не проходит нормальный жизненный цикл запущенного
потока.

### RUNNABLE

После успешного `start()` поток обычно переходит в `RUNNABLE`. В Java это
состояние объединяет два случая:

- поток прямо сейчас исполняет инструкции на CPU;
- поток готов исполняться, но ждёт, пока планировщик выделит ему CPU.

Отдельного состояния `RUNNING` в `Thread.State` нет.

```text
выполняется на CPU ┐
                  ├→ RUNNABLE
готов получить CPU┘
```

Следовательно, `getState() == RUNNABLE` не доказывает, что поток выполняет
инструкцию именно в момент проверки.

### BLOCKED

`BLOCKED` имеет узкий смысл: поток пытается получить intrinsic monitor для входа
в `synchronized`, но этот монитор удерживает другой поток.

```java
synchronized (lock) {
    doWork();
}
```

Если первый поток уже находится в этом блоке, второй поток, пытающийся войти в
`synchronized (lock)`, становится `BLOCKED` до освобождения монитора.

`BLOCKED` не означает произвольное «ожидание чего-либо». Например, спящий поток и
поток, вызвавший `wait()`, находятся в других состояниях.

### WAITING

`WAITING` означает ожидание без заданного таймаута. Поток не продолжит работу,
пока не произойдёт соответствующее событие.

Примеры:

```java
lock.wait();
thread.join();
```

В первом случае требуется пробуждение и последующий повторный захват монитора. Во
втором текущий поток ожидает завершения `thread`.

### TIMED_WAITING

`TIMED_WAITING` означает ожидание с ограничением по времени:

```java
Thread.sleep(1000);
thread.join(1000);
lock.wait(1000);
```

Продолжение становится возможным после нужного события, прерывания либо истечения
указанного времени — в зависимости от операции.

### TERMINATED

Поток становится `TERMINATED`, когда его метод `run()` завершился нормально либо
из-за необработанного исключения.

Один объект `Thread` нельзя запустить второй раз:

```java
Thread worker = new Thread(() -> doWork());

worker.start();
worker.join();
worker.start(); // IllegalThreadStateException
```

Для новой попытки выполнения нужно создать новый объект `Thread`. Повторный
`start()` недопустим как после завершения, так и пока поток уже запущен.

### Схема переходов

Упрощённая схема жизненного цикла:

```text
NEW
  │ start()
  ▼
RUNNABLE ◄────────────────────────────────────────────┐
  │                                                  │
  ├─ попытка войти в занятый synchronized ─→ BLOCKED ┤ monitor получен
  │                                                  │
  ├─ wait() / join() без таймаута ─────────→ WAITING ┤ событие + готовность продолжить
  │                                                  │
  ├─ sleep(t) / wait(t) / join(t) ─────→ TIMED_WAITING
  │                                      │           │
  │                                      └───────────┘ событие или таймаут
  │
  └─ run() завершился ─────────────────────→ TERMINATED
```

После пробуждения из `wait()` поток должен снова захватить монитор. Если монитор
занят, поток будет `BLOCKED`, а не сразу продолжит выполнение защищённого кода.
Схема упрощена: реальный момент перехода зависит от операции, владения монитором
и планирования JVM и ОС.

## BLOCKED, WAITING и TIMED_WAITING

Главное различие удобно запомнить так:

```text
BLOCKED
→ ждёт захвата intrinsic monitor

WAITING
→ ждёт события без таймаута

TIMED_WAITING
→ ждёт события или времени с таймаутом
```

| Состояние | Чего ждёт поток | Типичный пример | Как продолжится |
|---|---|---|---|
| `BLOCKED` | освобождения занятого intrinsic monitor | вход в `synchronized (lock)` | после получения монитора |
| `WAITING` | события без ограничения времени | `lock.wait()`, `worker.join()` | после события и выполнения условий операции |
| `TIMED_WAITING` | события или окончания времени | `sleep(1000)`, `wait(1000)`, `join(1000)` | после события, таймаута либо прерывания |

Пример разных причин ожидания:

```java
synchronized (lock) {
    lock.wait();       // WAITING, монитор lock освобождён
}

Thread.sleep(1000);   // TIMED_WAITING

synchronized (lock) { // BLOCKED, если lock удерживает другой поток
    doWork();
}
```

`sleep()` не переводит поток в `WAITING`. Вызов с положительной длительностью
переводит его в `TIMED_WAITING`.

## Thread.sleep()

```java
Thread.sleep(1000);
```

`sleep()` приостанавливает текущий поток, то есть тот, который вызвал статический
метод. В течение указанного времени поток находится в `TIMED_WAITING`. После
таймаута он снова становится готовым к выполнению, но это не гарантирует
немедленного получения CPU.

```text
RUNNABLE
→ sleep(1000)
→ TIMED_WAITING
→ прошёл таймаут
→ RUNNABLE
→ планировщик когда-нибудь выделяет CPU
```

Указанное время — минимальная задержка до готовности продолжить, а не обещание
возобновить выполнение ровно через заданное число миллисекунд.

Самое важное monitor-правило:

> `sleep()` не освобождает ни один монитор, которым владеет поток.

```java
synchronized (lock) {
    Thread.sleep(5000);
}
```

Во время сна поток продолжает владеть монитором `lock`. Другой поток, пытающийся
войти в тот же блок:

```java
synchronized (lock) {
    doOtherWork();
}
```

будет `BLOCKED`, пока первый поток не выйдет из `synchronized` и не освободит
монитор. Само истечение времени `sleep()` монитор не освобождает: освобождение
произойдёт при выходе из защищённого блока, в том числе при раскрутке стека из-за
исключения.

`sleep()` не является механизмом ожидания результата другого потока и не создаёт
между потоками happens-before связь. Если требуется дождаться завершения потока,
используется `join()`.

## Thread.join()

```java
worker.start();
worker.join();
```

`join()` вызывается текущим потоком на объекте другого потока. Смысл вызова:
текущий поток ждёт завершения `worker`.

```text
main: worker.start()
main: worker.join() ────── ждёт

worker: выполняет run()
worker: завершает run()

main: join() возвращается
main: продолжает работу
```

Для обычного `join()` ожидающий живой поток может находиться в `WAITING`. Вариант
с таймаутом:

```java
worker.join(1000);
```

может перевести ожидающий поток в `TIMED_WAITING`. Возврат timed `join()` сам по
себе не доказывает завершение worker: таймаут мог истечь раньше.

`join()` также связан с Java Memory Model: все действия завершившегося worker
happen-before обнаружению его завершения через успешно завершившее ожидание
`join()`.

```java
int[] result = new int[1];

Thread worker = new Thread(() -> result[0] = 42);

worker.start();
worker.join();

System.out.println(result[0]);
```

Цепочка рассуждения:

```text
worker записывает result[0] = 42
→ worker завершается
→ join() успешно возвращается после завершения worker
→ main читает result[0]
```

Поэтому после такого `join()` main гарантированно увидит `42`, хотя элемент
массива не объявлен `volatile`. Нужную гарантию видимости уже создаёт завершение
worker и успешное ожидание через `join()`. Если ожидание было прервано или timed
`join()` вернулся только из-за таймаута, эту цепочку нельзя считать доказанной.

## Interrupt

Interruption — кооперативный механизм запроса на прерывание работы потока:

```java
thread.interrupt();
```

Обычно этот вызов не означает «немедленно уничтожить поток». Поток должен
отреагировать на запрос сам: проверить interrupt status либо находиться в
операции, которая умеет завершать ожидание через `InterruptedException`.

Если поток не находится в такой блокирующей операции, `interrupt()` обычно
устанавливает его interrupt status. Проверить флаг без сброса можно так:

```java
boolean interrupted = Thread.currentThread().isInterrupted();
```

Классический вариант cooperative cancellation:

```java
while (!Thread.currentThread().isInterrupted()) {
    doWork();
}
```

```text
другой поток вызывает interrupt()
→ у worker появляется запрос на прерывание
→ worker замечает status
→ worker корректно завершает цикл и освобождает свои ресурсы
```

Это протокол сотрудничества. Если код никогда не проверяет status, не вызывает
interruptible operations и не завершает работу по другой причине, один вызов
`interrupt()` не обязан его остановить.

Нужно различать два способа проверки:

| Вызов | Что проверяет | Сбрасывает status? |
|---|---|---|
| `thread.isInterrupted()` | status указанного потока | нет |
| `Thread.interrupted()` | status текущего потока | да |

Случайный вызов `Thread.interrupted()` может потерять сигнал для следующего уровня
кода, поэтому сбрасывающую семантику нужно учитывать явно.

## InterruptedException

К interruptible blocking operations относятся:

- `Thread.sleep()`;
- `Object.wait()`;
- `Thread.join()`.

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    // выбрать корректную реакцию на запрос
}
```

Если спящий поток прервали, `sleep()` завершается раньше и выбрасывает
`InterruptedException`. При выбрасывании этого исключения interrupt status
очищается. Аналогичная базовая модель действует для `wait()` и `join()`.

Пустой обработчик — типичная ошибка:

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
}
```

Такой код «проглатывает interruption»:

- блокирующая операция уже завершилась досрочно;
- status был сброшен при выбрасывании исключения;
- обработчик не завершил работу и не восстановил status;
- вышестоящий код больше не видит запрос на прерывание.

Если метод не может пробросить `InterruptedException`, распространённый вариант —
восстановить status и завершить текущую работу:

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

Повторный `interrupt()` здесь не повторяет исключение. Он восстанавливает флаг,
чтобы вышестоящий код мог узнать о запросе на прерывание.

Если контракт метода допускает `throws InterruptedException`, часто лучше не
перехватывать исключение без необходимости, а позволить вызывающему уровню
выбрать политику остановки. Конкретная реакция зависит от контракта: завершить
операцию, пробросить исключение или восстановить status. Универсально опасно
только молча потерять сигнал.

## synchronized и monitor

Каждый Java-объект может использоваться как intrinsic monitor:

```java
synchronized (lock) {
    // критическая секция
}
```

Перед входом поток должен захватить монитор `lock`. Одновременно владеть данным
монитором может только один поток. Если монитор уже принадлежит другому потоку,
претендент становится `BLOCKED`.

```text
Thread 1: захватил monitor lock
Thread 1: выполняет критическую секцию

Thread 2: пытается захватить тот же monitor
Thread 2: BLOCKED

Thread 1: выходит из synchronized и освобождает monitor
Thread 2: получает возможность захватить monitor
```

Выход из `synchronized` освобождает монитор. Это происходит и при обычном выходе,
и при выходе из блока из-за исключения.

Важно синхронизироваться именно на одном и том же объекте. Два блока на разных
объектах используют разные мониторы и не обеспечивают взаимного исключения друг с
другом.

Синхронизированные методы используют неявно выбранный монитор:

```java
public synchronized void update() {
    // monitor: this
}

public static synchronized void reset() {
    // monitor: CurrentClass.class
}
```

- instance `synchronized` method использует монитор `this`;
- static `synchronized` method использует монитор объекта `Class`, например
  `CurrentClass.class`.

Монитор экземпляра и монитор объекта его класса — разные мониторы. Поэтому
instance synchronized method и static synchronized method сами по себе не
блокируют друг друга.

`synchronized` также предоставляет гарантии видимости и порядка, разобранные в
конспекте по JMM. Здесь ключевой поведенческий аспект — взаимное исключение и
переход конкурирующего потока в `BLOCKED` при занятом мониторе.

## wait()

`wait()` используется для ожидания изменения общего состояния, защищённого
монитором:

```java
synchronized (lock) {
    lock.wait();
}
```

Самое важное отличие от `sleep()`:

> `wait()` освобождает монитор объекта, на котором вызван.

Последовательность выглядит так:

```text
поток владеет monitor lock
→ вызывает lock.wait()
→ освобождает monitor lock
→ переходит в WAITING
→ получает сигнал, interruption или иное допустимое пробуждение
→ снова пытается получить monitor lock
→ после успешного захвата продолжает работу после wait()
```

Для `wait(timeout)` ожидание ограничено временем, поэтому поток находится в
`TIMED_WAITING`:

```java
synchronized (lock) {
    lock.wait(1000);
}
```

Вызвать `wait()` можно только владея монитором именно того объекта, у которого
вызывается метод:

```java
synchronized (lock) {
    lock.wait(); // корректно: текущий поток владеет monitor lock
}
```

Некорректно:

```java
lock.wait(); // IllegalMonitorStateException
```

Недостаточно владеть каким-то другим монитором:

```java
synchronized (otherLock) {
    lock.wait(); // IllegalMonitorStateException
}
```

`wait()` освобождает только монитор объекта, на котором он вызван. Если поток
владеет и другими мониторами, они автоматически не освобождаются. Перед возвратом
из `wait()` поток должен снова захватить освобождённый монитор; это верно и при
выходе через `InterruptedException`.

## sleep() и wait()

Главная формула:

```text
sleep()
→ TIMED_WAITING
→ monitor НЕ освобождает

wait()
→ WAITING или TIMED_WAITING
→ monitor освобождает
```

| Свойство | `Thread.sleep()` | `Object.wait()` |
|---|---|---|
| Где объявлен | `Thread` | `Object` |
| На кого действует | на текущий поток | на текущий поток, ожидающий на monitor данного объекта |
| Назначение | временно приостановить выполнение | координировать потоки через условие под monitor |
| Типичное состояние | `TIMED_WAITING` | `WAITING` или `TIMED_WAITING` |
| Освобождает monitor | нет | да, monitor объекта вызова |
| Требует владения monitor | нет | да |
| Может завершиться через `InterruptedException` | да | да |

`sleep()` можно вызвать внутри `synchronized`, но монитор останется у спящего
потока. `wait()` имеет смысл именно внутри синхронизированного протокола:
проверить условие, освободить монитор на время ожидания, после пробуждения снова
получить монитор и повторно проверить условие.

## notify() и notifyAll()

Ожидающие через `wait()` потоки пробуждаются с помощью методов того же объекта:

```java
synchronized (lock) {
    lock.notify();
}
```

```java
synchronized (lock) {
    lock.notifyAll();
}
```

`notify()` выбирает один поток из wait set данного монитора. Нельзя полагаться на
то, какой именно поток будет выбран.

`notifyAll()` пробуждает все потоки, ожидающие на этом мониторе. Но они не могут
все одновременно войти в защищённую секцию: каждый должен конкурировать за тот же
монитор и повторно проверить своё условие.

Ключевое правило:

> `notify()` и `notifyAll()` не освобождают монитор.

Вызывающий поток продолжает владеть монитором до выхода из `synchronized` либо до
другого действия, которое освобождает его. Поэтому пробуждение не означает
немедленного продолжения ожидающего потока:

```text
producer владеет monitor lock
→ меняет общее состояние
→ вызывает lock.notifyAll()
→ всё ещё владеет monitor lock
→ выходит из synchronized
→ освобождает monitor lock
→ пробуждённые потоки конкурируют за monitor
→ один успешно захватывает monitor и проверяет условие
```

Как и `wait()`, оба метода требуют владения монитором объекта вызова. Иначе
выбрасывается `IllegalMonitorStateException`:

```java
lock.notify();    // ошибка без владения monitor lock
lock.notifyAll(); // ошибка без владения monitor lock
```

## Почему wait() вызывают в while, а не в if

Классический guard-паттерн:

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }

    // работа, для которой condition должна быть true
}
```

`while` нужен потому, что возврат из `wait()` не является гарантией истинности
условия. Есть как минимум две причины проверить его снова.

### Spurious wakeup

Допускается spurious wakeup: поток может выйти из ожидания без ожидаемого
изменения условия. Код должен быть корректен даже после такого пробуждения.

```text
wait() вернулся
≠
condition гарантированно true
```

### Condition changed again

После сигнала поток не получает монитор мгновенно. Пока он конкурирует за
монитор, другой поток может захватить его раньше и снова изменить общее состояние.

Пример с очередью и несколькими consumers:

```java
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();
    }

    queue.remove();
}
```

Возможный сценарий:

```text
очередь пуста
→ Consumer 1 и Consumer 2 ждут
→ producer добавляет один элемент и пробуждает consumers
→ Consumer 1 первым получает monitor и забирает элемент
→ Consumer 1 освобождает monitor
→ Consumer 2 получает monitor, но очередь снова пуста
```

С `if` Consumer 2 пошёл бы дальше с ложным предположением и попытался удалить
несуществующий элемент. `while` отправит его ждать снова.

Правило координации:

> `notify()` означает «состояние могло измениться», а не «нужное условие
> гарантированно выполнено».

Условие читают и изменяют под тем же монитором, а после каждого возврата из
`wait()` проверяют заново.

## Deadlock

Deadlock — состояние взаимного ожидания, при котором участвующие потоки не могут
продолжить выполнение.

Классический пример — разный порядок захвата двух мониторов:

```text
Thread 1:
lockA → lockB

Thread 2:
lockB → lockA
```

Возможное выполнение:

```text
T1 захватил A
T2 захватил B
T1 пытается захватить B → BLOCKED
T2 пытается захватить A → BLOCKED

T1 держит A и ждёт B
T2 держит B и ждёт A
```

Никто не может продолжить и освободить уже удерживаемый монитор. Образовался цикл
ожидания ресурсов:

```text
T1 → ждёт ресурс T2
T2 → ждёт ресурс T1
```

Deadlock не обязан завершать JVM или выбрасывать исключение. Приложение может
просто перестать продвигаться в затронутой части.

## Предотвращение deadlock

Главный способ для нескольких совместно используемых мониторов — установить
единый глобальный порядок их захвата и соблюдать его во всём коде.

Вместо противоположных порядков:

```text
Thread 1: A → B
Thread 2: B → A
```

оба потока используют один порядок:

```text
Thread 1: A → B
Thread 2: A → B
```

Если `A` занят, второй поток ждёт `A`, ещё не удерживая `B`. Он не может создать
ситуацию «держит `B`, ожидая `A`».

```text
запрещено брать B раньше A
→ невозможно одновременно получить:
  T1 держит A и ждёт B
  T2 держит B и ждёт A
→ цикл ожидания не формируется
```

Причина предотвращения deadlock здесь — устранение возможности циклического
ожидания ресурсов. Это не объяснение через happens-before.

Практически порядок должен определяться стабильным правилом и соблюдаться во всех
местах, где захватываются несколько мониторов. Локальная договорённость в одном
методе не поможет, если другой код берёт те же мониторы в обратном порядке.

Дополнительно полезно сокращать время владения монитором и не выполнять внутри
критической секции долгие или неизвестные внешние вызовы, но это само по себе не
заменяет единый порядок захвата.

## Livelock

Livelock — ситуация, когда потоки не заблокированы и продолжают изменять
состояние, но полезного прогресса нет.

Пример: два потока видят конфликт, оба уступают ресурс друг другу и сразу
повторяют попытку. Если их реакции постоянно синхронны, они бесконечно остаются
активными, но ни один не завершает полезную операцию.

```text
Thread 1: вижу Thread 2 → уступаю → повторяю
Thread 2: вижу Thread 1 → уступаю → повторяю
```

Главное различие:

```text
deadlock
→ потоки не двигаются

livelock
→ потоки двигаются, но не продвигаются
```

## Starvation

Starvation — ситуация, когда система в целом работает, но конкретный поток очень
долго не получает необходимый ресурс или возможность выполнения.

Например, после каждого освобождения монитора другие потоки постоянно успевают
захватить его раньше одного и того же потока. Остальные операции завершаются, но
этот поток не продвигается.

```text
monitor освобождён
→ его получает T2
→ затем T3
→ затем снова T2
→ T1 продолжает ждать
```

Starvation не означает взаимного циклического ожидания. В отличие от deadlock,
система и другие потоки могут продолжать полезную работу.

## Deadlock, livelock и starvation

| Проблема | Потоки активны? | Система делает прогресс? | Конкретный поток делает прогресс? | Основная причина |
|---|---|---|---|---|
| Deadlock | участвующие потоки заблокированы | в затронутой цепочке — нет | нет | цикл взаимного ожидания ресурсов |
| Livelock | да | полезного прогресса в затронутой работе нет | нет | потоки постоянно реагируют друг на друга и повторяют действия |
| Starvation | другие потоки могут быть активны | обычно да | один поток очень долго — нет | несправедливое или постоянное получение ресурса другими потоками |

```text
deadlock   → ждут друг друга и стоят
livelock   → действуют, но результат не приближается
starvation → другие продвигаются, один поток остаётся без ресурса
```

## Типичные ошибки на собеседовании

### Считать, что run() создаёт новый поток

Прямой вызов `run()` выполняет обычный метод в текущем потоке. Новый поток
запускает `start()`.

### Добавлять отдельный RUNNING в Thread.State

В `Thread.State` нет `RUNNING`. Состояние `RUNNABLE` включает и фактическое
выполнение на CPU, и готовность получить CPU.

### Определять BLOCKED как любое ожидание

`BLOCKED` означает ожидание захвата занятого intrinsic monitor. Ожидание в
`wait()`, `join()` или `sleep()` представлено другими состояниями.

### Считать, что sleep() освобождает монитор

`sleep()` временно приостанавливает текущий поток, но оставляет за ним все
удерживаемые мониторы.

### Считать, что notify() освобождает монитор

`notify()` только выбирает ожидающий поток для пробуждения. Вызывающий поток
владеет монитором до выхода из `synchronized` либо другого освобождающего
действия.

### Ожидать немедленного продолжения после notify()

Пробуждённый поток должен снова получить монитор. До этого вызывающий поток или
другой конкурент может продолжать работу.

### Вызывать wait() вне synchronized

Текущий поток должен владеть монитором объекта вызова. Иначе `wait()` выбрасывает
`IllegalMonitorStateException`.

### Всегда использовать if вокруг wait()

После spurious wakeup или изменения условия другим потоком предположение может
быть ложным. Условие проверяют в цикле `while`.

### Считать, что interrupt() насильно уничтожает поток

Interruption — запрос. Поток завершает работу кооперативно, если его код корректно
обрабатывает status или `InterruptedException`.

### Считать пустой catch InterruptedException безопасным

При выбрасывании исключения status сбрасывается. Пустой `catch` теряет сигнал и
лишает вызывающий код возможности отреагировать.

### Считать deadlock и starvation одним явлением

При deadlock существует взаимное ожидание и цикл ресурсов. При starvation система
может работать, но один поток очень долго не получает ресурс.

### Объяснять lock ordering через happens-before

Единый порядок предотвращает рассматриваемый deadlock потому, что не позволяет
сформировать цикл ожидания ресурсов. Happens-before описывает гарантии наблюдения
и порядка действий JMM, а не является причиной устранения этого цикла.

## Как кратко объяснить базовый Multithreading на собеседовании

`Thread` представляет поток выполнения, а `Runnable` — выполняемую задачу.
`start()` запускает новый поток, после чего JVM вызывает в нём `run()`, тогда как
прямой `run()` остаётся обычным вызовом в текущем потоке. `Thread.State` содержит
`NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING` и `TERMINATED`, причём
отдельного `RUNNING` нет. `synchronized` захватывает intrinsic monitor, и
конкурент за занятый монитор становится `BLOCKED`. `sleep()` переводит текущий
поток в `TIMED_WAITING` и не освобождает монитор, а `wait()` освобождает монитор и
ожидает сигнал без таймаута или с таймаутом. `wait()`, `notify()` и `notifyAll()`
вызывают с владением тем же монитором, а условие вокруг `wait()` проверяют в
`while`. `notify()` пробуждает один неопределённый поток, `notifyAll()` — всех
ожидающих, но продолжить они смогут только после повторного захвата монитора.
Interruption — кооперативный запрос на остановку, который обрабатывают через
interrupt status или `InterruptedException`, не проглатывая сигнал. `join()`
ожидает завершения потока и после успешного ожидания даёт видимость его действий.
Deadlock означает взаимную блокировку, livelock — активность без полезного
прогресса, а starvation — длительное отсутствие ресурса у конкретного потока.
