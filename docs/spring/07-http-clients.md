# HTTP-клиенты в Spring

## Зачем отдельная тема

Устойчивость к отказам — таймауты, повторы, размыкатель цепи — разобрана на уровне
принципов в конспекте по архитектуре. Здесь то же самое на уровне кода: чем именно
вызвать соседний сервис и как не получить при этом исчерпание пула потоков.

Вопрос «вы вызывали внешние сервисы, чем и с какими таймаутами» на собеседовании
задают почти всегда, и он хорошо отличает прочитанное от сделанного.

---

## Четыре варианта

```text
RestTemplate → синхронный, исторический, в поддержке, но новых возможностей не получит
RestClient   → синхронный, Spring 6.1, текущий выбор по умолчанию
WebClient    → реактивный, умеет и блокирующий вызов, нужен при стриминге и высокой параллельности
@HttpExchange / Feign → декларативный клиент: интерфейс вместо кода запроса
```

Практическое правило: в новом коде на Spring 6.1 и новее — `RestClient`; в проекте
постарше — `RestTemplate`, менять его без причины не нужно; `WebClient` — когда
нужен реактивный стек или потоковый ответ; декларативный клиент — когда вызовов к
одному сервису много и хочется видеть их как интерфейс.

### RestTemplate

```java
ResponseEntity<OrderDto> response = restTemplate.getForEntity(
        "/api/orders/{id}", OrderDto.class, id);
```

Важно: `RestTemplate` потокобезопасен после настройки, поэтому создаётся один раз
как бин, а не в каждом вызове. Создание клиента на каждый запрос — типовая причина
исчерпания сокетов.

### RestClient

```java
@Bean
public RestClient orderClient(RestClient.Builder builder) {
    return builder
            .baseUrl("https://orders.internal")
            .requestFactory(requestFactory())
            .build();
}
```

```java
OrderDto order = orderClient.get()
        .uri("/api/orders/{id}", id)
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError,
                  (req, res) -> { throw new OrderNotFoundException(id); })
        .body(OrderDto.class);
```

Тот же транспорт, что у `RestTemplate`, но текучий интерфейс в стиле `WebClient`.

### WebClient

```java
Mono<OrderDto> order = webClient.get()
        .uri("/api/orders/{id}", id)
        .retrieve()
        .bodyToMono(OrderDto.class);
```

```java
OrderDto result = order.block();   // допустимо, но осознанно
```

`block()` в обычном сервлетном приложении работает, однако смысл реактивного
клиента при этом теряется. Вызывать `block()` внутри реактивной цепочки нельзя —
это заблокирует поток event loop, которых всего по числу ядер.

### Декларативный клиент

```java
@HttpExchange("/api/orders")
public interface OrderClient {

    @GetExchange("/{id}")
    OrderDto findById(@PathVariable Long id);

    @PostExchange
    OrderDto create(@RequestBody CreateOrderRequest request);
}
```

```java
@Bean
public OrderClient orderClient(RestClient restClient) {
    return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(restClient))
            .build()
            .createClient(OrderClient.class);
}
```

Встроено в Spring 6 и не требует Spring Cloud. Feign даёт то же самое, но тянет
отдельную зависимость; в новых проектах смысла в нём мало.

## Таймауты

Самая важная часть темы.

```text
connect timeout  → сколько ждём установления соединения
read timeout     → сколько ждём данных между пакетами
общий бюджет     → сколько вообще может длиться вызов
```

По умолчанию у большинства фабрик запросов таймауты **не заданы**, то есть
бесконечны. Один недоступный сервис в этом случае занимает потоки навсегда, и
приложение перестаёт отвечать, оставаясь технически живым.

```java
@Bean
public ClientHttpRequestFactory requestFactory() {
    ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.DEFAULTS
            .withConnectTimeout(Duration.ofSeconds(2))
            .withReadTimeout(Duration.ofSeconds(5));

    return ClientHttpRequestFactories.get(settings);
}
```

Для `WebClient` таймаут ответа задаётся на уровне транспорта:

```java
HttpClient httpClient = HttpClient.create()
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000)
        .responseTimeout(Duration.ofSeconds(5));
```

Правило бюджета: сумма таймаутов внутренних вызовов не должна превышать время,
обещанное внешнему потребителю. Если API обещает ответ за 3 секунды, три
последовательных вызова по 5 секунд бессмысленны — клиент уйдёт раньше.

## Пул соединений

Установление TCP-соединения и TLS-рукопожатие стоят дороже самого запроса, поэтому
соединения переиспользуются.

```text
maxTotal            → всего соединений
maxPerRoute         → на один хост, ограничение по умолчанию часто мало
connection TTL      → принудительное закрытие, чтобы не держать мёртвые
connectionRequestTimeout → сколько ждём свободное соединение из пула
```

Последний параметр забывают чаще всего: если пул исчерпан, поток ждёт свободного
соединения, и это ожидание тоже должно быть ограничено, иначе таймауты на самом
запросе не спасают.

## Ошибки и коды ответа

```text
RestTemplate → 4xx и 5xx превращаются в HttpClientErrorException / HttpServerErrorException
RestClient   → retrieve() бросает по умолчанию, поведение настраивается onStatus
WebClient    → retrieve() даёт WebClientResponseException; exchange() отдаёт ответ как есть
```

Разумная практика — транслировать чужие ошибки в свои исключения прямо в клиенте,
чтобы сервисный слой не знал про HTTP:

```java
.onStatus(HttpStatusCode::is5xxServerError,
          (req, res) -> { throw new PaymentUnavailableException(); })
```

И отдельное правило: чужой `404` почти никогда не должен становиться вашим `500`.

## Повторы и размыкатель цепи

Повторять можно только идемпотентные операции. `GET` — да, `POST` — только с
ключом идемпотентности на стороне получателя.

```java
@Retryable(
        retryFor = PaymentUnavailableException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 200, multiplier = 2, random = true))
public PaymentDto charge(ChargeRequest request) { }
```

Параметр `random = true` добавляет то самое рассеивание задержки, без которого все
клиенты приходят к поднявшемуся сервису одновременно.

Resilience4j даёт размыкатель цепи:

```java
@CircuitBreaker(name = "payments", fallbackMethod = "chargeFallback")
@TimeLimiter(name = "payments")
public CompletableFuture<PaymentDto> charge(ChargeRequest request) { }
```

Обе аннотации работают через прокси, со всеми известными последствиями для
self-invocation.

Повторы ставятся **на одном уровне**. Три попытки на клиенте, умноженные на три
попытки в шлюзе, дают девять запросов к уже упавшему сервису.

## Вызовы и транзакции

```java
@Transactional
public void process(Order order) {
    orderRepository.save(order);
    paymentClient.charge(order);   // соединение с БД занято всё это время
}
```

Внешний вызов внутри транзакции удерживает соединение с базой и блокировки строк
на всё время ожидания. При таймауте в пять секунд транзакция живёт пять секунд.
Внешние вызовы выносятся за границу транзакции или выполняются после фиксации
через `@TransactionalEventListener`.

## Тестирование

```java
@RestClientTest(OrderService.class)
class OrderServiceTest {

    @Autowired
    private MockRestServiceServer server;

    @Test
    void returnsOrder() {
        server.expect(requestTo("/api/orders/1"))
              .andRespond(withSuccess("{\"id\":1}", MediaType.APPLICATION_JSON));
    }
}
```

`MockRestServiceServer` подменяет транспорт и проверяет, что запрос ушёл нужный.
WireMock поднимает настоящий HTTP-сервер и потому позволяет проверить то, чего
подмена транспорта не покажет: поведение при таймауте, при разрыве соединения, при
медленном ответе.

## Типичные ошибки

### Не задавать таймауты

Значения по умолчанию бесконечны. Один медленный сервис исчерпывает пул потоков, и
приложение перестаёт отвечать целиком.

### Забывать connectionRequestTimeout

Ограничен сам запрос, но не ожидание свободного соединения из пула. Поток снова
висит без предела.

### Создавать клиент на каждый вызов

Теряется пул соединений, растёт число сокетов в состоянии TIME_WAIT. Клиент
создаётся один раз как бин.

### Повторять неидемпотентные операции

Повтор `POST` без ключа идемпотентности создаёт дубликат платежа или заказа.

### Повторять на нескольких уровнях

Число запросов растёт произведением попыток и добивает сервис, который пытался
подняться.

### Повторять без рассеивания задержки

Все клиенты приходят одновременно ровно в момент восстановления.

### Вызывать block() внутри реактивной цепочки

Блокируется поток event loop, которых по числу ядер. Приложение встаёт целиком.

### Делать внешний вызов внутри транзакции

Соединение с базой и блокировки удерживаются всё время ожидания ответа.

### Транслировать чужой 404 в свой 500

Отсутствие ресурса у соседа — не внутренняя ошибка. Ответ клиенту должен
соответствовать реальной причине.

### Тестировать только успешный сценарий

Самое интересное поведение клиента проявляется при таймауте и разрыве соединения,
а подмена транспорта их не показывает.

## Краткий ответ для собеседования

Для синхронных вызовов в новом коде используется `RestClient`, появившийся в
Spring 6.1; `RestTemplate` делает то же самое и остаётся в поддержке, но новых
возможностей не получает. `WebClient` нужен, когда стек реактивный или ответ
потоковый. Поверх любого из них можно объявить декларативный клиент через
`@HttpExchange`, что убирает ручную сборку запросов.

Главное в теме — таймауты, потому что по умолчанию их нет. Различают время
установления соединения, время ожидания данных и время ожидания свободного
соединения из пула; последнее забывают чаще всего, и поток из-за этого продолжает
висеть без ограничения. Сумма таймаутов внутренних вызовов не должна превышать
время, обещанное внешнему потребителю.

Клиент создаётся один раз как бин: иначе теряется пул соединений и растёт число
открытых сокетов.

Повторы допустимы только для идемпотентных операций, с экспоненциальной задержкой
и случайным рассеиванием, и только на одном уровне, иначе число запросов растёт
произведением попыток. Для защиты от упавшего соседа применяется размыкатель цепи.

Внешние вызовы не делаются внутри транзакции: соединение с базой и блокировки
строк удерживаются всё время ожидания ответа.

## Вопросы на собеседовании

### 1. Чем RestClient отличается от RestTemplate?

**Ответ:** транспорт тот же, отличается интерфейс — у `RestClient` он текучий, в
стиле `WebClient`. `RestTemplate` остаётся в поддержке, но развивать его не
планируют.

### 2. Когда нужен WebClient?

**Ответ:** при реактивном стеке, потоковом ответе или очень большом числе
одновременных вызовов, где модель «поток на запрос» становится дорогой.

### 3. Можно ли вызвать block() у WebClient?

**Ответ:** в сервлетном приложении можно, хотя выигрыш при этом теряется. Внутри
реактивной цепочки нельзя — блокируется поток event loop.

### 4. Какие таймауты нужно задавать?

**Ответ:** на установление соединения, на ожидание данных и на получение
соединения из пула. По умолчанию они не заданы.

### 5. Что произойдёт без таймаутов?

**Ответ:** поток ждёт ответа бесконечно. При нескольких таких вызовах пул потоков
исчерпывается, и сервис перестаёт отвечать, оставаясь запущенным.

### 6. Что такое бюджет времени?

**Ответ:** сумма таймаутов вложенных вызовов не должна превышать время, обещанное
внешнему клиенту, иначе он отвалится раньше, чем закончится наша обработка.

### 7. Почему клиент создают как бин?

**Ответ:** чтобы переиспользовать пул соединений. Создание на каждый вызов теряет
keep-alive и оставляет множество сокетов в TIME_WAIT.

### 8. Какие операции можно повторять?

**Ответ:** только идемпотентные. `POST` — лишь если получатель поддерживает ключ
идемпотентности.

### 9. Зачем в backoff случайная составляющая?

**Ответ:** чтобы клиенты не пришли одновременно в момент восстановления сервиса и
не уронили его снова.

### 10. Почему повторы ставят на одном уровне?

**Ответ:** попытки перемножаются. Три на клиенте и три на шлюзе дают девять
запросов вместо трёх.

### 11. Как работает circuit breaker?

**Ответ:** при превышении доли ошибок переходит в состояние OPEN и отклоняет
вызовы сразу, через время пробует несколько запросов в HALF_OPEN и по результату
возвращается в CLOSED или снова в OPEN.

### 12. Почему нельзя делать HTTP-вызов внутри транзакции?

**Ответ:** соединение с базой и блокировки строк удерживаются всё время ожидания
ответа, а вакуум не может очистить старые версии строк.

### 13. Как выполнить вызов после фиксации транзакции?

**Ответ:** через `@TransactionalEventListener` с фазой `AFTER_COMMIT`.

### 14. Как транслировать ошибки внешнего сервиса?

**Ответ:** в собственные исключения на уровне клиента, чтобы сервисный слой не
зависел от HTTP. Чужой `404` не должен превращаться в наш `500`.

### 15. Чем MockRestServiceServer отличается от WireMock?

**Ответ:** первый подменяет транспорт и проверяет, что ушёл ожидаемый запрос.
Второй поднимает настоящий сервер и позволяет воспроизвести таймаут, медленный
ответ и разрыв соединения.
