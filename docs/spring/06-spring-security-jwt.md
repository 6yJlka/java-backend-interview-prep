# Spring Security и JWT

## Зачем нужен отдельный слой

Аутентификация и авторизация — сквозная задача. Если проверять права в каждом
контроллере вручную, проверка рано или поздно будет забыта в одном месте, и это
место окажется дырой.

```text
аутентификация → кто ты
авторизация    → что тебе можно
```

Spring Security решает это перехватом всех запросов до того, как они дойдут до
контроллера. Отсюда главное следствие: безопасность работает на уровне фильтров
Servlet API, а не Spring MVC.

```text
запрос
→ цепочка фильтров Security
→ DispatcherServlet
→ контроллер
```

Именно поэтому `@RestControllerAdvice` не поймает исключение, выброшенное при
неудачной аутентификации: до контроллера запрос не дошёл.

---

## Цепочка фильтров

### Устройство

В контейнере сервлетов регистрируется один фильтр `DelegatingFilterProxy`, который
делегирует бину `springSecurityFilterChain` — это `FilterChainProxy`. Внутри него
находится список `SecurityFilterChain`, каждая со своим шаблоном путей.

```text
DelegatingFilterProxy
→ FilterChainProxy
  → SecurityFilterChain #1  (/api/**)
  → SecurityFilterChain #2  (/**)
```

Для запроса выбирается **первая подходящая** цепочка, остальные не выполняются.
Это частая причина недоумения: настройки из второй цепочки «не работают».

### Ключевые фильтры

Порядок фиксирован и важен:

```text
SecurityContextHolderFilter   → достаёт контекст из хранилища
CorsFilter                    → preflight-запросы
CsrfFilter                    → проверка токена для небезопасных методов
UsernamePasswordAuthenticationFilter → форма логина
BearerTokenAuthenticationFilter / свой JWT-фильтр
ExceptionTranslationFilter    → превращает исключения в 401 и 403
AuthorizationFilter           → собственно проверка прав, последний
```

`AuthorizationFilter` идёт последним не случайно: к моменту проверки прав
аутентификация уже должна быть выполнена предыдущими фильтрами.

### Свой фильтр

```java
public class JwtAuthFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws IOException, ServletException {

        String header = request.getHeader(HttpHeaders.AUTHORIZATION);

        if (header != null && header.startsWith("Bearer ")) {
            Authentication auth = tokenService.parse(header.substring(7));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        chain.doFilter(request, response);
    }
}
```

`OncePerRequestFilter` гарантирует однократное выполнение: при forward и include
обычный фильтр отработал бы дважды.

Важная деталь: фильтр не должен сам отклонять запрос при отсутствии токена. Его
задача — установить аутентификацию, если токен есть. Решение о доступе принимает
`AuthorizationFilter`, иначе публичные эндпоинты перестанут работать.

## Аутентификация

### Участники

```text
AuthenticationManager       → точка входа, обычно ProviderManager
  AuthenticationProvider    → умеет проверить конкретный тип credentials
    UserDetailsService      → загружает пользователя по имени
    PasswordEncoder         → сверяет пароль
→ Authentication            → результат: principal, credentials, authorities
```

`DaoAuthenticationProvider` — стандартная реализация для пары «логин и пароль».

```java
@Bean
public UserDetailsService userDetailsService(UserRepository repository) {
    return username -> repository.findByUsername(username)
            .map(user -> User.withUsername(user.getUsername())
                    .password(user.getPasswordHash())
                    .authorities(user.getRoles().toArray(String[]::new))
                    .build())
            .orElseThrow(() -> new UsernameNotFoundException(username));
}
```

### Хранение паролей

Пароль не хранится и не шифруется — хранится хеш, полученный медленной функцией с
солью.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);
}
```

```text
BCrypt / Argon2 / PBKDF2 → медленные по построению, соль внутри хеша
SHA-256, MD5             → быстрые, поэтому для паролей непригодны
```

Медленность здесь — свойство, а не недостаток: она делает перебор дорогим.
Параметр стоимости (`12` выше) определяет число итераций; его повышают по мере
роста производительности железа.

Соль генерируется автоматически и хранится внутри строки хеша, поэтому два
одинаковых пароля дают разные хеши.

`DelegatingPasswordEncoder`, который создаёт `PasswordEncoderFactories`, хранит
префикс алгоритма прямо в строке: `{bcrypt}$2a$...`. Это позволяет менять алгоритм
без единовременной перегенерации всех паролей.

### Ответ на неудачу

```text
401 Unauthorized → не аутентифицирован, вход может помочь
403 Forbidden    → пользователь известен, но прав не хватает
```

За это отвечает `ExceptionTranslationFilter`: `AuthenticationException`
превращается в 401, `AccessDeniedException` — в 403.

## SecurityContext

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
```

Контекст хранится в `ThreadLocal`. Практические следствия:

```text
другой поток (@Async, ExecutorService) → контекст пуст
```

Решается стратегией `MODE_INHERITABLETHREADLOCAL` либо
`DelegatingSecurityContextExecutor`, который копирует контекст в задачу явно.

Второе следствие — в stateless-приложении контекст живёт ровно один запрос: его
устанавливает фильтр в начале и очищает `SecurityContextHolderFilter` в конце.
Забыть очистку опасно ровно потому, что поток вернётся в пул контейнера.

Получить текущего пользователя в контроллере можно без обращения к холдеру:

```java
@GetMapping("/me")
public UserDto me(@AuthenticationPrincipal UserDetails user) {
    return UserDto.from(user);
}
```

## Авторизация

### На уровне запросов

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/auth/**").permitAll()
                    .requestMatchers(HttpMethod.GET, "/api/orders/**").hasAuthority("SCOPE_orders.read")
                    .requestMatchers("/api/admin/**").hasRole("ADMIN")
                    .anyRequest().authenticated())
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
}
```

Правила проверяются сверху вниз, срабатывает первое подходящее. Поэтому
`anyRequest()` всегда последний, а более узкие шаблоны идут перед широкими.

### Роли и права

```text
hasRole("ADMIN")        → ищет authority "ROLE_ADMIN"
hasAuthority("ADMIN")   → ищет authority "ADMIN"
```

Префикс `ROLE_` добавляется неявно, и несовпадение здесь — самая частая причина
неожиданного 403. Разумное соглашение: роль описывает, кто пользователь, право —
что он может делать.

### На уровне методов

```java
@EnableMethodSecurity
@Configuration
public class MethodSecurityConfig { }
```

```java
@PreAuthorize("hasRole('ADMIN') or #userId == authentication.name")
public UserDto get(String userId) { }

@PostAuthorize("returnObject.ownerId == authentication.name")
public Order find(Long id) { }
```

Работает через прокси AOP. Отсюда два знакомых ограничения: аннотация на
`private`-методе не действует, и вызов метода изнутри того же класса проходит мимо
прокси — проверки не будет.

`@PostAuthorize` выполняет метод и только потом проверяет результат, поэтому для
операций с побочными эффектами он не подходит.

## Сессии и stateless

```text
сессия
+ токен можно отозвать мгновенно — удалить сессию
+ в cookie с HttpOnly, недоступна из JavaScript
− состояние на сервере: sticky sessions или общее хранилище

самодостаточный токен (JWT)
+ сервер не хранит ничего, любой инстанс проверит подпись
− отозвать до истечения срока нельзя, не заведя список отозванных
```

Выбор — компромисс, а не вопрос современности. Для монолита с одним хранилищем
сессия в Redis часто проще и безопаснее JWT.

## JWT

### Структура

Три части, разделённые точками, каждая в base64url:

```text
header.payload.signature
```

```json
{ "alg": "HS256", "typ": "JWT" }
```

```json
{
  "sub": "user-42",
  "iss": "https://auth.example.com",
  "aud": "orders-api",
  "exp": 1750000000,
  "iat": 1749996400,
  "jti": "b1f2...",
  "roles": ["USER"]
}
```

Стандартные claims: `sub` — субъект, `iss` — издатель, `aud` — получатель, `exp` —
момент истечения, `iat` — момент выпуска, `nbf` — не ранее, `jti` — идентификатор
токена.

### Главное, что нужно проговорить на собеседовании

> JWT не шифрует полезную нагрузку. Payload закодирован base64url и читается кем
> угодно. Подпись защищает от изменения, а не от чтения.

Отсюда прямое правило: в токен нельзя класть пароли, персональные данные и любые
секреты. Для шифрования существует JWE, но в типовом бэкенде он не применяется.

### Подпись

```text
HMAC (HS256)   → один общий секрет на подпись и проверку
                 подходит, когда выпускает и проверяет один сервис

RSA/EC (RS256) → приватный ключ подписывает, публичный проверяет
                 подходит, когда проверяющих много: ключ можно раздать
                 публичный ключ отдаётся через JWKS-эндпоинт
```

### Access и refresh

```text
access-токен  → короткоживущий, 5–15 минут, ходит в каждом запросе
refresh-токен → долгоживущий, дни, ходит только к эндпоинту обновления
```

Смысл разделения: украденный access-токен быстро протухнет, а refresh-токен
хранится на сервере и потому может быть отозван. Практика — ротация: при каждом
обновлении выдаётся новый refresh, старый помечается использованным. Повторное
использование старого токена означает кражу, и вся цепочка аннулируется.

### Отзыв

Основная слабость схемы. Варианты:

```text
короткий срок жизни           → окно компрометации мало, самое дешёвое
denylist по jti в Redis       → работает, но возвращает состояние на сервер
версия токенов у пользователя → инкремент при смене пароля обнуляет все токены
```

### Где хранить на клиенте

```text
localStorage → доступен из JavaScript, уязвим к XSS
cookie HttpOnly + Secure + SameSite → недоступен скриптам, но нужен CSRF-контроль
```

Универсально верного ответа нет; на собеседовании ценится именно понимание
компромисса, а не заученный вариант.

### Проверка на стороне сервиса

Использовать готовый стартер лучше, чем разбирать токен вручную:

```gradle
implementation 'org.springframework.boot:spring-boot-starter-oauth2-resource-server'
```

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com
```

Стартер сам проверит подпись, `exp`, `iss`, заберёт ключи по JWKS и положит
`JwtAuthenticationToken` в контекст.

Обязательный минимум проверок, если писать руками: подпись, срок действия,
издатель, получатель и **алгоритм**. Последнее существенно: библиотека, слепо
доверяющая полю `alg` из заголовка, уязвима к подмене алгоритма на `none` или к
подсовыванию публичного RSA-ключа в качестве HMAC-секрета. Алгоритм задаётся
конфигурацией, а не берётся из токена.

## CORS и CSRF

```text
CORS → браузер спрашивает разрешение на кросс-доменный запрос
CSRF → чужой сайт заставляет браузер отправить запрос с вашими cookie
```

CSRF-атака возможна, когда учётные данные прикрепляются браузером автоматически,
то есть при сессии в cookie. Если токен передаётся заголовком `Authorization`,
браузер его сам не подставит, и защита от CSRF не нужна — отсюда типовое
`csrf.disable()` в stateless-конфигурации. Отключать её при сессионной
аутентификации нельзя.

Настройка CORS выполняется в Security, а не только в MVC: preflight-запрос
`OPTIONS` придёт без токена и должен быть пропущен.

## Типичные ошибки

### Отключать CSRF при сессионной аутентификации

Защита отключается там, где она как раз необходима. Правило простое: cookie —
CSRF нужен, заголовок `Authorization` — не нужен.

### Считать, что JWT скрывает данные

Payload читается любым, у кого есть токен. Подпись даёт целостность, не
конфиденциальность.

### Доверять полю alg из заголовка токена

Позволяет подменить алгоритм и обойти проверку подписи. Алгоритм задаётся
конфигурацией проверяющей стороны.

### Путать hasRole и hasAuthority

`hasRole("ADMIN")` ищет authority `ROLE_ADMIN`. Несовпадение даёт 403 без видимой
причины.

### Ставить широкий матчер выше узкого

Правила применяются сверху вниз, первое совпавшее выигрывает. `anyRequest()`
всегда последний.

### Отклонять запрос в собственном JWT-фильтре

Фильтр только устанавливает аутентификацию. Отказ — дело `AuthorizationFilter`,
иначе публичные эндпоинты перестанут отвечать.

### Хранить пароли быстрым хешем

MD5 и SHA-семейство перебираются на GPU миллиардами вариантов в секунду. Нужен
BCrypt, Argon2 или PBKDF2.

### Выдавать долгоживущий access-токен

Отозвать его нельзя, поэтому кража даёт злоумышленнику доступ на весь срок.

### Ожидать, что @ControllerAdvice поймает ошибку аутентификации

Она возникает в фильтре, до `DispatcherServlet`. Нужен
`AuthenticationEntryPoint` или `AccessDeniedHandler`.

### Рассчитывать на SecurityContext в другом потоке

Контекст лежит в `ThreadLocal` и в задачу `@Async` не попадает без явного
переноса.

### Ставить @PreAuthorize на метод, вызываемый изнутри класса

Проверка работает через прокси, внутренний вызов идёт мимо неё.

## Краткий ответ для собеседования

Spring Security встраивается в приложение как цепочка фильтров сервлетов и потому
работает до `DispatcherServlet`. Запрос проходит фильтры по фиксированному
порядку: восстановление контекста, CORS, CSRF, фильтры аутентификации, перевод
исключений и последним — проверка прав.

Аутентификацией занимается `AuthenticationManager`, делегирующий провайдерам;
стандартный провайдер берёт пользователя через `UserDetailsService` и сверяет
пароль через `PasswordEncoder`. Результат — объект `Authentication`, который
кладётся в `SecurityContextHolder`, то есть в `ThreadLocal`, и потому не виден в
других потоках.

Пароли хранятся как хеши, полученные намеренно медленной функцией с солью —
BCrypt или Argon2. Быстрые хеши вроде SHA-256 для этого непригодны.

Авторизация задаётся либо правилами по путям в `authorizeHttpRequests`, либо
аннотациями `@PreAuthorize` на методах, которые работают через прокси и потому не
срабатывают при вызове изнутри класса. `hasRole` добавляет префикс `ROLE_`
неявно.

JWT — самодостаточный токен из заголовка, полезной нагрузки и подписи, где первые
две части просто закодированы base64url и читаются кем угодно. Подпись
обеспечивает целостность, а не конфиденциальность, поэтому секретов в токене быть
не должно. Проверять нужно подпись, срок действия, издателя, получателя и
алгоритм, причём алгоритм берётся из конфигурации, а не из самого токена.

Основная слабость схемы — невозможность отозвать выданный токен. Её компенсируют
коротким сроком жизни access-токена, долгоживущим refresh-токеном с ротацией и
при необходимости списком отозванных идентификаторов, который, впрочем, снова
возвращает состояние на сервер.

## Вопросы на собеседовании

### 1. Где в жизненном цикле запроса работает Spring Security?

**Ответ:** в цепочке фильтров сервлетов, до `DispatcherServlet`. Поэтому
контроллер и `@ControllerAdvice` исключений безопасности не видят.

### 2. Чем аутентификация отличается от авторизации?

**Ответ:** первая устанавливает, кто пользователь, вторая — что ему разрешено. На
уровне ответов это `401` и `403`.

### 3. Что произойдёт, если объявить несколько SecurityFilterChain?

**Ответ:** для запроса выберется первая цепочка, чей матчер совпал, остальные не
выполнятся. Порядок объявления определяет поведение.

### 4. Зачем наследовать OncePerRequestFilter?

**Ответ:** он гарантирует однократное выполнение в пределах запроса — при forward
и include обычный фильтр отработал бы повторно.

### 5. Как устроена аутентификация по логину и паролю?

**Ответ:** `AuthenticationManager` передаёт запрос провайдерам;
`DaoAuthenticationProvider` загружает пользователя через `UserDetailsService` и
сверяет пароль через `PasswordEncoder`, возвращая заполненный `Authentication`.

### 6. Почему пароли хешируют BCrypt, а не SHA-256?

**Ответ:** BCrypt намеренно медленный и имеет настраиваемую стоимость, что делает
перебор дорогим. SHA-256 быстрый, и подбор на GPU идёт миллиардами вариантов в
секунду.

### 7. Где хранится соль при использовании BCrypt?

**Ответ:** внутри самой строки хеша. Она генерируется случайно, поэтому одинаковые
пароли дают разные хеши.

### 8. Где хранится текущий пользователь и в чём подвох?

**Ответ:** в `SecurityContextHolder`, основанном на `ThreadLocal`. В другом потоке
контекста не будет, если не перенести его явно.

### 9. В чём разница между hasRole и hasAuthority?

**Ответ:** `hasRole` неявно добавляет префикс `ROLE_`. `hasRole("ADMIN")`
эквивалентен `hasAuthority("ROLE_ADMIN")`.

### 10. Почему @PreAuthorize иногда не срабатывает?

**Ответ:** проверка реализована через прокси AOP. Вызов метода изнутри того же
класса идёт мимо прокси, как и в случае с `@Transactional`.

### 11. Из чего состоит JWT?

**Ответ:** из заголовка, полезной нагрузки и подписи, разделённых точками. Первые
две части закодированы base64url.

### 12. Шифрует ли JWT данные?

**Ответ:** нет. Payload читается любым, кто получил токен. Подпись защищает от
подделки, но не от чтения.

### 13. Что обязательно проверять при валидации токена?

**Ответ:** подпись, срок действия, издателя, получателя и алгоритм, причём
алгоритм задаётся конфигурацией. Доверие полю `alg` из токена позволяет обойти
проверку подписи.

### 14. Чем HS256 отличается от RS256?

**Ответ:** HMAC использует один общий секрет для подписи и проверки, RSA — пару
ключей: приватным подписывают, публичный можно раздать всем проверяющим.

### 15. Зачем нужен refresh-токен?

**Ответ:** чтобы access-токен жил недолго и его кража давала малое окно, а
продление доступа шло через долгоживущий токен, который хранится на сервере и
может быть отозван.

### 16. Как отозвать JWT?

**Ответ:** напрямую никак. Применяют короткий срок жизни, список отозванных
идентификаторов `jti` или версию токенов у пользователя, которая инкрементируется
при смене пароля.

### 17. Почему в stateless-конфигурации отключают CSRF?

**Ответ:** атака опирается на то, что браузер сам подставляет учётные данные.
Заголовок `Authorization` он не подставляет. При сессии в cookie отключать защиту
нельзя.

### 18. Чем сессия лучше JWT?

**Ответ:** её можно отозвать мгновенно, а идентификатор в `HttpOnly`-cookie
недоступен скриптам. Цена — состояние на сервере и необходимость общего хранилища
при нескольких инстансах.
