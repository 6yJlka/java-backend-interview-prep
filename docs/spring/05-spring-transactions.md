# Транзакции в Spring

## Что делает @Transactional

Аннотация объявляет, что метод должен выполняться в транзакции. Работу выполняет
прокси, созданный `BeanPostProcessor`.

```text
1. вызов приходит на прокси
2. перехватчик читает атрибуты @Transactional
3. менеджер транзакций открывает транзакцию или присоединяется к текущей
4. соединение и EntityManager привязываются к текущему потоку
5. вызывается целевой метод
6. успех      → flush и commit
   исключение → commit или rollback, по правилам
7. привязка к потоку снимается
```

### Менеджер транзакций

`PlatformTransactionManager` — абстракция над конкретной технологией:

```text
DataSourceTransactionManager → JDBC напрямую
JpaTransactionManager        → JPA, используется при наличии Hibernate
JtaTransactionManager        → распределённые транзакции
```

Spring Boot выбирает подходящий автоматически.

### Привязка к потоку

Ключевая деталь реализации: соединение с базой и `EntityManager` хранятся в
`ThreadLocal` через `TransactionSynchronizationManager`.

Отсюда следует важное: **транзакция не переходит в другой поток**.

```java
@Transactional
public void process(List<Order> orders) {
    orders.parallelStream().forEach(orderRepository::save);   // другие потоки
}
```

Задачи в параллельном стриме, в `@Async`-методе или в `ExecutorService`
выполняются вне транзакции — они не видят привязанного соединения. Ошибки при этом
может не быть, поведение просто окажется другим.

---

## Границы транзакции

Транзакция задаёт время жизни контекста персистентности, поэтому её границы — это
границы работы с управляемыми сущностями.

```text
@Transactional открылся → создан persistence context
метод завершился        → flush → commit → контекст закрыт
после этого             → сущности отсоединены
```

Ставится аннотация на сервисный слой:

```text
контроллер  → нет, транзакция охватит сериализацию
репозиторий → нет, каждый вызов станет отдельной транзакцией
сервис      → да, там единица бизнес-операции
```

Аннотацию можно поставить на класс — тогда она применится ко всем публичным
методам, а метод может переопределить настройки своей аннотацией.

## Правила отката

Самая неочевидная часть темы.

```text
RuntimeException и её наследники → откат
Error                            → откат
checked exception                → COMMIT
```

Да, проверяемое исключение по умолчанию **не откатывает** транзакцию.

```java
@Transactional
public void process() throws IOException {
    orderRepository.save(order);
    throw new IOException("сбой");   // транзакция зафиксируется
}
```

Поведение унаследовано из EJB, где checked-исключение считалось частью нормального
контракта метода, а не сбоем. Логика спорная, но менять её было бы ломающим
изменением.

Настраивается явно:

```java
@Transactional(rollbackFor = Exception.class)
@Transactional(noRollbackFor = ValidationException.class)
```

На практике проще использовать unchecked-исключения для бизнес-ошибок — тогда
поведение по умолчанию оказывается правильным.

### Перехваченное исключение не откатывает

```java
@Transactional
public void process() {
    try {
        orderRepository.save(order);
        riskyOperation();
    } catch (Exception e) {
        log.error("ошибка", e);      // проглочено
    }
}
```

Прокси видит нормальное завершение метода и фиксирует транзакцию. Половина
операций записана, ошибка залогирована, данные в противоречивом состоянии.

Если нужно и обработать, и откатить:

```java
TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
```

Или, что читается лучше, пробросить исключение дальше.

### UnexpectedRollbackException

Классическая ситуация, которую любят разбирать на собеседовании.

```java
@Service
public class OuterService {

    @Transactional
    public void outer() {
        try {
            innerService.inner();     // упадёт
        } catch (Exception e) {
            log.warn("продолжаем");   // перехватили
        }
        orderRepository.save(order);
    }
}

@Service
public class InnerService {

    @Transactional                     // REQUIRED, та же транзакция
    public void inner() {
        throw new IllegalStateException();
    }
}
```

Результат — `UnexpectedRollbackException` при выходе из `outer()`.

Причина: `inner()` с распространением `REQUIRED` не создал новую транзакцию, а
присоединился к существующей. Исключение из него пометило транзакцию как
`rollback-only`. Внешний метод исключение перехватил и завершился нормально, но
фиксировать уже нечего — транзакция помечена к откату, и Spring сообщает об этом
исключением.

```text
пометка rollback-only необратима
перехват исключения снаружи её не снимает
```

Решения: либо не перехватывать, либо объявить внутренний метод с `REQUIRES_NEW`,
чтобы у него была собственная транзакция.

## Propagation

Определяет поведение при вызове транзакционного метода из другого транзакционного
метода.

```text
REQUIRED (по умолчанию)
→ есть транзакция  → присоединиться
→ нет транзакции   → создать

REQUIRES_NEW
→ приостановить текущую, создать новую
→ отдельное соединение с базой

NESTED
→ вложенная транзакция через SAVEPOINT
→ откат только до точки сохранения

SUPPORTS
→ есть транзакция → участвовать
→ нет             → выполнить без транзакции

NOT_SUPPORTED
→ приостановить текущую, выполнить без транзакции

MANDATORY
→ требует существующую, иначе исключение

NEVER
→ требует отсутствия транзакции, иначе исключение
```

### REQUIRED

Используется почти всегда. Важно понимать, что присоединение к существующей
транзакции означает единый исход: либо всё фиксируется, либо всё откатывается.
Отдельного отката «только внутреннего метода» не будет — это и порождает
`UnexpectedRollbackException`.

### REQUIRES_NEW

Нужен, когда операция должна сохраниться независимо от исхода внешней — например,
запись в журнал аудита.

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(AuditEvent event) {
    auditRepository.save(event);
}
```

Два предупреждения.

**Отдельное соединение.** Внешняя транзакция приостановлена, но её соединение
удерживается. Значит, одновременно занято два соединения из пула. При большом числе
параллельных запросов это приводит к дедлоку на пуле — ситуации из конспекта по
транзакциям в базе, которую сама база не видит.

**Не видит незафиксированных данных внешней транзакции.** Новая транзакция читает
базу, где изменения внешней ещё не подтверждены. Попытка прочитать только что
сохранённую сущность вернёт пустоту либо заблокируется на строке, которую внешняя
транзакция уже заблокировала — то есть даст самоблокировку.

### NESTED

Реализуется через точки сохранения. Откат вложенной транзакции возвращает состояние
к savepoint, не отменяя внешнюю.

```text
NESTED работает с DataSourceTransactionManager
с JpaTransactionManager обычно не поддерживается
```

На практике встречается редко.

## Isolation

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

```text
DEFAULT          → уровень базы данных
READ_UNCOMMITTED
READ_COMMITTED
REPEATABLE_READ
SERIALIZABLE
```

Уровень передаётся драйверу и применяется базой — значения и поведение разбирались
в конспекте по транзакциям PostgreSQL.

Две особенности Spring:

**Уровень нельзя сменить внутри существующей транзакции.** Метод с `REQUIRED`,
присоединившийся к чужой транзакции, унаследует её уровень, а собственный будет
проигнорирован. Некоторые менеджеры при несовпадении бросают исключение. Сменить
уровень можно только с `REQUIRES_NEW`.

**Не все базы поддерживают все уровни.** PostgreSQL принимает
`READ_UNCOMMITTED`, но выполняет как `READ_COMMITTED`.

---

## readOnly

```java
@Transactional(readOnly = true)
```

Делает несколько вещей сразу:

```text
Hibernate → FlushMode.MANUAL, снимки для dirty checking не создаются
драйвер   → соединение помечается только для чтения
маршрутизация → запрос может уйти на реплику, если она настроена
```

Главный выигрыш — отсутствие снимков. При чтении тысяч сущностей это заметная
экономия памяти и времени сброса.

Важно понимать, что это не защита: `readOnly` не гарантирует, что запись не
произойдёт. Некоторые базы отклонят её, некоторые — нет. Это подсказка для
оптимизации, а не ограничение.

---

## Timeout

```java
@Transactional(timeout = 5)
```

Ограничивает время транзакции в секундах. При превышении выбрасывается исключение и
происходит откат.

Полезно для операций, которые не должны выполняться долго. Не заменяет
`lock_timeout` и `statement_timeout` на стороне базы — те работают на уровне
отдельных запросов и блокировок.

## Ограничения прокси

Всё, что разбиралось в конспекте по AOP, применимо здесь напрямую.

```text
self-invocation   → вызов через this идёт мимо прокси
private-метод     → не может быть переопределён
final-метод       → не может быть переопределён
@PostConstruct    → прокси ещё не создан
другой поток      → соединение привязано к исходному
```

Во всех случаях ошибки не будет — метод просто выполнится без транзакции.

### Обход self-invocation

```java
@Service
public class OrderService {

    private final OrderService self;

    public OrderService(@Lazy OrderService self) {
        this.self = self;
    }

    public void processAll(List<Order> orders) {
        orders.forEach(self::saveOne);    // через прокси
    }

    @Transactional
    public void saveOne(Order order) { }
}
```

Предпочтительнее всё же вынести метод в отдельный бин.

## Действия после фиксации

Частая задача: отправить уведомление или событие, но только если транзакция
успешно завершилась.

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    notificationClient.send(event.orderId());
}
```

Публикация события выполняется внутри транзакции, а обработчик — после фиксации.
Если транзакция откатится, обработчик не вызовется.

Это правильный способ вынести внешние вызовы за пределы транзакции, не удерживая
соединение на время HTTP-запроса.

---

## Транзакции в тестах

```java
@SpringBootTest
@Transactional
class OrderServiceTest {

    @Test
    void createsOrder() {
        // после теста произойдёт откат
    }
}
```

Аннотация в тестах откатывает транзакцию по умолчанию, что удобно для изоляции.

Но есть подвох: тест выполняется внутри той же транзакции, что и проверяемый код.
Поэтому не проверяется реальная фиксация, а `LazyInitializationException`, который
возникнет в проде, в тесте не воспроизведётся — контекст всё ещё открыт.

Для проверки поведения на границах транзакций нужен тест без `@Transactional`.

## Типичные ошибки

### Ожидать отката при checked-исключении

По умолчанию откатывают только `RuntimeException` и `Error`. Нужен `rollbackFor`.

### Перехватывать исключение внутри транзакционного метода

Прокси увидит нормальное завершение и зафиксирует транзакцию.

### Перехватывать исключение из вложенного метода с REQUIRED

Транзакция уже помечена `rollback-only`, и на выходе будет
`UnexpectedRollbackException`.

### Ставить @Transactional на private-метод

Прокси не может его перехватить, аннотация игнорируется.

### Вызывать транзакционный метод изнутри класса

Вызов идёт через `this`, минуя прокси.

### Рассчитывать на транзакцию в другом потоке

Соединение привязано к потоку через `ThreadLocal`. Параллельный стрим, `@Async` и
задачи в пуле работают вне транзакции.

### Злоупотреблять REQUIRES_NEW

Каждый вызов занимает второе соединение при удерживаемом первом. Прямой путь к
исчерпанию пула.

### Читать во вложенной REQUIRES_NEW данные внешней транзакции

Они ещё не зафиксированы. Возможна и самоблокировка на строке, заблокированной
внешней транзакцией.

### Менять isolation у метода с REQUIRED

При присоединении к существующей транзакции уровень наследуется, а собственный
игнорируется.

### Считать readOnly защитой от записи

Это подсказка для оптимизации, а не ограничение.

### Выполнять внешние вызовы внутри транзакции

Соединение и блокировки удерживаются всё время ожидания. Нужен
`@TransactionalEventListener` с фазой после фиксации.

## Краткая памятка

```text
@Transactional работает через прокси
соединение и EntityManager привязаны к потоку через ThreadLocal
→ в другом потоке транзакции нет
```

```text
откат

checked                 → COMMIT, нужен rollbackFor
```

```text

```



```text
внешние вызовы

```

## Краткий ответ для собеседования

`@Transactional` обрабатывается прокси: перехватчик открывает транзакцию через
менеджер транзакций, вызывает целевой метод и по результату фиксирует или
откатывает её. Соединение и `EntityManager` привязываются к текущему потоку через
`ThreadLocal`, поэтому транзакция не переходит в другие потоки — в параллельном
стриме или `@Async`-методе её не будет.

По умолчанию откат происходит только при `RuntimeException` и `Error`, а
проверяемые исключения транзакцию фиксируют. Это поведение унаследовано от EJB и
меняется параметром `rollbackFor`. Перехваченное внутри метода исключение тоже не
приводит к откату, поскольку прокси видит нормальное завершение.

Отдельный случай — вложенный метод с распространением `REQUIRED`. Он не создаёт
новую транзакцию, а присоединяется к существующей, поэтому исключение из него
помечает всю транзакцию как `rollback-only`. Если внешний метод перехватит это
исключение и завершится нормально, на выходе возникнет
`UnexpectedRollbackException`.

Основные виды распространения: `REQUIRED` присоединяется или создаёт транзакцию,
`REQUIRES_NEW` приостанавливает текущую и открывает новую в отдельном соединении,
`NESTED` использует точки сохранения. Злоупотребление `REQUIRES_NEW` опасно: при
приостановленной внешней транзакции занято сразу два соединения из пула.

Уровень изоляции передаётся базе, но сменить его для метода, присоединившегося к
существующей транзакции, нельзя — только через `REQUIRES_NEW`. Параметр `readOnly`
отключает снимки для dirty checking и служит подсказкой для оптимизации, а не
запретом на запись.

## Вопросы на собеседовании

### 1. Как работает @Transactional?

**Ответ:** через прокси. Перехватчик открывает транзакцию, вызывает целевой метод и
фиксирует или откатывает её по результату.

### 2. Где хранится соединение во время транзакции?

**Ответ:** в `ThreadLocal` через `TransactionSynchronizationManager`. Поэтому
транзакция действует только в том потоке, где была открыта.

### 3. Будет ли транзакция работать в параллельном стриме?

**Ответ:** нет. Задачи выполняются в других потоках, к которым соединение не
привязано.

### 4. Какие исключения вызывают откат по умолчанию?

**Ответ:** `RuntimeException` и `Error`. Проверяемые исключения приводят к фиксации.

### 5. Почему checked-исключения не откатывают транзакцию?

**Ответ:** поведение унаследовано из EJB, где такие исключения считались частью
нормального контракта метода. Меняется параметром `rollbackFor`.

### 6. Что произойдёт, если перехватить исключение внутри транзакционного метода?

**Ответ:** прокси увидит нормальное завершение и зафиксирует транзакцию, несмотря
на ошибку.

### 7. Как откатить транзакцию, обработав исключение?

**Ответ:** пробросить его дальше либо вызвать
`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.

### 8. Что такое UnexpectedRollbackException и когда возникает?

**Ответ:** возникает, когда вложенный метод с `REQUIRED` выбросил исключение и
пометил транзакцию как `rollback-only`, а внешний метод перехватил исключение и
попытался завершиться нормально.

### 9. Как избежать этой ситуации?

**Ответ:** не перехватывать исключение либо объявить внутренний метод с
`REQUIRES_NEW`, чтобы у него была собственная транзакция.

### 10. Какие бывают виды propagation?

**Ответ:** `REQUIRED`, `REQUIRES_NEW`, `NESTED`, `SUPPORTS`, `NOT_SUPPORTED`,
`MANDATORY`, `NEVER`.

### 11. Что делает REQUIRED?

**Ответ:** присоединяется к существующей транзакции или создаёт новую, если её нет.
Это значение по умолчанию.

### 12. Чем опасен REQUIRES_NEW?

**Ответ:** внешняя транзакция приостанавливается, но её соединение удерживается,
поэтому одновременно заняты два соединения. При большом числе запросов это приводит
к исчерпанию пула.

### 13. Увидит ли REQUIRES_NEW данные внешней транзакции?

**Ответ:** нет, они ещё не зафиксированы. Возможна и самоблокировка, если внешняя
транзакция заблокировала нужную строку.

### 14. Как работает NESTED?

**Ответ:** через точки сохранения: откат возвращает состояние к savepoint, не
отменяя внешнюю транзакцию. С `JpaTransactionManager` обычно не поддерживается.

### 15. Можно ли изменить уровень изоляции у вложенного метода?

**Ответ:** при `REQUIRED` нет — уровень наследуется от внешней транзакции. Только
через `REQUIRES_NEW`.

### 16. Что делает readOnly?

**Ответ:** отключает снимки для dirty checking, помечает соединение только для
чтения и позволяет маршрутизировать запрос на реплику. Это оптимизация, а не запрет
записи.

### 17. Почему @Transactional не работает на private-методе?

**Ответ:** прокси перехватывает вызовы через переопределение методов в подклассе, а
`private`-методы не наследуются.

### 18. Почему аннотация не срабатывает при вызове метода изнутри класса?

**Ответ:** вызов идёт через `this`, то есть на целевом объекте, минуя прокси.

### 19. На каком слое ставить @Transactional?

**Ответ:** на сервисном, где находится единица бизнес-операции. На контроллере
транзакция охватит сериализацию, на репозитории распадётся на отдельные транзакции.

### 20. Как отправить уведомление только после успешной фиксации?

**Ответ:** через `@TransactionalEventListener` с фазой `AFTER_COMMIT`. Событие
публикуется в транзакции, обработчик выполняется после её фиксации.

### 21. Чем опасен @Transactional в тестах?

**Ответ:** тест выполняется внутри той же транзакции, что и код, поэтому реальная
фиксация не проверяется, а `LazyInitializationException` не воспроизводится.

### 22. Что задаёт границы persistence context?

**Ответ:** границы транзакции. Контекст создаётся при её открытии и закрывается
после фиксации.
