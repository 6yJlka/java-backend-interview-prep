# Spring Data JPA

Надстройка над `EntityManager`, которая убирает написание типового кода доступа к
данным. Реализацию репозитория генерирует контейнер, а разработчик объявляет
интерфейс.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByStatus(OrderStatus status);
}
```

Ни одной строки реализации — и при этом работают и `findById`, и `save`, и
`findByStatus`.

Важно понимать границу ответственности. Spring Data не заменяет JPA и не отменяет
её правил: контекст персистентности, состояния сущности, ленивая загрузка, N+1 —
всё это остаётся ровно таким же. Меняется только способ вызова.

```text
JPA         → спецификация
Hibernate   → реализация
Spring Data → способ объявить операции без кода
```

## Репозитории

### Иерархия интерфейсов

```text
Repository<T, ID>                 маркер, ни одного метода
└── CrudRepository                save, findById, delete, count
    └── ListCrudRepository        то же, но возвращает List вместо Iterable
    └── PagingAndSortingRepository findAll(Pageable), findAll(Sort)
        └── JpaRepository         flush, saveAndFlush, deleteAllInBatch,
                                  getReferenceById
```

На практике почти всегда берут `JpaRepository` — он включает всё остальное.

Наследование от `Repository` напрямую имеет смысл, когда нужно намеренно скрыть
лишние методы: если репозиторий должен только читать, наличие `deleteAll` в
публичном API — приглашение к ошибке.

```java
public interface OrderReadRepository extends Repository<Order, Long> {

    Optional<Order> findById(Long id);

    List<Order> findByStatus(OrderStatus status);
}
```

### Как это работает

Никакой магии здесь нет, и на собеседовании полезно уметь это проговорить.

```text
1. при старте сканируются интерфейсы, наследующие Repository
2. для каждого создаётся динамический прокси
3. вызов метода попадает в RepositoryProxy
4. метод ищется среди:
   - объявленных в SimpleJpaRepository (findById, save, delete)
   - помеченных @Query
   - разбираемых по имени
5. выбранная стратегия строит и выполняет запрос через EntityManager
```

Реализация базовых методов — обычный класс `SimpleJpaRepository`, внутри которого
лежит `EntityManager`. Посмотреть его исходники полезно: становится видно, что
`save()` — это семь строк с проверкой на новизну сущности.

Отсюда же следует, что подменить поведение можно обычным способом — объявив
собственный фрагмент репозитория:

```java
public interface OrderRepositoryCustom {
    List<Order> findComplex(OrderFilter filter);
}

public class OrderRepositoryCustomImpl implements OrderRepositoryCustom {

    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public List<Order> findComplex(OrderFilter filter) {
        // ручной запрос через Criteria API или JPQL
    }
}

public interface OrderRepository
        extends JpaRepository<Order, Long>, OrderRepositoryCustom {
}
```

Суффикс `Impl` обязателен — по нему Spring Data находит реализацию фрагмента.

## Производные методы

Метод, объявленный по соглашению об именовании, превращается в запрос.

```java
List<Order> findByStatus(OrderStatus status);

Optional<Order> findByNumber(String number);

List<Order> findByStatusAndCustomerId(OrderStatus status, Long customerId);

List<Order> findByCreatedAtAfterOrderByCreatedAtDesc(Instant from);

long countByStatus(OrderStatus status);

boolean existsByNumber(String number);
```

Имя разбирается на части:

```text
findBy | ReadBy | getBy | queryBy   → выборка
countBy                             → количество
existsBy                            → проверка
deleteBy | removeBy                 → удаление
```

Дальше идут свойства и ключевые слова:

```text
And, Or
Between, LessThan, GreaterThan, After, Before
IsNull, IsNotNull
Like, StartingWith, EndingWith, Containing
In, NotIn
True, False
IgnoreCase
OrderBy...Asc / Desc
Distinct
```

Вложенные свойства указываются через имя связи:

```java
List<Order> findByCustomerName(String name);       // order.customer.name
List<Order> findByCustomer_Name(String name);      // то же, но однозначно
```

Подчёркивание нужно при неоднозначности: если у заказа есть и поле
`customerName`, и связь `customer` с полем `name`, без него Spring Data выберет
первое совпадение.

### Ограничение выборки

```java
Optional<Order> findFirstByStatusOrderByCreatedAtDesc(OrderStatus status);

List<Order> findTop10ByStatusOrderByCreatedAtDesc(OrderStatus status);
```

### Возвращаемые типы

```text
List<T>, Set<T>       → коллекция
Optional<T>           → ноль или один
T                     → ноль или один, при отсутствии null
Stream<T>             → потоковая обработка, требует try-with-resources
Page<T>, Slice<T>     → с пагинацией
long, boolean         → count и exists
```

Если метод объявлен как возвращающий один объект, а запрос вернул несколько,
будет `IncorrectResultSizeDataAccessException`.

### Когда останавливаться

Механизм удобен ровно до определённой сложности. Метод вида

```java
List<Order> findByStatusAndCustomerIdAndCreatedAtBetweenAndTotalGreaterThanOrderByCreatedAtDesc(
        OrderStatus status, Long customerId, Instant from, Instant to, BigDecimal total);
```

формально работает, но читать его невозможно. Практическое правило — три условия
максимум, дальше `@Query` или спецификация.

## @Query

### JPQL

Запрос пишется по сущностям, а не по таблицам.

```java
@Query("""
        select o from Order o
        where o.status = :status
          and o.createdAt > :from
        order by o.createdAt desc
        """)
List<Order> findRecent(@Param("status") OrderStatus status,
                       @Param("from") Instant from);
```

Текстовые блоки делают многострочные запросы читаемыми, и в новом коде их стоит
использовать.

Параметры бывают именованными и позиционными:

```java
@Query("select o from Order o where o.status = ?1")
List<Order> findByStatus(OrderStatus status);
```

Именованные предпочтительнее: при изменении порядка аргументов позиционные молча
ломаются.

### Нативный SQL

```java
@Query(
        value = "select * from orders where status = :status",
        nativeQuery = true
)
List<Order> findByStatusNative(@Param("status") String status);
```

Нужен, когда требуется то, чего нет в JPQL: оконные функции, специфичные для
PostgreSQL конструкции, `ON CONFLICT`, работа с JSONB. Цена — привязка к диалекту
и отсутствие проверки при старте.

Существенная деталь: JPQL-запросы разбираются при инициализации контекста, поэтому
опечатка в имени поля обнаружится при старте приложения. Нативный запрос — просто
строка, и ошибка в нём проявится только при вызове.

### @Modifying

Изменяющие запросы требуют отдельной аннотации:

```java
@Modifying
@Transactional
@Query("update Order o set o.status = :status where o.id = :id")
int updateStatus(@Param("id") Long id, @Param("status") OrderStatus status);
```

Без `@Modifying` будет исключение: Spring Data попытается выполнить запрос как
выборку.

Но главная ловушка не в этом. Такой запрос идёт **мимо контекста персистентности**:

```text
выполняется прямой UPDATE в базе
→ сущности, уже загруженные в контекст, остаются со старыми значениями
→ dirty checking при сбросе может затереть изменение
```

Отсюда параметры:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
```

Первый очищает контекст после выполнения, второй сбрасывает накопленные изменения
до. Пользоваться ими нужно осознанно: очистка контекста отсоединяет все загруженные
сущности, и обращение к ним после этого даст `LazyInitializationException`.

Разумное правило: массовое обновление одним запросом выполнять в отдельном методе,
не смешивая с работой через сущности.

### @EntityGraph

Способ побороть N+1 не переписывая запрос:

```java
@EntityGraph(attributePaths = {"items", "customer"})
List<Order> findByStatus(OrderStatus status);
```

Перечисленные связи загружаются одним запросом с соединением, даже если в сущности
они помечены ленивыми. Это предпочтительнее, чем менять `fetch` на `EAGER` в самой
сущности: жадность в объявлении действует всегда, а граф — только там, где нужен.

## Пагинация и сортировка

```java
Page<Order> findByStatus(OrderStatus status, Pageable pageable);
```

```java
Pageable pageable = PageRequest.of(0, 20, Sort.by("createdAt").descending());

Page<Order> page = orderRepository.findByStatus(OrderStatus.NEW, pageable);

page.getContent();        // список
page.getTotalElements();  // всего записей
page.getTotalPages();
page.hasNext();
```

В контроллере `Pageable` можно принимать прямо параметром — Spring MVC соберёт его
из query-параметров `page`, `size` и `sort`.

### Page против Slice

```text
Page  → знает общее количество, выполняет дополнительный count-запрос
Slice → знает только, есть ли следующая страница; берёт на один элемент больше
List  → просто срез, без информации о следующих
```

Разница практическая: `count` по большой таблице с фильтром может оказаться
дороже самой выборки. Если интерфейсу не нужен номер последней страницы —
бесконечная прокрутка, мобильный список, — `Slice` экономит целый запрос.

### Пагинация и join fetch

Самая болезненная связка в теме.

```java
@Query("select o from Order o join fetch o.items where o.status = :status")
Page<Order> findWithItems(@Param("status") OrderStatus status, Pageable pageable);
```

В логе появится предупреждение `HHH000104: firstResult/maxResults specified with
collection fetch; applying in memory`.

Причина: соединение с коллекцией размножает строки. Заказ с тремя позициями даёт
три строки результата, и `LIMIT 20` отрежет не двадцать заказов, а двадцать строк.
Чтобы вернуть корректную страницу, Hibernate загружает **всю** выборку в память и
режет её там.

На тысяче заказов это незаметно, на миллионе — гарантированная нехватка памяти.

Решения:

```text
@EntityGraph вместо join fetch → Hibernate сам выберет безопасную стратегию
два запроса → сначала страница идентификаторов, затем загрузка с join fetch по in
@BatchSize на коллекции → N+1 превращается в несколько запросов вместо тысячи
```

Соединение с связью типа «к одному» проблемы не создаёт: строк не становится
больше.

### Сортировка

```java
Sort.by("createdAt").descending().and(Sort.by("id"));
```

Две вещи стоит помнить. Сортировка по полю, которого нет в сущности, даст ошибку
при выполнении, а не при старте. И сортировка по вычисляемому выражению в
производном методе невозможна — для этого нужен `@Query` либо `JpaSort.unsafe()`,
который открывает дорогу для SQL-инъекции, если строка приходит от пользователя.

## Проекции

Возвращать сущность, когда нужны два поля, — расточительно: грузится весь объект,
он попадает в контекст, для него создаётся снимок для dirty checking.

### Интерфейсная проекция

```java
public interface OrderSummary {

    Long getId();

    String getNumber();

    BigDecimal getTotal();
}
```

```java
List<OrderSummary> findByStatus(OrderStatus status);
```

Spring Data сгенерирует прокси и выберет из базы только три колонки. Это закрытая
проекция — все её методы соответствуют свойствам сущности.

Открытая проекция использует выражение:

```java
public interface OrderView {

    @Value("#{target.customer.name + ' / ' + target.number}")
    String getTitle();
}
```

Удобно, но цена высока: для вычисления выражения нужна сущность целиком, поэтому
оптимизация выборки колонок отключается.

### DTO через конструктор

```java
public record OrderSummary(Long id, String number, BigDecimal total) {
}
```

```java
@Query("""
        select new com.example.order.OrderSummary(o.id, o.number, o.total)
        from Order o
        where o.status = :status
        """)
List<OrderSummary> findSummaries(@Param("status") OrderStatus status);
```

Либо без `@Query` — Spring Data сам сопоставит конструктор с производным методом:

```java
List<OrderSummary> findByStatus(OrderStatus status);
```

`record` подходит идеально. В отличие от сущности, проекция не управляется
контекстом, снимков для неё не создаётся и изменения в базу не попадут — именно то,
что нужно для чтения.

### Динамическая проекция

```java
<T> List<T> findByStatus(OrderStatus status, Class<T> type);
```

```java
List<OrderSummary> summaries = repository.findByStatus(NEW, OrderSummary.class);
List<Order> orders = repository.findByStatus(NEW, Order.class);
```

Один метод обслуживает разные представления.

## Динамические запросы

Когда набор условий зависит от ввода пользователя, производные методы и `@Query`
не подходят: писать метод на каждое сочетание фильтров бессмысленно.

### Specification

```java
public interface OrderRepository
        extends JpaRepository<Order, Long>, JpaSpecificationExecutor<Order> {
}
```

```java
public final class OrderSpecifications {

    public static Specification<Order> hasStatus(OrderStatus status) {
        return (root, query, cb) -> status == null
                ? null
                : cb.equal(root.get("status"), status);
    }

    public static Specification<Order> createdAfter(Instant from) {
        return (root, query, cb) -> from == null
                ? null
                : cb.greaterThan(root.get("createdAt"), from);
    }
}
```

```java
Specification<Order> spec = Specification
        .where(hasStatus(filter.status()))
        .and(createdAfter(filter.from()));

Page<Order> page = orderRepository.findAll(spec, pageable);
```

Возврат `null` из спецификации означает «условие не применяется» — это и делает
сборку фильтра удобной.

Под капотом Criteria API, поэтому код получается многословным. Зато проверяется
компилятором и не склеивается из строк.

### Query by Example

```java
Order probe = new Order();
probe.setStatus(OrderStatus.NEW);

Example<Order> example = Example.of(probe);

List<Order> orders = orderRepository.findAll(example);
```

Простой способ искать по совпадению заполненных полей. Ограничения серьёзные:
только равенство, нет диапазонов и условий `or`, не работает с примитивами, у
которых нет `null`. Годится для несложного поиска, дальше — спецификации.

## save и удаление

### Что делает save

```java
orderRepository.save(order);
```

Внутри — проверка на новизну и вызов `persist` либо `merge`:

```text
сущность новая  → persist
иначе           → merge, а значит дополнительный SELECT
```

Новизна определяется по идентификатору: `null` или нулевое значение примитива
означает новую сущность.

Отсюда важное следствие: для управляемой сущности вызов `save()` не нужен вовсе —
изменения запишет dirty checking. Лишний вызов приводит к `merge` и лишнему
запросу.

### Когда isNew ошибается

Если идентификатор присваивается приложением, а не базой — например, `UUID`,
сгенерированный в конструкторе, — проверка сломается: `id` не `null`, значит
сущность «не новая», значит `merge`, значит лишний `SELECT` перед каждой вставкой.

Решение — реализовать `Persistable`:

```java
@Entity
public class Order implements Persistable<UUID> {

    @Id
    private UUID id;

    @Transient
    private boolean isNew = true;

    @Override
    public boolean isNew() {
        return isNew;
    }

    @PostPersist
    @PostLoad
    void markNotNew() {
        this.isNew = false;
    }
}
```

Вопрос про это задают редко, но он хорошо показывает, что `save()` — не магия, а
обычная ветвь `if`.

### saveAll и пакетная вставка

```java
orderRepository.saveAll(orders);
```

Метод не делает пакетной вставки сам по себе — он вызывает `save()` в цикле. Для
настоящих пакетов нужна настройка Hibernate:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
        order_updates: true
```

И генерация идентификаторов через `SEQUENCE`: с `IDENTITY` пакетная вставка
невозможна в принципе, потому что идентификатор известен только после `INSERT`.

### Удаление

```text
delete(entity)        загружает сущность, удаляет по одной, каскады работают
deleteAll()           то же для всех записей: SELECT, затем DELETE на каждую
deleteAllInBatch()    один DELETE на таблицу, каскады и события не работают
deleteById(id)        сначала SELECT, затем DELETE
```

Разница принципиальная. `deleteAll()` на десяти тысячах записей выполнит десять
тысяч запросов. `deleteAllInBatch()` — один, но в обход контекста: события
жизненного цикла не сработают, `orphanRemoval` не отработает, загруженные сущности
останутся в контексте устаревшими.

## Транзакции

Методы `SimpleJpaRepository` уже транзакционные: читающие помечены
`@Transactional(readOnly = true)`, изменяющие — обычной `@Transactional`.

Из этого иногда делают неверный вывод, что транзакция в сервисе не нужна. Нужна, и
вот почему:

```java
public void process(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    order.setStatus(OrderStatus.DONE);
    // изменение не сохранится
}
```

Транзакция закрылась вместе с вызовом `findById`, сущность стала отсоединённой, и
dirty checking не сработает. Границу транзакции задаёт бизнес-операция, а не
отдельный запрос к базе.

Второе следствие — атомарность. Два вызова репозитория без общей транзакции
выполнятся в двух разных, и откат первого при ошибке второго не произойдёт.

```java
@Transactional
public void process(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    order.setStatus(OrderStatus.DONE);
}
```

Для операций только на чтение полезен `@Transactional(readOnly = true)` на уровне
сервиса: Hibernate не создаёт снимки для dirty checking, а драйвер может
направить запрос на реплику.

## Типичные ошибки

### Вызывать save для управляемой сущности

Изменения запишет dirty checking. Лишний вызов означает `merge` и дополнительный
`SELECT`.

### Обходиться без транзакции в сервисе

Каждый вызов репозитория откроет свою транзакцию. Сущность станет отсоединённой
сразу после чтения, а несколько операций перестанут быть атомарными.

### Соединять коллекцию с пагинацией

`join fetch` вместе с `Pageable` заставляет Hibernate грузить всю выборку в память.
Нужен `@EntityGraph` или два запроса.

### Использовать EAGER вместо графа

Жадная загрузка в объявлении сущности действует всегда, даже там, где связь не
нужна. `@EntityGraph` включает её точечно.

### Забывать @Modifying

Изменяющий запрос без аннотации приведёт к исключению.

### Не учитывать, что @Modifying идёт мимо контекста

Загруженные сущности останутся со старыми значениями, а dirty checking способен
затереть изменение.

### Применять clearAutomatically не думая

Очистка контекста отсоединяет все сущности, и последующее обращение к ленивым
связям даст `LazyInitializationException`.

### Возвращать сущность там, где нужна проекция

Грузится весь объект, создаётся снимок для dirty checking, сущность попадает в
контекст. Для чтения достаточно интерфейса или `record`.

### Писать производные методы на пять условий

Имя становится нечитаемым. Три условия — разумный предел, дальше `@Query` или
спецификация.

### Использовать Page там, где достаточно Slice

Дополнительный `count` по большой таблице может стоить дороже самой выборки.

### Считать saveAll пакетной вставкой

Без настройки `batch_size` и генерации через `SEQUENCE` это обычный цикл вызовов
`save()`.

### Путать deleteAll и deleteAllInBatch

Первый выполняет запрос на каждую запись, второй — один, но в обход каскадов и
событий.

### Полагаться на нативный запрос как на проверяемый

JPQL разбирается при старте, нативный SQL — обычная строка, и ошибка в нём
проявится только при вызове.

## Краткий ответ для собеседования

Spring Data JPA избавляет от написания реализаций репозиториев: достаточно
объявить интерфейс, наследующий `JpaRepository`, а прокси создаётся при старте
контекста. Базовые методы реализованы в обычном классе `SimpleJpaRepository`,
внутри которого лежит `EntityManager`, — никакой магии там нет.

Запросы объявляются тремя способами. Производные методы разбираются по имени и
удобны примерно до трёх условий, дальше имя становится нечитаемым. `@Query` с
JPQL пишется по сущностям и проверяется при старте приложения. Нативный SQL нужен
для специфичных для СУБД конструкций, но он остаётся обычной строкой, и ошибка в
нём всплывёт только при вызове. Изменяющие запросы требуют `@Modifying` и идут
мимо контекста персистентности, из-за чего уже загруженные сущности остаются со
старыми значениями.

Пагинация задаётся объектом `Pageable`. `Page` дополнительно выполняет `count`,
`Slice` обходится без него и потому дешевле, когда номер последней страницы не
нужен. Отдельная ловушка — соединение с коллекцией вместе с пагинацией:
соединение размножает строки, и Hibernate вынужден грузить всю выборку в память,
о чём честно предупреждает в логе. Лечится графом сущности, двумя запросами или
пакетной загрузкой.

Для чтения предпочтительны проекции, а не сущности: интерфейс или `record`
позволяют выбрать только нужные колонки, не помещая объект в контекст и не создавая
снимок для отслеживания изменений. Когда набор условий зависит от пользователя,
применяют спецификации на Criteria API.

Метод `save()` не соответствует напрямую ни `persist`, ни `merge`: он проверяет
новизну сущности по идентификатору и выбирает одно из двух. Для управляемой
сущности вызывать его не нужно — изменения запишет dirty checking.

Наконец, транзакционность методов репозитория не отменяет необходимости
`@Transactional` на уровне сервиса: границу транзакции задаёт бизнес-операция, а
иначе сущность оказывается отсоединённой сразу после чтения.

## Вопросы на собеседовании

### 1. Что такое Spring Data JPA?

**Ответ:** надстройка над JPA, избавляющая от написания реализаций репозиториев.
Правила самой JPA она не меняет: контекст персистентности, состояния сущности и
ленивая загрузка работают как прежде.

### 2. Как устроена иерархия интерфейсов репозиториев?

**Ответ:** `Repository` — маркер без методов, `CrudRepository` добавляет базовые
операции, `PagingAndSortingRepository` — пагинацию и сортировку, `JpaRepository` —
специфичные для JPA методы вроде `flush` и `deleteAllInBatch`.

### 3. Зачем наследоваться от Repository напрямую?

**Ответ:** чтобы объявить только нужные методы и не открывать в публичном API
удаление там, где репозиторий должен только читать.

### 4. Откуда берётся реализация репозитория?

**Ответ:** при старте создаётся динамический прокси; базовые методы реализованы в
классе `SimpleJpaRepository`, работающем через `EntityManager`.

### 5. Как добавить собственный метод с ручным запросом?

**Ответ:** объявить отдельный интерфейс-фрагмент, реализовать его в классе с
суффиксом `Impl` и унаследовать основной репозиторий от обоих.

### 6. Как работают производные методы?

**Ответ:** имя метода разбирается на префикс, свойства и ключевые слова, из
которых строится запрос. Ошибка в имени свойства обнаруживается при старте.

### 7. Какие ключевые слова доступны в именах методов?

**Ответ:** `And`, `Or`, `Between`, `LessThan`, `After`, `IsNull`, `Like`,
`StartingWith`, `Containing`, `In`, `IgnoreCase`, `OrderBy`, `Top`, `First`,
`Distinct` и другие.

### 8. Как обратиться к полю связанной сущности?

**Ответ:** указать путь в имени метода, при неоднозначности разделив его
подчёркиванием: `findByCustomer_Name`.

### 9. До какой сложности стоит пользоваться производными методами?

**Ответ:** примерно до трёх условий. Дальше имя становится нечитаемым, и лучше
перейти на `@Query` или спецификацию.

### 10. Чем JPQL отличается от нативного SQL в @Query?

**Ответ:** JPQL оперирует сущностями и проверяется при инициализации контекста,
нативный запрос — строка на диалекте конкретной СУБД, и ошибка в нём проявится
только при вызове.

### 11. Когда оправдан нативный запрос?

**Ответ:** когда нужны возможности, которых нет в JPQL: оконные функции,
`ON CONFLICT`, работа с JSONB, специфичные подсказки планировщику.

### 12. Чем именованные параметры лучше позиционных?

**Ответ:** они не ломаются при изменении порядка аргументов метода.

### 13. Для чего нужна аннотация @Modifying?

**Ответ:** она помечает запрос как изменяющий. Без неё Spring Data попытается
выполнить `update` или `delete` как выборку и выбросит исключение.

### 14. Чем опасен запрос с @Modifying?

**Ответ:** он выполняется мимо контекста персистентности. Загруженные сущности
остаются со старыми значениями, а dirty checking при сбросе способен затереть
изменение.

### 15. Что делают clearAutomatically и flushAutomatically?

**Ответ:** первый очищает контекст после выполнения запроса, второй сбрасывает
накопленные изменения до него. Очистка отсоединяет все сущности, поэтому применять
её нужно осознанно.

### 16. Для чего нужен @EntityGraph?

**Ответ:** чтобы загрузить указанные связи одним запросом там, где это нужно, не
делая их жадными в объявлении сущности.

### 17. Чем Page отличается от Slice?

**Ответ:** `Page` знает общее количество записей и выполняет дополнительный
`count`. `Slice` знает только, есть ли следующая страница, и берёт на один элемент
больше.

### 18. Когда Slice предпочтительнее?

**Ответ:** когда интерфейсу не нужен номер последней страницы — бесконечная
прокрутка, мобильные списки. `count` по большой таблице может стоить дороже самой
выборки.

### 19. Что произойдёт при join fetch коллекции вместе с Pageable?

**Ответ:** соединение размножит строки, и чтобы вернуть корректную страницу,
Hibernate загрузит всю выборку в память. В логе появится предупреждение
`HHH000104`, а на больших объёмах — нехватка памяти.

### 20. Как правильно сделать страницу с загруженной коллекцией?

**Ответ:** через `@EntityGraph`, через два запроса — сначала страница
идентификаторов, затем загрузка по ним с соединением — либо через `@BatchSize`.

### 21. Создаёт ли соединение со связью «к одному» ту же проблему?

**Ответ:** нет. Число строк при этом не увеличивается, поэтому пагинация работает
корректно.

### 22. Зачем нужны проекции?

**Ответ:** чтобы не грузить сущность целиком ради нескольких полей. Проекция не
попадает в контекст, для неё не создаётся снимок и изменения в базу не пишутся.

### 23. Чем закрытая интерфейсная проекция отличается от открытой?

**Ответ:** в закрытой все методы соответствуют свойствам сущности, и выбираются
только нужные колонки. Открытая использует выражение `@Value`, для вычисления
которого нужна сущность целиком, поэтому оптимизация отключается.

### 24. Как вернуть DTO из репозитория?

**Ответ:** объявить `record` и либо использовать конструктор в JPQL, либо просто
указать его как возвращаемый тип производного метода.

### 25. Что такое динамическая проекция?

**Ответ:** метод с параметром `Class<T>`, позволяющий одним объявлением получать
разные представления одной выборки.

### 26. Когда применяют Specification?

**Ответ:** когда набор условий зависит от ввода пользователя и писать метод на
каждое сочетание фильтров нецелесообразно.

### 27. Что означает возврат null из спецификации?

**Ответ:** что условие не применяется. Это позволяет собирать фильтр из
необязательных частей.

### 28. Какие ограничения у Query by Example?

**Ответ:** только равенство заполненных полей, нет диапазонов и условий `or`, не
работает с примитивами, у которых отсутствует `null`.

### 29. Что делает метод save?

**Ответ:** проверяет, новая ли сущность, обычно по `null` в идентификаторе, и
вызывает `persist` либо `merge`. Во втором случае выполняется дополнительный
`SELECT`.

### 30. Нужно ли вызывать save для загруженной сущности?

**Ответ:** нет. Она управляемая, и изменения запишет dirty checking. Лишний вызов
приведёт к `merge`.

### 31. Что сломается, если идентификатор присваивает приложение?

**Ответ:** проверка на новизну: идентификатор не `null`, поэтому `save` выполнит
`merge` с лишним запросом. Решается реализацией интерфейса `Persistable`.

### 32. Выполняет ли saveAll пакетную вставку?

**Ответ:** сам по себе нет, это цикл вызовов `save`. Нужны настройка `batch_size`
у Hibernate и генерация идентификаторов через `SEQUENCE`.

### 33. Чем deleteAll отличается от deleteAllInBatch?

**Ответ:** первый загружает сущности и выполняет запрос на каждую, поддерживая
каскады и события. Второй делает один запрос, но идёт мимо контекста, и ни каскады,
ни `orphanRemoval` не срабатывают.

### 34. Транзакционны ли методы репозитория?

**Ответ:** да, читающие помечены `readOnly`, изменяющие — обычной
`@Transactional`.

### 35. Зачем тогда @Transactional в сервисе?

**Ответ:** границу транзакции задаёт бизнес-операция. Без неё сущность становится
отсоединённой сразу после чтения, dirty checking не сработает, а несколько вызовов
репозитория перестанут быть атомарными.
