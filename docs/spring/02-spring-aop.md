# Spring AOP и прокси

## Какую задачу решает

Есть логика, которая не относится ни к одному слою в отдельности, но нужна во
многих местах: транзакции, логирование, кеширование, метрики, проверка прав.

Без AOP она расползается по коду:

```java
public void createOrder(Order order) {
    long start = System.currentTimeMillis();
    log.info("createOrder start");

    TransactionStatus tx = txManager.getTransaction(definition);
    try {
        orderRepository.save(order);          // единственная полезная строка
        txManager.commit(tx);
    } catch (Exception e) {
        txManager.rollback(tx);
        throw e;
    } finally {
        log.info("createOrder done in {} ms", System.currentTimeMillis() - start);
    }
}
```

Полезного — одна строка. Остальное повторяется в каждом методе и смешивает
инфраструктуру с бизнес-логикой.

Такая логика называется сквозной функциональностью (cross-cutting concern). AOP
позволяет описать её один раз и применить к нужным методам декларативно:

```java
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
}
```

## Терминология

```text
Join point → точка, куда можно вклиниться
             в Spring AOP это всегда вызов метода

Pointcut   → выражение, отбирающее нужные join points
             «все методы в пакете service»

Advice     → сам код, который выполняется
             «открыть транзакцию до, закрыть после»

Aspect     → модуль, объединяющий pointcut и advice

Target     → исходный объект, к которому применяется аспект

Proxy      → обёртка вокруг target, которую получает вызывающий код

Weaving    → процесс связывания аспектов с целевым кодом
```

Самое частое затруднение — различить pointcut и advice. Pointcut отвечает на вопрос
«где», advice — «что делать».

## Виды advice

```java
@Aspect
@Component
public class LoggingAspect {

    @Before("execution(* com.example.service.*.*(..))")
    public void before(JoinPoint joinPoint) {
        log.info("before {}", joinPoint.getSignature().getName());
    }

    @AfterReturning(pointcut = "...", returning = "result")
    public void afterReturning(JoinPoint joinPoint, Object result) {
    }

    @AfterThrowing(pointcut = "...", throwing = "error")
    public void afterThrowing(JoinPoint joinPoint, Throwable error) {
    }

    @After("...")
    public void after(JoinPoint joinPoint) {
        // выполняется всегда, как finally
    }

    @Around("...")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();      // вызов целевого метода
        } finally {
            log.info("took {} ns", System.nanoTime() - start);
        }
    }
}
```

```text
@Before         → до вызова
@AfterReturning → после успешного возврата
@AfterThrowing  → при выбросе исключения
@After          → всегда, аналог finally
@Around         → полный контроль: до, после, вместо
```

`@Around` — самый мощный: он может изменить аргументы, подменить результат,
подавить исключение или вовсе не вызвать целевой метод. Именно на нём построены
транзакции и кеширование: `@Cacheable` при попадании в кеш просто не вызывает
`proceed()`.

Обязательное условие: `@Around` должен вернуть результат `proceed()`, иначе
вызывающий получит `null`. Это распространённая ошибка.

## Pointcut-выражения

```java
execution(* com.example.service.*.*(..))
```

Разбор по частям:

```text
execution   → выполнение метода
*           → любой возвращаемый тип
com.example.service.*  → любой класс в пакете
.*          → любой метод
(..)        → любые аргументы
```

Другие обозначения:

```java
within(com.example.service..*)          // всё внутри пакета и подпакетов
@annotation(com.example.Audited)        // методы, помеченные аннотацией
@within(org.springframework.stereotype.Service)  // методы классов с аннотацией
bean(*Service)                          // бины по имени
args(String, ..)                        // по типам аргументов
```

Выражения можно комбинировать и выносить в именованные pointcut:

```java
@Pointcut("within(com.example.service..*)")
public void serviceLayer() {}

@Pointcut("@annotation(com.example.Audited)")
public void audited() {}

@Around("serviceLayer() && audited()")
public Object audit(ProceedingJoinPoint pjp) throws Throwable {
    return pjp.proceed();
}
```

На практике чаще всего используют `@annotation(...)` — он явно виден в коде, в
отличие от выражения по пакетам, которое начинает применяться к новым классам
незаметно.

## Weaving

Связывание аспектов с кодом возможно на трёх этапах.

```text
compile-time weaving
→ AspectJ-компилятор вставляет код прямо в байт-код при сборке
→ работает где угодно, включая поля и конструкторы
→ требует отдельного компилятора

load-time weaving
→ байт-код модифицируется агентом при загрузке класса
→ требует -javaagent

runtime weaving (proxy-based)
→ создаётся объект-обёртка
→ это и есть Spring AOP
→ ничего дополнительно настраивать не нужно
```

Spring AOP использует третий вариант. Отсюда все его ограничения.

---

## Spring AOP против AspectJ

```text
Spring AOP
→ только вызовы методов
→ только публичные и protected методы
→ только бины контейнера
→ вызов изнутри класса не перехватывается
→ никакой дополнительной настройки

AspectJ
→ методы, поля, конструкторы, статические инициализаторы
→ любые объекты, не только бины
→ внутренние вызовы перехватываются
→ нужен компилятор или агент
```

Для типового приложения возможностей Spring AOP достаточно, и в подавляющем
большинстве проектов используется именно он.

## Как создаётся прокси

Прокси создаёт `BeanPostProcessor` — тот самый механизм из жизненного цикла бина.
После инициализации постпроцессор проверяет, подходит ли бин под какой-либо
pointcut, и если да, возвращает вместо него обёртку.

```text
контейнер создал OrderService
→ BeanPostProcessor.postProcessAfterInitialization
→ бин подходит под pointcut
→ вместо него в контейнер попадает прокси
```

Ключевое следствие: **все, кто внедряет `OrderService`, получают прокси, а не
исходный объект**. Исходный объект существует, но на него ссылается только сам
прокси.

```text
клиент → прокси → target
```

### JDK Dynamic Proxy

Работает, если у класса есть интерфейс. Использует `java.lang.reflect.Proxy` и
создаёт класс, реализующий тот же интерфейс.

```java
public interface OrderService { void createOrder(Order order); }

@Service
public class OrderServiceImpl implements OrderService { }
```

Ограничение существенное: прокси реализует интерфейс, но не наследует класс.
Поэтому внедрять его можно только по типу интерфейса — попытка внедрить по типу
`OrderServiceImpl` завершится ошибкой.

### CGLIB

Генерирует подкласс целевого класса, переопределяя его методы. Интерфейс не нужен.

Ограничения вытекают из наследования:

```text
final-класс   → унаследовать невозможно, прокси не создастся
final-метод   → нельзя переопределить, аннотация не сработает
private-метод → не наследуется, перехвата нет
static-метод  → не переопределяется
```

Причём `final`-метод — молчаливая ошибка: приложение стартует, аннотация не
работает, никаких предупреждений.

### Что выбирает Spring

```text
до Spring Boot 2.0 → JDK Proxy при наличии интерфейса, иначе CGLIB
с Spring Boot 2.0  → CGLIB по умолчанию всегда
```

Переключается свойством `spring.aop.proxy-target-class`. Причина перехода на CGLIB
— меньше сюрпризов: не нужно помнить, что бин с интерфейсом нельзя внедрить по
классу.

## Self-invocation

Главное ограничение прокси-подхода и самый частый вопрос по теме.

```java
@Service
public class OrderService {

    public void processAll(List<Order> orders) {
        for (Order order : orders) {
            save(order);              // вызов через this
        }
    }

    @Transactional
    public void save(Order order) {
        orderRepository.save(order);
    }
}
```

Внешний вызов `processAll()` идёт через прокси. Но внутренний вызов `save()`
выполняется напрямую через `this` — то есть на целевом объекте, а не на прокси.
Перехватывать некому, транзакция не открывается.

```text
клиент → прокси → processAll на target
                       ↓
                  this.save() → прямой вызов, прокси не участвует
```

Ошибки не будет. Код просто выполнится вне транзакции.

Та же логика распространяется на `@Cacheable`, `@Async`, `@Retryable`,
`@PreAuthorize` — на всё, что построено на прокси.

### Решения

**Вынести в отдельный бин** — правильный и обычно самый чистый вариант:

```java
@Service
public class OrderProcessor {

    private final OrderSaver orderSaver;   // другой бин, вызов идёт через прокси

    public void processAll(List<Order> orders) {
        orders.forEach(orderSaver::save);
    }
}
```

**Внедрить самого себя:**

```java
@Service
public class OrderService {

    @Lazy
    private final OrderService self;

    public void processAll(List<Order> orders) {
        orders.forEach(self::save);
    }
}
```

`@Lazy` необходим, иначе получится циклическая зависимость через конструктор.

**Получить прокси из контекста:**

```java
((OrderService) AopContext.currentProxy()).save(order);
```

Требует `@EnableAspectJAutoProxy(exposeProxy = true)`. Работает, но привязывает код
к Spring и читается плохо.

**Перейти на AspectJ** с load-time weaving — тогда перехват работает и для
внутренних вызовов. Решение тяжеловесное и применяется редко.

## Что делает прокси для @Transactional

Теперь механизм можно описать целиком.

```text
1. вызов метода приходит на прокси
2. перехватчик читает @Transactional через рефлексию
3. открывает транзакцию через PlatformTransactionManager
4. вызывает целевой метод
5. успех       → commit
   исключение  → rollback либо commit, в зависимости от типа
6. возвращает результат вызывающему
```

Из этого следуют вещи, которые иначе выглядят необъяснимыми:

```text
self-invocation не работает   → прокси не участвует
private-метод не работает     → нельзя переопределить
final-метод не работает       → нельзя переопределить
аннотация на @PostConstruct   → прокси ещё не создан на момент вызова
```

Последний пункт стоит пояснить. `@PostConstruct` вызывается на этапе инициализации,
а прокси создаётся после неё, в `postProcessAfterInitialization`. Поэтому
`@Transactional` на методе инициализации не сработает — оборачивать ещё нечего.

## Порядок аспектов

Когда к методу применимо несколько аспектов, порядок задаётся `@Order`: меньшее
значение выполняется раньше и оборачивает остальные.

```java
@Aspect
@Component
@Order(1)
public class LoggingAspect { }

@Aspect
@Component
@Order(2)
public class MetricsAspect { }
```

```text
Logging.before → Metrics.before → метод → Metrics.after → Logging.after
```

Порядок имеет значение: аспект логирования снаружи транзакционного увидит успешное
завершение метода до фиксации транзакции, а изнутри — после.

## Типичные ошибки

### Ожидать работы аннотации при вызове изнутри класса

Прокси не участвует во внутреннем вызове через `this`.

### Ставить @Transactional на private-метод

Прокси не может его перехватить, аннотация игнорируется молча.

### Делать класс или метод final при использовании CGLIB

Наследование невозможно, прокси не создастся или метод не будет переопределён.

### Не возвращать результат proceed() в @Around

Вызывающий получит `null`.

### Внедрять бин с JDK-прокси по типу реализации

Прокси реализует интерфейс, но не наследует класс. Нужно внедрять по интерфейсу или
переключиться на CGLIB.

### Ожидать работы аннотации в @PostConstruct

На момент инициализации прокси ещё не создан.

### Писать слишком широкий pointcut

`execution(* com.example..*.*(..))` со временем начинает применяться к новым
классам незаметно для автора. Надёжнее `@annotation`.

### Забывать про стоимость @Around

Каждый вызов проходит через дополнительный слой с рефлексией. На горячем пути это
заметно.

### Считать, что AOP перехватывает обращения к полям

Spring AOP работает только с вызовами методов. Поля и конструкторы — только
AspectJ.

## Краткая памятка

```text
join point → точка вклинивания, в Spring AOP только вызов метода
pointcut   → где
advice     → что
aspect     → pointcut + advice
target     → исходный объект
proxy      → обёртка, которую получает клиент
```

```text
@Before / @After / @AfterReturning / @AfterThrowing / @Around
@Around → полный контроль, обязан вернуть proceed()
```

```text
weaving
compile-time → AspectJ-компилятор
load-time    → javaagent
runtime      → прокси ← Spring AOP
```

```text
JDK Dynamic Proxy → нужен интерфейс, внедрять только по интерфейсу
CGLIB             → подкласс, интерфейс не нужен
                    ломается на final и private

Spring Boot 2.0+ → CGLIB по умолчанию
```

```text
прокси создаётся в BeanPostProcessor.postProcessAfterInitialization
→ в контейнер попадает обёртка, не исходный объект

не работает:
self-invocation, private, final, static, @PostConstruct
```

## Краткий ответ для собеседования

AOP решает проблему сквозной функциональности — логики, которая нужна во многих
местах, но не относится к бизнес-задаче: транзакции, логирование, кеширование,
метрики.

Основные понятия: join point — точка вклинивания, в Spring AOP это всегда вызов
метода; pointcut — выражение, отбирающее такие точки; advice — код, который
выполняется; аспект объединяет их.

Spring AOP реализован через прокси, создаваемые во время выполнения. Прокси
создаёт `BeanPostProcessor` после инициализации бина, и в контейнер попадает
обёртка, а не исходный объект. Используются два механизма: JDK Dynamic Proxy,
который требует интерфейс и реализует его, и CGLIB, который генерирует подкласс.
Начиная со Spring Boot 2.0 по умолчанию применяется CGLIB.

Отсюда ограничения. Вызов метода изнутри того же класса идёт через `this`, минуя
прокси, поэтому аннотация не срабатывает. То же касается `private`- и
`final`-методов: их невозможно переопределить в подклассе. Ошибок при этом не
возникает — код просто выполняется без ожидаемого поведения.

Так работает `@Transactional`: перехватчик открывает транзакцию, вызывает целевой
метод и фиксирует или откатывает её в зависимости от результата. По тому же
принципу устроены `@Cacheable`, `@Async` и `@PreAuthorize`.

## Вопросы на собеседовании

### 1. Какую задачу решает AOP?

**Ответ:** выносит сквозную функциональность — транзакции, логирование,
кеширование, метрики — из бизнес-логики, позволяя описать её один раз и применять
декларативно.

### 2. Что такое join point, pointcut и advice?

**Ответ:** join point — точка, куда можно вклиниться, в Spring AOP это вызов
метода. Pointcut — выражение, отбирающее такие точки. Advice — код, который
выполняется.

### 3. Какие есть виды advice?

**Ответ:** `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing` и `@Around`.
Последний даёт полный контроль и может не вызывать целевой метод вовсе.

### 4. Чем @Around отличается от остальных?

**Ответ:** он оборачивает вызов целиком, может изменить аргументы, подменить
результат, подавить исключение или не вызывать метод. Обязан вернуть результат
`proceed()`.

### 5. Какие бывают виды weaving?

**Ответ:** во время компиляции через AspectJ-компилятор, при загрузке класса через
агент и во время выполнения через прокси. Spring AOP использует последний.

### 6. Чем Spring AOP отличается от AspectJ?

**Ответ:** Spring AOP перехватывает только вызовы методов на бинах контейнера и не
видит внутренних вызовов. AspectJ работает с полями и конструкторами, с любыми
объектами и перехватывает внутренние вызовы, но требует компилятора или агента.

### 7. Где создаётся прокси?

**Ответ:** в `BeanPostProcessor`, на этапе `postProcessAfterInitialization`. В
контейнер попадает обёртка вместо исходного объекта.

### 8. Чем JDK Dynamic Proxy отличается от CGLIB?

**Ответ:** JDK-прокси реализует интерфейс целевого класса и требует его наличия.
CGLIB генерирует подкласс и обходится без интерфейса, но не работает с `final`.

### 9. Какой механизм используется по умолчанию?

**Ответ:** до Spring Boot 2.0 — JDK-прокси при наличии интерфейса, иначе CGLIB. С
версии 2.0 — всегда CGLIB.

### 10. Почему @Transactional не работает на private-методе?

**Ответ:** прокси перехватывает вызовы через переопределение методов в подклассе, а
`private`-методы не наследуются.

### 11. Что произойдёт, если пометить final-метод аннотацией @Transactional?

**Ответ:** CGLIB не сможет его переопределить, и аннотация будет проигнорирована
без каких-либо ошибок.

### 12. Что такое self-invocation и почему это проблема?

**Ответ:** вызов метода изнутри того же класса идёт через `this`, минуя прокси.
Перехватчик не срабатывает, и транзакция или кеширование не применяются.

### 13. Как обойти self-invocation?

**Ответ:** вынести метод в отдельный бин, внедрить самого себя через `@Lazy`,
получить прокси через `AopContext.currentProxy()` или перейти на AspectJ.
Предпочтителен первый вариант.

### 14. Почему @Transactional не работает в методе с @PostConstruct?

**Ответ:** прокси создаётся после инициализации бина, а `@PostConstruct`
вызывается во время неё — оборачивать ещё нечего.

### 15. Что получает бин, внедряющий проксированный сервис?

**Ответ:** прокси, а не исходный объект. На целевой объект ссылается только сам
прокси.

### 16. Как задать порядок нескольких аспектов?

**Ответ:** через `@Order`. Меньшее значение выполняется раньше и оборачивает
остальные.

### 17. Можно ли перехватить обращение к полю через Spring AOP?

**Ответ:** нет, только вызовы методов. Для полей и конструкторов нужен AspectJ.

### 18. Как работает @Transactional изнутри?

**Ответ:** прокси перехватывает вызов, читает аннотацию, открывает транзакцию через
менеджер транзакций, вызывает целевой метод и по результату выполняет фиксацию или
откат.
