# Spring Core: IoC, DI и контейнер

## Inversion of Control

Обычный код сам создаёт свои зависимости:

```java
public class OrderService {

    private final PaymentClient paymentClient = new PaymentClient("https://api...");
}
```

Класс жёстко привязан к конкретной реализации и к способу её настройки. Подменить
`PaymentClient` в тесте невозможно, изменить адрес — только правкой кода.

Инверсия управления означает, что созданием и связыванием объектов занимается не
сам класс, а внешний механизм — контейнер.

```java
public class OrderService {

    private final PaymentClient paymentClient;

    public OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}
```

Класс объявляет, что ему нужно, но не решает, откуда это возьмётся.

```text
без IoC → объект сам ищет зависимости
с IoC   → зависимости передаются извне
```

Dependency Injection — конкретный способ реализовать IoC: зависимости
«впрыскиваются» контейнером. Термины часто используют как синонимы, но IoC — это
принцип, а DI — приём.

## Контейнер

### BeanFactory и ApplicationContext

```text
BeanFactory
→ базовый контейнер: хранит определения бинов, создаёт их по требованию

ApplicationContext
→ наследует BeanFactory
→ добавляет события, интернационализацию, работу с ресурсами,
  автоматическое применение постпроцессоров
→ создаёт singleton-бины заранее, при старте
```

На практике всегда используется `ApplicationContext`. Разницу спрашивают, и
ключевое отличие — ленивая инициализация против ранней: `ApplicationContext`
создаёт синглтоны при старте, поэтому ошибки конфигурации обнаруживаются сразу, а
не при первом обращении.

### Bean

Бин — объект, которым управляет контейнер. От обычного объекта его отличает не
устройство, а то, что жизненным циклом занимается Spring.

Контейнер хранит не сами объекты, а их **определения** (`BeanDefinition`): класс,
scope, зависимости, имя, способ создания. Объекты создаются уже по определениям.

Это различие важно: определение появляется на этапе разбора конфигурации, а
экземпляр — позже, и между этими моментами определение можно изменить программно.

## Как бины попадают в контейнер

### Сканирование компонентов

```java
@Component
public class PaymentClient {
}
```

Аннотация ничего не создаёт — она лишь помечает класс. При старте сканирование
обходит указанные пакеты, находит помеченные классы через рефлексию и регистрирует
их определения.

Стереотипные аннотации — это `@Component` с дополнительным смыслом:

```text
@Component  → общий случай
@Service    → сервисный слой
@Repository → слой доступа к данным, плюс трансляция исключений
@Controller → веб-слой
```

Все они помечены `@Component` как мета-аннотацией, поэтому обрабатываются
одинаково. Разница почти целиком семантическая, кроме `@Repository`: он включает
перевод специфичных для JDBC и Hibernate исключений в общую иерархию
`DataAccessException`.

В Spring Boot базовым пакетом для сканирования по умолчанию служит пакет класса с
`@SpringBootApplication` и все вложенные в него. Классы, лежащие выше по дереву
пакетов, найдены не будут — частая причина «бин не найден».

### Явное объявление

```java
@Configuration
public class AppConfig {

    @Bean
    public PaymentClient paymentClient(RestTemplate restTemplate) {
        return new PaymentClient(restTemplate, "https://api...");
    }
}
```

Нужно, когда класс чужой и пометить его аннотацией нельзя, либо когда создание
требует логики.

Имя бина по умолчанию — имя метода.

### @Configuration против @Component

Тонкость, которую спрашивают у тех, кто уверенно ответил про `@Bean`.

```java
@Configuration
public class AppConfig {

    @Bean
    public ClientConfig config() {
        return new ClientConfig();
    }

    @Bean
    public PaymentClient paymentClient() {
        return new PaymentClient(config());   // прямой вызов метода
    }
}
```

Класс с `@Configuration` оборачивается CGLIB-прокси, который перехватывает вызовы
`@Bean`-методов. Поэтому `config()` внутри `paymentClient()` не создаёт новый
объект, а возвращает тот же бин из контейнера.

Если заменить `@Configuration` на `@Component`, прокси не будет, и `config()`
выполнится как обычный метод — появится второй экземпляр, не управляемый
контейнером.

Отключить проксирование можно явно:

```java
@Configuration(proxyBeanMethods = false)
```

Так делают ради ускорения старта, когда межбиновых вызовов нет. В автоконфигурациях
Spring Boot этот режим используется повсеместно.

## Способы внедрения

### Через конструктор

```java
@Service
public class OrderService {

    private final PaymentClient paymentClient;
    private final OrderRepository orderRepository;

    public OrderService(PaymentClient paymentClient, OrderRepository orderRepository) {
        this.paymentClient = paymentClient;
        this.orderRepository = orderRepository;
    }
}
```

С версии 4.3 `@Autowired` не нужен, если конструктор единственный.

### Через сеттер

```java
@Autowired
public void setPaymentClient(PaymentClient paymentClient) {
    this.paymentClient = paymentClient;
}
```

Применяется для необязательных зависимостей.

### Через поле

```java
@Autowired
private PaymentClient paymentClient;
```

Компактно и потому соблазнительно, но проблемно.

### Почему предпочтителен конструктор

Аргументов несколько, и на собеседовании стоит назвать хотя бы три.

**Поля можно сделать `final`.** Объект неизменяем после создания, состояние
гарантированно проинициализировано.

**Объект всегда в корректном состоянии.** При внедрении через поле между созданием
и заполнением зависимостей существует момент, когда они `null`.

**Зависимости видны в сигнатуре.** Конструктор с восемью параметрами выглядит
плохо — и это честный сигнал, что класс делает слишком много. Внедрение в поля
прячет ту же проблему.

**Тесты не требуют Spring.** Объект создаётся обычным `new` с моками. При внедрении
в поля приходится поднимать контекст или использовать рефлексию.

**Циклические зависимости обнаруживаются сразу.** Через конструктор цикл невозможен
физически, и контейнер падает при старте. Через поля он разрешается незаметно и
проявляется позже.

## Разрешение зависимостей

Основной механизм — по типу. Если подходящих бинов несколько, требуется уточнение.

```java
@Service
public class NotificationService {

    public NotificationService(@Qualifier("emailSender") MessageSender sender) {
    }
}
```

```java
@Component
@Primary
public class EmailSender implements MessageSender {
}
```

```text
@Qualifier → выбрать конкретный бин в точке внедрения
@Primary   → назначить бин по умолчанию среди нескольких
по имени   → если имя параметра совпадает с именем бина
```

Можно внедрить и все реализации сразу:

```java
public NotificationService(List<MessageSender> senders) {
}
```

Удобно для стратегий: добавление новой реализации не требует правки потребителя.
Порядок задаётся `@Order` или интерфейсом `Ordered`.

Если бин может отсутствовать:

```java
@Autowired(required = false)
private MetricsCollector collector;

// или
private final ObjectProvider<MetricsCollector> collector;
```

## Циклические зависимости

```java
@Service
public class A {
    public A(B b) { }
}

@Service
public class B {
    public B(A a) { }
}
```

Через конструкторы это неразрешимо: чтобы создать `A`, нужен готовый `B`, и
наоборот. Контейнер падает с `BeanCurrentlyInCreationException`.

Через поля или сеттеры Spring справляется — он создаёт объект, кладёт раннюю ссылку
на него в специальный кеш и заполняет зависимости позже. Формально работает, но
цикл в графе зависимостей почти всегда означает ошибку проектирования: два класса
знают друг о друге и не могут существовать раздельно.

Начиная со Spring Boot 2.6 циклические зависимости запрещены по умолчанию.
Разрешить можно свойством, но правильнее выделить третий компонент или пересмотреть
границы ответственности.

Обходной путь — `@Lazy`, который внедряет прокси вместо реального бина и создаёт
его при первом обращении. Тоже лечит симптом, а не причину.

## Жизненный цикл бина

```text
1. чтение определений бинов
2. BeanFactoryPostProcessor  → можно изменить определения до создания
3. создание экземпляра
4. внедрение зависимостей
5. вызов *Aware-интерфейсов
6. BeanPostProcessor.postProcessBeforeInitialization
7. @PostConstruct
8. InitializingBean.afterPropertiesSet
9. init-method
10. BeanPostProcessor.postProcessAfterInitialization  ← здесь создаются прокси
11. бин готов к работе
...
12. @PreDestroy
13. DisposableBean.destroy
14. destroy-method
```

Три способа задать инициализацию делают одно и то же. `@PostConstruct`
предпочтительнее: он не привязывает класс к интерфейсам Spring.

```java
@Component
public class CacheWarmer {

    @PostConstruct
    public void warmUp() {
    }

    @PreDestroy
    public void flush() {
    }
}
```

### BeanPostProcessor

Самая важная точка расширения. Это интерфейс с двумя методами, которые вызываются
для **каждого** бина до и после инициализации.

```java
@Component
public class AuditProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        return bean;   // можно вернуть другой объект — например, прокси
    }
}
```

Ключевой момент: метод может вернуть **не тот объект, который получил**. Именно так
работают `@Transactional`, `@Async`, `@Cacheable` и вся AOP — постпроцессор
подменяет бин прокси-обёрткой.

Это объясняет то, что иначе выглядит магией: почему аннотация на методе вдруг
начинает открывать транзакцию, и почему при вызове изнутри класса она не
срабатывает — внутри `this` указывает на исходный объект, а не на прокси.

### Aware-интерфейсы

```text
BeanNameAware            → узнать своё имя в контейнере
ApplicationContextAware  → получить ссылку на контекст
EnvironmentAware         → получить доступ к окружению
```

Привязывают класс к Spring, поэтому применяются в инфраструктурном коде, а не в
бизнес-логике.

## Scopes

```text
singleton → один экземпляр на контейнер, по умолчанию
prototype → новый экземпляр на каждое обращение
request   → один на HTTP-запрос
session   → один на HTTP-сессию
application → один на ServletContext
websocket → один на сессию WebSocket
```

### Singleton и паттерн Singleton

Их регулярно путают. Классический шаблон GoF гарантирует один экземпляр на JVM и
реализуется приватным конструктором со статическим методом доступа. Spring-синглтон
— один экземпляр **на контейнер**: два контекста в одной JVM дадут два объекта.

Практическое следствие: синглтон-бин разделяется всеми потоками, обрабатывающими
запросы, поэтому изменяемое состояние в его полях — гонка. Бины должны быть без
состояния.

### Prototype

```java
@Component
@Scope("prototype")
public class ReportBuilder {
}
```

Важная особенность: для прототипов контейнер не вызывает методы уничтожения. Он
создаёт объект, отдаёт его и забывает о нём. Освобождение ресурсов остаётся на
вызывающем.

### Прототип внутри синглтона

Классическая ловушка.

```java
@Service
public class ReportService {

    private final ReportBuilder builder;   // внедрён один раз

    public ReportService(ReportBuilder builder) {
        this.builder = builder;
    }
}
```

`ReportService` — синглтон, он создаётся один раз, и внедрение выполняется тоже
один раз. Прототип превращается в синглтон де-факто: каждый вызов получает тот же
экземпляр.

Решения:

```java
// провайдер
private final ObjectProvider<ReportBuilder> builderProvider;

public Report build() {
    return builderProvider.getObject().build();   // новый экземпляр
}
```

```java
// scoped proxy
@Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ReportBuilder {
}
```

Тот же вопрос возникает с `request`-бинами внутри синглтонов, и решается так же —
через прокси, который на каждый вызов обращается к бину текущего запроса.

## Конфигурация

### Свойства

```java
@Component
public class PaymentClient {

    @Value("${payment.api.url}")
    private String url;

    @Value("${payment.timeout:5000}")
    private int timeout;              // значение по умолчанию после двоеточия
}
```

Для группы связанных свойств удобнее типизированный вариант:

```java
@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(String url, int timeout) {
}
```

Преимущества: типобезопасность, валидация через `@Validated`, все свойства в одном
месте, поддержка вложенных структур.

### Профили

```java
@Component
@Profile("dev")
public class InMemoryPaymentClient implements PaymentClient {
}

@Component
@Profile("!dev")
public class HttpPaymentClient implements PaymentClient {
}
```

Бин регистрируется, только если профиль активен. Активация — через
`spring.profiles.active`, переменную окружения или аргумент запуска.

Профили удобны для подмены реализаций между средами, но злоупотребление ими делает
конфигурацию трудной для понимания: чтобы узнать, какой бин работает, приходится
собирать условия по всему коду.

### Условная регистрация

```java
@ConditionalOnMissingBean
@ConditionalOnProperty(name = "feature.metrics.enabled", havingValue = "true")
@ConditionalOnClass(RedisTemplate.class)
```

На этих аннотациях построена автоконфигурация Spring Boot. Идея простая: бин
регистрируется, только если выполнено условие — есть класс в classpath, включено
свойство, не определён собственный бин того же типа.

## Типичные ошибки

### Внедрение через поля

Мешает `final`, скрывает зависимости, усложняет тесты, маскирует циклы.

### Изменяемое состояние в синглтон-бине

Бин разделяется всеми потоками. Поля с состоянием — гонка данных.

### Ожидать новый экземпляр прототипа внутри синглтона

Внедрение произошло один раз при создании синглтона. Нужен `ObjectProvider` или
scoped proxy.

### Рассчитывать на @PreDestroy у прототипа

Контейнер не отслеживает прототипы после создания и методы уничтожения не вызывает.

### Класс вне пакета сканирования

Spring Boot сканирует пакет главного класса и вложенные. Классы выше по дереву не
найдутся.

### Вызывать @Bean-метод из класса с @Component

Без CGLIB-прокси `@Configuration` вызов создаст новый объект вне контейнера.

### Разрешать циклическую зависимость через @Lazy

Лечится симптом. Цикл в графе почти всегда означает проблему с границами
ответственности.

### Путать Spring-синглтон с шаблоном Singleton

Первый — один на контейнер, второй — один на JVM.

### Считать, что @Service отличается от @Component функционально

Разница семантическая. Исключение — `@Repository` с трансляцией исключений.

### Ожидать работы @Transactional при self-invocation

Аннотацию обрабатывает прокси, созданный `BeanPostProcessor`. Вызов через `this`
идёт мимо прокси.

## Краткая памятка

```text
IoC → создание и связывание объектов вынесено во внешний механизм
DI  → способ реализации IoC

BeanFactory        → базовый, ленивый
ApplicationContext → синглтоны при старте, события, ресурсы
```

```text
регистрация бинов
@Component + сканирование
@Bean внутри @Configuration

@Configuration → CGLIB-прокси, вызов @Bean-метода вернёт бин
@Component     → прокси нет, вызов создаст новый объект
```

```text
внедрение
конструктор → final, обязательные зависимости, тесты без Spring, цикл виден сразу
сеттер      → необязательные зависимости
поле        → не рекомендуется
```

```text
разрешение
по типу → @Qualifier, @Primary, по имени
List<T> → все реализации, порядок через @Order
ObjectProvider → отсутствующий или новый экземпляр
```

```text
жизненный цикл
определения → BeanFactoryPostProcessor → создание → внедрение
→ Aware → BPP.before → @PostConstruct → BPP.after (прокси) → работа
→ @PreDestroy → destroy

BeanPostProcessor может вернуть другой объект
→ здесь рождаются прокси @Transactional, @Async, @Cacheable
```

```text
scopes
singleton → один на контейнер, не на JVM
prototype → новый на каждое обращение, без вызова destroy
request / session → веб-контекст

прототип в синглтоне → внедряется один раз
→ ObjectProvider или scoped proxy
```

## Краткий ответ для собеседования

Инверсия управления означает, что объект не создаёт свои зависимости сам —
созданием и связыванием занимается контейнер. Dependency Injection — конкретный
способ это реализовать.

Контейнер хранит определения бинов: класс, scope, зависимости, способ создания.
Определения появляются из сканирования компонентов либо из методов, помеченных
`@Bean`. Сами аннотации ничего не создают — их находит сканирование через
рефлексию при старте приложения.

`@Configuration` отличается от `@Component` тем, что оборачивается CGLIB-прокси, и
вызов одного `@Bean`-метода из другого возвращает бин из контейнера, а не создаёт
новый объект.

Внедрять зависимости предпочтительно через конструктор: поля становятся `final`,
объект всегда в корректном состоянии, зависимости видны в сигнатуре, тесты не
требуют поднимать контекст, а циклические зависимости обнаруживаются при старте.

Жизненный цикл проходит через создание, внедрение зависимостей, `Aware`-интерфейсы,
постпроцессоры и `@PostConstruct`. Ключевая точка расширения —
`BeanPostProcessor`: он вызывается для каждого бина и может вернуть другой объект.
Именно там создаются прокси для `@Transactional`, `@Async` и `@Cacheable`, и
именно поэтому аннотации не срабатывают при вызове метода изнутри того же класса.

Scope по умолчанию — singleton, то есть один экземпляр на контейнер, а не на JVM.
Такой бин разделяется всеми потоками, поэтому изменяемого состояния в нём быть не
должно. Прототип, внедрённый в синглтон, создаётся один раз; чтобы получать новые
экземпляры, нужен `ObjectProvider` или scoped proxy.

## Вопросы на собеседовании

### 1. Что такое IoC и чем он отличается от DI?

**Ответ:** IoC — принцип, при котором создание и связывание объектов вынесено во
внешний механизм. DI — конкретный способ его реализации через передачу зависимостей
извне.

### 2. Чем ApplicationContext отличается от BeanFactory?

**Ответ:** `ApplicationContext` наследует `BeanFactory` и добавляет события, работу
с ресурсами, интернационализацию и автоматическое применение постпроцессоров. Кроме
того, он создаёт синглтоны при старте, а не по требованию.

### 3. Что хранит контейнер?

**Ответ:** определения бинов — класс, scope, зависимости, способ создания. Сами
экземпляры создаются уже по этим определениям.

### 4. Чем отличаются @Component, @Service и @Repository?

**Ответ:** семантикой. Все они помечены `@Component` как мета-аннотацией.
Функциональное отличие есть только у `@Repository` — он включает трансляцию
исключений доступа к данным в иерархию `DataAccessException`.

### 5. Чем @Configuration отличается от @Component?

**Ответ:** класс с `@Configuration` оборачивается CGLIB-прокси, который
перехватывает вызовы `@Bean`-методов и возвращает бин из контейнера. Без прокси
такой вызов создал бы новый объект.

### 6. Что делает proxyBeanMethods = false?

**Ответ:** отключает CGLIB-проксирование конфигурации ради ускорения старта.
Применимо, когда `@Bean`-методы не вызывают друг друга.

### 7. Какие есть способы внедрения и какой предпочтительнее?

**Ответ:** через конструктор, сеттер и поле. Предпочтителен конструктор: позволяет
`final`-поля, гарантирует корректное состояние, делает зависимости явными, упрощает
тесты и выявляет циклы при старте.

### 8. Нужен ли @Autowired на конструкторе?

**Ответ:** нет, если конструктор единственный. Так с версии Spring 4.3.

### 9. Что произойдёт при циклической зависимости через конструкторы?

**Ответ:** контейнер не сможет создать бины и упадёт с
`BeanCurrentlyInCreationException`. Через поля цикл разрешается через раннюю
ссылку, но начиная со Spring Boot 2.6 запрещён по умолчанию.

### 10. Как выбрать нужный бин, если подходящих несколько?

**Ответ:** через `@Qualifier` в точке внедрения, через `@Primary` на бине по
умолчанию или по совпадению имени параметра с именем бина.

### 11. Можно ли внедрить все реализации интерфейса?

**Ответ:** да, объявив параметр как `List<T>` или `Map<String, T>`. Порядок задаётся
через `@Order`.

### 12. Опишите жизненный цикл бина.

**Ответ:** чтение определений, `BeanFactoryPostProcessor`, создание экземпляра,
внедрение зависимостей, `Aware`-интерфейсы, `postProcessBeforeInitialization`,
`@PostConstruct`, `afterPropertiesSet`, `init-method`,
`postProcessAfterInitialization`, работа, затем `@PreDestroy` и `destroy`.

### 13. Зачем нужен BeanPostProcessor?

**Ответ:** это точка расширения, вызываемая для каждого бина до и после
инициализации. Она может вернуть другой объект, и именно так создаются прокси для
`@Transactional`, `@Async` и `@Cacheable`.

### 14. Какие есть scopes?

**Ответ:** singleton, prototype, а в веб-контексте также request, session,
application и websocket.

### 15. Spring-синглтон — это шаблон Singleton?

**Ответ:** нет. Шаблон GoF гарантирует один экземпляр на JVM, Spring — один на
контейнер. Два контекста в одной JVM дадут два объекта.

### 16. Почему в синглтон-бине не должно быть изменяемого состояния?

**Ответ:** бин разделяется всеми потоками, обрабатывающими запросы, поэтому
изменяемые поля становятся источником гонки.

### 17. Что произойдёт, если внедрить прототип в синглтон?

**Ответ:** внедрение произойдёт один раз при создании синглтона, и прототип станет
фактически синглтоном. Нужен `ObjectProvider` или scoped proxy.

### 18. Вызывается ли @PreDestroy у прототипа?

**Ответ:** нет. Контейнер не отслеживает прототипы после создания, освобождение
ресурсов остаётся на вызывающем коде.

### 19. Как задать значение свойства с умолчанием?

**Ответ:** через двоеточие в выражении: `@Value("${timeout:5000}")`. Для группы
связанных свойств удобнее `@ConfigurationProperties`.

### 20. Что делают профили?

**Ответ:** позволяют регистрировать бины в зависимости от активного окружения.
Бин с `@Profile("dev")` появится, только если этот профиль активен.

### 21. Почему бин может не находиться при старте?

**Ответ:** частая причина — класс лежит вне пакета сканирования. Spring Boot
сканирует пакет главного класса и вложенные в него.
