# Архитектура бэкенда

## Слоистая архитектура

```text
Controller  → приём HTTP, валидация формата, преобразование в DTO
Service     → бизнес-логика, границы транзакций
Repository  → доступ к данным
```

Правило одно: зависимости направлены вниз. Контроллер знает о сервисе, сервис — о
репозитории, обратных зависимостей нет.

### Что где лежит

**Контроллер** отвечает за протокол: разбирает запрос, проверяет формат, вызывает
сервис, преобразует результат в ответ. Бизнес-логики в нём быть не должно — иначе
её нельзя переиспользовать из другого источника вызова, будь то очередь или
планировщик.

**Сервис** содержит логику и задаёт границы транзакции. Это единица бизнес-операции.

**Репозиторий** только читает и пишет. Условия выборки — его дело, решения о том,
что делать с данными, — нет.

Признак нарушения: контроллер, который вызывает три репозитория и что-то между ними
считает. Логика оказалась в слое протокола.

### Организация пакетов

```text
по слоям                     по функциональности
├── controller               ├── order
│   ├── OrderController      │   ├── OrderController
│   └── UserController       │   ├── OrderService
├── service                  │   ├── OrderRepository
│   ├── OrderService         │   └── Order
│   └── UserService          ├── user
└── repository               │   ├── UserController
    ├── OrderRepository      │   └── ...
    └── UserRepository
```

Деление по слоям привычнее и удобно на старте. Деление по функциональности лучше
масштабируется: всё, относящееся к заказам, лежит вместе, изменение затрагивает
один пакет, а видимость на уровне пакета помогает не тянуть чужие внутренности.

Второй вариант к тому же готовит почву для выделения модулей.

## Модель данных

### DTO и сущности

Три вида объектов, которые путают:

```text
Entity → отображение на таблицу, живёт в слое данных
Domain → бизнес-объект с поведением
DTO    → контракт с внешним миром
```

В небольших приложениях сущность и доменная модель совпадают — это нормально и не
требует исправления. Разделять их стоит, когда бизнес-правила становятся сложнее
отображения на таблицы.

DTO же отделяют всегда: причины разбирались в конспекте по Spring MVC — утечка
полей, ломающиеся контракты, проблемы сериализации ленивых связей.

### Анемичная и богатая модель

```java
// анемичная: данные отдельно, логика отдельно
public class Order {
    private String status;
    // только геттеры и сеттеры
}

public class OrderService {
    public void cancel(Order order) {
        if (!"NEW".equals(order.getStatus())) {
            throw new IllegalStateException();
        }
        order.setStatus("CANCELLED");
    }
}
```

```java
// богатая: поведение рядом с данными
public class Order {

    private OrderStatus status;

    public void cancel() {
        if (status != OrderStatus.NEW) {
            throw new OrderCannotBeCancelledException(id, status);
        }
        status = OrderStatus.CANCELLED;
    }
}
```

Анемичная модель преобладает в приложениях на Spring и часто критикуется. Оценка
зависит от сложности: для CRUD-сервиса она проще и честнее, для домена со
множеством правил переноса состояний богатая модель уменьшает дублирование —
правило живёт в одном месте, а не в каждом сервисе, который меняет статус.

## Монолит и микросервисы

### Когда микросервисы преждевременны

```text
монолит
+ один процесс, одна база, транзакции работают
+ рефакторинг через IDE
+ простые развёртывание и отладка
− связность растёт, границы размываются
− масштабируется целиком

микросервисы
+ независимое развёртывание и масштабирование
+ границы закреплены сетью
− распределённые транзакции невозможны
− сеть ненадёжна, нужны таймауты, ретраи, circuit breaker
− нужна инфраструктура: трассировка, агрегация логов, оркестрация
```

Практическая позиция: начинать с монолита и выделять сервисы, когда для этого есть
причина — разная нагрузка, разный темп изменений, разные команды. Дробление «потому
что так современно» даёт распределённый монолит: сервисы связаны синхронными
вызовами и не могут развёртываться независимо, то есть минусы обоих подходов сразу.

### Модульный монолит

Компромисс: один процесс и одна база, но чёткие границы модулей внутри.

```text
com.example
├── order       → публичный API модуля + внутренние классы
├── payment
└── shared
```

Правило — модули общаются только через объявленные интерфейсы, а не через
репозитории друг друга. Если границы соблюдены, выделение модуля в сервис
превращается в техническую задачу, а не в переписывание.

## Синхронное и асинхронное взаимодействие

```text
синхронно (REST, gRPC)
→ вызывающий ждёт ответ
→ результат сразу
→ доступность перемножается

асинхронно (Kafka, очереди)
→ отправил и продолжил
→ получатель может быть недоступен
→ результат не мгновенный
```

### Перемножение доступности

Аргумент, который стоит уметь приводить.

```text
сервис зависит от 5 других, каждый доступен на 99.9%
0.999^5 ≈ 99.5%
```

Полчаса недоступности в месяц превращаются в два с половиной часа. Каждая новая
синхронная зависимость ухудшает доступность, даже если сама по себе надёжна.

Асинхронное взаимодействие эту цепочку разрывает: получатель может быть недоступен,
сообщение подождёт в брокере.

### Что выбирать

```text
синхронно
→ нужен ответ для продолжения: проверка баланса, получение данных
→ пользователь ждёт результат

асинхронно
→ уведомление о факте: заказ создан, платёж прошёл
→ получателей несколько или они неизвестны
→ обработка может занять время
```

Признак неверного выбора — синхронный вызов ради действия, результат которого
никому не нужен немедленно. Отправка письма внутри обработки HTTP-запроса
замедляет ответ и роняет его при недоступности почтового сервиса.

## Устойчивость

### Таймауты

Самое дешёвое и самое пропускаемое средство.

```text
без таймаута → поток ждёт бесконечно
поток занят  → пул исчерпывается
пул исчерпан → сервис не отвечает, хотя сам исправен
```

Значения по умолчанию у многих клиентов — бесконечность либо минуты. Их нужно
задавать явно.

Полезное понятие — бюджет времени: если внешний контракт обещает ответ за 2
секунды, сумма таймаутов внутренних вызовов не должна его превышать. Таймаут в 30
секунд у зависимости, вызываемой из метода с обещанием в 2 секунды, бессмыслен.

### Повторы

```text
повторять можно только идемпотентные операции
```

Иначе повтор создаст второй заказ или спишет деньги дважды. Это ровно тот же
критерий, что в HTTP-методах и в Kafka: `GET`, `PUT`, `DELETE` повторять безопасно,
`POST` — только с ключом идемпотентности.

```text
экспоненциальная задержка: 1 с, 2 с, 4 с, 8 с
+ случайное рассеивание (jitter)
```

Рассеивание нужно, чтобы клиенты не повторяли синхронно. Без него после сбоя все
приходят одновременно и добивают только что поднявшийся сервис.

Отдельная опасность — умножение повторов по слоям:

```text
A повторяет 3 раза → B повторяет 3 раза → C получает 9 запросов
```

При трёх уровнях получается 27. Поэтому повторы делают на одном уровне, обычно
ближайшем к вызову.

### Circuit breaker

Если сервис лежит, продолжать его звать бессмысленно: запросы всё равно упадут, но
займут потоки и время.

```text
CLOSED    → запросы проходят, ошибки считаются
          → доля ошибок превысила порог → OPEN

OPEN      → запросы отклоняются сразу, без обращения
          → выждали интервал → HALF_OPEN

HALF_OPEN → пропускаем несколько пробных запросов
          → успех → CLOSED
          → неудача → OPEN
```

Смысл двойной: защитить себя от исчерпания ресурсов на заведомо неудачных вызовах и
дать упавшему сервису подняться, а не добивать его нагрузкой.

Сопутствующий приём — bulkhead: ограничение числа одновременных вызовов к каждой
зависимости, чтобы одна медленная не забрала все потоки.

### Деградация

```java
if (recommendationsUnavailable) {
    return popularItems();     // вместо ошибки
}
```

Не всякая недоступность должна означать отказ. Рекомендации можно заменить
популярными товарами, курс валюты — последним известным. Пользователь получит
работающий сервис с ухудшенным качеством вместо страницы с ошибкой.

Важно, чтобы деградация была видна в мониторинге: молча отдавать устаревшие данные
опасно.

## Идемпотентность

Сквозная тема, встречавшаяся уже трижды: в HTTP, в Kafka, в повторах.

Формулировка общая: повторное выполнение операции с теми же входными данными не
меняет результат.

Способы обеспечить:

```text
ключ идемпотентности
→ клиент передаёт уникальный идентификатор запроса
→ сервер сохраняет результат и при повторе возвращает его

естественный ключ
→ уникальное ограничение в базе на бизнес-идентификатор
→ повторная вставка отклоняется базой

проверка состояния
→ операция применяется, только если объект в подходящем статусе

UPSERT
→ вставка или обновление вместо слепой вставки
```

Практический вывод: в распределённой системе доставка гарантируется минимум
однократная, значит дубликаты неизбежны, и идемпотентность обработчика — не
опциональное улучшение, а условие корректности.

## Кеширование

### Стратегии

```text
cache-aside (наиболее распространён)
→ читаем из кеша; промах → идём в базу, кладём в кеш

write-through
→ пишем в кеш и в базу одновременно

write-behind
→ пишем в кеш, в базу асинхронно; быстро, но можно потерять данные
```

```java
@Cacheable("products")
public Product findById(Long id) { }

@CacheEvict(value = "products", key = "#product.id")
public void update(Product product) { }
```

### Что кешировать

```text
подходит → редко меняется, часто читается, допускает устаревание
не подходит → часто меняется, требует точности (баланс, остатки)
```

### Инвалидация

Основная сложность. Три подхода:

```text
TTL           → простой, данные устаревают на время жизни записи
явное удаление → точный, но легко забыть место изменения
версионирование ключа → меняем ключ при изменении данных
```

TTL выигрывает простотой, и для большинства задач его достаточно. Точная
инвалидация оправдана там, где устаревание недопустимо.

### Локальный и распределённый

```text
локальный (Caffeine)
+ быстрый, без сети
− у каждого экземпляра свой, данные расходятся

распределённый (Redis)
+ общий для всех экземпляров
− сетевая задержка, дополнительная зависимость
```

### Промах в кеше под нагрузкой

Ситуация, о которой стоит знать: запись устарела, и сто параллельных запросов
одновременно обнаруживают промах и идут в базу.

Лечится блокировкой на время обновления, чтобы в базу шёл один запрос, либо
опережающим обновлением до истечения срока.

## Наблюдаемость

```text
логи     → что произошло
метрики  → сколько и как быстро
трассировка → путь запроса через сервисы
```

Минимум для сервиса: сквозной идентификатор запроса во всех логах, метрики
задержек и ошибок по эндпоинтам, проверки состояния.

```text
liveness  → процесс жив, иначе перезапустить
readiness → готов принимать трафик, иначе не направлять запросы
```

Различие практическое: сервис, потерявший базу, жив, но не готов. Перезапуск не
поможет, а вот исключение из балансировки — да.

## Типичные ошибки

### Бизнес-логика в контроллере

Её нельзя переиспользовать из другого источника вызова и трудно тестировать.

### Отдавать сущности вместо DTO

Внутренняя модель попадает в контракт API.

### Дробить на микросервисы преждевременно

Получается распределённый монолит: связность осталась, а сложность выросла.

### Синхронный вызов там, где достаточно события

Доступность перемножается, ответ замедляется.

### Не выставлять таймауты

Значения по умолчанию часто бесконечны, и один медленный вызов исчерпывает пул
потоков.

### Повторять неидемпотентные операции

Дубликаты заказов и повторные списания.

### Повторять на нескольких уровнях

Число запросов растёт степенью, и сбой усугубляется.

### Повторять без рассеивания задержки

Клиенты приходят синхронно и добивают поднявшийся сервис.

### Кешировать данные, требующие точности

Устаревший остаток на складе приводит к продаже отсутствующего товара.

### Забывать про инвалидацию

Кеш начинает жить своей жизнью, и данные расходятся.

### Не различать liveness и readiness

Сервис перезапускается вместо того, чтобы просто выйти из балансировки.


## Краткий ответ для собеседования

Слоистая архитектура разделяет ответственность: контроллер занимается протоколом,
сервис содержит бизнес-логику и задаёт границы транзакции, репозиторий работает с
данными. Зависимости направлены только вниз. Наружу отдаются DTO, а не сущности,
чтобы внутренняя модель не попадала в контракт API.

Микросервисы решают задачи независимого развёртывания и масштабирования, но
приносят распределённость: транзакции между сервисами невозможны, сеть ненадёжна,
требуется инфраструктура наблюдаемости. Разумный путь — начинать с монолита,
поддерживая чёткие границы модулей, и выделять сервисы при появлении причины.
Иначе получается распределённый монолит с недостатками обоих подходов.

Синхронное взаимодействие нужно, когда ответ требуется для продолжения работы, но
каждая такая зависимость перемножает доступность: пять зависимостей по 99,9 процента
дают около 99,5. Асинхронное взаимодействие эту связь разрывает.

Устойчивость строится на нескольких приёмах. Таймауты выставляются всегда, иначе
один медленный вызов исчерпывает пул потоков. Повторы допустимы только для
идемпотентных операций, с экспоненциальной задержкой и случайным рассеиванием, и
только на одном уровне, иначе число запросов растёт степенью. Circuit breaker
прекращает обращения к упавшему сервису, защищая и вызывающего, и вызываемого.

Идемпотентность в распределённой системе обязательна, поскольку доставка
гарантируется минимум однократная и дубликаты неизбежны.

## Вопросы на собеседовании

### 1. Зачем нужно разделение на слои?

**Ответ:** каждый слой отвечает за своё: протокол, логику, доступ к данным. Это
позволяет переиспользовать логику из разных источников вызова и тестировать её
отдельно.

### 2. Почему бизнес-логика не должна быть в контроллере?

**Ответ:** её невозможно вызвать из обработчика очереди или планировщика, и для
теста придётся поднимать веб-слой.

### 3. Чем анемичная модель отличается от богатой?

**Ответ:** в анемичной объект хранит только данные, а логика лежит в сервисах. В
богатой поведение находится рядом с данными. Для CRUD проще первая, для сложного
домена вторая уменьшает дублирование правил.

### 4. Когда стоит переходить на микросервисы?

**Ответ:** когда есть конкретная причина — разная нагрузка, разный темп изменений,
разные команды. Дробление без причины даёт распределённый монолит.

### 5. Что такое распределённый монолит?

**Ответ:** система из сервисов, связанных настолько тесно, что они не могут
развёртываться независимо. Сложность распределённой системы есть, преимуществ нет.

### 6. Что такое модульный монолит?

**Ответ:** один процесс с чёткими границами модулей, взаимодействующих через
объявленные интерфейсы. Позволяет позже выделить модуль в сервис без переписывания.

### 7. Когда выбирать асинхронное взаимодействие?

**Ответ:** когда ответ не нужен немедленно, получателей несколько или они
неизвестны, а обработка может занять время.

### 8. Как зависимости влияют на доступность?

**Ответ:** при синхронных вызовах доступности перемножаются. Пять зависимостей по
99,9 процента дают около 99,5, то есть на порядок больше недоступного времени.

### 9. Зачем нужны таймауты?

**Ответ:** без них поток ждёт бесконечно, пул исчерпывается, и сервис перестаёт
отвечать, оставаясь технически исправным.

### 10. Что такое бюджет времени?

**Ответ:** сумма таймаутов внутренних вызовов не должна превышать время, обещанное
внешнему потребителю.

### 11. Какие операции можно повторять?

**Ответ:** только идемпотентные. Для остальных нужен ключ идемпотентности.

### 12. Зачем нужно рассеивание задержки при повторах?

**Ответ:** без него все клиенты повторяют одновременно и добивают только что
поднявшийся сервис.

### 13. Чем опасны повторы на нескольких уровнях?

**Ответ:** число запросов умножается: три уровня по три попытки дают двадцать семь
обращений к нижнему сервису.

### 14. Как работает circuit breaker?

**Ответ:** в закрытом состоянии пропускает запросы и считает ошибки; при превышении
порога открывается и отклоняет вызовы сразу; через интервал переходит в
полуоткрытое состояние и пробует несколько запросов.

### 15. Что такое bulkhead?

**Ответ:** ограничение числа одновременных вызовов к каждой зависимости, чтобы одна
медленная не заняла все потоки.

### 16. Что такое graceful degradation?

**Ответ:** отдавать урезанный результат вместо ошибки, когда часть системы
недоступна — например, популярные товары вместо персональных рекомендаций.

### 17. Как обеспечить идемпотентность?

**Ответ:** ключом идемпотентности от клиента, уникальным ограничением в базе,
проверкой текущего состояния или использованием `UPSERT`.

### 18. Какие есть стратегии кеширования?

**Ответ:** cache-aside с чтением через кеш и обращением к базе при промахе,
write-through с одновременной записью и write-behind с отложенной.

### 19. Что кешировать не стоит?

**Ответ:** данные, требующие точности, — остатки, балансы, — и то, что меняется
чаще, чем читается.

### 20. Чем локальный кеш отличается от распределённого?

**Ответ:** локальный быстрее, но у каждого экземпляра свой, и данные расходятся.
Распределённый согласован для всех, но добавляет сетевую задержку и зависимость.

### 21. Чем liveness отличается от readiness?

**Ответ:** liveness отвечает, жив ли процесс и нужно ли его перезапустить.
Readiness — готов ли он принимать трафик. Сервис без базы жив, но не готов.
