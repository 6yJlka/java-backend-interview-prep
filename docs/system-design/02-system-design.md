# System Design

## Что проверяют на самом деле

На уровне Junior и Junior+ от кандидата не ждут проектирования системы на миллионы
пользователей. Проверяют другое:

```text
задаёте ли уточняющие вопросы или бросаетесь решать
умеете ли оценить порядок нагрузки
понимаете ли, где данные и как они меняются
видите ли конкурентный доступ и отказы
можете ли объяснить выбор, а не назвать технологию
```

Худший ответ — сразу начать с «берём Kafka, Redis и микросервисы». Лучший —
выяснить, что именно нужно построить, и обосновать каждое решение.

Правильного ответа не существует, есть обоснованные компромиссы.

## Порядок разбора

### 1. Уточнить требования

Функциональные — что система должна делать:

```text
кто пользователи
какие основные сценарии
что обязательно, что можно отложить
```

Нефункциональные — какой она должна быть:

```text
сколько пользователей и запросов
соотношение чтения и записи
допустима ли задержка
насколько критична потеря данных
нужна ли строгая согласованность или достаточно отложенной
```

Последний пункт часто определяет всю архитектуру. Счётчик просмотров может
отставать на минуту, остаток на складе — нет.

### 2. Прикинуть масштаб

Считать нужно в порядках величин, точность не важна.

```text
1 000 000 активных пользователей в сутки
каждый делает 10 запросов
→ 10 000 000 запросов в сутки

86 400 секунд в сутках
→ ≈ 120 запросов в секунду в среднем
→ пик в 2–3 раза выше → ≈ 300 RPS
```

Объём данных:

```text
1 000 000 записей в сутки × 500 байт = 500 МБ в сутки
→ ≈ 180 ГБ в год
```

Вывод из таких расчётов важнее самих чисел. Триста запросов в секунду и двести
гигабайт в год — обычная нагрузка для одного экземпляра приложения и одной базы
PostgreSQL. Никакого шардирования и микросервисов не требуется, и сказать об этом
вслух — сильный ход.

### 3. Описать API

```text
POST   /api/orders          создать
GET    /api/orders/{id}     получить
GET    /api/orders?status=  список с фильтром
PATCH  /api/orders/{id}     изменить
```

Заодно проговорить коды ответов, идемпотентность и пагинацию.

### 4. Спроектировать данные

Таблицы, ключи, связи и — обязательно — индексы под конкретные запросы из API.

```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
```

Хороший приём: показать запрос из сценария и индекс, который его обслуживает.

### 5. Основной поток

Пройти главный сценарий по шагам: что происходит при создании заказа, куда идут
данные, что возвращается пользователю.

### 6. Узкие места

```text
много чтения      → кеш, реплики
долгие операции   → очередь
рост нагрузки     → горизонтальное масштабирование
конкурентный доступ → блокировки
```

### 7. Отказы

```text
что если база недоступна
что если внешний сервис не отвечает
что если сообщение обработано дважды
что если запрос повторили
```

## Базовые приёмы

### Горизонтальное масштабирование

```text
приложение без состояния → добавляем экземпляры за балансировщиком
```

Условие — отсутствие состояния в памяти экземпляра. Сессия в памяти, локальный кеш
с бизнес-данными, счётчики в полях синглтона — всё это ломает масштабирование, так
как запрос может попасть на любой экземпляр.

База масштабируется хуже приложения и почти всегда становится узким местом первой.

### Реплики и шардирование

```text
реплики чтения
→ запись на основной узел, чтение с реплик
→ помогает при преобладании чтения
→ появляется отставание реплики: данные могут быть чуть устаревшими

шардирование
→ данные разбиваются по узлам
→ снимает предел на объём и запись
→ ломает соединения и транзакции между шардами
→ применяют последним, когда всё остальное исчерпано
```

Отставание реплики создаёт заметный эффект: пользователь создал заказ, тут же
открыл список и не увидел его. Обычное решение — читать с основного узла сразу
после записи.

### Очереди

```text
долгая операция внутри запроса
→ вынести в очередь
→ ответить пользователю сразу
```

Отправка писем, генерация отчётов, обработка изображений. Пользователь получает
подтверждение приёма, а не результат.

### Кеш

Первое средство при преобладании чтения. Что кешировать и как инвалидировать —
разбиралось в конспекте по архитектуре.

## Задача: сокращатель ссылок

### Требования

```text
функциональные
→ создать короткую ссылку из длинной
→ переход по короткой ссылке
→ опционально: срок жизни, статистика переходов

нефункциональные
→ чтений на порядки больше, чем записей
→ переход должен быть быстрым
→ ссылка не должна перестать работать
```

### Оценка

```text
100 000 новых ссылок в сутки → ≈ 1 запись в секунду
10 000 000 переходов в сутки → ≈ 120 чтений в секунду, пик ≈ 350
```

Запись мизерная, чтение умеренное. Соотношение примерно 1 к 100 — система на
чтение.

### API

```text
POST /api/links          {"url": "...", "ttl": 86400} → 201 {"code": "aB3xY9"}
GET  /{code}             → 302 + Location
```

### Данные

```sql
CREATE TABLE links (
    code        VARCHAR(10) PRIMARY KEY,
    original_url TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    expires_at  TIMESTAMPTZ
);
```

Первичный ключ — сам код: поиск идёт по нему, дополнительный индекс не нужен.

### Генерация кода

Ключевое решение задачи, три варианта:

```text
случайная строка
→ проверять коллизию перед вставкой
→ при 62^6 ≈ 56 млрд комбинаций коллизии редки
→ уникальное ограничение в базе гарантирует корректность

хеш от URL
→ одинаковые ссылки дают один код, это может быть и плюсом, и минусом
→ коллизии требуют обработки

счётчик в base62
→ коллизий нет по построению
→ коды предсказуемы, можно перебрать чужие ссылки
→ в распределённой системе нужен общий источник номеров
```

Разумный выбор — случайный код с уникальным ограничением и повтором при конфликте.
Обосновать выбор здесь важнее, чем угадать «правильный».

### Оптимизация

```text
кеш code → url
→ ссылки не меняются, инвалидация почти не нужна
→ TTL по сроку жизни ссылки
→ горячие ссылки обслуживаются без обращения к базе
```

Про код перенаправления стоит сказать отдельно: `301` кешируется браузером
навсегда, и статистика переходов перестанет собираться, а изменить цель ссылки
станет невозможно. Поэтому обычно используют `302`.

### Отказы

Недоступность базы при промахе кеша означает отказ перехода. Если статистика не
критична, её можно писать асинхронно, чтобы не замедлять перенаправление.

## Задача: сервис уведомлений

### Требования

```text
→ отправка по нескольким каналам: email, SMS, push
→ доставка гарантирована, дубликаты нежелательны
→ учитывать настройки пользователя
→ внешние провайдеры ненадёжны
```

### Архитектура

Отправка — классический асинхронный сценарий: результат вызывающему не нужен
немедленно, а провайдер может лежать.

```text
сервис-источник
    ↓ событие в топик
notification-service
    ↓ проверка настроек, дедупликация
    ↓ отправка через провайдера
    ↓ ошибка → retry-топик → DLQ
```

### Данные

```sql
CREATE TABLE notifications (
    id             UUID PRIMARY KEY,
    user_id        BIGINT NOT NULL,
    channel        VARCHAR(20) NOT NULL,
    status         VARCHAR(20) NOT NULL,
    idempotency_key VARCHAR(100) NOT NULL,
    attempts       INT NOT NULL DEFAULT 0,
    created_at     TIMESTAMPTZ NOT NULL,
    CONSTRAINT uq_idempotency UNIQUE (idempotency_key)
);
```

### Ключевые решения

**Идемпотентность.** Доставка из очереди — at-least-once, дубликаты неизбежны.
Уникальное ограничение на ключ идемпотентности не даст отправить письмо дважды: при
повторе вставка отклоняется базой.

**Повторы.** Разделить временные ошибки от постоянных. Недоступность провайдера —
повторять с нарастающей задержкой. Некорректный адрес — сразу в DLQ, повторы
бессмысленны.

**Ограничение частоты.** У провайдеров есть лимиты. Нужен либо счётчик отправок,
либо ограничение числа параллельных обработчиков.

**Каналы за интерфейсом.** Добавление нового провайдера не должно менять логику
сервиса.

## Задача: система управления инцидентами

### Требования

```text
→ создание инцидента, назначение исполнителя
→ смена статусов по правилам
→ комментарии и история изменений
→ уведомления об изменениях
→ отсчёт времени реакции по SLA
```

### Данные

```sql
CREATE TABLE incidents (
    id          BIGSERIAL PRIMARY KEY,
    title       TEXT NOT NULL,
    status      VARCHAR(20) NOT NULL,
    priority    VARCHAR(20) NOT NULL,
    assignee_id BIGINT,
    version     BIGINT NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ NOT NULL,
    resolved_at TIMESTAMPTZ
);

CREATE TABLE incident_history (
    id          BIGSERIAL PRIMARY KEY,
    incident_id BIGINT NOT NULL REFERENCES incidents(id),
    field       VARCHAR(50) NOT NULL,
    old_value   TEXT,
    new_value   TEXT,
    changed_by  BIGINT NOT NULL,
    changed_at  TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_incidents_assignee_status ON incidents (assignee_id, status);
CREATE INDEX idx_incidents_status_priority ON incidents (status, priority)
    WHERE status != 'CLOSED';
```

Частичный индекс здесь оправдан: закрытых инцидентов со временем становится
большинство, а работают со списком открытых.

### Ключевые решения

**Конкурентное редактирование.** Два человека открыли инцидент и меняют его
одновременно. Без защиты второе сохранение затрёт первое — классическое потерянное
обновление. Решение — колонка версии и оптимистическая блокировка: при
несовпадении версии пользователь получает сообщение, что данные устарели.

Это тот же механизм, что `@Version` в JPA и `If-Match` в HTTP.

**Переходы статусов.** Не любой статус переходит в любой. Правила стоит собрать в
одном месте — в самой сущности или в отдельном компоненте, а не рассыпать по
сервисам.

```text
NEW → IN_PROGRESS → RESOLVED → CLOSED
        ↓
     ON_HOLD
```

**История.** Отдельная таблица, а не поле «последнее изменение». Записывается в той
же транзакции, что и само изменение.

**SLA.** Сроки реакции считаются от создания. Отдельный планировщик проверяет
приближение дедлайна и отправляет уведомление. Важно, чтобы при нескольких
экземплярах приложения задача выполнялась один раз — нужна блокировка или
координация, иначе уведомления придут кратно числу экземпляров.

**Уведомления.** Через очередь, а не синхронным вызовом. Недоступность почтового
сервиса не должна мешать работе с инцидентами.

## Задача: сервис заказов

Самая содержательная задача из четырёх, потому что в ней сходятся конкурентность,
внешние вызовы и согласованность.

### Требования

```text
→ создание заказа с позициями
→ резервирование товара на складе
→ оплата через внешний сервис
→ отслеживание статуса
```

### Жизненный цикл

```text
CREATED → RESERVED → PAID → SHIPPED → DELIVERED
    ↓         ↓        ↓
CANCELLED CANCELLED  REFUNDED
```

### Резервирование остатков

Главная сложность. Два покупателя одновременно берут последний товар.

```java
// неверно: чтение и запись разнесены
Product product = repository.findById(id);
if (product.getStock() >= quantity) {
    product.setStock(product.getStock() - quantity);
}
```

Между чтением и записью другая транзакция успевает сделать то же самое. Классическое
потерянное обновление.

Варианты решения:

```sql
-- пессимистическая блокировка
SELECT stock FROM products WHERE id = ? FOR UPDATE;
```

```sql
-- атомарное обновление с условием, обычно предпочтительнее
UPDATE products
SET stock = stock - :quantity
WHERE id = :id AND stock >= :quantity;
```

Второй вариант выполняется одним запросом, база сама берёт блокировку строки на
время обновления. Если обновлено ноль строк — товара не хватило.

Важно: заказы должны блокировать товары в едином порядке, например по возрастанию
идентификатора. Иначе два заказа с пересекающимися позициями дадут дедлок.

### Оплата

Внешний вызов, и значит ненадёжный.

```text
→ не внутри транзакции: соединение и блокировки удерживались бы всё ожидание
→ с ключом идемпотентности: повтор не должен списать дважды
→ с таймаутом
→ неопределённость таймаута решается запросом статуса, а не повторным списанием
```

### Согласованность с событиями

Заказ сохраняется в базу, событие уходит в Kafka. Атомарности между системами нет,
поэтому применяется Outbox: событие пишется в ту же базу в одной транзакции, а
отдельный процесс отправляет его в брокер.

### Схема

```sql
CREATE TABLE orders (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    status          VARCHAR(20) NOT NULL,
    total           NUMERIC(19,2) NOT NULL,
    idempotency_key VARCHAR(100) UNIQUE,
    version         BIGINT NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL
);

CREATE TABLE outbox_events (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id BIGINT NOT NULL,
    type         VARCHAR(50) NOT NULL,
    payload      JSONB NOT NULL,
    sent_at      TIMESTAMPTZ
);

CREATE INDEX idx_outbox_unsent ON outbox_events (id) WHERE sent_at IS NULL;
```

Ключ идемпотентности на заказе защищает от двойного создания при повторе запроса —
пользователь дважды нажал кнопку или клиент повторил `POST` по таймауту.

## Как отвечать

```text
1. уточняющие вопросы — до всякого проектирования
2. проговаривать компромиссы: выбрал это, потому что…
3. начинать с простого решения, усложнять по мере необходимости
4. называть узкие места самому, не дожидаясь вопроса
5. не бояться сказать «для такой нагрузки это не нужно»
```

Признание, что при трёхстах запросах в секунду достаточно одного приложения и одной
базы PostgreSQL, говорит о зрелости больше, чем перечисление технологий.

## Типичные ошибки

### Начинать с технологий

Kafka и Redis до выяснения требований — решение без задачи.

### Не спрашивать про масштаб

Архитектура для тысячи и для миллиона пользователей различается принципиально.

### Усложнять без причины

Микросервисы и шардирование для нагрузки, которую вытянет один сервер.

### Игнорировать конкурентный доступ

Резервирование остатков и параллельное редактирование — места, где ошибка
проявляется только под нагрузкой.

### Забывать про отказы

Внешний сервис недоступен, сообщение пришло дважды, запрос повторили.

### Не думать об индексах

Схема без индексов под заявленные запросы — незаконченная схема.

### Хранить состояние в памяти приложения

Ломает горизонтальное масштабирование.

### Делать внешние вызовы внутри транзакции

Соединение и блокировки удерживаются всё время ожидания.

### Не различать строгую и отложенную согласованность

Для счётчика просмотров отставание допустимо, для остатков на складе — нет.

## Краткий ответ для собеседования

Разбор задачи начинается с уточнения требований — функциональных и нефункциональных,
включая масштаб и допустимость отставания данных. Затем делается грубая оценка
нагрузки: число запросов в секунду и объём данных. Часто выясняется, что нагрузка
умеренная и достаточно одного приложения с одной базой, и сказать об этом важнее,
чем предложить сложную схему.

Дальше описывается API, схема данных с индексами под конкретные запросы и основной
сценарий. После этого разбираются узкие места: кеш и реплики при преобладании
чтения, очередь для долгих операций, горизонтальное масштабирование приложения без
состояния. Шардирование применяется в последнюю очередь, поскольку ломает
соединения и транзакции.

Отдельно проговариваются конкурентный доступ и отказы. Конкурентное изменение
решается атомарным обновлением с условием, пессимистической блокировкой или
версионированием. Для внешних вызовов нужны таймауты, повторы только для
идемпотентных операций и ключ идемпотентности. Согласованность записи в базу и
отправки события обеспечивается паттерном Outbox.

## Вопросы на собеседовании

### 1. С чего начинать разбор задачи?

**Ответ:** с уточняющих вопросов о требованиях, сценариях и масштабе. Проектировать
до выяснения задачи бессмысленно.

### 2. Как оценить нагрузку?

**Ответ:** разделить число запросов в сутки на 86 400, получив средний RPS, и
умножить на два-три для пика. Объём данных считается как число записей на их размер
и срок хранения.

### 3. Что делать, если расчёт показал невысокую нагрузку?

**Ответ:** предложить простое решение — одно приложение и одну базу. Усложнение без
причины является ошибкой проектирования.

### 4. Что нужно, чтобы приложение масштабировалось горизонтально?

**Ответ:** отсутствие состояния в памяти экземпляра. Сессии, локальные кеши с
бизнес-данными и счётчики в полях ломают эту возможность.

### 5. Когда применять реплики чтения?

**Ответ:** при преобладании чтения. Нужно учитывать отставание реплики: только что
записанные данные могут быть не видны.

### 6. Когда применять шардирование?

**Ответ:** в последнюю очередь, когда исчерпаны вертикальное масштабирование, кеш и
реплики. Оно ломает соединения и транзакции между шардами.

### 7. Как решить конкурентное изменение остатка на складе?

**Ответ:** атомарным обновлением с условием `stock >= quantity`, пессимистической
блокировкой через `FOR UPDATE` или версионированием. Первый вариант проще и
выполняется одним запросом.

### 8. Как избежать дедлоков при резервировании нескольких товаров?

**Ответ:** блокировать строки в едином порядке, например по возрастанию
идентификатора.

### 9. Как защититься от двойного создания заказа?

**Ответ:** ключом идемпотентности с уникальным ограничением в базе. Повторный
запрос вернёт результат первого.

### 10. Как согласовать сохранение в базу и отправку события?

**Ответ:** через Outbox — событие пишется в ту же базу в одной транзакции, а
отдельный процесс отправляет его в брокер.

### 11. Почему нельзя вызывать платёжный сервис внутри транзакции?

**Ответ:** соединение с базой и блокировки удерживаются всё время ожидания ответа,
которое может исчисляться десятками секунд.

### 12. Что делать, если платёж завершился по таймауту?

**Ответ:** запросить статус операции, а не повторять списание. Повтор допустим
только с ключом идемпотентности.

### 13. Как генерировать код для короткой ссылки?

**Ответ:** случайной строкой с уникальным ограничением и повтором при конфликте.
Счётчик даёт предсказуемые коды, хеш требует обработки коллизий.

### 14. Какой код ответа использовать при перенаправлении?

**Ответ:** `302`. Постоянное перенаправление кешируется браузером, из-за чего
теряется статистика и становится невозможно изменить цель ссылки.

### 15. Почему уведомления отправляют асинхронно?

**Ответ:** результат не нужен вызывающему немедленно, а провайдер может быть
недоступен. Синхронный вызов замедлил бы ответ и связал бы доступность систем.

### 16. Как не отправить уведомление дважды?

**Ответ:** уникальным ограничением на ключ идемпотентности. Доставка из очереди
гарантируется минимум однократная, поэтому дубликаты неизбежны.

### 17. Как обрабатывать ошибки отправки?

**Ответ:** разделять временные и постоянные. Временные повторять с нарастающей
задержкой, постоянные сразу направлять в мёртвую очередь.

### 18. Как защититься от одновременного редактирования одной записи?

**Ответ:** колонкой версии и оптимистической блокировкой. При несовпадении версии
пользователь получает сообщение, что данные устарели.

### 19. Как хранить историю изменений?

**Ответ:** отдельной таблицей, записываемой в той же транзакции, что и само
изменение.

### 20. Что учесть при выполнении периодических задач на нескольких экземплярах?

**Ответ:** задача должна выполняться один раз. Нужна блокировка или внешняя
координация, иначе действие произойдёт кратно числу экземпляров.
