# Docker и CI/CD

## Образ и контейнер

```text
образ     → неизменяемый шаблон: файловая система и метаданные запуска
контейнер → запущенный экземпляр образа
```

Соотношение примерно как у класса и объекта: из одного образа запускается сколько
угодно контейнеров.

Контейнер — не виртуальная машина. Он использует ядро хоста, а изоляция достигается
средствами самого ядра: пространства имён разделяют процессы, сеть и файловую
систему, контрольные группы ограничивают ресурсы.

```text
виртуальная машина → своё ядро, гипервизор, гигабайты, старт десятки секунд
контейнер          → ядро хоста, мегабайты, старт доли секунды
```

### Слои

Образ состоит из слоёв, каждый из которых — набор изменений файловой системы.

```text
слой 4: приложение
слой 3: зависимости
слой 2: JRE
слой 1: базовая ОС
```

Слои неизменяемы и переиспользуются: десять образов на одной базе хранят её один
раз. При запуске сверху добавляется тонкий слой записи, и изменения внутри
контейнера не затрагивают образ.

Отсюда правило: данные, которые должны пережить контейнер, в него не пишут.

## Dockerfile

### Многоэтапная сборка

Для Java это стандарт: собирать нужно с JDK и Gradle, а запускать — с одним JRE.

```dockerfile
FROM gradle:8-jdk21 AS build
WORKDIR /app

COPY build.gradle settings.gradle ./
RUN gradle dependencies --no-daemon

COPY src ./src
RUN gradle bootJar --no-daemon

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

RUN addgroup -S app && adduser -S app -G app
USER app

COPY --from=build /app/build/libs/*.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

В итоговый образ попадает только результат сборки. Исходники, Gradle и JDK
остаются в промежуточном этапе и до продакшена не доезжают — это и меньше по
размеру, и безопаснее.

### Порядок команд и кеш

Каждая инструкция создаёт слой. При повторной сборке Docker переиспользует слои до
первого изменения, а всё после него пересобирает.

Отсюда главный приём для Java:

```dockerfile
COPY build.gradle settings.gradle ./
RUN gradle dependencies          # слой с зависимостями

COPY src ./src                   # меняется при каждой правке кода
RUN gradle bootJar
```

Зависимости копируются и загружаются раньше исходников. Пока файл сборки не
менялся, слой с зависимостями берётся из кеша, и сборка занимает секунды вместо
минут.

Обратный порядок — `COPY . .` в начале — сводит кеш на нет: любая правка кода
запускает повторную загрузку всех зависимостей.

### Основные инструкции

```text
FROM        базовый образ
WORKDIR     рабочий каталог
COPY        копирование из контекста сборки
RUN         выполнение команды на этапе сборки
ENV         переменная окружения
EXPOSE      документирование порта, ничего не открывает
USER        пользователь, от которого работает процесс
ENTRYPOINT  основная команда
CMD         аргументы по умолчанию или команда
HEALTHCHECK проверка состояния
```

### ENTRYPOINT и CMD

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--spring.profiles.active=prod"]
```

`ENTRYPOINT` задаёт саму команду, `CMD` — аргументы, которые легко переопределить
при запуске. Если указан только `CMD`, он целиком заменяется переданной командой.

Форму записи массивом предпочитают строке: при строковой форме команда выполняется
через оболочку, и процесс приложения перестаёт быть первым в контейнере — сигналы
завершения до него не доходят.

### .dockerignore

```text
.git
build
.gradle
*.md
.env
```

Контекст сборки целиком передаётся демону Docker. Без этого файла туда попадут
история Git и каталоги сборки — медленно, а иногда и небезопасно.

## JVM в контейнере

Тема, которую спрашивают именно у Java-разработчиков.

Исторически JVM определяла доступную память по хосту, игнорируя ограничение
контейнера. Приложение в контейнере с лимитом 512 МБ видело 64 ГБ хоста, выставляло
кучу под четверть этого объёма и получало принудительное завершение по превышению
лимита.

Современные версии учитывают контрольные группы автоматически, но полагаться на
умолчания не стоит:

```dockerfile
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
```

Процент, а не фиксированное значение: образ работает при любом лимите памяти, и
менять его при изменении квоты не нужно.

Оставшиеся 25% нужны не «на всякий случай»: помимо кучи JVM расходует память на
метапространство, стеки потоков, буферы вне кучи и сам процесс. Задание
`-Xmx`, равного лимиту контейнера, гарантированно приводит к завершению по памяти.

### Корректное завершение

При остановке контейнера процессу отправляется `SIGTERM`, и через отведённое время
— `SIGKILL`. Приложение должно успеть дообработать текущие запросы.

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

Условие — приложение должно быть первым процессом в контейнере. Поэтому важна
форма записи `ENTRYPOINT` массивом: при запуске через оболочку сигнал получит она,
а не JVM.

## Тома, сеть, порты

### Тома

```text
volume      → управляется Docker, для данных
bind mount  → каталог хоста, для разработки
tmpfs       → в памяти, исчезает вместе с контейнером
```

```bash
docker run -v pgdata:/var/lib/postgresql/data postgres:16
```

Без тома данные базы исчезнут вместе с контейнером.

### Порты

```bash
docker run -p 8080:8080 app
```

Слева порт хоста, справа — контейнера. Инструкция `EXPOSE` в Dockerfile ничего не
публикует, она лишь документирует.

### Сеть

Контейнеры в одной пользовательской сети видят друг друга по именам — работает
встроенное разрешение имён.

```yaml
services:
  app:
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app
  postgres:
    image: postgres:16
```

Здесь `postgres` — имя сервиса, а не хоста. Обращение к `localhost` из контейнера
приложения ведёт в него самого, а не на хост — частая ошибка.

## Docker Compose

Описание нескольких связанных сервисов одним файлом. Основное применение —
локальная разработка.

```yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: dev
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5

volumes:
  pgdata:
```

Важная деталь: обычный `depends_on` дожидается только запуска контейнера, а не
готовности сервиса. База может ещё инициализироваться, пока приложение уже пытается
подключиться. Условие `service_healthy` вместе с проверкой состояния решает это.

## Проверки состояния

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s \
  CMD wget -q --spider http://localhost:8080/actuator/health || exit 1
```

Параметр `start-period` учитывает время старта приложения: до его истечения
неудачные проверки не считаются отказом. Для Spring Boot это существенно — старт
занимает секунды.

В оркестраторах различают два вида проверок:

```text
liveness  → процесс жив, иначе перезапустить
readiness → готов принимать трафик, иначе не направлять запросы
```

Spring Boot предоставляет их отдельно:

```text
/actuator/health/liveness
/actuator/health/readiness
```

## Конфигурация и секреты

```text
переменные окружения → основной способ, работает с relaxed binding Spring
```

```text
SPRING_DATASOURCE_URL      → spring.datasource.url
SPRING_PROFILES_ACTIVE     → spring.profiles.active
```

Чего делать нельзя:

```dockerfile
ENV DB_PASSWORD=secret123     # попадёт в слой образа навсегда
```

Значение сохранится в истории слоёв, и удалить его последующей командой не выйдет —
слои неизменяемы. Любой, кто получит образ, увидит пароль.

Секреты передают через переменные окружения при запуске, механизмы секретов
оркестратора или внешние хранилища.

## CI

Непрерывная интеграция: каждый коммит собирается и проверяется автоматически.

```text
push → сборка → тесты → анализ → сборка образа → публикация
```

Пример для GitHub Actions:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: gradle

      - name: Build and test
        run: ./gradlew build

      - name: Build image
        run: docker build -t app:${{ github.sha }} .
```

Смысл в быстрой обратной связи: ошибка обнаруживается на коммите, а не при
развёртывании. Отсюда требование к тестам — они должны выполняться быстро, иначе их
начинают отключать.

Хеш коммита в теге образа лучше, чем `latest`: понятно, что именно развёрнуто, и
возможен откат на конкретную версию.

## CD и стратегии развёртывания

```text
Continuous Delivery → артефакт всегда готов к выкладке, решение принимает человек
Continuous Deployment → выкладка автоматическая после прохождения проверок
```

```text
rolling update
→ экземпляры заменяются по одному
→ две версии работают одновременно
→ требует обратной совместимости

blue-green
→ поднимается полное окружение с новой версией
→ трафик переключается разом
→ быстрый откат, двойной расход ресурсов

canary
→ новая версия получает малую долю трафика
→ при отсутствии ошибок доля растёт
```

Практическое следствие постепенной выкладки: миграции базы должны быть совместимы
с обеими версиями. Удаление колонки в одном релизе с кодом, который её больше не
использует, сломает старые экземпляры, работающие параллельно. Поэтому удаление
разносят на два релиза: сначала код перестаёт использовать колонку, затем в
следующем релизе она удаляется.

## Типичные ошибки

### Копировать исходники до зависимостей

Кеш слоёв не работает, каждая сборка загружает зависимости заново.

### Собирать и запускать в одном образе

В продакшен попадают JDK, Gradle и исходники: больше размер и шире поверхность
атаки.

### Задавать -Xmx равным лимиту контейнера

Помимо кучи JVM нужна память на метапространство, стеки и буферы. Контейнер будет
завершён по превышению лимита.

### Записывать секреты в Dockerfile через ENV

Значение остаётся в слое образа навсегда.

### Хранить данные внутри контейнера

Исчезнут при пересоздании. Нужен том.

### Обращаться к localhost между контейнерами

Внутри контейнера это он сам. Используются имена сервисов.

### Полагаться на depends_on без проверки состояния

Дожидается запуска контейнера, а не готовности сервиса.

### Использовать строковую форму ENTRYPOINT

Процесс запускается через оболочку и не получает сигнал завершения.

### Работать от root

Компрометация процесса даёт больше возможностей, чем следовало бы.

### Тегировать образы как latest

Непонятно, какая версия развёрнута, и откат затруднён.

### Не думать о совместимости миграций

При постепенной выкладке две версии кода работают с одной схемой одновременно.

## Краткий ответ для собеседования

Образ — неизменяемый шаблон из слоёв, контейнер — его запущенный экземпляр.
Контейнер не является виртуальной машиной: он использует ядро хоста, а изоляция
обеспечивается пространствами имён и контрольными группами, поэтому запуск занимает
доли секунды.

Для Java применяют многоэтапную сборку: приложение собирается образом с JDK, а в
итоговый попадает только jar поверх JRE. Порядок инструкций подбирают под кеш
слоёв — зависимости копируются и загружаются до исходников, иначе каждая правка
кода вызывает повторную загрузку всех зависимостей.

Отдельного внимания требует JVM в контейнере. Указывать `-Xmx` равным лимиту
памяти нельзя: помимо кучи нужны метапространство, стеки потоков и буферы вне кучи.
Используется доля от доступной памяти через `MaxRAMPercentage`. Приложение должно
быть первым процессом, чтобы получать `SIGTERM` и корректно завершаться.

Данные хранятся в томах, а не внутри контейнера. Контейнеры одной сети обращаются
друг к другу по именам сервисов. Секреты передаются переменными окружения при
запуске: указанные через `ENV` в Dockerfile остаются в слое образа навсегда.

CI обеспечивает сборку и прогон тестов на каждом коммите, CD — выкладку. При
постепенной замене экземпляров две версии приложения работают одновременно, поэтому
миграции базы должны быть совместимы с обеими.

## Вопросы на собеседовании

### 1. Чем образ отличается от контейнера?

**Ответ:** образ — неизменяемый шаблон, контейнер — его запущенный экземпляр. Из
одного образа можно запустить много контейнеров.

### 2. Чем контейнер отличается от виртуальной машины?

**Ответ:** контейнер использует ядро хоста, изоляция достигается пространствами имён
и контрольными группами. Виртуальная машина несёт собственное ядро и запускается на
порядки дольше.

### 3. Что такое слои образа?

**Ответ:** наборы изменений файловой системы. Они неизменяемы и переиспользуются
между образами, а при запуске сверху добавляется слой записи.

### 4. Зачем нужна многоэтапная сборка?

**Ответ:** чтобы инструменты сборки и исходники не попадали в итоговый образ.
Собирают образом с JDK, запускают на JRE.

### 5. Почему зависимости копируют до исходников?

**Ответ:** ради кеша слоёв. Пока файл сборки не менялся, слой с зависимостями
берётся из кеша, и правка кода не вызывает их повторную загрузку.

### 6. Что делает EXPOSE?

**Ответ:** только документирует порт. Публикация выполняется параметром `-p` при
запуске.

### 7. Чем ENTRYPOINT отличается от CMD?

**Ответ:** `ENTRYPOINT` задаёт саму команду, `CMD` — аргументы по умолчанию,
которые легко переопределить при запуске.

### 8. Почему важна форма записи ENTRYPOINT массивом?

**Ответ:** при строковой форме команда выполняется через оболочку, и приложение не
является первым процессом, поэтому не получает сигнал завершения.

### 9. Какие проблемы возникают у JVM в контейнере?

**Ответ:** исторически JVM определяла память по хосту, игнорируя лимит контейнера, и
процесс завершался по превышению. Современные версии учитывают контрольные группы,
но размер кучи всё равно задают явно.

### 10. Почему нельзя задать -Xmx равным лимиту памяти?

**Ответ:** помимо кучи JVM использует метапространство, стеки потоков и буферы вне
кучи. Суммарное потребление превысит лимит.

### 11. Как обеспечить корректное завершение?

**Ответ:** включить graceful shutdown в приложении и убедиться, что оно является
первым процессом контейнера и получает `SIGTERM`.

### 12. Где хранить данные?

**Ответ:** в томах. Слой записи контейнера исчезает вместе с ним.

### 13. Как контейнеры находят друг друга?

**Ответ:** по именам сервисов внутри общей сети, через встроенное разрешение имён.
Обращение к `localhost` ведёт в сам контейнер.

### 14. Гарантирует ли depends_on готовность зависимости?

**Ответ:** нет, он ждёт только запуска контейнера. Нужна проверка состояния с
условием `service_healthy`.

### 15. Почему нельзя писать секреты в Dockerfile?

**Ответ:** значение попадёт в слой образа и останется там навсегда, поскольку слои
неизменяемы.

### 16. Чем liveness отличается от readiness?

**Ответ:** liveness отвечает, нужно ли перезапустить процесс, readiness — можно ли
направлять на него трафик.

### 17. Что такое CI?

**Ответ:** автоматическая сборка и проверка каждого коммита, дающая быструю
обратную связь об ошибках.

### 18. Чем Continuous Delivery отличается от Continuous Deployment?

**Ответ:** в первом случае артефакт готов к выкладке, но решение принимает человек;
во втором выкладка происходит автоматически после прохождения проверок.

### 19. Какие есть стратегии развёртывания?

**Ответ:** rolling с поочерёдной заменой экземпляров, blue-green с переключением
трафика между окружениями и canary с постепенным увеличением доли трафика.

### 20. Почему при rolling update важна совместимость миграций?

**Ответ:** две версии приложения работают одновременно с одной схемой. Удаление
колонки сломает ещё не заменённые экземпляры, поэтому его разносят на два релиза.
