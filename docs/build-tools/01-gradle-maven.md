# Gradle и Maven

## Зачем нужен сборщик

Сборка Java-проекта вручную означает компиляцию с указанием classpath, загрузку
десятков библиотек вместе с их собственными зависимостями, прогон тестов и
упаковку. Сборщик делает это по описанию проекта и, что важнее, обеспечивает
воспроизводимость: одна и та же команда даёт один и тот же результат на любой
машине.

```text
управление зависимостями и их транзитивными связями
компиляция и упаковка
запуск тестов
единый жизненный цикл сборки
```

## Maven

### pom.xml

Описание проекта в XML, декларативное по устройству.

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>order-service</artifactId>
    <version>1.0.0</version>
    <packaging>jar</packaging>

    <properties>
        <java.version>21</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
    </dependencies>
</project>
```

Артефакт однозначно определяется тройкой: группа, идентификатор, версия.

### Жизненный цикл

Maven задаёт фиксированную последовательность фаз, и запуск любой выполняет все
предыдущие.

```text
validate → compile → test → package → verify → install → deploy
```

```text
mvn compile → компиляция
mvn test    → компиляция + тесты
mvn package → всё выше + сборка jar
mvn install → плюс установка в локальный репозиторий
mvn clean   → отдельный цикл, очистка target
```

Отсюда привычное `mvn clean install`: очистить и пройти цикл до установки.

Жёсткость цикла — одновременно достоинство и ограничение. Проект собирается
предсказуемо, но нестандартный шаг встроить сложнее.

### Scopes

```text
compile   → доступна везде, попадает в артефакт (по умолчанию)
provided  → нужна для компиляции, предоставляется средой выполнения
runtime   → не нужна при компиляции, нужна при запуске (драйвер БД)
test      → только для тестов
import    → только для подключения BOM
```

`provided` типична для API сервлетов при развёртывании в контейнер, `runtime` — для
драйверов JDBC: код обращается к ним через интерфейсы JDBC, а не напрямую.

### Плагины

Вся работа в Maven выполняется плагинами; жизненный цикл лишь определяет, когда их
цели вызываются.

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>
```

## Gradle

### build.gradle

Скрипт на Groovy или Kotlin, то есть код, а не декларация.

```gradle
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.0'
    id 'io.spring.dependency-management' version '1.1.5'
}

group = 'com.example'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    runtimeOnly 'org.postgresql:postgresql'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
```

Гибкость выше, чем у Maven: можно описывать условия и собственную логику. Обратная
сторона — скрипт легко превратить в программу, которую трудно понять.

### Задачи

Единица работы в Gradle — задача. Задачи образуют граф зависимостей, и Gradle
выполняет только необходимые.

```bash
./gradlew build        # компиляция, тесты, сборка
./gradlew test
./gradlew bootJar
./gradlew tasks        # список доступных задач
```

В отличие от фаз Maven, задачи не выстроены в жёсткую линию — важны объявленные
между ними зависимости.

### Configurations

Аналог scopes, но устроенный иначе.

```text
implementation     → нужна для компиляции и выполнения, не видна потребителям
api                → то же, но видна потребителям модуля
compileOnly        → только компиляция, аналог provided
runtimeOnly        → только выполнение
testImplementation → для тестов
annotationProcessor → обработчики аннотаций, например Lombok
```

Различие `implementation` и `api` — ключевое нововведение Gradle. При
`implementation` зависимость не попадает в classpath компиляции тех, кто использует
ваш модуль. Это ускоряет сборку многомодульных проектов: изменение внутренней
зависимости не требует перекомпиляции всех потребителей.

`api` следует использовать только тогда, когда типы библиотеки действительно
встречаются в публичной сигнатуре модуля.

### Ускорение сборки

```text
демон             → JVM не перезапускается между сборками
инкрементальность → пересобирается только изменившееся
кеш сборки        → результаты переиспользуются, в том числе между машинами
параллельность    → независимые модули собираются одновременно
```

Это основное практическое преимущество Gradle перед Maven на больших проектах.

## Транзитивные зависимости и конфликты

Каждая библиотека тянет свои зависимости, те — свои. Одна и та же библиотека
нередко попадает в дерево в разных версиях, и сборщик должен выбрать одну.

Здесь Maven и Gradle ведут себя **по-разному**, и это классический вопрос на
собеседовании.

```text
Maven  → ближайшее определение в дереве зависимостей
Gradle → наибольшая версия
```

```text
A → B → C:1.0
A → D → E → C:2.0

Maven:  выберет C:1.0 (ближе к корню — два уровня против трёх)
Gradle: выберет C:2.0 (версия выше)
```

Стратегия Maven приводит к неожиданностям: добавление новой зависимости может
понизить версию уже используемой библиотеки. Стратегия Gradle предсказуемее, хотя
и не гарантирует совместимости.

Просмотр дерева:

```bash
mvn dependency:tree
./gradlew dependencies
```

Управление:

```xml
<exclusions>
    <exclusion>
        <groupId>org.slf4j</groupId>
        <artifactId>slf4j-log4j12</artifactId>
    </exclusion>
</exclusions>
```

```gradle
implementation('org.example:library') {
    exclude group: 'org.slf4j', module: 'slf4j-log4j12'
}
```

Исключения нужны регулярно — например, при подключении Log4j2 в Spring Boot
требуется исключить стандартный стартер логирования, иначе в classpath окажутся две
реализации.

### BOM

Спецификация, фиксирующая согласованные версии набора библиотек.

```gradle
implementation platform('org.springframework.boot:spring-boot-dependencies:3.3.0')
implementation 'org.springframework.boot:spring-boot-starter-web'   // без версии
```

Именно так Spring Boot избавляет от подбора версий вручную. Указывать версию
отдельной библиотеки из BOM можно, но осознанно: она проверялась в связке с
остальными.

## Wrapper

```bash
./gradlew build
./mvnw package
```

Wrapper — скрипт и небольшой jar в репозитории, которые сами загружают нужную
версию сборщика.

Смысл в воспроизводимости: у всех участников и на сервере сборки используется одна
и та же версия, независимо от того, что установлено локально. Более того, сборщик
вообще не нужно устанавливать.

Файлы wrapper коммитятся в репозиторий. Запуск через `gradle` вместо `./gradlew`
сводит эту гарантию на нет.

## Многомодульный проект

```text
order-service/
├── settings.gradle
├── build.gradle
├── domain/
│   └── build.gradle
├── application/
│   └── build.gradle
└── infrastructure/
    └── build.gradle
```

```gradle
// settings.gradle
rootProject.name = 'order-service'
include 'domain', 'application', 'infrastructure'
```

```gradle
// application/build.gradle
dependencies {
    implementation project(':domain')
}
```

В Maven то же выражается через `<modules>` и родительский pom.

Польза не только техническая: модули закрепляют границы. Зависимость между ними
объявляется явно, и случайно обратиться к внутренностям чужого модуля не выйдет —
это дисциплинирует сильнее, чем соглашения о пакетах.

## Сравнение

| Критерий | Maven | Gradle |
|---|---|---|
| Формат | XML, декларативный | Groovy или Kotlin, код |
| Жизненный цикл | фиксированные фазы | граф задач |
| Гибкость | ограниченная | высокая |
| Порог входа | ниже | выше |
| Скорость на больших проектах | ниже | выше за счёт кеша и демона |
| Конфликт версий | ближайшее определение | наибольшая версия |
| Предсказуемость | выше | зависит от скрипта |

Обоснованный выбор: Maven — когда важны простота и единообразие, Gradle — когда
нужны скорость сборки и нестандартная логика. В новых проектах на Spring Boot чаще
встречается Gradle, в корпоративной среде по-прежнему много Maven.

## Типичные ошибки

### Указывать версии библиотек, входящих в BOM

Смысл спецификации в согласованности; ручное переопределение легко ломает
совместимость.

### Использовать api вместо implementation

Зависимость протекает к потребителям модуля, сборка замедляется, границы
размываются.

### Не коммитить wrapper

Теряется гарантия одинаковой версии сборщика у всех участников.

### Запускать gradle вместо ./gradlew

Используется локально установленная версия, которая может отличаться.

### Не смотреть дерево зависимостей при конфликте

Причина странного поведения часто в подтянутой транзитивно версии библиотеки.

### Помещать драйвер БД в implementation

Он нужен только при выполнении, для этого есть `runtimeOnly`.

### Держать библиотеки для тестов в основной конфигурации

Они попадут в артефакт и увеличат его размер.

### Писать сложную логику в build.gradle

Скрипт превращается в программу, которую никто не хочет трогать.

## Краткая памятка

```text
Maven
pom.xml, XML, фиксированные фазы
validate → compile → test → package → verify → install → deploy
scopes: compile, provided, runtime, test, import
конфликт версий → ближайшее определение
```

```text
Gradle
build.gradle, код, граф задач
implementation / api / compileOnly / runtimeOnly / testImplementation
implementation не протекает к потребителям
конфликт версий → наибольшая версия
демон, инкрементальность, кеш сборки
```

```text
wrapper → одинаковая версия сборщика у всех, коммитится в репозиторий
BOM     → согласованные версии, поэтому версии не указываются
```

## Краткий ответ для собеседования

Сборщик управляет зависимостями, компиляцией, тестами и упаковкой, обеспечивая
воспроизводимость сборки.

Maven описывает проект декларативно в XML и работает по фиксированному жизненному
циклу: запуск любой фазы выполняет все предыдущие. Область видимости зависимости
задаётся scope — `compile`, `provided`, `runtime`, `test`.

Gradle использует скрипт на Groovy или Kotlin и строит граф задач вместо линейной
последовательности фаз. Аналог scopes здесь — конфигурации, среди которых важно
различать `implementation` и `api`: первая не пропускает зависимость в classpath
потребителей модуля, что ускоряет сборку и не размывает границы. Gradle быстрее на
крупных проектах за счёт демона, инкрементальной сборки и кеша.

Существенное различие — разрешение конфликтов версий. Maven выбирает определение,
ближайшее к корню дерева зависимостей, поэтому добавление новой библиотеки может
неожиданно понизить версию существующей. Gradle выбирает наибольшую версию.

Wrapper фиксирует версию самого сборщика и коммитится в репозиторий, чтобы сборка
была одинаковой у всех участников и на сервере сборки. BOM фиксирует согласованные
версии библиотек — на этом основано управление зависимостями в Spring Boot.

## Вопросы на собеседовании

### 1. Зачем нужен сборщик?

**Ответ:** управлять зависимостями с их транзитивными связями, компилировать,
запускать тесты и упаковывать артефакт воспроизводимым образом.

### 2. Что такое жизненный цикл Maven?

**Ответ:** фиксированная последовательность фаз от валидации до развёртывания.
Запуск любой фазы выполняет все предшествующие.

### 3. Какие есть scopes в Maven?

**Ответ:** `compile` по умолчанию, `provided` для предоставляемых средой,
`runtime` для нужных только при выполнении, `test` для тестов и `import` для
подключения BOM.

### 4. Когда использовать runtime?

**Ответ:** для библиотек, не нужных при компиляции, — типичный пример драйвер базы
данных, к которому обращаются через интерфейсы JDBC.

### 5. Чем Gradle отличается от Maven по устройству?

**Ответ:** Maven декларативен и работает по фиксированным фазам, Gradle использует
скрипт и строит граф задач, выполняя только необходимые.

### 6. Чем implementation отличается от api?

**Ответ:** при `implementation` зависимость не попадает в classpath компиляции
потребителей модуля, при `api` попадает. Первый вариант ускоряет сборку и не
размывает границы модулей.

### 7. Как разрешается конфликт версий?

**Ответ:** Maven выбирает ближайшее к корню определение, Gradle — наибольшую
версию.

### 8. Чем опасна стратегия Maven?

**Ответ:** добавление новой зависимости может понизить версию уже используемой
библиотеки, поскольку её определение окажется ближе к корню дерева.

### 9. Как посмотреть дерево зависимостей?

**Ответ:** `mvn dependency:tree` или `./gradlew dependencies`.

### 10. Как исключить транзитивную зависимость?

**Ответ:** через `exclusions` в Maven или блок `exclude` в объявлении зависимости в
Gradle. Типичный случай — исключение стандартного стартера логирования при переходе
на Log4j2.

### 11. Что такое BOM?

**Ответ:** спецификация с согласованными версиями набора библиотек. Позволяет не
указывать версии отдельных зависимостей.

### 12. Зачем нужен wrapper?

**Ответ:** чтобы у всех участников и на сервере сборки использовалась одна версия
сборщика, а устанавливать его локально было не нужно.

### 13. Нужно ли коммитить wrapper?

**Ответ:** да, иначе гарантия одинаковой версии теряется.

### 14. За счёт чего Gradle быстрее?

**Ответ:** демон не перезапускает JVM между сборками, пересобирается только
изменившееся, результаты кешируются, независимые модули собираются параллельно.

### 15. Что даёт разделение проекта на модули?

**Ответ:** явные границы и явные зависимости между частями системы, а также
возможность собирать и тестировать модули по отдельности.

### 16. Куда помещать библиотеки для тестов?

**Ответ:** в `test` или `testImplementation`, иначе они попадут в артефакт.

### 17. Что такое provided и когда он нужен?

**Ответ:** зависимость нужна при компиляции, но предоставляется средой выполнения.
Классический пример — API сервлетов при развёртывании в контейнер. В Gradle
соответствует `compileOnly`.

### 18. Что выбрать для нового проекта?

**Ответ:** зависит от приоритетов. Maven проще и предсказуемее, Gradle быстрее на
крупных проектах и гибче. Однозначно верного ответа нет.
