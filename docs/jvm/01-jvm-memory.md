# JVM и области памяти

Как устроено выполнение Java-программы и где во время работы находятся данные.
Тема отвечает на вопрос «где что лежит»; правила видимости этих данных между
потоками — предмет модели памяти и разбираются отдельно.

---

## Как выполняется Java-программа

```text
исходный код .java
→ компилятор javac
→ байт-код .class
→ JVM
→ машинные инструкции конкретной платформы
```

Компилятор `javac` преобразует исходный код в байт-код и записывает его в файл
`.class`. JVM байт-код не создаёт — она загружает, проверяет и выполняет уже
скомпилированный.

Байт-код представляет собой инструкции для виртуальной машины и не привязан к
командам конкретной операционной системы. Для его выполнения устанавливается
реализация JVM под нужную платформу.

```text
один файл .class
├── JVM для Windows
├── JVM для Linux
└── JVM для macOS
```

Принцип «написано один раз — работает везде» означает, что корректный байт-код
можно выполнять на разных платформах при наличии совместимой JVM. Абсолютной
переносимости это не гарантирует: код может зависеть от нативных библиотек,
файловой системы, кодировок и прав доступа.

### JVM, JRE и JDK

JVM исполняет байт-код и берёт на себя загрузку классов, проверку корректности
байт-кода, управление памятью и сборку мусора, выполнение потоков, работу
интерпретатора и JIT, взаимодействие с операционной системой.

JRE — среда, необходимая для запуска приложения: JVM плюс стандартные библиотеки
и runtime-компоненты. Начиная с Java 11 отдельной публичной поставки JRE нет:
разработчики устанавливают JDK либо собирают собственный runtime-образ через
`jlink`.

JDK добавляет к среде выполнения инструменты разработки:

```text
javac → компиляция
java  → запуск
jar   → работа с архивами
javadoc → документация
jdb   → отладка
jcmd, jstack, jmap → диагностика JVM
```

```text
JVM → выполняет байт-код
JRE → предоставляет среду для запуска
JDK → предоставляет среду и инструменты разработки
```

## Интерпретатор и JIT

JVM сочетает интерпретацию байт-кода и его компиляцию в машинный код прямо во
время работы приложения.

Интерпретатор последовательно читает и выполняет инструкции. Его преимущество —
мгновенный старт: не нужно ждать компиляции. Недостаток — часто выполняемые
инструкции приходится интерпретировать снова и снова.

JIT, то есть just-in-time compiler, работает во время выполнения. JVM собирает
статистику: методы и циклы, выполняемые особенно часто, становятся горячим кодом,
и JIT компилирует их в машинный код конкретного процессора.

```text
байт-код
→ интерпретация
→ сбор статистики
→ обнаружение горячего кода
→ JIT-компиляция
→ машинный код
```

Прогрев JVM — период, когда приложение уже работает, но профиль ещё собирается и
важные участки ещё не скомпилированы. Поэтому результаты короткого запуска
отличаются от производительности после прогрева, и замеры на непрогретой машине
недостоверны.

JIT не компилирует всё приложение заранее: он выбирает участки по статистике и
применяет к ним оптимизации.

## Загрузка и инициализация классов

```text
Loading
→ Verification
→ Preparation
→ Resolution
→ Initialization
```

Три средних этапа вместе называются Linking.

**Loading.** JVM находит байт-код класса, загружает его и создаёт внутреннее
представление типа. Поиск выполняет соответствующий ClassLoader.

**Verification.** Проверяются формат файла, корректность байт-кода,
совместимость типов, допустимость инструкций и корректность работы со стеком
операндов. Это не проверка бизнес-логики, а защита среды выполнения от
структурно некорректного или намеренно искажённого кода.

**Preparation.** Статическим полям выделяется память и присваиваются значения по
умолчанию.

```java
public class Counter {

    static int count = 10;
}
```

На этом этапе `count` равен нулю: выражение `10` ещё не вычисляется.

Исключение — константы времени компиляции, объявленные `static final` и
представленные атрибутом `ConstantValue`: они могут получить итоговое значение уже
здесь.

```java
static final int LIMIT = 10;
```

**Resolution.** Символические ссылки из constant pool заменяются фактическими.
Разрешение может выполняться лениво, при первом реальном использовании ссылки.

```text
класс Order
метод Order.getEmail()
поле Order.status
```

**Initialization.** Выполняются присваивания статическим полям и статические
блоки.

```text
Preparation    → count = 0
Initialization → count = 10
```

## ClassLoader

Загрузчик находит байт-код и загружает определения классов в JVM. Разделение
загрузчиков организует платформенные классы, классы приложения и библиотеки.

```text
Bootstrap ClassLoader
        ↓
Platform ClassLoader
        ↓
Application ClassLoader
```

Bootstrap загружает базовые классы платформы — например, `java.lang.Object` и
`java.lang.String`. Platform загружает классы платформенных модулей, не входящих
в этот минимальный набор. Application загружает классы приложения и библиотек из
classpath и module path.

Привязывать каждый пакет целиком к одному загрузчику не стоит: состав зависит от
версии Java и набора модулей.

### Родительское делегирование

При классической модели parent-first загрузчик сначала передаёт запрос родителю:

```text
Application ClassLoader → передаёт родителю
Platform ClassLoader    → передаёт родителю
Bootstrap ClassLoader   → пытается найти класс

если родитель не нашёл
→ поиск выполняет дочерний ClassLoader
```

Модель защищает базовые классы от подмены: класс приложения с именем
`java.lang.String` не заменит платформенный.

Parent-first — стандарт для встроенной иерархии, но собственные загрузчики могут
реализовывать другие стратегии, если это нужно контейнеру или системе плагинов.

## Runtime Data Areas

```text
JVM Process
├── Heap                              общая
├── Method Area                       общая
├── JVM Stack каждого потока          своя
├── PC Register каждого потока        своя
└── Native Method Stack каждого потока своя
```

Куча и область методов связаны со всей JVM и могут содержать данные, доступные
нескольким потокам. Стек вызовов, счётчик команд и стек нативных методов — часть
индивидуального состояния потока. Конкретная реализация может иметь
дополнительные внутренние структуры, не показанные в этой схеме.

### Heap

Общая область, где в базовой модели размещаются объекты и массивы.

```java
new Order(...)
new int[100]
new ArrayList<>()
new HashMap<>()
```

```text
Thread 1 ──┐
           ├──→ Heap
Thread 2 ──┘
```

Несколько потоков могут обращаться к одному объекту, и отсюда возникают вопросы
видимости, синхронизации и гонок. Но это предмет модели памяти, а не
классификации областей.

Фраза «объект всегда физически находится в Heap» — концептуальное упрощение. JIT
применяет escape analysis и скалярную замену и может устранить отдельное
выделение памяти, если поведение программы сохраняется. Базовая модель — объекты
и массивы в куче — остаётся рабочей для рассуждений.

### JVM Stack

У каждого потока собственный стек, хранящий последовательность активных вызовов в
виде кадров. При вызове метода создаётся кадр, при возврате или выходе из-за
исключения — удаляется.

```java
public static void main(String[] args) {
    createOrder();
}

private static void createOrder() {
    validate();
}

private static void validate() {
}
```

```text
верх стека

┌──────────────────────┐
│ frame validate()     │
├──────────────────────┤
│ frame createOrder()  │
├──────────────────────┤
│ frame main()         │
└──────────────────────┘

низ стека
```

Собственный стек нужен не только для защиты от гонок: у каждого потока своя
последовательность вызовов, свои локальные переменные и своё место выполнения.
При этом локальная ссылка из стека может указывать на общий объект в куче, и он
по-прежнему может участвовать в гонке.

### Stack Frame

```text
Stack Frame
├── массив локальных переменных
├── Operand Stack
└── служебная информация
```

Схема отражает модель спецификации; точный внутренний формат зависит от
реализации и применённых оптимизаций.

Массив локальных переменных содержит параметры метода, локальные примитивы,
локальные ссылки и ссылку `this` у нестатического метода.

```java
public void process(long orderId) {
    int attempts = 3;
    Order order = repository.findById(orderId);
}
```

```text
this      → ссылка на текущий объект
orderId   → значение long
attempts  → значение int
order     → ссылка на объект Order
```

Локальная переменная объектного типа содержит значение ссылки, а не сам объект.

Operand Stack — рабочая область внутри одного кадра для промежуточных значений.
Для выражения:

```java
int result = a + b;
```

упрощённо выполняется:

```text
загрузить a в Operand Stack
→ загрузить b
→ снять два значения
→ выполнить сложение
→ положить результат обратно
```

Различать два уровня важно:

```text
JVM Stack     → весь стек потока
Operand Stack → часть конкретного Stack Frame
```

Служебная информация кадра включает данные о возврате из метода, данные для
вызова других методов, обработку исключений и связь с runtime constant pool.

### Method Area и Metaspace

```text
Method Area → понятие спецификации JVM
Metaspace   → реализация значительной части Method Area в HotSpot
```

С областью методов связаны метаданные классов, описания методов и полей, runtime
constant pool, байт-код методов и данные, связанные с типами. Спецификация не
требует, чтобы всё это физически лежало в одном непрерывном участке.

Metaspace использует нативную память процесса и не является частью Java Heap.

```text
Heap      → объекты Java
Metaspace → метаданные загруженных классов

до Java 8        → PermGen
начиная с Java 8 → Metaspace
```

Утверждать, что все статические поля находятся в Metaspace, неверно: там лежат
прежде всего метаданные, а значения статических полей — в куче.

Безопасная формулировка для собеседования:

> Metaspace в HotSpot хранит метаданные загруженных классов и использует нативную
> память.

### String Pool

Пул хранит канонические экземпляры строк, поэтому одинаковые литералы могут
ссылаться на один объект. Начиная с Java 7 пул находится в куче; метод `intern()`
возвращает каноническую строку.

```java
String first = "java";
String second = "java";

System.out.println(first == second);   // true
```

Результат `true` объясняется именно интернированием литералов. Сравнивать строки
всё равно нужно через `equals()`: оператор `==` сравнивает значения ссылок, а не
содержимое.

### PC Register и Native Method Stack

У каждого потока свой счётчик команд: для выполняемого Java-метода он указывает
на текущую инструкцию и позволяет продолжить выполнение после переключения
контекста. При выполнении нативного метода значение не определено.

Стек нативных методов связан с вызовами кода вне JVM через JNI:

```text
Java-метод → JNI → нативная функция C или C++
```

Точная организация зависит от реализации и платформы.

## Что где лежит

```java
public void example() {
    int count = 5;
    Order order = new Order("A-1");
}
```

```text
Stack Frame example()

count = 5
order = ссылка ──────────────┐
                             │
Heap                         │
                             ↓
                        Order("A-1")
```

```text
локальный примитив              → значение во Stack Frame
локальная переменная-объект     → ссылка во Stack Frame
сам объект                      → обычно в Heap
```

Распространённое «объекты в Heap, ссылки в Stack» слишком грубо: ссылка может быть
полем объекта.

```java
class Order {

    private Customer customer;
}
```

```text
Heap

Order
└── customer ─────→ Customer
```

Точная формулировка:

```text
локальная ссылка → Stack Frame
поле-ссылка      → внутри объекта в Heap
```

Ссылок на один объект может быть несколько:

```java
Order first = new Order("A-1");
Order second = first;
```

```text
first  ─────┐
second ─────┴────→ один объект Order в Heap
```

Объект один, ссылок две, и изменение состояния через одну будет видно через
другую.

С этим связано правило передачи параметров: Java всегда передаёт аргументы по
значению, а для объектов копируется значение ссылки. Метод может изменить
состояние объекта, но переназначение параметра меняет только локальную копию
ссылки — переменная вызывающего кода продолжит указывать на прежний объект.
Подробный разбор с примерами — в конспекте по основам языка.

## Жизненный цикл объекта и сборка мусора

```text
создание
→ использование
→ потеря достижимости
→ обнаружение GC
→ возможное освобождение памяти
```

```java
Order order = new Order("A-1");
order = null;
```

Если других путей к объекту нет, присваивание делает его недостижимым через эту
переменную. Но:

```text
объект стал недостижимым ≠ объект немедленно удалён
```

Момент обработки выбирает сборщик; присваивание `null` его не запускает.

### GC Roots и достижимость

Сборщик обходит граф объектов от корневых ссылок. К ним относятся локальные
ссылки активных кадров, активные потоки, часть статических ссылок, ссылки из
нативного кода.

```text
GC Root → Object A → Object B → Object C
```

```text
достижим от GC Roots     → объект считается живым
не достижим от GC Roots  → объект может быть удалён
```

Отсюда важное следствие про циклические ссылки: сами по себе они утечкой не
являются. Если до группы взаимно ссылающихся объектов нет пути от корней, вся
группа недостижима и будет собрана. Java использует анализ достижимости, а не
подсчёт ссылок.

### Как работает сборка

```text
найти GC Roots
→ пройти по ссылкам
→ определить достижимые объекты
→ обработать недостижимые
```

В зависимости от алгоритма и фазы сборщик выполняет маркировку, очистку,
перемещение, уплотнение, обновление ссылок. Не каждый использует все операции
одинаково, и описывать один алгоритм как универсальное устройство любого GC
нельзя.

Stop-the-World означает временную остановку прикладных потоков ради операций,
которым нужно согласованное состояние программы.

```text
потоки приложения остановлены
→ JVM выполняет операцию
→ потоки продолжают работу
```

При этом весь цикл сборки не обязан проходить при остановленном приложении:
современные сборщики выполняют значительную часть работы конкурентно или
параллельно несколькими служебными потоками.

### Поколения

Многие подходы опираются на слабую гипотезу поколений:

> Большинство объектов живёт недолго.

```text
Young Generation → новые и короткоживущие объекты
Old Generation   → долгоживущие объекты
```

Классическая схема молодого поколения — Eden и два Survivor. Новые объекты
создаются в Eden, пережившие сборку перемещаются в Survivor, а после нескольких
сборок переходят в старое поколение. Там обычно оказываются кеши, контейнеры
приложения и долгоживущие сервисные структуры.

Современные сборщики могут иметь другую физическую организацию: деление на Eden,
Survivor и Old полезно как классическая модель, но универсальной схемой не
является.

```text
Minor GC → обычно работа с молодым поколением
Major GC → обычно работа со старым поколением
Full GC  → обработка значительной части Heap и других структур
```

Точное значение терминов зависит от сборщика и диагностического инструмента.

## Утечки памяти

Утечка возникает, когда объект больше не нужен бизнес-логике, но программа
продолжает его удерживать.

```text
объект больше не нужен бизнес-логике
→ но остаётся достижимым от GC Roots
→ GC считает его живым
→ память не освобождается
```

```java
private static final List<byte[]> CACHE = new ArrayList<>();

public void process() {
    CACHE.add(new byte[1_000_000]);
}
```

```text
static field → List → byte[]
```

Статическое поле удерживает список, список удерживает массивы, и если элементы
никогда не удаляются, занятая память растёт.

Типичные причины:

```text
бесконечно растущий кеш
статические коллекции
незакрытые слушатели
неправильное использование ThreadLocal
утечки ClassLoader
коллекции без удаления старых элементов
удержание больших графов объектов
```

Наличие сборщика утечки не исключает: он определяет достижимость, но не знает,
нужен ли объект бизнес-логике.

### Виды ссылок

Пакет `java.lang.ref` даёт несколько типов ссылок с разным влиянием на жизненный
цикл.

Обычная ссылка является сильной: пока объект сильно достижим от корней, он
удерживается.

`SoftReference` позволяет объекту сохраняться некоторое время, но сборщик может
очистить её при нехватке памяти. Поведение зависит от JVM и доступной памяти,
поэтому как основной механизм управляемого кеша она не годится: там нужны явные
ограничения размера, политика вытеснения и наблюдаемое поведение.

`WeakReference` не удерживает объект при отсутствии сильной достижимости, и после
очистки `get()` возвращает `null`.

```java
WeakReference<Order> reference = new WeakReference<>(new Order("A-1"));
```

`WeakHashMap` использует слабые ссылки на ключи: запись исчезает, когда ключ
теряет обычную сильную достижимость.

`PhantomReference` используется вместе с `ReferenceQueue` для отслеживания поздней
стадии жизненного цикла и контролируемой очистки внешних ресурсов. Получить сам
объект через `get()` нельзя.

```text
Strong  → удерживает объект
Soft    → может быть очищена при нехватке памяти
Weak    → не удерживает при отсутствии сильной достижимости
Phantom → отслеживание финальной стадии жизненного цикла
```

### System.gc()

```java
System.gc();
```

Это запрос или рекомендация выполнить сборку, а не гарантия. JVM вправе его
проигнорировать, а флаг `-XX:+DisableExplicitGC` отключает такие вызовы
полностью. Программная логика не должна зависеть от того, что сразу после вызова
будет запущен сборщик или освобождён конкретный объём памяти.

## Ошибки исчерпания памяти

### StackOverflowError

Стек каждого потока ограничен по размеру, и каждый активный вызов добавляет кадр.

```java
public void recurse() {
    recurse();
}
```

```text
recurse() → recurse() → recurse() → ... → StackOverflowError
```

Типичные причины: бесконечная рекурсия, слишком глубокая рекурсия, слишком
большие кадры. Ошибка относится к стеку конкретного потока, а не к куче.

### OutOfMemoryError

Это один тип ошибки, возникающий по разным причинам; конкретный ресурс уточняет
сообщение.

**`Java heap space`** — не удалось разместить объект в куче.

```java
List<byte[]> data = new ArrayList<>();

while (true) {
    data.add(new byte[10_000_000]);
}
```

Список удерживает ссылки на массивы, те остаются достижимыми, и сборщик не может
освободить занятую ими память.

**`Metaspace`** — слишком много загруженных классов, динамическая генерация
классов, утечка ClassLoader. Пока загрузчик и его классы достижимы, метаданные
продолжают занимать память.

**`unable to create new native thread`** — слишком много потоков, нехватка
нативной памяти или ограничения операционной системы. Куча при этом может быть
свободна.

**`Direct buffer memory`** — исчерпана нативная память direct-буферов, а не
память обычных объектов.

**`Requested array size exceeds VM limit`** — запрошен массив длиннее, чем
допускает реализация.

**`GC overhead limit exceeded`** — сборщик тратит почти всё время на работу,
освобождая ничтожно мало памяти.

### Сравнение

| Ошибка | Причина |
|---|---|
| `StackOverflowError` | переполнение стека конкретного потока |
| `OutOfMemoryError` | невозможность выделить Heap, Metaspace, native thread, direct memory или другой ресурс |

Обе наследуются от `Error`, но описывают разные виды исчерпания ресурсов.

## Heap и Stack

| Характеристика | Heap | JVM Stack |
|---|---|---|
| Принадлежность | общий для потоков | отдельный для каждого потока |
| Основное содержимое | объекты и массивы | кадры вызванных методов |
| Управление памятью | сборщик мусора | освобождение кадра при возврате |
| Типичная ошибка | `OutOfMemoryError` | `StackOverflowError` |
| Многопоточность | возможен общий доступ | локален потоку |

Локальность стека не делает связанный объект потокобезопасным: ссылка из кадра
может указывать на объект в куче, доступный другим потокам.

## Runtime Data Areas и Java Memory Model

Разные вопросы, которые постоянно смешивают.

```text
Runtime Data Areas отвечают на вопрос:
где JVM концептуально хранит данные во время выполнения

Java Memory Model отвечает на вопросы:
как потоки видят изменения общих данных
какие операции атомарны
в каком порядке могут выполняться операции
что гарантирует happens-before
как работают volatile и synchronized
```

```text
области памяти JVM ≠ Java Memory Model
```

Гарантии межпоточного наблюдения разбираются в отдельном конспекте; здесь —
организация выполнения и памяти.

## Типичные ошибки

### Считать, что байт-код создаёт JVM

Байт-код создаёт `javac`. JVM его загружает, проверяет и выполняет.

### Говорить «объекты в Heap, ссылки в Stack»

Правило слишком грубое: локальная ссылка действительно в кадре стека, но
поле-ссылка находится внутри объекта в куче.

### Считать, что объект удаляется сразу после присваивания null

Он лишь может стать недостижимым. Момент обработки выбирает сборщик.

### Считать, что достижимый объект может быть удалён

Достижимый от корней объект считается живым и обычной сборкой не удаляется.

### Считать циклическую ссылку утечкой

Недостижимый от корней цикл будет собран: Java анализирует достижимость, а не
считает ссылки.

### Считать, что сборщик исключает утечки

Логически ненужный, но достижимый объект остаётся живым. Сборщик не знает о
намерениях бизнес-логики.

### Считать, что System.gc() гарантирует сборку

Это только запрос, который JVM вправе проигнорировать.

### Считать, что все static-поля лежат в Metaspace

Там прежде всего метаданные классов. Значения статических полей находятся в куче.

### Считать, что Stack всегда быстрее Heap

Слишком грубо. Производительность зависит от JIT, кешей процессора, escape
analysis, шаблона доступа, структуры данных и работы сборщика. Выбирать структуру
программы по такому лозунгу нельзя.

### Считать, что весь цикл GC проходит в Stop-the-World

Современные сборщики выполняют значительную часть работы конкурентно с
приложением.

### Путать Method Area и Metaspace

Первое — понятие спецификации, второе — его реализация в HotSpot начиная с
Java 8.

## Краткий ответ для собеседования

Компилятор `javac` преобразует исходный файл в байт-код, а JVM его загружает,
проверяет и выполняет — сначала интерпретируя, затем компилируя горячие участки
JIT-компилятором. JDK содержит и среду выполнения, и инструменты разработки.

Класс проходит загрузку, связывание и инициализацию. На подготовке статические
поля получают значения по умолчанию, на инициализации — заданные в коде; это
различие любят спрашивать. Загрузчики выстроены в иерархию и работают по принципу
parent-first, что не позволяет подменить платформенные классы собственными.

Области данных делятся на общие и принадлежащие потоку. Общие — куча, где лежат
объекты и массивы, и область методов, реализованная в HotSpot как Metaspace,
который хранит метаданные классов в нативной памяти. Своими у каждого потока
являются стек вызовов, счётчик команд и стек нативных методов. Стек состоит из
кадров, а кадр — из массива локальных переменных, стека операндов и служебной
информации.

Формулировку «объекты в куче, ссылки в стеке» стоит уточнять: локальная ссылка
действительно лежит в кадре, но поле объекта — это тоже ссылка, и она находится в
куче. С этим же связано правило передачи аргументов: Java всегда передаёт по
значению, для объектов копируется значение ссылки, поэтому метод может изменить
состояние объекта, но не может заставить переменную снаружи указывать на другой.

Сборщик определяет живые объекты по достижимости от корней, а не подсчётом
ссылок, — поэтому циклические ссылки сами по себе утечкой не являются. Зато
утечкой является достижимый объект, который бизнес-логике уже не нужен: типичный
случай — бесконечно растущая статическая коллекция.

Из ошибок: `StackOverflowError` означает исчерпание стека конкретного потока и
обычно вызвана рекурсией, а `OutOfMemoryError` — это целое семейство, где
сообщение уточняет, какой именно ресурс закончился: куча, Metaspace, нативная
память под поток или direct-буферы.

И отдельно стоит развести Runtime Data Areas и модель памяти: первое описывает,
где данные хранятся, второе — какие гарантии видимости и порядка получают потоки.

## Вопросы на собеседовании

### 1. Кто преобразует .java в .class?

**Ответ:** компилятор `javac`, входящий в JDK. Он переводит исходный код в
байт-код, а не в машинные инструкции конкретного процессора.

### 2. Что содержится в .class?

**Ответ:** байт-код методов, constant pool с литералами и ссылками на типы,
информация о полях, методах, суперклассе и интерфейсах, а также атрибуты вроде
таблицы номеров строк.

### 3. Почему один .class можно запускать на разных платформах?

**Ответ:** байт-код рассчитан на абстрактную виртуальную машину, а не на
процессор. Платформенно зависимой является сама JVM, существующая в реализации
под каждую систему.

### 4. Чем JVM отличается от JDK?

**Ответ:** JVM исполняет байт-код. JDK — комплект разработчика, включающий
компилятор, инструменты и среду выполнения.

### 5. Что концептуально входит в JRE?

**Ответ:** JVM и стандартная библиотека классов — минимум для запуска готового
приложения. Начиная с Java 11 отдельной поставки нет, вместо неё собирают образ
через `jlink`.

### 6. Чем интерпретатор отличается от JIT?

**Ответ:** интерпретатор выполняет байт-код инструкция за инструкцией, начиная
сразу. JIT компилирует часто исполняемые участки в машинный код, что даёт заметный
выигрыш, но требует времени на компиляцию.

### 7. Что называется горячим кодом?

**Ответ:** участок, выполняемый достаточно часто, чтобы JIT счёл компиляцию
оправданной — например, тело цикла или регулярно вызываемый метод.

### 8. Что такое прогрев JVM?

**Ответ:** период после запуска, пока код ещё интерпретируется, а JIT не собрал
статистику. Производительность в это время ниже установившейся, поэтому измерения
на непрогретой машине недостоверны.

### 9. Какие основные стадии проходит класс?

**Ответ:** загрузку, связывание из верификации, подготовки и разрешения ссылок, и
инициализацию.

### 10. Что происходит на этапе Loading?

**Ответ:** загрузчик находит байт-код, читает его и создаёт в памяти объект
`Class`, описывающий тип.

### 11. Что проверяет Verification?

**Ответ:** корректность байт-кода: соответствие типов, отсутствие переполнения
стека операндов, допустимость переходов. Защищает JVM от повреждённого или
намеренно искажённого кода.

### 12. Что происходит на Preparation?

**Ответ:** статическим полям выделяется память и присваиваются значения по
умолчанию — нули, `false` и `null`.

### 13. Чем Preparation отличается от Initialization?

**Ответ:** на подготовке поля получают значения по умолчанию, на инициализации —
заданные в коде, вместе с выполнением статических блоков.

### 14. Что происходит на Resolution?

**Ответ:** символические ссылки из constant pool заменяются прямыми. Может
выполняться отложенно, при первом фактическом использовании ссылки.

### 15. Какие ClassLoader существуют?

**Ответ:** загрузчик времени начальной загрузки, платформенный и загрузчик
приложения. Дополнительно можно создавать собственные.

### 16. Что такое родительское делегирование?

**Ответ:** загрузчик сначала передаёт запрос родителю и берётся за работу, только
если тот не справился. Это не позволяет подменить системные классы собственными.

### 17. Какие области памяти общие для потоков?

**Ответ:** куча и область методов, реализованная в современных версиях как
Metaspace.

### 18. Какие области принадлежат конкретному потоку?

**Ответ:** стек вызовов, счётчик команд и стек нативных методов.

### 19. Что находится в Heap?

**Ответ:** все объекты и массивы, включая внутренние массивы коллекций и сами
строки.

### 20. Что находится в JVM Stack?

**Ответ:** кадры вызванных методов: локальные переменные, стек операндов и
служебная информация для возврата.

### 21. Что создаётся при вызове метода?

**Ответ:** новый кадр стека, который уничтожается при выходе из метода.

### 22. Чем JVM Stack отличается от Operand Stack?

**Ответ:** стек вызовов хранит кадры методов. Стек операндов существует внутри
одного кадра и служит рабочей областью для вычисления выражений.

### 23. Почему у каждого потока свой Stack?

**Ответ:** потоки выполняют разные последовательности вызовов, и локальные
переменные каждого не должны быть видны остальным. Общий стек сделал бы
независимое исполнение невозможным.

### 24. Где находится локальная ссылка и может ли ссылка быть в Heap?

**Ответ:** локальная ссылка лежит в кадре стека того потока, который выполняет
метод, а объект — в куче. Но поле объекта тоже является ссылкой, и оно хранится
внутри объекта, то есть в куче.

### 25. Как Java передаёт параметры и почему нельзя говорить «по ссылке»?

**Ответ:** всегда по значению; для объектов копируется значение ссылки. Передача
по ссылке означала бы, что метод способен заставить переменную вызывающего кода
указывать на другой объект, а в Java это невозможно: изменить состояние объекта
метод может, саму переменную снаружи — нет.

### 26. Чем Method Area отличается от Metaspace?

**Ответ:** область методов — понятие спецификации. Metaspace — её реализация в
HotSpot начиная с Java 8, размещённая вне кучи в нативной памяти.

### 27. Что находится в Metaspace?

**Ответ:** метаданные классов: структура типа, описания методов и полей, constant
pool. Значения статических полей при этом хранятся в куче, и утверждать обратное —
распространённая ошибка.

### 28. Где находится String Pool?

**Ответ:** в куче, начиная с Java 7. До этого он размещался в PermGen, что
приводило к отдельным ошибкам нехватки памяти.

### 29. Что хранит PC Register?

**Ответ:** адрес текущей исполняемой инструкции для своего потока. При выполнении
нативного метода значение не определено.

### 30. Для чего нужен Native Method Stack?

**Ответ:** для вызовов методов, реализованных вне JVM, через интерфейс нативных
методов.

### 31. Когда возникает StackOverflowError?

**Ответ:** при исчерпании стека потока — обычно из-за слишком глубокой или
бесконечной рекурсии.

### 32. Какие варианты OutOfMemoryError существуют?

**Ответ:** нехватка кучи, нехватка Metaspace, невозможность создать новый поток,
исчерпание памяти direct-буферов, превышение лимита размера массива и
срабатывание ограничения на долю времени, проводимого в сборке мусора.

### 33. Чем StackOverflowError отличается от OutOfMemoryError: Java heap space?

**Ответ:** первый означает исчерпание стека конкретного потока, обычно из-за
рекурсии. Второй — нехватку места в общей куче для размещения объектов.

### 34. Что такое GC Roots?

**Ответ:** точки, от которых начинается обход достижимости: локальные переменные
активных кадров, статические поля, ссылки из нативного кода, объекты мониторов.

### 35. Когда объект считается живым и когда может быть удалён?

**Ответ:** живым — пока существует путь по ссылкам от какого-либо корня. Удалён
может быть после потери достижимости, но момент выбирает сборщик, гарантии
немедленности нет.

### 36. Почему присваивание null не удаляет объект немедленно?

**Ответ:** оно лишь убирает одну ссылку. Объект удаляется, только когда становится
недостижимым от корней и когда до него доходит сборщик.

### 37. Почему циклическая ссылка не обязательно является утечкой?

**Ответ:** сборщик определяет достижимость от корней, а не считает ссылки. Два
объекта, ссылающиеся друг на друга, но недостижимые извне, будут собраны.

### 38. Что такое Stop-the-World?

**Ответ:** пауза, на время которой приложение останавливается ради работы
сборщика. Полностью избежать её нельзя, но современные сборщики значительную часть
работы выполняют конкурентно.

### 39. Что такое слабая гипотеза поколений?

**Ответ:** наблюдение, что подавляющее большинство объектов умирает вскоре после
создания. На нём основано деление кучи на поколения.

### 40. Чем Young Generation отличается от Old Generation?

**Ответ:** в молодом объекты создаются и в большинстве своём быстро умирают, его
сборка частая и дешёвая. В старое попадают пережившие несколько сборок, и его
обработка дороже.

### 41. Почему наличие GC не исключает утечки памяти?

**Ответ:** сборщик определяет достижимость, а не полезность. Объект, который
программе больше не нужен, но на который остаётся ссылка из статической коллекции
или кеша, будет жить бесконечно.

### 42. Чем Strong, Soft, Weak и Phantom references отличаются друг от друга?

**Ответ:** сильная ссылка не даёт собрать объект. Мягкая позволяет собрать при
нехватке памяти. Слабая не препятствует сборке при ближайшем цикле. Фантомная не
даёт доступа к объекту и служит только для уведомления о том, что он стал
недостижим.

### 43. Гарантирует ли System.gc() немедленную сборку?

**Ответ:** нет, это лишь запрос. JVM вправе его проигнорировать, а флаг
`-XX:+DisableExplicitGC` отключает такие вызовы полностью.

### 44. Чем области памяти JVM отличаются от Java Memory Model?

**Ответ:** области памяти описывают, где хранятся данные. Модель памяти описывает
правила видимости изменений между потоками и порядок операций. Это разные вопросы,
и их регулярно путают.

### 45. Почему локальность JVM Stack не гарантирует потокобезопасность объекта?

**Ответ:** локальной является ссылка, а не объект. Если один и тот же объект
доступен нескольким потокам, доступ к нему требует синхронизации независимо от
того, где лежат ссылки.
