# JVM и области памяти

## Как выполняется Java-программа

Исходный код Java проходит несколько этапов до выполнения процессором.

```text
исходный код .java
→ компилятор javac
→ байт-код .class
→ JVM
→ машинные инструкции конкретной платформы
```

Компилятор `javac` преобразует исходный код из файла `.java` в байт-код и записывает его в файл `.class`. JVM не создаёт байт-код из исходного файла. Она загружает, проверяет и выполняет уже скомпилированный байт-код.

Байт-код представляет собой инструкции для виртуальной машины и не привязан к машинным командам конкретной операционной системы. Для его выполнения устанавливается реализация JVM, соответствующая платформе.

```text
один файл .class
├── JVM для Windows
├── JVM для Linux
└── JVM для macOS
```

Принцип `Write once, run anywhere` означает, что один и тот же корректный байт-код можно выполнять на разных платформах при наличии совместимой JVM. Это не гарантирует абсолютную переносимость любого приложения. Код может зависеть от нативных библиотек, файловой системы, кодировок, прав доступа и других особенностей окружения.

## JVM, JRE и JDK

### JVM

JVM, или Java Virtual Machine, является виртуальной машиной, которая исполняет байт-код Java.

JVM выполняет несколько задач:

- загружает классы
- проверяет корректность байт-кода
- выполняет байт-код
- управляет памятью
- запускает Garbage Collector
- управляет выполнением потоков
- использует интерпретатор и JIT-компилятор
- взаимодействует с операционной системой

```text
.class
→ JVM
→ машинный код конкретной платформы
```

JVM является частью среды выполнения, а не инструментом компиляции `.java` в `.class`.

### JRE

JRE, или Java Runtime Environment, концептуально является средой, необходимой для запуска Java-приложения.

```text
JRE
├── JVM
└── стандартные библиотеки и runtime-компоненты
```

В современных поставках Java отдельный публичный JRE встречается реже. Разработчики обычно устанавливают JDK или создают собственный runtime-образ с необходимыми модулями.

### JDK

JDK, или Java Development Kit, предоставляет среду выполнения и инструменты разработки.

```text
JDK
├── среда выполнения
├── JVM
├── стандартные библиотеки
└── инструменты разработки
```

Основные инструменты:

```text
javac
→ компиляция исходного кода

java
→ запуск приложения

jar
→ работа с JAR-архивами

javadoc
→ генерация документации

jdb
→ отладка

jcmd, jstack, jmap
→ диагностика JVM
```

Итоговое сравнение:

```text
JVM
→ выполняет байт-код

JRE
→ предоставляет среду для запуска

JDK
→ предоставляет среду и инструменты для разработки
```

## Интерпретатор и JIT-компилятор

JVM может сочетать интерпретацию байт-кода и его компиляцию в машинный код во время работы приложения.

### Интерпретатор

Интерпретатор последовательно читает и выполняет инструкции байт-кода.

```text
прочитать инструкцию
→ выполнить
→ прочитать следующую
→ выполнить
```

Преимущество интерпретации заключается в быстром начале выполнения. Не нужно ждать компиляции всего приложения в машинный код.

Недостаток состоит в том, что часто выполняемые инструкции приходится интерпретировать повторно.

### JIT

JIT означает Just-In-Time compiler. Такой компилятор работает во время выполнения приложения.

JVM собирает статистику выполнения. Методы и циклы, которые выполняются особенно часто, становятся горячим кодом. JIT компилирует горячий байт-код в машинный код конкретного процессора, поэтому последующие вызовы могут выполняться быстрее.

```text
байт-код
→ интерпретация
→ сбор статистики
→ обнаружение горячего кода
→ JIT-компиляция
→ машинный код
```

Прогрев JVM — это период, в течение которого приложение уже выполняется, но JVM ещё собирает профиль и компилирует наиболее важные участки. Поэтому результаты короткого запуска могут отличаться от производительности приложения после прогрева.

JIT не обязан заранее компилировать весь код приложения. Он выбирает участки на основании собранной статистики и может применять к ним оптимизации.

## Загрузка и инициализация классов

Жизненный цикл класса до начала его полноценного использования включает три основные стадии.

```text
Loading
→ Linking
→ Initialization
```

Linking состоит из трёх частей.

```text
Verification
→ Preparation
→ Resolution
```

Полная схема:

```text
Loading
→ Verification
→ Preparation
→ Resolution
→ Initialization
```

### Loading

На этапе Loading JVM находит байт-код класса, загружает его и создаёт внутреннее представление класса. Поиск байт-кода выполняет соответствующий ClassLoader.

### Verification

На этапе Verification JVM проверяет:

- формат файла `.class`
- корректность байт-кода
- совместимость типов
- допустимость инструкций
- корректность работы со стеком операндов

Эта проверка не доказывает правильность бизнес-логики. Она защищает среду выполнения от структурно некорректного или недопустимого байт-кода.

### Preparation

На этапе Preparation JVM подготавливает статические поля класса и устанавливает для них значения по умолчанию.

```java
public class Counter {

    static int count = 10;
}
```

На этапе Preparation:

```text
count = 0
```

Выражение `10` ещё не присваивается полю в рамках обычной инициализации класса.

Константы времени компиляции, объявленные как `static final` и представленные атрибутом `ConstantValue`, могут получить своё итоговое значение уже на этапе Preparation. Это исключение из упрощённой схемы, в которой статическое поле сначала получает значение по умолчанию.

```java
static final int LIMIT = 10;
```

### Resolution

На этапе Resolution JVM заменяет символические ссылки из constant pool на фактические ссылки, понятные среде выполнения.

Примеры символических ссылок:

```text
класс User
метод User.getEmail()
поле Incident.status
```

Разрешение некоторых ссылок может выполняться лениво, когда ссылка впервые действительно потребуется.

### Initialization

На этапе Initialization выполняются присваивания статическим полям, статические блоки и другая логика инициализации класса.

Для поля:

```java
static int count = 10;
```

на этом этапе устанавливается значение `10`.

```text
Preparation
→ count = 0

Initialization
→ count = 10
```

## ClassLoader

ClassLoader находит байт-код и загружает определения классов в JVM. Разделение загрузчиков помогает организовать платформенные классы, классы приложения и библиотеки.

```text
Bootstrap ClassLoader
        ↓
Platform ClassLoader
        ↓
Application ClassLoader
```

### Bootstrap ClassLoader

Bootstrap ClassLoader загружает базовые классы платформы Java. К таким классам относятся, например, `java.lang.Object` и `java.lang.String`.

Классы платформенных API, включая типы вроде `java.util.List`, доступны приложению через систему загрузки классов. Однако не следует привязывать каждый пакет целиком к одному загрузчику без учёта версии Java и состава модулей.

### Platform ClassLoader

Platform ClassLoader загружает классы платформенных модулей, которые не относятся к минимальному набору, загружаемому Bootstrap ClassLoader.

### Application ClassLoader

Application ClassLoader обычно загружает классы приложения и библиотек из classpath и module path.

```text
ru.donskikh.incidenthub.incident.Incident
org.springframework.stereotype.Service
```

## Родительское делегирование

При классической parent-first модели загрузчик сначала передаёт запрос родителю.

```text
Application ClassLoader
→ передаёт запрос родителю

Platform ClassLoader
→ передаёт запрос родителю

Bootstrap ClassLoader
→ пытается найти класс

если родитель не нашёл
→ поиск выполняет дочерний ClassLoader
```

Такая модель помогает защищать базовые классы Java от подмены пользовательскими классами. Например, класс приложения с именем, похожим на `java.lang.String`, не должен заменить платформенный класс.

Parent-first является стандартной моделью для встроенной иерархии, но пользовательские ClassLoader могут реализовывать другие стратегии, если это необходимо контейнеру, системе модулей или плагинов.

## Runtime Data Areas JVM

Спецификация JVM описывает области данных, которые используются во время выполнения.

```text
JVM Process
├── Heap
├── Method Area
├── JVM Stack каждого потока
├── PC Register каждого потока
└── Native Method Stack каждого потока
```

### Общие для потоков

```text
Heap
Method Area
```

Эти области связаны со всей JVM и могут содержать данные, доступные из нескольких потоков.

### Отдельные для каждого потока

```text
JVM Stack
PC Register
Native Method Stack
```

Каждый поток получает собственное состояние выполнения. Конкретная реализация JVM может иметь дополнительные внутренние области, структуры и оптимизации, не показанные в этой концептуальной схеме.

## Heap

Heap является общей областью памяти JVM. В базовой модели в нём размещаются объекты и массивы.

```java
new User(...)
new Incident(...)
new int[100]
new ArrayList<>()
new HashMap<>()
```

Heap доступен всем потокам, а память в нём управляется Garbage Collector.

```text
Thread 1 ──┐
           ├──→ Heap
Thread 2 ──┘
```

Несколько потоков могут обращаться к одному объекту. Это создаёт вопросы видимости изменений, синхронизации и гонок данных. Такие гарантии относятся к Java Memory Model и многопоточности, а не к классификации областей памяти JVM.

Фраза «объект всегда физически находится в Heap» является концептуальным упрощением. JIT может применять escape analysis и scalar replacement, а также устранять отдельные выделения памяти, если поведение программы сохраняется.

Для junior-уровня полезна базовая модель:

```text
объекты и массивы
→ Heap
```

## JVM Stack

У каждого потока есть собственный JVM Stack. Он хранит последовательность активных вызовов методов этого потока и состоит из Stack Frame.

При вызове метода создаётся новый frame. После нормального возврата или выхода из-за исключения frame удаляется из стека.

```java
public static void main(String[] args) {
    createIncident();
}

private static void createIncident() {
    validate();
}

private static void validate() {
}
```

Во время выполнения `validate()` стек можно представить так:

```text
верх стека

┌────────────────────────┐
│ frame validate()       │
├────────────────────────┤
│ frame createIncident() │
├────────────────────────┤
│ frame main()           │
└────────────────────────┘

низ стека
```

Собственный стек нужен каждому потоку не только для предотвращения гонок. У каждого потока своя последовательность выполнения, свои вызовы методов, локальные переменные, текущий Stack Frame и место выполнения.

При этом локальная ссылка из стека может указывать на общий объект в Heap. Такой объект всё равно может участвовать в гонке данных.

## Stack Frame

Каждый вызов метода представлен отдельным кадром стека.

```text
Stack Frame
├── массив локальных переменных
├── Operand Stack
└── служебная информация
```

Эта схема отражает модель спецификации. Точный внутренний формат кадра зависит от реализации JVM и применённых оптимизаций.

### Локальные переменные

Массив локальных переменных содержит:

- параметры метода
- локальные примитивные значения
- локальные ссылки
- ссылку `this` у нестатического метода

```java
public void process(long incidentId) {
    int attempts = 3;
    Incident incident = repository.findById(incidentId);
}
```

```text
this
→ ссылка на текущий объект

incidentId
→ значение long

attempts
→ значение int

incident
→ ссылка на объект Incident
```

Локальная переменная объектного типа содержит значение ссылки, а не сам объект целиком.

### Operand Stack

Operand Stack является частью одного Stack Frame. Он используется байт-кодом как рабочая область для промежуточных значений и операций.

Для выражения:

```java
int result = a + b;
```

упрощённая последовательность выглядит так:

```text
загрузить a в Operand Stack
→ загрузить b
→ снять два значения
→ выполнить сложение
→ положить результат обратно
```

Важно различать два уровня:

```text
JVM Stack
→ весь стек потока

Operand Stack
→ часть конкретного Stack Frame
```

### Служебная информация

Stack Frame также содержит служебные данные, необходимые для выполнения метода:

- информацию о возврате из метода
- данные для вызова других методов
- данные обработки исключений
- связь с runtime constant pool

Конкретное физическое представление этих данных не задаётся как единый внутренний формат для всех JVM.

## Что находится в Stack, а что в Heap

Рассмотрим локальный примитив и локальную ссылку.

```java
public void example() {
    int count = 5;
    User user = new User("Dima");
}
```

```text
Stack Frame example()

count = 5
user = ссылка ───────────────┐
                             │
Heap                         │
                             ↓
                         User("Dima")
```

Основная модель:

```text
локальный примитив
→ значение во Stack Frame

локальная переменная объектного типа
→ ссылка во Stack Frame

сам объект
→ обычно в Heap
```

Эта модель помогает рассуждать о выполнении программы, но не описывает все оптимизации JIT.

## Ссылки могут находиться в Heap

Фраза «объекты в Heap, ссылки в Stack» не является полностью правильной. Ссылка может быть полем объекта.

```java
class Incident {

    private User reporter;
}
```

```text
Heap

Incident
└── reporter ─────→ User
```

Ссылка `reporter` находится внутри объекта `Incident`, поэтому концептуально она также хранится в Heap.

Точная формулировка:

```text
локальная ссылка
→ Stack Frame

поле-ссылка
→ внутри объекта в Heap
```

## Несколько ссылок на один объект

Несколько переменных могут содержать значение ссылки на один объект.

```java
User first = new User("Dima");
User second = first;
```

```text
Stack

first  ─────┐
second ─────┴────→ один объект User в Heap
```

Объект один, а ссылок две. Изменение состояния объекта через `second` будет наблюдаться при обращении к тому же состоянию через `first`.

## Передача параметров в Java

Главное правило:

```text
Java всегда передаёт аргументы по значению
```

### Примитивы

При передаче примитива копируется само значение.

```java
int number = 10;
change(number);
```

Изменение параметра внутри `change()` не изменит локальную переменную `number` вызывающего метода.

### Объекты

При передаче аргумента объектного типа копируется значение ссылки.

```java
User user = new User("Dima");
change(user);
```

```text
исходная ссылка ──┐
копия ссылки ─────┴──→ один объект
```

Обе ссылки указывают на один объект. Поэтому метод может изменить его состояние.

```java
private void change(User user) {
    user.setName("Alex");
}
```

Однако переназначение параметра меняет только локальную копию ссылки.

```java
private void replace(User user) {
    user = new User("Other");
}
```

После `replace(user)` исходная переменная вызывающего метода продолжает указывать на прежний объект. Поэтому формулировка «объекты передаются по ссылке» неверна.

## Method Area и Metaspace

Эти понятия связаны, но не являются синонимами.

```text
Method Area
→ понятие спецификации JVM

Metaspace
→ реализация значительной части Method Area в HotSpot
```

### Method Area

Method Area является логической областью, общей для потоков. С ней связаны:

- метаданные классов
- описание методов
- описание полей
- runtime constant pool
- байт-код методов
- данные, связанные с типами

Спецификация не требует, чтобы все эти сущности физически находились в одном непрерывном участке памяти.

### Metaspace

Metaspace используется HotSpot JVM для хранения метаданных загруженных классов. Он использует нативную память процесса и не является обычным Java Heap.

```text
Heap
→ объекты Java

Metaspace
→ метаданные загруженных классов
```

Историческое сравнение:

```text
до Java 8
→ PermGen

начиная с Java 8
→ Metaspace
```

Нельзя говорить, что все static-поля и все static-объекты находятся в Metaspace. Точное размещение статических данных зависит от реализации JVM.

Безопасный ответ для собеседования:

> Metaspace в HotSpot хранит метаданные загруженных классов и использует нативную память.

## String Pool

Строковый пул хранит канонические экземпляры строк. Одинаковые строковые литералы могут ссылаться на один объект.

Начиная с Java 7 строковый пул находится в Heap. Метод `intern()` возвращает каноническую строку из пула.

```java
String first = "java";
String second = "java";

System.out.println(first == second);
```

Для этого примера результат будет `true`, потому что одинаковые строковые литералы интернируются и обе переменные ссылаются на один канонический объект из строкового пула.

Однако строки нужно сравнивать через `equals()`, а не через `==`. Оператор `==` сравнивает значения ссылок и не выражает проверку содержимого строк.

## PC Register

У каждого потока есть собственный Program Counter Register. Для выполняемого Java-метода он указывает на текущую инструкцию JVM и помогает продолжить выполнение после переключения контекста.

```text
Thread 1
→ свой PC Register

Thread 2
→ свой PC Register
```

Это часть индивидуального состояния выполнения потока.

## Native Method Stack

Java-код может вызывать нативный код через JNI, или Java Native Interface. Native Method Stack связан с выполнением нативных методов.

```text
Java-метод
→ JNI
→ нативная функция C или C++
```

Для junior-уровня достаточно понимать назначение этой области. Её точная организация зависит от реализации JVM и платформы.

## StackOverflowError

Стек каждого потока имеет ограниченный размер. Каждый активный вызов метода добавляет Stack Frame, поэтому глубокая или бесконечная рекурсия может исчерпать стек.

```java
public void recurse() {
    recurse();
}
```

```text
recurse()
→ recurse()
→ recurse()
→ ...
→ StackOverflowError
```

Типичные причины:

- бесконечная рекурсия
- слишком глубокая рекурсия
- слишком большие Stack Frame

Ошибка относится к стеку конкретного потока, а не ко всему Heap.

## OutOfMemoryError

`OutOfMemoryError` — один тип ошибки, который может возникать по разным причинам. Сообщение и контекст уточняют, какой ресурс JVM или процесса не удалось выделить.

### Java heap space

```text
OutOfMemoryError: Java heap space
```

```java
List<byte[]> data = new ArrayList<>();

while (true) {
    data.add(new byte[10_000_000]);
}
```

Список удерживает ссылки на созданные массивы. Массивы остаются достижимыми, поэтому GC не может освободить занятую ими память.

### Metaspace

```text
OutOfMemoryError: Metaspace
```

Возможные причины:

- слишком много загруженных классов
- динамическая генерация классов
- утечка ClassLoader

Пока ClassLoader и связанные с ним классы остаются достижимыми, их метаданные могут продолжать занимать Metaspace.

### Unable to create new native thread

```text
OutOfMemoryError: unable to create new native thread
```

Возможные причины:

- слишком много потоков
- нехватка нативной памяти
- ограничения операционной системы

Эта ошибка не обязательно означает заполнение Java Heap.

### Direct buffer memory

```text
OutOfMemoryError: Direct buffer memory
```

Ошибка связана с нативной памятью direct-буферов, а не с памятью, которую занимают обычные объекты в Heap.

## StackOverflowError и OutOfMemoryError

| Ошибка | Причина |
|---|---|
| `StackOverflowError` | Переполнение стека конкретного потока |
| `OutOfMemoryError` | Невозможность выделить Heap, Metaspace, native thread, direct memory или другой ресурс |

```text
StackOverflowError
→ часто глубокая рекурсия

OutOfMemoryError
→ нехватка одного из ресурсов памяти JVM или процесса
```

Обе ошибки наследуются от `Error`, но описывают разные виды исчерпания ресурсов.

## Жизненный цикл объекта

Упрощённый жизненный цикл объекта выглядит так:

```text
создание
→ использование
→ потеря достижимости
→ обнаружение GC
→ возможное освобождение памяти
```

```java
User user = new User("Dima");
user = null;
```

Если других путей к объекту нет, присваивание `null` делает объект недостижимым через переменную `user`.

```text
объект стал недостижимым
≠
объект немедленно удалён
```

GC сам выбирает время обработки. Присваивание `null` не запускает сборку и не гарантирует немедленное освобождение памяти.

## GC Roots и достижимость

Garbage Collector начинает обход графа объектов от специальных корневых ссылок, которые называются GC Roots.

Примеры GC Roots:

- локальные ссылки активных методов
- активные потоки
- некоторые статические ссылки
- ссылки из JNI

```text
GC Root
→ Object A
→ Object B
→ Object C
```

Основное правило:

```text
достижим от GC Roots
→ объект считается живым

не достижим от GC Roots
→ объект может быть удалён
```

Корректная формулировка особенно важна. Достижимый объект считается живым и не удаляется обычной сборкой как мусор.

## Циклические ссылки

Объекты могут ссылаться друг на друга.

```text
Object A ↔ Object B
```

Цикл ссылок сам по себе не является утечкой. Если до этой группы объектов нет пути от GC Roots, вся группа недостижима и может быть удалена.

Java GC использует анализ достижимости, а не простой подсчёт ссылок. Поэтому взаимные ссылки не делают объекты бессмертными.

## Garbage Collection

Общую модель работы GC можно представить так:

```text
найти GC Roots
→ пройти по ссылкам
→ определить достижимые объекты
→ обработать недостижимые объекты
```

В зависимости от алгоритма и фазы сборщик может выполнять разные операции:

- маркировку
- очистку
- перемещение
- уплотнение
- обновление ссылок

Не каждый сборщик использует все операции одинаково. Нельзя описывать один конкретный алгоритм как универсальное устройство любого GC.

## Stop-the-World

Stop-the-World означает, что JVM временно останавливает прикладные Java-потоки. Это требуется для операций, которым нужно согласованное состояние программы.

```text
потоки приложения остановлены
→ JVM выполняет необходимую операцию
→ потоки продолжают работу
```

Продолжительность и назначение пауз зависят от сборщика и выполняемой фазы.

```text
Stop-the-World
≠
весь GC всегда полностью выполняется только при остановленном приложении
```

Современные сборщики могут выполнять часть работы конкурентно с приложением или параллельно несколькими служебными потоками.

## Поколения Heap

Многие подходы к сборке мусора опираются на слабую гипотезу поколений:

> Большинство объектов живёт недолго.

Упрощённая модель:

```text
Young Generation
→ новые и короткоживущие объекты

Old Generation
→ долгоживущие объекты
```

### Young Generation

Классическая схема молодого поколения:

```text
Eden
Survivor 0
Survivor 1
```

Новые объекты обычно создаются в Eden. Объекты, пережившие сборку, могут перемещаться в Survivor. После нескольких сборок или при других условиях долгоживущие объекты могут перейти в Old Generation.

### Old Generation

В старом поколении обычно оказываются долгоживущие объекты. Примеры:

- кеши
- контейнеры приложения
- долго живущие сервисные структуры
- объекты, пережившие несколько сборок

Современные GC могут иметь другую физическую организацию памяти. Деление на Eden, Survivor и Old полезно как классическая модель, но не является универсальной внутренней схемой каждого сборщика.

## Minor, Major и Full GC

Термины часто используются в логах и обсуждениях в следующем смысле:

```text
Minor GC
→ обычно работа с молодым поколением

Major GC
→ обычно работа со старым поколением

Full GC
→ обработка значительной части Heap и других структур
```

Точное значение терминов зависит от конкретного сборщика и диагностического инструмента. Full GC не означает строго одинаковый набор действий и одинаковый тип паузы во всех JVM.

## Утечки памяти в Java

Утечка возникает, когда объект больше не нужен бизнес-логике, но программа продолжает его удерживать.

```text
объект больше не нужен бизнес-логике
→ но остаётся достижимым от GC Roots
→ GC считает его живым
→ память не освобождается
```

```java
private static final List<byte[]> CACHE = new ArrayList<>();

public void process() {
    CACHE.add(new byte[1_000_000]);
}
```

```text
static field
→ List
→ byte[]
```

Статическое поле удерживает список, а список удерживает массивы. Если элементы никогда не удаляются, объём занятой памяти растёт.

Типичные причины утечек:

- бесконечно растущий кеш
- статические коллекции
- незакрытые слушатели
- неправильное использование `ThreadLocal`
- утечки ClassLoader
- коллекции без удаления старых элементов
- удержание больших графов объектов

Наличие GC не исключает утечки. Сборщик определяет достижимость, но не знает, нужен ли объект бизнес-логике.

## Виды ссылок

Пакет `java.lang.ref` предоставляет несколько типов ссылок с разным влиянием на жизненный цикл объекта.

### Strong Reference

```java
User user = new User();
```

Обычная ссылка является сильной. Пока объект сильно достижим от GC Roots, он удерживается от удаления.

### SoftReference

`SoftReference` позволяет объекту сохраняться некоторое время, но GC может очистить такую ссылку при нехватке памяти.

Поведение зависит от JVM и доступной памяти, поэтому `SoftReference` не стоит использовать как основной механизм современного управляемого кеша. Для кеша обычно нужны явные ограничения размера, политика удаления и наблюдаемое поведение.

### WeakReference

`WeakReference` не удерживает объект от сборки при отсутствии сильной достижимости. После очистки метод `get()` может вернуть `null`.

```java
WeakReference<User> reference =
        new WeakReference<>(new User());
```

`WeakHashMap` использует слабые ссылки на ключи. Запись может исчезнуть, когда ключ больше не имеет обычной сильной достижимости.

### PhantomReference

`PhantomReference` используется вместе с `ReferenceQueue`. Она позволяет отслеживать позднюю стадию жизненного цикла объекта и выполнять контролируемую очистку внешних ресурсов.

Это низкоуровневый механизм. Получить сам объект через `get()` такой ссылки нельзя.

Итоговая схема:

```text
Strong
→ удерживает объект

Soft
→ может быть очищена при нехватке памяти

Weak
→ не удерживает объект при отсутствии сильной достижимости

Phantom
→ отслеживание финальной стадии жизненного цикла
```

## System.gc()

```java
System.gc();
```

`System.gc()` выражает запрос или рекомендацию JVM выполнить сборку мусора. Вызов не гарантирует немедленную полную сборку.

Программная логика не должна зависеть от того, что сразу после вызова будет запущен GC или освобождён конкретный объём памяти.

## Частые заблуждения

### JVM создаёт байт-код

Неверно.

```text
javac
→ создаёт байт-код

JVM
→ загружает и выполняет байт-код
```

### Объекты находятся в Heap, ссылки в Stack

Это слишком грубое правило.

```text
локальная ссылка
→ Stack Frame

поле-ссылка
→ внутри объекта в Heap
```

### Объект удаляется сразу после присваивания null

Неверно. Объект только может стать недостижимым. Момент обработки выбирает GC.

### Достижимый объект может быть удалён GC

Неверно.

```text
достижим от GC Roots
→ считается живым
```

### Циклическая ссылка всегда создаёт утечку

Неверно. Недостижимый от GC Roots цикл может быть удалён.

### Garbage Collector исключает утечки памяти

Неверно. Логически ненужный, но достижимый объект остаётся живым для GC.

### System.gc() гарантирует сборку

Неверно. Это только запрос JVM, а не гарантия немедленной полной сборки.

### Все static-поля находятся в Metaspace

Неверно. Metaspace хранит прежде всего метаданные классов. Точное размещение статических данных зависит от реализации JVM.

### Stack всегда быстрее Heap

Это слишком грубое утверждение. Производительность зависит от:

- JIT
- кешей процессора
- escape analysis
- шаблона доступа
- структуры данных
- работы GC

Нельзя выбирать структуру программы только по лозунгу о скорости одной области памяти.

## Краткая схема областей памяти

```text
JVM Process

Heap
→ объекты и массивы
→ общий между потоками
→ управляется GC

JVM Stack каждого потока
→ Stack Frame
→ локальные значения
→ локальные ссылки
→ Operand Stack

Method Area
→ понятие спецификации JVM

Metaspace в HotSpot
→ метаданные загруженных классов
→ нативная память

PC Register каждого потока
→ текущая выполняемая инструкция

Native Method Stack
→ выполнение нативного кода
```

## Heap и Stack

| Характеристика | Heap | JVM Stack |
|---|---|---|
| Принадлежность | Общий для потоков | Отдельный для каждого потока |
| Основное содержимое | Объекты и массивы | Stack Frame вызванных методов |
| Управление памятью | Garbage Collector | Освобождение frame при возврате из метода |
| Типичная ошибка | `OutOfMemoryError` | `StackOverflowError` |
| Многопоточность | Возможен общий доступ | Локален конкретному потоку |

Локальность стека не делает любой связанный объект потокобезопасным. Ссылка из Stack Frame может указывать на объект в Heap, который доступен другим потокам.

## JVM Memory и Java Memory Model

Области памяти JVM и Java Memory Model отвечают на разные вопросы.

### JVM Runtime Data Areas

JVM Runtime Data Areas отвечают на вопрос:

```text
Где JVM концептуально хранит данные во время выполнения?
```

К этой теме относятся:

- Heap
- Stack
- Stack Frame
- Method Area
- Metaspace
- PC Register
- Native Method Stack

### Java Memory Model

Java Memory Model отвечает на вопросы:

```text
Как потоки видят изменения общих данных?
Какие операции атомарны?
В каком порядке могут выполняться операции?
Что гарантирует happens-before?
Как работают volatile и synchronized?
```

```text
области памяти JVM
≠
Java Memory Model
```

Java Memory Model будет оформлена отдельным следующим файлом. В этом конспекте рассматривается организация выполнения и памяти JVM, а не гарантии взаимодействия потоков.

## Краткий ответ для собеседования

JDK содержит среду выполнения и инструменты разработки, а JVM отвечает за загрузку и выполнение байт-кода. Компилятор `javac` преобразует исходный файл `.java` в файл `.class`, после чего JVM выполняет байт-код с помощью интерпретатора и JIT-компилятора. Heap является общей для потоков областью, где в базовой модели находятся объекты и массивы. У каждого потока есть собственный JVM Stack, состоящий из Stack Frame активных вызовов методов. Stack Frame содержит локальные переменные, Operand Stack и служебную информацию. Method Area является понятием спецификации, а Metaspace в HotSpot хранит метаданные загруженных классов в нативной памяти. Garbage Collector определяет живые объекты по достижимости от GC Roots и может освобождать память недостижимых объектов. `StackOverflowError` обычно возникает при исчерпании стека конкретного потока из-за глубокой рекурсии. `OutOfMemoryError` означает, что JVM не смогла выделить Heap, Metaspace, новый native thread, direct memory или другой необходимый ресурс.
