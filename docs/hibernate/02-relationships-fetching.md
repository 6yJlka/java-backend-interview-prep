# Связи, загрузка и каскады

## Виды связей

```text
@ManyToOne  → много заказов на одного покупателя
@OneToMany  → у покупателя много заказов
@OneToOne   → у заказа одна доставка
@ManyToMany → у товара много категорий, у категории много товаров
```

В реляционной модели связь выражается внешним ключом, и он всегда находится на
стороне «многие». Это и определяет понятие владеющей стороны.

---

## Владеющая и обратная сторона

```java
@Entity
public class Order {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;              // владеющая сторона
}

@Entity
public class Customer {

    @OneToMany(mappedBy = "customer")
    private List<Order> orders = new ArrayList<>();   // обратная сторона
}
```

**Владеющая сторона** — та, где физически находится внешний ключ. Только её
изменения приводят к записи в базу.

**Обратная сторона** помечается `mappedBy` и содержит имя поля на владеющей
стороне. Она нужна для навигации по объектной модели, но сама по себе ничего не
сохраняет.

Отсюда типичная ошибка:

```java
customer.getOrders().add(order);   // изменена только обратная сторона
// внешний ключ в таблице orders останется null
```

Правильно установить связь с владеющей стороны или, при двунаправленной связи, с
обеих:

```java
@Entity
public class Customer {

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {
        orders.add(order);
        order.setCustomer(this);      // синхронизация обеих сторон
    }

    public void removeOrder(Order order) {
        orders.remove(order);
        order.setCustomer(null);
    }
}
```

Такие вспомогательные методы — стандартная практика. Без них объектная модель и
база расходятся: в памяти связь есть, в базе нет.

### Однонаправленный @OneToMany

```java
@Entity
public class Customer {

    @OneToMany              // без mappedBy
    @JoinColumn(name = "customer_id")
    private List<Order> orders = new ArrayList<>();
}
```

Работает, но плохо: Hibernate сначала вставляет заказ с `null` во внешнем ключе, а
затем отдельным `UPDATE` его проставляет. Лишние запросы и требование, чтобы
колонка допускала `null`.

Практическое правило: связь «один ко многим» делают двунаправленной либо
ограничиваются `@ManyToOne` со стороны «многих». Отдельная коллекция нужна не так
часто, как кажется.

## Стратегии загрузки

### Значения по умолчанию

```text
@ManyToOne   → EAGER   ← источник проблем
@OneToOne    → EAGER   ← источник проблем
@OneToMany   → LAZY
@ManyToMany  → LAZY
```

Умолчания для связей «к одному» неудачны. Загрузка заказа автоматически подтянет
покупателя, тот — свой город, город — страну. Один `find()` превращается в цепочку
соединений, о которой в коде ничего не написано.

Хуже того, EAGER нельзя отключить в конкретном запросе: если связь объявлена
жадной, она будет загружаться всегда.

Практическое правило: **все связи объявляются LAZY**, а нужные данные подгружаются
явно там, где они действительно нужны.

```java
@ManyToOne(fetch = FetchType.LAZY)
@OneToOne(fetch = FetchType.LAZY)
```

### Как работает LAZY

Вместо связанной сущности Hibernate подставляет прокси — сгенерированный подкласс.
При первом обращении к любому полю, кроме идентификатора, выполняется запрос.

```java
Order order = orderRepository.findById(1L).orElseThrow();
Customer customer = order.getCustomer();      // запроса ещё нет, это прокси
String name = customer.getName();             // здесь SELECT
```

Отсюда требование, чтобы класс сущности не был `final`: иначе подкласс не
создать — та же причина, что и в Spring AOP с CGLIB.

Если контекст закрыт, обращение к прокси даёт `LazyInitializationException`.

### Ленивый @OneToOne

Особый случай. Ленивость связи «к одному» работает не всегда.

```java
@OneToOne(fetch = FetchType.LAZY)
private Delivery delivery;
```

Если связь необязательная, Hibernate обязан узнать, существует ли связанная запись:
поле должно быть либо прокси, либо `null`, и решить это без запроса невозможно.
Поэтому запрос выполняется сразу, несмотря на `LAZY`.

Обходные пути:

```java
@OneToOne(fetch = FetchType.LAZY, optional = false)   // связь обязательна
```

```java
@OneToOne(fetch = FetchType.LAZY)
@MapsId                              // общий первичный ключ
private Delivery delivery;
```

Со стороны, где находится внешний ключ, ленивость работает нормально — проблема
касается обратной стороны.

## Проблема N+1

Самая известная проблема ORM и почти обязательный вопрос.

```java
List<Order> orders = orderRepository.findAll();      // 1 запрос

for (Order order : orders) {
    System.out.println(order.getCustomer().getName()); // N запросов
}
```

Сто заказов дадут сто один запрос. В коде при этом нет ни одного явного обращения к
базе внутри цикла.

Проблема возникает и при EAGER: Hibernate часто загружает основной список одним
запросом, а связи — отдельными.

### Как обнаружить

```yaml
spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true
logging:
  level:
    org.hibernate.SQL: DEBUG
```

Ещё надёжнее — тесты, проверяющие число запросов, например через datasource-proxy.
N+1 не проявляется на трёх записях в тестовой базе и вылезает на проде.

### Решения

**JOIN FETCH** — самый прямой способ:

```java
@Query("select o from Order o join fetch o.customer")
List<Order> findAllWithCustomer();
```

Один запрос с соединением. Работает и для коллекций:

```java
@Query("select distinct o from Order o join fetch o.items where o.id in :ids")
List<Order> findWithItems(@Param("ids") List<Long> ids);
```

**EntityGraph** — декларативная альтернатива:

```java
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(String status);
```

Удобен тем, что не требует писать запрос, и хорошо сочетается с производными
методами Spring Data.

**@BatchSize** — не убирает дополнительные запросы, но резко сокращает их число:

```java
@Entity
@BatchSize(size = 50)
public class Customer { }
```

Вместо ста запросов по одному покупателю будет два запроса с `IN` по пятьдесят.
Полезно, когда `join fetch` неудобен.

### JOIN FETCH и пагинация

Ловушка, о которой стоит знать.

```java
@Query("select o from Order o join fetch o.items")
Page<Order> findAll(Pageable pageable);
```

В логе появится предупреждение `HHH000104`: применяется пагинация в памяти.
Причина в том, что соединение с коллекцией размножает строки — один заказ с тремя
позициями даёт три строки результата. Ограничить их через `LIMIT` нельзя, не
исказив выборку заказов, поэтому Hibernate загружает **всё** и режет уже в памяти.

На больших таблицах это приводит к нехватке памяти.

Решение — два запроса:

```java
// 1. получаем идентификаторы с пагинацией
Page<Long> ids = orderRepository.findIdsByStatus(status, pageable);

// 2. загружаем сущности с коллекциями по этим идентификаторам
List<Order> orders = orderRepository.findWithItemsByIdIn(ids.getContent());
```

Соединение с коллекцией выполняется по ограниченному набору, `LIMIT` больше не
нужен.

### MultipleBagFetchException

```java
@Query("select o from Order o join fetch o.items join fetch o.payments")
```

Два `join fetch` по коллекциям типа `List` без порядка дают исключение. Причина —
декартово произведение: Hibernate не может корректно разложить результат обратно в
две коллекции.

Решения: сделать коллекции `Set` вместо `List`, либо выполнить два запроса в одной
транзакции, либо для второй коллекции использовать `@BatchSize`.

## @ManyToMany

```java
@Entity
public class Product {

    @ManyToMany
    @JoinTable(
        name = "product_category",
        joinColumns = @JoinColumn(name = "product_id"),
        inverseJoinColumns = @JoinColumn(name = "category_id")
    )
    private Set<Category> categories = new HashSet<>();
}
```

Работает, но у аннотации есть проблемы.

**Нет места для дополнительных полей.** Промежуточная таблица скрыта, и добавить в
неё дату создания или флаг невозможно. А такая потребность возникает почти всегда.

**Удаление и повторная вставка.** При изменении коллекции Hibernate нередко удаляет
все связи и вставляет заново, вместо точечного изменения. На больших коллекциях это
заметно.

Практическая рекомендация — заменить связь на две `@ManyToOne` через явную
сущность:

```java
@Entity
public class ProductCategory {

    @EmbeddedId
    private ProductCategoryId id;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("productId")
    private Product product;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("categoryId")
    private Category category;

    private Instant addedAt;        // теперь есть куда положить
}
```

Кода больше, зато поведение предсказуемо и связь расширяема.

## Коллекции: List или Set

```java
private List<Order> orders;   // bag, без гарантии порядка
private Set<Order> orders;    // требует корректных equals и hashCode
```

`List` без `@OrderColumn` трактуется как bag — неупорядоченная коллекция с
возможными дубликатами. Два `join fetch` по таким коллекциям дают
`MultipleBagFetchException`.

`Set` этой проблемы лишён, но требует корректных `equals` и `hashCode` у сущности —
тема со своими тонкостями, разбирается отдельно.

Для явного порядка:

```java
@OneToMany(mappedBy = "order")
@OrderBy("createdAt DESC")
private List<Item> items;
```

`@OrderBy` добавляет сортировку в запрос, в отличие от `@OrderColumn`, который
хранит позицию в отдельной колонке и обходится дороже.

## Каскады

Каскад определяет, какие операции распространяются с родительской сущности на
связанные.

```java
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Item> items = new ArrayList<>();
```

```text
PERSIST → сохранение родителя сохраняет детей
MERGE   → слияние распространяется на детей
REMOVE  → удаление родителя удаляет детей
REFRESH → обновление из базы
DETACH  → отсоединение
ALL     → все перечисленные
```

### orphanRemoval и CascadeType.REMOVE

Различие тонкое и его спрашивают.

```text
CascadeType.REMOVE
→ срабатывает при удалении родителя
→ дети удаляются вместе с ним

orphanRemoval = true
→ срабатывает при удалении ребёнка из коллекции
→ ребёнок, потерявший родителя, удаляется из базы
```

```java
order.getItems().remove(item);

// с orphanRemoval        → DELETE для item
// только с REMOVE        → item останется в базе с null во внешнем ключе
```

`orphanRemoval` подразумевает и поведение `REMOVE`, поэтому указывать оба обычно
избыточно.

### Где каскады неуместны

```java
@ManyToOne(cascade = CascadeType.ALL)     // так делать не нужно
private Customer customer;
```

Удаление заказа удалит покупателя вместе со всеми его остальными заказами.

Правило простое: каскад направляют от родителя к детям, где дети не существуют
самостоятельно — позиции заказа, адреса пользователя. Со стороны `@ManyToOne`
каскадов быть не должно, особенно `REMOVE`.

## Типичные ошибки

### Изменять только обратную сторону связи

Внешний ключ не обновится. Нужны методы синхронизации обеих сторон.

### Оставлять EAGER по умолчанию для @ManyToOne

Загружается граф связей, о котором в коде ничего не сказано, и отключить это в
конкретном запросе невозможно.

### Не замечать N+1

На тестовых данных из трёх строк проблема не видна. Нужны логирование SQL и
проверка числа запросов.

### Сочетать join fetch по коллекции с пагинацией

Hibernate загрузит всё и выполнит пагинацию в памяти. Решение — сначала выбрать
идентификаторы, затем загрузить по ним.

### Делать два join fetch по коллекциям List

`MultipleBagFetchException`. Помогают `Set`, два запроса или `@BatchSize`.

### Использовать @ManyToMany

Нет места для полей связи, возможны удаление и повторная вставка всей коллекции.
Лучше явная промежуточная сущность.

### Ставить каскад на @ManyToOne

Удаление дочерней сущности может удалить родителя со всеми его связями.

### Путать orphanRemoval и CascadeType.REMOVE

Первое срабатывает при удалении из коллекции, второе — при удалении родителя.

### Ожидать ленивости от необязательного @OneToOne

Hibernate обязан узнать, есть ли связанная запись, и выполняет запрос сразу.

### Возвращать сущности со связями из контроллера

Сериализация обойдёт ленивые связи и вызовет либо N+1, либо исключение.

## Краткая памятка

```text
внешний ключ всегда на стороне «многие»
владеющая сторона  → где внешний ключ, только её изменения пишутся
обратная сторона   → mappedBy, для навигации

двунаправленная связь → методы синхронизации обеих сторон
```

```text
умолчания
@ManyToOne  EAGER  ← менять на LAZY
@OneToOne   EAGER  ← менять на LAZY
@OneToMany  LAZY
@ManyToMany LAZY

правило: всё LAZY, нужное подгружать явно
```

```text
N+1
причина  → обращение к связи в цикле
решения  → join fetch, EntityGraph, @BatchSize
```

```text
join fetch по коллекции + пагинация
→ HHH000104, пагинация в памяти
→ сначала id с LIMIT, затем загрузка по id

два join fetch по List
→ MultipleBagFetchException
→ Set, два запроса или @BatchSize
```

```text
@OneToOne LAZY не работает при optional = true
→ optional = false или @MapsId
```

```text
CascadeType.REMOVE → при удалении родителя
orphanRemoval      → при удалении из коллекции

каскады только от родителя к детям
на @ManyToOne каскадов не ставят
```

## Краткий ответ для собеседования

Внешний ключ в реляционной модели всегда находится на стороне «многие», и эта
сторона является владеющей: только её изменения приводят к записи в базу. Обратная
сторона помечается `mappedBy` и служит для навигации. При двунаправленной связи
нужны методы, синхронизирующие обе стороны, иначе объектная модель и база
расходятся.

Умолчания по загрузке неудачны: связи «к одному» жадные по умолчанию, из-за чего
один запрос тянет за собой цепочку соединений, и отключить это в конкретном месте
невозможно. Практическое правило — объявлять все связи ленивыми и подгружать
нужное явно.

Ленивая загрузка реализована через прокси-подкласс, поэтому класс сущности не может
быть `final`. Обращение к прокси после закрытия контекста даёт
`LazyInitializationException`.

Проблема N+1 возникает, когда основной запрос загружает список, а обращение к связи
в цикле порождает по запросу на элемент. Решается через `join fetch`, `EntityGraph`
или `@BatchSize`, который объединяет запросы пачками.

С `join fetch` по коллекции нельзя использовать пагинацию: соединение размножает
строки, и Hibernate загружает всё, отсекая лишнее в памяти. Правильный подход —
сначала выбрать идентификаторы с ограничением, затем загрузить сущности по ним.

Каскады направляют от родителя к детям. `CascadeType.REMOVE` срабатывает при
удалении родителя, `orphanRemoval` — при удалении ребёнка из коллекции.

## Вопросы на собеседовании

### 1. Что такое владеющая сторона связи?

**Ответ:** сторона, где физически находится внешний ключ, всегда сторона «многие».
Только её изменения приводят к записи в базу.

### 2. Для чего нужен mappedBy?

**Ответ:** помечает обратную сторону и указывает имя поля на владеющей стороне.
Сообщает, что связь уже отображена и дублировать её не нужно.

### 3. Что произойдёт, если добавить элемент только в коллекцию обратной стороны?

**Ответ:** внешний ключ не будет установлен. Нужно менять владеющую сторону или
синхронизировать обе.

### 4. Какие значения fetch по умолчанию?

**Ответ:** `@ManyToOne` и `@OneToOne` — `EAGER`, `@OneToMany` и `@ManyToMany` —
`LAZY`.

### 5. Почему EAGER считается плохой практикой?

**Ответ:** загружается граф связей, не отражённый в коде, и отключить жадность в
конкретном запросе невозможно.

### 6. Как реализована ленивая загрузка?

**Ответ:** через прокси — сгенерированный подкласс сущности. Запрос выполняется при
первом обращении к полю, кроме идентификатора.

### 7. Почему LAZY не работает для необязательного @OneToOne?

**Ответ:** Hibernate обязан определить, существует ли связанная запись, чтобы
подставить прокси или `null`. Без запроса это невозможно, поэтому он выполняется
сразу.

### 8. Что такое проблема N+1?

**Ответ:** один запрос загружает список, и обращение к связи для каждого элемента
порождает дополнительный запрос — итого N+1 обращений к базе.

### 9. Как решить N+1?

**Ответ:** `join fetch` в запросе, `@EntityGraph` или `@BatchSize`, который
объединяет загрузку связей пачками через `IN`.

### 10. Чем EntityGraph удобнее join fetch?

**Ответ:** не требует писать запрос вручную и сочетается с производными методами
Spring Data.

### 11. Что делает @BatchSize?

**Ответ:** не убирает дополнительные запросы, но выполняет их пачками. Сто
отдельных запросов превращаются в два по пятьдесят.

### 12. Почему join fetch по коллекции нельзя сочетать с пагинацией?

**Ответ:** соединение размножает строки, и `LIMIT` исказил бы выборку. Hibernate
загружает весь результат и применяет пагинацию в памяти, о чём предупреждает в
логе.

### 13. Как правильно сделать пагинацию с коллекциями?

**Ответ:** двумя запросами — сначала получить идентификаторы с ограничением, затем
загрузить сущности с коллекциями по этим идентификаторам.

### 14. Почему возникает MultipleBagFetchException?

**Ответ:** два `join fetch` по коллекциям типа `List` дают декартово произведение,
которое невозможно корректно разложить обратно. Помогают `Set`, отдельные запросы
или `@BatchSize`.

### 15. Чем плох @ManyToMany?

**Ответ:** в промежуточную таблицу нельзя добавить поля, а изменение коллекции
может приводить к удалению и повторной вставке всех связей.

### 16. Чем заменить @ManyToMany?

**Ответ:** явной сущностью связи с двумя `@ManyToOne`. Появляется место для
дополнительных полей и предсказуемое поведение при изменениях.

### 17. Какие бывают типы каскадов?

**Ответ:** `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH` и объединяющий их
`ALL`.

### 18. Чем orphanRemoval отличается от CascadeType.REMOVE?

**Ответ:** `REMOVE` удаляет детей при удалении родителя, `orphanRemoval` удаляет
ребёнка при исключении его из коллекции.

### 19. Почему нельзя ставить каскад на @ManyToOne?

**Ответ:** удаление дочерней сущности приведёт к удалению родителя вместе со всеми
связанными с ним объектами.

### 20. List или Set для коллекции сущностей?

**Ответ:** `List` без указания порядка трактуется как bag и вызывает
`MultipleBagFetchException` при двух `join fetch`. `Set` этой проблемы лишён, но
требует корректных `equals` и `hashCode`.
