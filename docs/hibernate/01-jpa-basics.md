# JPA: основы и Persistence Context

## ORM и зачем он нужен

Объектная модель и реляционная устроены по-разному, и это расхождение называют
impedance mismatch.

```text
объекты                     таблицы
├── наследование            нет прямого аналога
├── ссылки и графы          внешние ключи
├── идентичность по ссылке  идентичность по первичному ключу
├── коллекции внутри        отдельная таблица
└── типы Java               типы SQL
```

ORM берёт на себя перевод между ними: превращает строки в объекты, отслеживает
изменения и генерирует SQL.

Плата — потеря прозрачности. Один вызов геттера может обернуться запросом к базе, а
одно сохранение — десятком. Отсюда большинство проблем с Hibernate: они возникают
не там, где написан код, а там, где ORM решил что-то сделать сам.

### JPA, Hibernate и Spring Data

```text
JPA         → спецификация, набор интерфейсов и аннотаций
Hibernate   → реализация, самая распространённая
Spring Data JPA → надстройка: репозитории, производные методы, пагинация
```

`EntityManager` — интерфейс JPA, `Session` — его расширение в Hibernate.
`JpaRepository` из Spring Data внутри работает через `EntityManager`.

## Сущность

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    @SequenceGenerator(name = "order_seq", sequenceName = "order_seq", allocationSize = 50)
    private Long id;

    @Column(nullable = false)
    private String status;

    @Column(name = "created_at")
    private Instant createdAt;

    protected Order() {
    }

    public Order(String status) {
        this.status = status;
    }
}
```

### Требования к классу сущности

```text
аннотация @Entity
поле или свойство с @Id
конструктор без аргументов, не приватный
класс не final
методы доступа не final
```

Требования продиктованы механизмом работы: Hibernate создаёт объект через
конструктор без аргументов и генерирует прокси-подкласс для ленивой загрузки.
`final` ломает наследование, как и в случае с CGLIB в Spring AOP.

Отсюда же следует, что `record` сущностью быть не может: он `final` и не имеет
конструктора без аргументов. Как проекция результата запроса — подходит отлично.

### Генерация идентификаторов

```text
IDENTITY  → автоинкремент на стороне базы
SEQUENCE  → отдельная последовательность
TABLE     → служебная таблица со счётчиком, устаревший вариант
AUTO      → выбирает провайдер
```

Разница между первыми двумя существенна на практике.

`IDENTITY` требует выполнить `INSERT`, чтобы узнать идентификатор. Поэтому Hibernate
не может отложить вставку до сброса контекста и вынужден выполнять её сразу при
`persist()`. Пакетная вставка при этом становится невозможной.

`SEQUENCE` позволяет получить значение заранее, отдельным запросом к
последовательности. Вставку можно отложить и объединить с другими. Параметр
`allocationSize` задаёт, сколько значений резервируется за одно обращение: при
значении 50 обращение к последовательности происходит раз на 50 сущностей.

Для PostgreSQL рекомендуется `SEQUENCE`. `allocationSize` при этом обязан
совпадать с `INCREMENT BY` последовательности в базе, иначе возможны конфликты
ключей.

## Persistence Context

Центральное понятие всей темы.

Контекст персистентности — область, в которой живут управляемые сущности. Обычно её
называют кешем первого уровня, но это описание неполное: контекст не только кеширует,
но и отслеживает изменения, обеспечивает единственность экземпляра и накапливает
операции.

### Единственность экземпляра

```java
Order a = entityManager.find(Order.class, 1L);
Order b = entityManager.find(Order.class, 1L);

a == b;   // true
```

Второй вызов не идёт в базу — сущность уже в контексте. Более того, гарантируется
именно тот же объект, а не равный ему. В пределах одного контекста одна строка
базы всегда представлена одним экземпляром.

### Границы

В Spring контекст по умолчанию привязан к транзакции:

```text
@Transactional начался → создан контекст
метод завершился       → flush, commit, контекст закрыт
```

Отсюда следует, что сущности, полученные внутри транзакционного метода, после
выхода из него становятся отсоединёнными, и ленивые связи у них больше не
загружаются.

## Состояния сущности

```text
              new Order()
                   ↓
              TRANSIENT
                   ↓ persist()
               MANAGED  ←──────── merge() ──── DETACHED
                   ↓ remove()          ↑            
                REMOVED           контекст закрыт / detach()
                   ↓ commit
              удалена из БД
```

### Transient

Объект создан оператором `new`, контекст о нём не знает, в базе записи нет.

### Managed

Сущность находится в контексте. Все изменения её полей будут записаны в базу
автоматически при сбросе — отдельный вызов сохранения не нужен.

```java
@Transactional
public void updateStatus(Long id, String status) {
    Order order = orderRepository.findById(id).orElseThrow();
    order.setStatus(status);
    // save() не требуется
}
```

Это первое, что удивляет при знакомстве с JPA, и частый вопрос на собеседовании.

### Detached

Сущность была управляемой, но контекст закрылся или её отсоединили явно. Объект
существует, но изменения в базу не попадут. Ленивые связи выбросят
`LazyInitializationException`.

### Removed

Помечена к удалению. Строка исчезнет при сбросе контекста.

## persist и merge

```java
entityManager.persist(order);   // transient → managed
Order managed = entityManager.merge(order);   // detached → managed
```

Разница глубже, чем кажется, и её любят проверять.

**`persist()`** привязывает переданный объект к контексту. После вызова тот же самый
экземпляр становится управляемым. На отсоединённой сущности бросает исключение.

**`merge()`** переданный объект **не привязывает**. Он копирует состояние в
управляемый экземпляр — найденный в контексте или загруженный из базы — и
возвращает его.

```java
Order detached = ...;              // с id = 1

Order merged = entityManager.merge(detached);

merged == detached;   // false
```

Отсюда правило: результат `merge()` нужно использовать дальше, а переданный объект
остаётся отсоединённым, и изменения в нём после вызова ни на что не влияют.

```java
// неверно
entityManager.merge(order);
order.setStatus("DONE");    // не сохранится

// верно
Order managed = entityManager.merge(order);
managed.setStatus("DONE");
```

### save в Spring Data

```java
orderRepository.save(order);
```

Метод не соответствует напрямую ни `persist`, ни `merge`. Внутри он проверяет,
новая ли сущность — обычно по `null` в идентификаторе, — и вызывает `persist()` для
новой либо `merge()` для остальных.

Практическое следствие: `save()` на сущности с заполненным `id` выполнит `merge`, а
значит, сначала загрузит её из базы дополнительным `SELECT`. Для управляемой
сущности вызов `save()` вообще не нужен — изменения запишет dirty checking.

## Dirty checking

Механизм автоматического обнаружения изменений.

```text
1. сущность загружается в контекст
2. Hibernate сохраняет снимок её полей
3. при сбросе текущее состояние сравнивается со снимком
4. для изменённых полей генерируется UPDATE
```

Отсюда две практические вещи.

**Расход памяти.** На каждую управляемую сущность хранится копия её состояния.
Загрузка десятков тысяч сущностей в одну транзакцию удваивает потребление памяти и
делает сброс дорогим — сравнивать нужно все.

Для операций только на чтение это лишняя работа, и её отключают:

```java
@Transactional(readOnly = true)
```

В этом режиме Hibernate не делает снимков.

**Изменение через сеттер достаточно.** Никакого вызова сохранения не требуется, и
попытка «отменить» изменение, не вызвав `save()`, не сработает — оно уже
зафиксировано в объекте, который находится в контексте.

## Flush

Сброс — момент, когда накопленные изменения превращаются в SQL и отправляются в
базу. Это не то же самое, что фиксация транзакции: SQL выполнен, но транзакция ещё
может быть откачена.

### Когда происходит

```text
перед commit
перед выполнением запроса, на результат которого могут повлиять изменения
при явном вызове flush()
```

Второй пункт неочевиден и важен:

```java
@Transactional
public void example() {
    Order order = new Order("NEW");
    orderRepository.save(order);          // INSERT может быть отложен

    List<Order> all = orderRepository.findAll();   // здесь произойдёт flush
}
```

Hibernate обязан выполнить вставку до запроса, иначе результат окажется
несогласованным.

### Порядок операций

При сбросе SQL выполняется не в порядке вызовов, а в фиксированном порядке по типам:

```text
1. INSERT
2. UPDATE
3. удаление элементов коллекций
4. вставка элементов коллекций
5. DELETE
```

Это регулярный источник недоумения. Классический случай — удаление строки и вставка
новой с тем же уникальным ключом в одной транзакции: `INSERT` выполнится раньше
`DELETE` и нарушит ограничение уникальности. Лечится явным `flush()` между
операциями.

## find и getReference

```java
Order order = entityManager.find(Order.class, 1L);        // SELECT сразу
Order proxy = entityManager.getReference(Order.class, 1L); // прокси без запроса
```

`getReference()` возвращает прокси и не обращается к базе. Запрос выполнится при
первом обращении к любому полю, кроме идентификатора.

Полезно, когда нужна только ссылка для установки связи:

```java
order.setCustomer(entityManager.getReference(Customer.class, customerId));
```

Загружать покупателя целиком ради записи внешнего ключа не требуется.

Обратная сторона: если сущности нет в базе, `find()` вернёт `null`, а
`getReference()` бросит `EntityNotFoundException` — но позже, при обращении к полю,
возможно уже за пределами исходного метода. В Spring Data аналог — `getReferenceById()`.

## Open Session In View

Особенность Spring Boot, о которой стоит знать.

По умолчанию включён режим OSIV: контекст персистентности остаётся открытым до
конца обработки HTTP-запроса, а не до конца транзакции.

```text
OSIV включён
→ ленивые связи загружаются даже в контроллере и при сериализации
→ LazyInitializationException не возникает

но
→ соединение с базой удерживается всё время обработки запроса
→ запросы выполняются вне транзакции, поштучно
→ N+1 при сериализации остаётся незамеченным
```

Режим удобен тем, что скрывает ошибки, и вреден по той же причине. Отключается
свойством:

```yaml
spring:
  jpa:
    open-in-view: false
```

После отключения все нужные данные приходится загружать явно внутри транзакции —
через `join fetch` или проекции. Это больше работы, но поведение становится
предсказуемым.

При старте Spring Boot пишет предупреждение об активном OSIV — на него обычно не
обращают внимания.

## Типичные ошибки

### Вызывать save для управляемой сущности

Изменения запишет dirty checking. Лишний вызов `save()` приводит к `merge` и
дополнительному `SELECT`.

### Использовать переданный объект после merge

`merge()` возвращает другой экземпляр. Изменения в исходном объекте не сохранятся.

### Вызывать persist на отсоединённой сущности

Приведёт к исключению. Для неё предназначен `merge()`.

### Использовать IDENTITY при массовых вставках

Идентификатор известен только после `INSERT`, поэтому пакетная вставка невозможна.

### Задать allocationSize, не совпадающий с шагом последовательности

Приведёт к конфликтам первичных ключей.

### Загружать тысячи сущностей в одну транзакцию

Снимки для dirty checking удваивают память, а сброс становится дорогим.

### Не использовать readOnly для чтения

Лишние снимки и проверки при сбросе.

### Ожидать, что SQL выполнится в порядке вызовов

При сбросе порядок фиксирован по типам операций. Между удалением и вставкой с тем
же ключом нужен явный `flush()`.

### Обращаться к ленивым связям вне транзакции

Отсоединённая сущность выбросит `LazyInitializationException`, если OSIV отключён.

### Полагаться на OSIV

Скрывает проблемы загрузки, удерживает соединение и маскирует N+1.

### Делать сущность record или final-классом

Hibernate требует конструктор без аргументов и возможность создать прокси-подкласс.

## Краткий ответ для собеседования

JPA — спецификация, Hibernate — её реализация, Spring Data JPA — надстройка с
репозиториями. Центральное понятие — контекст персистентности: область, где живут
управляемые сущности. Он служит кешем первого уровня, гарантирует, что одной строке
базы соответствует один объект, отслеживает изменения и накапливает операции. В
Spring его границы совпадают с границами транзакции.

Сущность проходит четыре состояния. Transient — обычный объект, о котором контекст
не знает. Managed — сущность в контексте, её изменения записываются автоматически.
Detached — контекст закрыт, изменения не сохранятся, ленивые связи недоступны.
Removed — помечена к удалению.

`persist()` привязывает переданный объект к контексту и работает только с новыми
сущностями. `merge()` переданный объект не привязывает: он копирует состояние в
управляемый экземпляр и возвращает его — это другой объект, и работать дальше нужно
именно с возвращённым.

Изменения обнаруживаются через dirty checking: при загрузке Hibernate сохраняет
снимок полей и сравнивает с ним при сбросе. Поэтому для управляемой сущности вызов
сохранения не нужен. Снимки стоят памяти, и для операций чтения их отключают через
`readOnly`.

Сброс происходит перед фиксацией, перед запросом, на результат которого могут
повлиять изменения, и при явном вызове. Порядок операций при этом фиксирован по
типам, а не по порядку вызовов.

Для генерации идентификаторов в PostgreSQL предпочтителен `SEQUENCE`: значение
можно получить заранее, поэтому вставки откладываются и объединяются в пакеты. С
`IDENTITY` это невозможно.

## Вопросы на собеседовании

### 1. Чем JPA отличается от Hibernate?

**Ответ:** JPA — спецификация с набором интерфейсов и аннотаций, Hibernate — её
реализация. Spring Data JPA — надстройка, работающая через `EntityManager`.

### 2. Что такое persistence context?

**Ответ:** область, где живут управляемые сущности. Служит кешем первого уровня,
гарантирует единственность экземпляра для строки, отслеживает изменения и
накапливает операции до сброса.

### 3. Что вернут два подряд вызова find с одним идентификатором?

**Ответ:** один и тот же объект. Второй вызов не пойдёт в базу, а гарантия
касается именно идентичности ссылок.

### 4. Какие требования предъявляются к классу сущности?

**Ответ:** аннотация `@Entity`, поле с `@Id`, конструктор без аргументов и
отсутствие `final` у класса и методов доступа — Hibernate создаёт прокси-подкласс.

### 5. Может ли record быть сущностью?

**Ответ:** нет. Он `final` и не имеет конструктора без аргументов. В качестве
проекции результата запроса подходит.

### 6. Какие состояния проходит сущность?

**Ответ:** transient, managed, detached и removed.

### 7. Нужно ли вызывать save после изменения загруженной сущности?

**Ответ:** нет. Сущность управляемая, и dirty checking запишет изменения при
сбросе.

### 8. Чем persist отличается от merge?

**Ответ:** `persist` привязывает переданный объект к контексту и применим к новым
сущностям. `merge` копирует состояние в управляемый экземпляр и возвращает его —
переданный объект остаётся отсоединённым.

### 9. Что произойдёт, если изменить объект после merge?

**Ответ:** ничего не сохранится. Работать нужно с экземпляром, который вернул
`merge`.

### 10. Что делает save в Spring Data?

**Ответ:** проверяет, новая ли сущность, и вызывает `persist` либо `merge`. Во
втором случае выполняется дополнительный `SELECT`.

### 11. Как работает dirty checking?

**Ответ:** при загрузке сохраняется снимок полей, при сбросе текущее состояние
сравнивается с ним, и для изменённых полей генерируется `UPDATE`.

### 12. Зачем нужен readOnly в @Transactional?

**Ответ:** Hibernate не создаёт снимки для dirty checking, что экономит память и
время сброса при операциях чтения.

### 13. Когда происходит flush?

**Ответ:** перед фиксацией транзакции, перед запросом, на результат которого могут
повлиять накопленные изменения, и при явном вызове.

### 14. В каком порядке выполняются операции при flush?

**Ответ:** сначала все `INSERT`, затем `UPDATE`, удаление элементов коллекций,
вставка элементов коллекций и в конце `DELETE`. Порядок вызовов в коде значения не
имеет.

### 15. Чем IDENTITY отличается от SEQUENCE?

**Ответ:** `IDENTITY` узнаёт идентификатор только после вставки, поэтому Hibernate
выполняет `INSERT` немедленно и не может объединять вставки в пакеты. `SEQUENCE`
позволяет получить значение заранее.

### 16. Что делает allocationSize?

**Ответ:** задаёт, сколько значений резервируется за одно обращение к
последовательности. Должен совпадать с шагом последовательности в базе.

### 17. Чем find отличается от getReference?

**Ответ:** `find` сразу выполняет запрос и возвращает `null`, если записи нет.
`getReference` возвращает прокси без запроса и бросает `EntityNotFoundException`
при первом обращении к полю.

### 18. Когда полезен getReference?

**Ответ:** когда нужна только ссылка для установки связи — загружать связанную
сущность целиком ради внешнего ключа не требуется.

### 19. Что такое Open Session In View?

**Ответ:** режим, при котором контекст остаётся открытым до конца обработки
HTTP-запроса. В Spring Boot включён по умолчанию.

### 20. Чем плох OSIV?

**Ответ:** удерживает соединение с базой на всё время обработки запроса, выполняет
ленивые загрузки вне транзакции и маскирует проблему N+1, из-за чего ошибки
проектирования остаются незамеченными.
