# Практические проблемы Hibernate

## equals и hashCode для сущностей

Самая тонкая тема во всей JPA. Сложность в том, что ни один очевидный вариант не
работает.

### Почему реализация по умолчанию не подходит

`Object.equals()` сравнивает ссылки. В пределах одного контекста персистентности
этого достаточно — гарантируется, что одной строке соответствует один экземпляр.

Но за границами контекста гарантия исчезает:

```java
Order a = repository.findById(1L).get();   // транзакция 1
Order b = repository.findById(1L).get();   // транзакция 2

a.equals(b);   // false, хотя это одна и та же строка
```

Та же проблема возникает с отсоединёнными сущностями, с объектами после
сериализации и при сравнении загруженной сущности с только что созданной.

### Почему нельзя использовать id

Кажется очевидным: сравнивать по первичному ключу. Но у него есть период, когда он
`null`.

```java
Order order = new Order();
Set<Order> set = new HashSet<>();

set.add(order);              // hashCode посчитан от id = null
repository.save(order);      // id присвоен базой

set.contains(order);         // false — hashCode изменился
```

Объект «теряется» в собственной коллекции. Контракт `hashCode` требует, чтобы
значение не менялось, пока объект находится в хеш-структуре, а генерируемый
идентификатор это требование нарушает по определению.

Проблема не теоретическая: коллекции сущностей в двунаправленных связях — это как
раз `HashSet`.

### Рабочие подходы

**Бизнес-ключ.** Естественный идентификатор, который известен при создании и не
меняется: номер заказа, email, артикул.

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Order other)) return false;
    return orderNumber != null && orderNumber.equals(other.orderNumber);
}

@Override
public int hashCode() {
    return Objects.hash(orderNumber);
}
```

Подходит, когда такой ключ действительно есть. Часто его нет.

**Идентификатор, присвоенный приложением.** Современный и наиболее удобный
вариант: UUID генерируется в конструкторе, а не базой.

```java
@Entity
public class Order {

    @Id
    private UUID id = UUID.randomUUID();
}
```

Идентификатор известен с момента создания и никогда не меняется, поэтому обе
проблемы исчезают.

**Идентификатор с постоянным hashCode.** Компромисс, описанный в документации
Hibernate:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Order other)) return false;
    return id != null && id.equals(other.getId());
}

@Override
public int hashCode() {
    return getClass().hashCode();   // константа для всех экземпляров
}
```

Выглядит странно, но корректно: `hashCode` не меняется никогда, а `equals`
различает объекты. Плата — все сущности одного класса попадают в один бакет, и
`HashSet` вырождается в список. Для коллекций разумного размера это приемлемо.

### Ловушка с getClass

```java
if (getClass() != o.getClass()) return false;   // сломается на прокси
```

Ленивая связь подставляет прокси — сгенерированный подкласс. Сравнение классов
вернёт `false` при сравнении сущности с прокси той же строки.

Поэтому используют `instanceof` либо `Hibernate.getClass(o)`, который разворачивает
прокси.

### Итог

```text
Object по умолчанию → ломается вне контекста
только id           → hashCode меняется после сохранения
бизнес-ключ         → работает, если он есть
UUID в конструкторе → работает всегда, предпочтительно
id + константный hashCode → работает, ценой производительности HashSet

getClass() → заменить на instanceof или Hibernate.getClass()
```

## LazyInitializationException

```text
org.hibernate.LazyInitializationException:
could not initialize proxy - no Session
```

Возникает при обращении к ленивой связи после закрытия контекста.

### Типичные места

```java
@Transactional
public Order getOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}

// контроллер, транзакция уже закрыта
order.getItems().size();   // исключение
```

Особенно неприятен случай сериализации: Jackson обходит геттеры уже после выхода из
транзакции, и исключение возникает посреди записи ответа, когда часть JSON
отправлена клиенту.

### Неправильные решения

```text
FetchType.EAGER
→ загружает связи всегда, включая случаи, когда они не нужны

open-in-view: true
→ прячет проблему, удерживает соединение, маскирует N+1

Hibernate.initialize() россыпью
→ лечит симптом, оставляет N+1
```

### Правильное решение

Загружать нужные данные явно внутри транзакции и отдавать наружу DTO:

```java
@Transactional(readOnly = true)
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findByIdWithItems(id)
            .orElseThrow(() -> new OrderNotFoundException(id));

    return orderMapper.toResponse(order);   // преобразование внутри транзакции
}
```

Границы транзакции при этом совпадают с границами работы с сущностями. Наружу
уходит объект, у которого нет ни прокси, ни связи с контекстом.

## Границы транзакций

### Где ставить @Transactional

```text
контроллер → нет: транзакция охватит сериализацию и обработку HTTP
репозиторий → нет: каждый вызов станет отдельной транзакцией
сервис     → да: там находится единица бизнес-операции
```

Сервисный слой — естественная граница: одна бизнес-операция должна быть атомарной
целиком, а не по одному запросу.

### Транзакция задаёт время жизни контекста

```text
@Transactional открылся → создан persistence context
метод завершился        → flush, commit, контекст закрыт
```

Отсюда всё поведение сущностей: внутри они управляемые и dirty checking работает,
снаружи — отсоединённые.

### Долгие транзакции

```java
@Transactional
public void process(Order order) {
    orderRepository.save(order);
    paymentClient.charge(order);      // HTTP-вызов внутри транзакции
    notificationClient.send(order);
}
```

Три проблемы сразу: соединение с базой занято всё время внешних вызовов, блокировки
строк удерживаются, вакуум не может очистить старые версии. При таймауте внешнего
сервиса в тридцать секунд транзакция живёт тридцать секунд.

Правильно — сузить транзакцию до работы с базой, а внешние вызовы вынести за её
пределы или выполнить после фиксации:

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    paymentClient.charge(event.orderId());
}
```

### Чтение

```java
@Transactional(readOnly = true)
```

Отключает снимки для dirty checking, экономит память и время сброса. Кроме того,
Spring передаёт флаг драйверу, и на репликах такой запрос может быть направлен на
读-узел.

### Self-invocation

```java
@Service
public class OrderService {

    public void processAll(List<Order> orders) {
        orders.forEach(this::save);    // транзакция не откроется
    }

    @Transactional
    public void save(Order order) { }
}
```

Механизм разобран в конспекте по AOP: внутренний вызов идёт мимо прокси. Ошибки
нет, транзакции тоже.

## Массовые операции

### Проблема

```java
for (Order order : orders) {          // 100 000 сущностей
    orderRepository.save(order);
}
```

Все сто тысяч сущностей остаются в контексте, для каждой хранится снимок, а сброс
сравнивает их все. Итог — нехватка памяти и квадратичное замедление.

### Пакетная обработка

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc.batch_size: 50
        order_inserts: true
        order_updates: true
```

```java
@Transactional
public void saveAll(List<Order> orders) {
    for (int i = 0; i < orders.size(); i++) {
        entityManager.persist(orders.get(i));

        if (i % 50 == 0) {
            entityManager.flush();
            entityManager.clear();     // освобождаем контекст
        }
    }
}
```

`clear()` здесь обязателен: без него сущности продолжают накапливаться, и настройка
пакета не поможет.

Важное ограничение: пакетная вставка не работает со стратегией `IDENTITY`, так как
идентификатор известен только после `INSERT`. Нужна `SEQUENCE`.

### Массовое обновление через JPQL

```java
@Modifying
@Query("update Order o set o.status = 'CANCELLED' where o.createdAt < :date")
int cancelOld(@Param("date") Instant date);
```

Выполняется одним запросом и не загружает сущности. Но есть подвох: такой запрос
идёт мимо контекста персистентности.

```text
сущности, уже загруженные в контекст, не узнают об изменении
последующее чтение вернёт устаревшие данные
```

Поэтому после массового обновления контекст очищают:

```java
@Modifying(clearAutomatically = true, flushBeforeQuery = true)
```

По той же причине массовое удаление через JPQL не вызывает каскады и
`orphanRemoval` — они работают на уровне ORM, а не SQL.

## Оптимистическая блокировка

```java
@Entity
public class Order {

    @Version
    private Long version;
}
```

Hibernate добавляет проверку версии в каждый `UPDATE`:

```sql
UPDATE orders SET status = ?, version = 8 WHERE id = ? AND version = 7
```

Если обновлено ноль строк, значит кто-то изменил запись параллельно, и выбрасывается
`OptimisticLockException`. В Spring она транслируется в
`ObjectOptimisticLockingFailureException`.

Это тот же механизм, что обсуждался в конспекте по транзакциям в базе и в HTTP с
`ETag` и `If-Match`. Приложение обязано обработать конфликт — обычно повторив
операцию с перечитанными данными.

Пессимистический вариант тоже доступен:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Order> findById(Long id);
```

## Проекции вместо сущностей

Когда нужны только несколько полей, загружать сущность целиком незачем.

```java
public record OrderSummary(Long id, String status, BigDecimal total) {}
```

```java
@Query("select new com.example.OrderSummary(o.id, o.status, o.total) from Order o")
List<OrderSummary> findSummaries();
```

Преимущества: нет снимков для dirty checking, нет прокси, нет риска
`LazyInitializationException`, меньше данных из базы.

Spring Data поддерживает и интерфейсные проекции:

```java
public interface OrderSummary {
    Long getId();
    String getStatus();
}

List<OrderSummary> findByStatus(String status);
```

Для чтения проекции почти всегда предпочтительнее сущностей.

## Кеш второго уровня

Кеш первого уровня — контекст персистентности, он живёт в пределах транзакции.
Кеш второго уровня общий для приложения и переживает транзакции.

```text
включается отдельно, требует провайдера (Ehcache, Hazelcast, Infinispan)
подходит для редко меняющихся справочников
плохо подходит для часто изменяемых данных
в кластере требует синхронизации между узлами
```

На собеседовании достаточно знать, что он существует, чем отличается от первого
уровня и что по умолчанию отключён. На практике для Junior-проектов чаще
используют обычный кеш приложения через `@Cacheable`, который проще и понятнее.

## Типичные ошибки

### Реализовать equals и hashCode через id

`hashCode` изменится после присвоения идентификатора, и объект потеряется в
`HashSet`.

### Сравнивать классы через getClass

Ленивая связь подставляет прокси-подкласс. Нужен `instanceof` или
`Hibernate.getClass()`.

### Использовать Lombok @Data на сущности

Генерирует `equals`, `hashCode` и `toString` по всем полям, включая связи. Первые
два ломаются, третий вызывает загрузку ленивых коллекций и возможную рекурсию.

### Лечить LazyInitializationException через EAGER

Связи начнут загружаться всегда, в том числе там, где не нужны.

### Ставить @Transactional на контроллер

Транзакция охватит сериализацию и обработку HTTP-запроса.

### Выполнять внешние вызовы внутри транзакции

Соединение и блокировки удерживаются всё время ожидания.

### Сохранять десятки тысяч сущностей без clear

Контекст накапливает объекты и снимки, сброс становится всё дороже.

### Ожидать пакетной вставки со стратегией IDENTITY

Идентификатор известен только после вставки, объединение невозможно.

### Забывать очистить контекст после JPQL-обновления

Загруженные сущности останутся с устаревшими значениями.

### Ожидать каскадов от массового удаления через JPQL

Каскады и `orphanRemoval` работают на уровне ORM, а не SQL.

### Возвращать сущности вместо проекций для чтения

Лишние снимки, прокси и риск исключений при сериализации.

## Краткий ответ для собеседования

Самая тонкая проблема — `equals` и `hashCode` для сущностей. Реализация по
умолчанию сравнивает ссылки и работает только внутри одного контекста. Реализация
через идентификатор ломает контракт `hashCode`: до сохранения он `null`, после
сохранения меняется, и объект теряется в `HashSet`. Рабочие варианты — бизнес-ключ,
идентификатор, присвоенный приложением, например UUID в конструкторе, либо
сравнение по идентификатору с константным `hashCode`. Сравнивать классы через
`getClass` нельзя из-за прокси.

`LazyInitializationException` возникает при обращении к ленивой связи после
закрытия контекста. Лечить его через `EAGER` или Open Session In View
неправильно — нужно загружать данные явно внутри транзакции и отдавать наружу DTO.

`@Transactional` ставится на сервисный слой, поскольку именно там находится
единица бизнес-операции. Транзакция задаёт время жизни контекста персистентности,
поэтому за её пределами сущности отсоединены. Внутри транзакции не должно быть
обращений к внешним сервисам: соединение и блокировки удерживаются всё время
ожидания.

При массовых операциях контекст нужно периодически сбрасывать и очищать, иначе
накапливаются сущности и их снимки. Пакетная вставка несовместима со стратегией
`IDENTITY`. Массовое обновление через JPQL выполняется мимо контекста, поэтому
после него загруженные сущности остаются устаревшими, а каскады не срабатывают.

Для чтения предпочтительны проекции: они не создают снимков и прокси.

## Вопросы на собеседовании

### 1. Почему equals по умолчанию не подходит для сущностей?

**Ответ:** он сравнивает ссылки. Гарантия единственности экземпляра действует
только внутри одного контекста, а для отсоединённых сущностей и разных транзакций
одна строка будет представлена разными объектами.

### 2. Почему нельзя реализовать hashCode через id?

**Ответ:** до сохранения идентификатор `null`, после — присвоен базой. Значение
`hashCode` изменится, и объект потеряется в хеш-коллекции, куда был добавлен ранее.

### 3. Как правильно реализовать equals и hashCode?

**Ответ:** по бизнес-ключу, если он есть; по идентификатору, присвоенному
приложением, например UUID в конструкторе; либо сравнивать по идентификатору,
возвращая константу из `hashCode`.

### 4. Почему нельзя сравнивать классы через getClass?

**Ответ:** ленивая связь подставляет прокси — подкласс сущности. Сравнение вернёт
`false` для одной и той же строки. Нужен `instanceof` или `Hibernate.getClass()`.

### 5. Можно ли использовать Lombok @Data на сущности?

**Ответ:** нет. Он генерирует `equals` и `hashCode` по всем полям, что нарушает
контракт, и `toString`, который вызывает загрузку ленивых связей и может привести к
рекурсии.

### 6. Когда возникает LazyInitializationException?

**Ответ:** при обращении к ленивой связи после закрытия контекста персистентности —
в контроллере, при сериализации, у отсоединённой сущности.

### 7. Почему нельзя решать её через EAGER?

**Ответ:** связи будут загружаться всегда, включая случаи, когда они не нужны, и
отключить это в конкретном запросе невозможно.

### 8. Как решать её правильно?

**Ответ:** загружать нужные данные внутри транзакции через `join fetch` или
`EntityGraph` и отдавать наружу DTO.

### 9. На каком слое ставить @Transactional?

**Ответ:** на сервисном. Там находится единица бизнес-операции, которая должна быть
атомарной целиком.

### 10. Чем плоха транзакция на контроллере?

**Ответ:** она охватит сериализацию ответа и обработку HTTP, удерживая соединение
дольше необходимого.

### 11. Почему нельзя вызывать внешние сервисы внутри транзакции?

**Ответ:** соединение с базой и блокировки строк удерживаются всё время ожидания
ответа, а долгая транзакция мешает очистке старых версий строк.

### 12. Как обработать сотни тысяч сущностей?

**Ответ:** настроить размер пакета и периодически вызывать `flush` и `clear`, иначе
контекст накапливает сущности и их снимки.

### 13. Почему batch insert не работает с IDENTITY?

**Ответ:** идентификатор становится известен только после выполнения `INSERT`,
поэтому вставки нельзя отложить и объединить.

### 14. Что не так с массовым обновлением через JPQL?

**Ответ:** оно выполняется мимо контекста персистентности, поэтому уже загруженные
сущности остаются с устаревшими значениями. Нужна очистка контекста.

### 15. Срабатывают ли каскады при удалении через JPQL?

**Ответ:** нет. Каскады и `orphanRemoval` реализованы на уровне ORM, а массовый
запрос выполняется напрямую в базе.

### 16. Как работает @Version?

**Ответ:** Hibernate добавляет проверку версии в условие `UPDATE` и увеличивает её.
Если обновлено ноль строк, значит запись изменили параллельно, и выбрасывается
`OptimisticLockException`.

### 17. Что делать при получении OptimisticLockException?

**Ответ:** перечитать данные и повторить операцию. Это штатная ситуация, а не сбой.

### 18. Чем проекция лучше сущности при чтении?

**Ответ:** не создаётся снимок для dirty checking, нет прокси и риска
`LazyInitializationException`, из базы выбирается меньше данных.

### 19. Чем кеш второго уровня отличается от первого?

**Ответ:** первый — это контекст персистентности, он живёт в пределах транзакции.
Второй общий для приложения, переживает транзакции, по умолчанию отключён и требует
провайдера.

### 20. Что задаёт время жизни persistence context в Spring?

**Ответ:** границы транзакции. Контекст создаётся при её открытии и закрывается
после фиксации, поэтому за пределами метода сущности отсоединены.
