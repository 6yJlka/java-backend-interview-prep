# JDBC

## Что это

JDBC — стандартный API Java для работы с реляционными базами. Он описывает набор
интерфейсов, а конкретную реализацию поставляет драйвер базы.

```text
приложение
    ↓
интерфейсы JDBC (java.sql)
    ↓
драйвер конкретной базы
    ↓
сетевой протокол базы
```

Смысл разделения — код приложения не зависит от конкретной СУБД. На практике
независимость неполная: диалекты SQL различаются, и переход с PostgreSQL на Oracle
одной заменой драйвера не обходится.

Всё, что делают Hibernate, Spring Data и `JdbcTemplate`, в конечном счёте
превращается в вызовы JDBC.

### Драйвер

Исторически выделяли четыре типа драйверов. Сегодня практически все — четвёртого
типа: чистая Java, напрямую говорящая с базой по её сетевому протоколу.

```gradle
runtimeOnly 'org.postgresql:postgresql'
```

Отдельно регистрировать драйвер через `Class.forName()` не нужно с JDBC 4:
механизм `ServiceLoader` находит его в classpath автоматически.

## Соединение

### DriverManager

```java
try (Connection connection = DriverManager.getConnection(
        "jdbc:postgresql://localhost:5432/app", "user", "password")) {
    // работа
}
```

Каждый вызов открывает новое физическое соединение: TCP-подключение,
аутентификация, выделение ресурсов на стороне базы. Операция дорогая — десятки
миллисекунд.

В приложениях так не делают.

### DataSource

```java
@Bean
public DataSource dataSource() {
    HikariConfig config = new HikariConfig();
    config.setJdbcUrl("jdbc:postgresql://localhost:5432/app");
    config.setMaximumPoolSize(10);
    return new HikariDataSource(config);
}
```

`DataSource` — фабрика соединений, за которой обычно стоит пул. Именно её
используют вместо `DriverManager`. В Spring Boot она настраивается автоматически из
свойств `spring.datasource.*`.

## Statement и его наследники

### Statement

```java
Statement statement = connection.createStatement();
ResultSet rs = statement.executeQuery("SELECT * FROM orders WHERE id = " + id);
```

Простой запрос без параметров. Использовать его с подстановкой значений нельзя —
это прямая дорога к SQL-инъекции.

### PreparedStatement

```java
String sql = "SELECT id, status FROM orders WHERE customer_id = ? AND status = ?";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, customerId);
    ps.setString(2, "NEW");

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            Long id = rs.getLong("id");
        }
    }
}
```

Нумерация параметров начинается с единицы — деталь, на которой регулярно
спотыкаются.

### CallableStatement

Для вызова хранимых процедур. На практике встречается редко.

## Почему PreparedStatement

Три причины, и первая важнее остальных.

### Защита от SQL-инъекции

```java
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
```

Если `name` равно `' OR '1'='1`, запрос превращается в выборку всех строк. При
более изобретательном вводе — в удаление таблицы.

`PreparedStatement` не подставляет значения в текст запроса. Структура запроса
отправляется отдельно от данных, и значение параметра всегда остаётся значением, что
бы в нём ни находилось. Экранирование при этом не требуется — оно решает ту же
задачу хуже и с ошибками.

Ключевой момент, который стоит проговаривать: защищает не экранирование, а
**разделение кода и данных**.

Ограничение: параметризовать можно значения, но не идентификаторы. Имя таблицы или
колонки через `?` подставить нельзя — их приходится проверять по белому списку.

### Повторное использование плана

База может разобрать запрос один раз и переиспользовать план выполнения для
последующих вызовов с другими параметрами.

Драйвер PostgreSQL делает это не сразу: по умолчанию запрос переходит на
серверную подготовку после пятого выполнения одного и того же
`PreparedStatement`. Порог задаётся параметром `prepareThreshold`.

Тонкость для эксплуатации: при использовании PgBouncer в режиме транзакций
серверные подготовленные запросы ломаются, поскольку соединение между транзакциями
меняется. Обычно это решается отключением подготовки на стороне драйвера.

### Типизация

```java
ps.setTimestamp(1, Timestamp.from(instant));
ps.setBigDecimal(2, amount);
```

Драйвер сам заботится о форматировании дат и чисел. При конкатенации это пришлось
бы делать вручную, с риском ошибиться в формате или локали.

## ResultSet

```java
while (rs.next()) {
    long id = rs.getLong("id");
    String status = rs.getString("status");
}
```

Курсор, изначально стоящий перед первой строкой, поэтому `next()` вызывается до
первого чтения.

### Работа с NULL

```java
int quantity = rs.getInt("quantity");   // NULL превратится в 0

if (rs.wasNull()) {
    // значение было NULL
}
```

Примитивные геттеры не различают `NULL` и нулевое значение. Либо проверять через
`wasNull()`, либо использовать объектные типы через `getObject()`.

### Размер выборки

```java
statement.setFetchSize(1000);
```

По умолчанию драйвер PostgreSQL загружает **весь результат** в память клиента.
Запрос на миллион строк приведёт к нехватке памяти.

Установка размера выборки включает курсор на стороне сервера и построчную
подгрузку. Дополнительное условие: автофиксация должна быть отключена, иначе
настройка игнорируется.

## Закрытие ресурсов

```java
try (Connection connection = dataSource.getConnection();
     PreparedStatement ps = connection.prepareStatement(sql);
     ResultSet rs = ps.executeQuery()) {

    while (rs.next()) {
    }
}
```

`Connection`, `Statement` и `ResultSet` реализуют `AutoCloseable`. Ресурсы
закрываются в порядке, обратном объявлению.

Незакрытое соединение не возвращается в пул. Достаточно нескольких таких утечек в
редком пути кода, чтобы пул исчерпался и приложение встало — при этом база будет
выглядеть здоровой.

---

## Транзакции

### Автофиксация

По умолчанию соединение работает в режиме автофиксации: каждый запрос —
самостоятельная транзакция.

```java
connection.setAutoCommit(false);

try {
    // несколько операций
    connection.commit();
} catch (SQLException e) {
    connection.rollback();
    throw e;
}
```

Именно это и делает `@Transactional`: отключает автофиксацию, выполняет метод,
вызывает `commit` или `rollback`.

### Уровень изоляции

```java
connection.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
```

Соответствует параметру `isolation` в `@Transactional`.

### Точки сохранения

```java
Savepoint savepoint = connection.setSavepoint();
connection.rollback(savepoint);
```

На этом механизме построено распространение `NESTED` в Spring.

## Пакетная обработка

```java
try (PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO orders (status, total) VALUES (?, ?)")) {

    for (Order order : orders) {
        ps.setString(1, order.getStatus());
        ps.setBigDecimal(2, order.getTotal());
        ps.addBatch();

        if (++count % 500 == 0) {
            ps.executeBatch();
        }
    }
    ps.executeBatch();
}
```

Вместо тысячи обращений к базе выполняется несколько. Выигрыш существенный, потому
что основные затраты — сетевые задержки, а не сама вставка.

Для PostgreSQL важно добавить в строку подключения:

```text
jdbc:postgresql://host:5432/db?reWriteBatchedInserts=true
```

Драйвер объединит вставки в один многострочный `INSERT`. Без этого пакет
отправляется одним запросом к сети, но выполняется на сервере по отдельности.

## Пул соединений

### Зачем нужен

Открытие соединения стоит десятки миллисекунд, и база ограничивает их число.
Пул держит соединения открытыми и выдаёт по запросу.

```text
без пула → открыть, использовать, закрыть
с пулом  → взять из пула, использовать, вернуть
```

Стандарт в Spring Boot — HikariCP.

### Основные параметры

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 10
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
      leak-detection-threshold: 60000
```

```text
maximum-pool-size → сколько соединений максимум
connection-timeout → сколько ждать свободное, иначе исключение
max-lifetime      → через сколько соединение пересоздаётся
leak-detection-threshold → предупреждение о невозвращённом соединении
```

### Размер пула

Распространённое заблуждение — что больше значит лучше. На деле зависимость
обратная: слишком большой пул ухудшает производительность.

Соединения обслуживаются процессорами и дисками базы, и их число ограничено.
Сотня одновременных запросов на восьмиядерном сервере не выполняется быстрее, чем
двадцать, — добавляется лишь конкуренция за ресурсы и переключение контекста.

Ориентир из документации HikariCP:

```text
пул ≈ количество ядер × 2 + количество дисков
```

Для типового сервиса это 10–20 соединений, а не 200. Полезное правило: пул должен
быть узким местом раньше, чем база, — тогда очередь выстраивается в приложении, где
её видно, а не внутри СУБД.

### Настройки для эксплуатации

`max-lifetime` следует делать меньше, чем таймаут соединения на стороне базы или
файрвола. Иначе приложение получит соединение, разорванное с той стороны, и
запрос упадёт непонятной ошибкой.

`leak-detection-threshold` включают в тестовых средах: он логирует стек потока,
удерживающего соединение дольше заданного времени. Это лучший способ найти
незакрытый `Connection`.

## JdbcTemplate

Обёртка Spring, убирающая шаблонный код и превращающая `SQLException` в
непроверяемые исключения иерархии `DataAccessException`.

```java
List<Order> orders = jdbcTemplate.query(
        "SELECT id, status FROM orders WHERE customer_id = ?",
        (rs, rowNum) -> new Order(rs.getLong("id"), rs.getString("status")),
        customerId
);
```

Ресурсы закрываются автоматически, параметры подставляются безопасно.

Есть и вариант с именованными параметрами, который читается лучше при большом их
числе:

```java
namedParameterJdbcTemplate.query(
        "SELECT * FROM orders WHERE status = :status",
        Map.of("status", "NEW"),
        rowMapper
);
```

## JDBC против JPA

```text
JDBC
→ полный контроль над SQL
→ предсказуемое число запросов
→ много ручного кода отображения
→ нет кеша, dirty checking, ленивой загрузки

JPA / Hibernate
→ меньше кода для типового CRUD
→ автоматическое отслеживание изменений
→ непредсказуемый SQL, N+1, LazyInitializationException
→ сложнее оптимизировать
```

На практике их часто сочетают: JPA для операций над отдельными сущностями,
`JdbcTemplate` или jOOQ для сложных отчётов и массовых операций. Отдельно стоит
Spring Data JDBC — упрощённый вариант без контекста персистентности и ленивой
загрузки.

Ответ на собеседовании «всегда использовать Hibernate» слабее, чем понимание, что
выбор зависит от задачи.

## Типичные ошибки

### Конкатенация параметров в SQL

Открывает SQL-инъекцию. Только `PreparedStatement` с параметрами.

### Считать, что экранирование решает проблему инъекций

Защищает разделение кода и данных, а не обработка символов.

### Не закрывать ресурсы

Соединение не возвращается в пул, и он со временем исчерпывается.

### Нумеровать параметры с нуля

Индексация в `PreparedStatement` начинается с единицы.

### Читать примитивы без проверки wasNull

`NULL` превратится в ноль, и это останется незамеченным.

### Выбирать большой результат без fetch size

Драйвер PostgreSQL по умолчанию загружает весь результат в память.

### Ставить огромный размер пула

Производительность падает: соединений больше, чем база способна обслуживать
параллельно.

### Не согласовывать max-lifetime с таймаутом базы

Приложение получит уже разорванное соединение.

### Выполнять вставки по одной

Пакетная обработка сокращает число сетевых обменов на порядок.

### Забывать про reWriteBatchedInserts в PostgreSQL

Без этого параметра пакет не превращается в многострочный `INSERT`.

## Краткий ответ для собеседования

JDBC — стандартный API для работы с реляционными базами: набор интерфейсов в
`java.sql`, реализуемых драйвером конкретной СУБД. Всё, что делают Hibernate и
Spring Data, в итоге сводится к вызовам JDBC.

Соединения не открывают напрямую через `DriverManager`, поскольку это дорогая
операция. Используется `DataSource`, за которым стоит пул — в Spring Boot это
HikariCP.

`PreparedStatement` предпочтительнее `Statement` прежде всего из-за защиты от
SQL-инъекций: структура запроса и данные передаются раздельно, поэтому значение
параметра не может изменить смысл запроса. Дополнительно база может переиспользовать
план выполнения, а драйвер берёт на себя преобразование типов. Параметризовать
можно значения, но не имена таблиц и колонок.

Ресурсы закрываются через try-with-resources. Незакрытое соединение не
возвращается в пул, и накопление таких утечек останавливает приложение.

Транзакции управляются отключением автофиксации и вызовами `commit` или `rollback`.
Именно это выполняет прокси `@Transactional`.

Размер пула не должен быть большим: соединений не может обслуживаться параллельно
больше, чем позволяют ресурсы базы, и избыточный пул только добавляет конкуренцию.
Ориентир — порядка десяти-двадцати соединений на сервис.

## Вопросы на собеседовании

### 1. Что такое JDBC?

**Ответ:** стандартный API Java для работы с реляционными базами. Интерфейсы
находятся в `java.sql`, реализацию поставляет драйвер конкретной СУБД.

### 2. Нужно ли регистрировать драйвер вручную?

**Ответ:** нет, начиная с JDBC 4 драйвер находится автоматически через
`ServiceLoader`.

### 3. Чем DataSource лучше DriverManager?

**Ответ:** `DriverManager` открывает новое физическое соединение при каждом вызове,
что дорого. `DataSource` — фабрика, за которой обычно стоит пул.

### 4. Чем PreparedStatement отличается от Statement?

**Ответ:** он принимает параметры, передаваемые отдельно от текста запроса.
Защищает от инъекций, позволяет переиспользовать план и берёт на себя типизацию.

### 5. Почему PreparedStatement защищает от SQL-инъекции?

**Ответ:** структура запроса отправляется отдельно от данных, и значение параметра
остаётся значением, что бы в нём ни находилось. Дело не в экранировании, а в
разделении кода и данных.

### 6. Можно ли параметризовать имя таблицы?

**Ответ:** нет, только значения. Идентификаторы приходится проверять по белому
списку.

### 7. С какого индекса нумеруются параметры?

**Ответ:** с единицы.

### 8. Как отличить NULL от нуля при чтении примитива?

**Ответ:** вызвать `wasNull()` после чтения либо использовать `getObject()` с
объектным типом.

### 9. Что произойдёт при выборке миллиона строк?

**Ответ:** драйвер PostgreSQL по умолчанию загрузит весь результат в память. Нужен
`setFetchSize` при отключённой автофиксации, чтобы включить серверный курсор.

### 10. Почему важно закрывать ресурсы?

**Ответ:** незакрытое соединение не возвращается в пул. Накопление утечек
исчерпывает пул, и приложение перестаёт обслуживать запросы.

### 11. Как управлять транзакцией в JDBC?

**Ответ:** отключить автофиксацию через `setAutoCommit(false)`, затем вызвать
`commit` или `rollback`.

### 12. Что делает @Transactional на уровне JDBC?

**Ответ:** отключает автофиксацию, выполняет метод и вызывает фиксацию или откат в
зависимости от результата.

### 13. Как ускорить массовую вставку?

**Ответ:** использовать `addBatch` и `executeBatch` порциями. Для PostgreSQL
дополнительно указать `reWriteBatchedInserts=true`, чтобы драйвер объединял вставки
в один многострочный запрос.

### 14. Зачем нужен пул соединений?

**Ответ:** открытие соединения занимает десятки миллисекунд, а база ограничивает
их количество. Пул переиспользует уже открытые.

### 15. Каким должен быть размер пула?

**Ответ:** небольшим — ориентировочно вдвое больше числа ядер базы, обычно
десять-двадцать. Избыточный пул только увеличивает конкуренцию за ресурсы.

### 16. Почему max-lifetime должен быть меньше таймаута базы?

**Ответ:** иначе приложение получит соединение, уже разорванное со стороны базы или
файрвола, и запрос упадёт с непонятной ошибкой.

### 17. Как найти утечку соединений?

**Ответ:** включить `leak-detection-threshold` — HikariCP залогирует стек потока,
удерживающего соединение дольше порога.

### 18. Что даёт JdbcTemplate?

**Ответ:** убирает шаблонный код, закрывает ресурсы и транслирует `SQLException` в
непроверяемые исключения иерархии `DataAccessException`.

### 19. Когда выбрать JDBC вместо JPA?

**Ответ:** когда нужен полный контроль над SQL и предсказуемое число запросов —
сложные отчёты, массовые операции, оптимизация горячих путей. Подходы часто
сочетают в одном приложении.

### 20. Что теряется при отказе от JPA?

**Ответ:** автоматическое отслеживание изменений, кеш первого уровня, ленивая
загрузка и генерация SQL для типового CRUD. Взамен появляется предсказуемость.
