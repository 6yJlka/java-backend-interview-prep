# SQL: выборки, джойны и группировки

## Логический порядок выполнения

Запрос пишется в одном порядке, а выполняется в другом. Это первое, что стоит
усвоить: из логического порядка выводится половина правил, которые иначе
приходится заучивать.

```text
1. FROM      → откуда берём данные
2. JOIN      → присоединяем таблицы
3. WHERE     → фильтруем строки
4. GROUP BY  → группируем
5. HAVING    → фильтруем группы
6. SELECT    → вычисляем выражения, назначаем алиасы
7. DISTINCT  → убираем дубликаты
8. ORDER BY  → сортируем
9. LIMIT     → ограничиваем
```

Отсюда сразу следует несколько вещей.

**Алиас из `SELECT` нельзя использовать в `WHERE`:**

```sql
SELECT price * quantity AS total
FROM order_items
WHERE total > 1000;              -- ошибка
```

К моменту выполнения `WHERE` шаг `SELECT` ещё не выполнен, алиаса не существует.
Нужно повторить выражение или обернуть запрос.

**А в `ORDER BY` — можно:**

```sql
SELECT price * quantity AS total
FROM order_items
ORDER BY total;                   -- работает
```

`ORDER BY` идёт после `SELECT`.

**В `WHERE` нельзя использовать агрегаты:**

```sql
SELECT customer_id
FROM orders
WHERE COUNT(*) > 5               -- ошибка
GROUP BY customer_id;
```

Агрегат появляется только после `GROUP BY`. Для фильтрации групп существует
`HAVING`.

Это логический порядок, а не физический. Оптимизатор волен выполнять операции
иначе, лишь бы результат совпадал.

## WHERE и HAVING

```sql
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'COMPLETED'        -- фильтр строк, до группировки
GROUP BY customer_id
HAVING COUNT(*) > 5;              -- фильтр групп, после группировки
```

```text
WHERE  → работает со строками, агрегаты недоступны
HAVING → работает с группами, агрегаты доступны
```

Практическое следствие: условие, которое можно поставить в `WHERE`, туда и надо
ставить. Оно отсеет строки до группировки, и группировать придётся меньше. То же
условие в `HAVING` даст верный результат, но лишнюю работу.

## NULL и трёхзначная логика

Источник большинства неочевидных ошибок. `NULL` означает не «пусто» и не «ноль», а
«неизвестно». Любое сравнение с неизвестным даёт неизвестный результат.

```sql
NULL = NULL      → NULL, не TRUE
NULL <> NULL     → NULL
NULL = 5         → NULL
NULL + 5         → NULL
```

Строки попадают в результат только при `TRUE`. `FALSE` и `NULL` отбрасываются
одинаково, поэтому кажется, что сравнение вернуло `FALSE`, хотя вернуло оно `NULL`.

Проверка выполняется отдельными операторами:

```sql
WHERE phone IS NULL
WHERE phone IS NOT NULL
```

### Ловушка NOT IN

Самая известная.

```sql
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM banned_users);
```

Если подзапрос вернёт хотя бы один `NULL`, результат окажется **пустым**. Логика
такая: `id NOT IN (1, 2, NULL)` разворачивается в `id <> 1 AND id <> 2 AND id <> NULL`,
последнее условие даёт `NULL`, всё выражение — `NULL`, строка отбрасывается.

Безопасная замена — `NOT EXISTS`:

```sql
SELECT * FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM banned_users b WHERE b.user_id = u.id
);
```

`NOT EXISTS` проверяет наличие строк, а не сравнивает значения, поэтому на `NULL`
не спотыкается.

### NULL в агрегатах

Агрегатные функции игнорируют `NULL`, кроме `COUNT(*)`.

```sql
SELECT
    COUNT(*),            -- все строки
    COUNT(phone),        -- строки, где phone не NULL
    AVG(rating)          -- среднее по не-NULL значениям
FROM users;
```

Это важно для `AVG`: он делит на количество не-`NULL` значений, а не на общее
число строк. Если нужно считать `NULL` за ноль, требуется `COALESCE`.

`COUNT(*)`, `COUNT(1)` и `COUNT('x')` эквивалентны — все считают строки. Мифы про
разную скорость не подтверждаются.

### NULL при сортировке и группировке

```sql
ORDER BY created_at DESC NULLS LAST
```

В PostgreSQL по умолчанию `NULL` считаются наибольшими: при `ASC` идут в конец,
при `DESC` — в начало. В других СУБД поведение отличается, поэтому порядок лучше
задавать явно.

`GROUP BY` при этом собирает все `NULL` в одну группу — здесь они считаются
равными, в отличие от сравнения.

### Полезные функции

```sql
COALESCE(phone, 'не указан')     -- первое не-NULL значение
NULLIF(value, 0)                 -- NULL, если равны, иначе value
```

`NULLIF` удобен для защиты от деления на ноль:

```sql
SELECT total / NULLIF(quantity, 0) FROM order_items;
```

## Соединения

### INNER JOIN

Только строки, для которых нашлось соответствие в обеих таблицах.

```sql
SELECT o.id, u.name
FROM orders o
INNER JOIN users u ON u.id = o.user_id;
```

Заказы без пользователя и пользователи без заказов не попадут в результат.

### LEFT JOIN

Все строки левой таблицы плюс совпавшие из правой. Где совпадения нет — `NULL`.

```sql
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
```

Пользователи без заказов останутся, `o.id` у них будет `NULL`.

### RIGHT JOIN и FULL JOIN

`RIGHT JOIN` — зеркальный `LEFT`. На практике используется редко: почти всегда
понятнее переставить таблицы и написать `LEFT`.

`FULL JOIN` — все строки обеих таблиц, с `NULL` там, где нет пары.

### CROSS JOIN

Декартово произведение: каждая строка с каждой.

```sql
SELECT * FROM sizes CROSS JOIN colors;
```

Осмысленно для генерации комбинаций. Чаще возникает случайно — при перечислении
таблиц через запятую без условия соединения.

### SELF JOIN

Таблица соединяется сама с собой, обязательно с разными алиасами.

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

`LEFT`, а не `INNER`, иначе потеряется сотрудник без руководителя.

### ON против WHERE во внешних соединениях

Классическая ловушка, которую спрашивают часто.

```sql
-- условие в ON: применяется при соединении
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'COMPLETED';
```

Пользователи без завершённых заказов останутся в результате с `NULL` вместо заказа.

```sql
-- условие в WHERE: применяется после соединения
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'COMPLETED';
```

Строки с `NULL` не проходят условие `o.status = 'COMPLETED'` — оно даёт `NULL`, а
не `TRUE`. Пользователи без заказов исчезают, и `LEFT JOIN` фактически превращается
в `INNER JOIN`.

```text
условие по правой таблице в ON    → LEFT JOIN остаётся LEFT
условие по правой таблице в WHERE → LEFT JOIN вырождается в INNER
```

Единственное исключение — `WHERE o.id IS NULL`, и это отдельный приём.

### Anti-join

Поиск строк без пары. Три способа, из которых один опасен.

```sql
-- LEFT JOIN + IS NULL
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- NOT EXISTS, обычно предпочтительнее
SELECT u.*
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- NOT IN — опасен из-за NULL
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders);
```

`NOT EXISTS` читается яснее всего и безопасен по отношению к `NULL`. В PostgreSQL
он же обычно и эффективнее.

## Агрегация

### Функции

```sql
COUNT, SUM, AVG, MIN, MAX
```

### Правило GROUP BY

Каждое поле в `SELECT` должно быть либо в `GROUP BY`, либо под агрегатной
функцией.

```sql
SELECT customer_id, status, COUNT(*)
FROM orders
GROUP BY customer_id;             -- ошибка: status не сгруппирован
```

Причина логичная: группа объединяет много строк, и непонятно, какое из значений
`status` показать.

Исключение: если группировка идёт по первичному ключу таблицы, PostgreSQL
разрешает выбирать остальные её колонки — они однозначно определены ключом.

### GROUP BY с несколькими полями

```sql
SELECT customer_id, status, COUNT(*)
FROM orders
GROUP BY customer_id, status;
```

Группа образуется на каждую уникальную комбинацию.

### FILTER

Условная агрегация — удобный синтаксис PostgreSQL:

```sql
SELECT
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE status = 'COMPLETED') AS completed,
    COUNT(*) FILTER (WHERE status = 'CANCELLED') AS cancelled
FROM orders;
```

Переносимый эквивалент — `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.

## DISTINCT

Убирает дубликаты строк результата.

```sql
SELECT DISTINCT status FROM orders;
```

`DISTINCT` относится ко всей строке, а не к одной колонке:

```sql
SELECT DISTINCT status, customer_id FROM orders;
```

Уникальными будут пары, а не значения `status`.

Операция требует сортировки или хеширования, поэтому не бесплатна. Часто
`DISTINCT` в запросе — признак того, что соединение размножило строки, и правильнее
исправить причину, а не прятать следствие.

PostgreSQL дополнительно поддерживает `DISTINCT ON`:

```sql
SELECT DISTINCT ON (customer_id) customer_id, id, created_at
FROM orders
ORDER BY customer_id, created_at DESC;
```

Возвращает по одной строке на каждое значение `customer_id` — последний заказ
каждого клиента. Конструкция нестандартная, но очень удобная.

## Подзапросы

### Скалярный

Возвращает одно значение, используется как выражение.

```sql
SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;
```

### В условии

```sql
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'RU');
```

### Коррелированный

Ссылается на внешний запрос и логически выполняется для каждой его строки:

```sql
SELECT * FROM orders o
WHERE o.total > (
    SELECT AVG(total) FROM orders WHERE user_id = o.user_id
);
```

Оптимизатор часто переписывает такое в соединение, но не всегда — коррелированные
подзапросы стоит проверять по плану.

### EXISTS против IN

```sql
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)
WHERE id IN (SELECT user_id FROM orders)
```

`EXISTS` останавливается на первом найденном совпадении и не спотыкается о `NULL`.
`IN` нагляднее для короткого списка значений. В современном PostgreSQL планы
обычно совпадают, но для `NOT`-версий разница принципиальна: `NOT EXISTS`
безопасен, `NOT IN` — нет.

## CTE

Общее табличное выражение — именованный подзапрос, объявленный до основного:

```sql
WITH active_users AS (
    SELECT id, name FROM users WHERE status = 'ACTIVE'
)
SELECT au.name, COUNT(o.id)
FROM active_users au
LEFT JOIN orders o ON o.user_id = au.id
GROUP BY au.name;
```

Главная польза — читаемость: сложный запрос разбивается на именованные шаги.

Про оптимизацию есть важная деталь. До PostgreSQL 12 CTE был барьером
оптимизации: он всегда материализовался, и условия из внешнего запроса внутрь не
проталкивались. Начиная с 12 версии CTE встраивается в основной запрос, если он не
рекурсивный и используется один раз. Прежнее поведение доступно явно:

```sql
WITH active_users AS MATERIALIZED (...)
```

### Рекурсивный CTE

Для иерархий и графов:

```sql
WITH RECURSIVE subordinates AS (
    SELECT id, name, manager_id
    FROM employees
    WHERE id = 1                          -- якорь

    UNION ALL

    SELECT e.id, e.name, e.manager_id
    FROM employees e
    JOIN subordinates s ON e.manager_id = s.id   -- рекурсивная часть
)
SELECT * FROM subordinates;
```

Работает так: выполняется якорная часть, затем рекурсивная применяется к
результату предыдущего шага, пока не перестанут появляться новые строки.

При циклах в данных запрос зациклится, поэтому на реальных графах нужен либо учёт
пройденного пути, либо ограничение глубины.

## UNION

```sql
SELECT name FROM customers
UNION
SELECT name FROM suppliers;
```

```text
UNION     → объединяет и убирает дубликаты
UNION ALL → объединяет без удаления дубликатов
```

`UNION ALL` быстрее, потому что не требует дедупликации. Если дубликаты заведомо
невозможны или не мешают, используют его.

Требования: одинаковое число колонок и совместимые типы. Имена берутся из первого
запроса.

Родственные операции: `INTERSECT` — только общие строки, `EXCEPT` — строки первого
запроса, отсутствующие во втором.

## Оконные функции

Ключевое отличие от `GROUP BY`: агрегация выполняется, но строки не схлопываются.

```sql
SELECT
    name,
    department,
    salary,
    AVG(salary) OVER (PARTITION BY department) AS dept_avg
FROM employees;
```

Каждая строка остаётся на месте и дополняется средним по своему отделу. Через
`GROUP BY` такое пришлось бы делать соединением с подзапросом.

### Синтаксис

```sql
функция() OVER (
    PARTITION BY поле      -- на какие группы делить, необязательно
    ORDER BY поле          -- порядок внутри группы
)
```

### Нумерация и ранжирование

```sql
SELECT
    name,
    salary,
    ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num,
    RANK()       OVER (ORDER BY salary DESC) AS rank,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank
FROM employees;
```

Различие проявляется на одинаковых значениях:

```text
salary  ROW_NUMBER  RANK  DENSE_RANK
100     1           1     1
90      2           2     2
90      3           2     2
80      4           4     3
```

```text
ROW_NUMBER → сквозная нумерация, дубликатов нет
RANK       → одинаковый ранг при равенстве, затем пропуск
DENSE_RANK → одинаковый ранг, без пропусков
```

### Top-N в каждой группе

Стандартная задача, которую без оконных функций решать неудобно:

```sql
SELECT * FROM (
    SELECT
        name,
        department,
        salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
) t
WHERE rn <= 3;
```

Подзапрос нужен потому, что оконная функция вычисляется на шаге `SELECT`, а
`WHERE` выполняется раньше — по логическому порядку фильтровать по `rn` напрямую
нельзя.

### LAG и LEAD

Доступ к соседним строкам:

```sql
SELECT
    created_at,
    total,
    LAG(total) OVER (ORDER BY created_at) AS prev_total,
    total - LAG(total) OVER (ORDER BY created_at) AS delta
FROM orders;
```

### Накопительные итоги

```sql
SELECT
    created_at,
    total,
    SUM(total) OVER (ORDER BY created_at) AS running_total
FROM orders;
```

Наличие `ORDER BY` внутри `OVER` меняет смысл: агрегат считается не по всей
партиции, а нарастающим итогом от начала до текущей строки.

## Типичные ошибки

### Использовать алиас из SELECT в WHERE

К этому моменту `SELECT` ещё не выполнен.

### Ставить агрегат в WHERE

Для фильтрации по агрегату существует `HAVING`.

### Условие по правой таблице в WHERE при LEFT JOIN

Соединение вырождается в `INNER`. Условие должно быть в `ON`.

### NOT IN с подзапросом

Один `NULL` внутри — и результат пуст. Использовать `NOT EXISTS`.

### Сравнивать с NULL через равенство

`value = NULL` всегда `NULL`. Нужен `IS NULL`.

### Ожидать, что AVG делит на общее число строк

Агрегаты игнорируют `NULL`. Для учёта их как нуля нужен `COALESCE`.

### Лечить дубликаты через DISTINCT

Обычно дубликаты порождены соединением, размножившим строки. Исправлять надо
причину.

### Забыть условие соединения

Перечисление таблиц через запятую без `WHERE` даёт декартово произведение.

### Фильтровать по оконной функции в WHERE

Окна вычисляются на шаге `SELECT`. Нужен подзапрос или `QUALIFY` там, где он есть.

### Использовать UNION вместо UNION ALL

Дедупликация стоит сортировки или хеширования, а часто не нужна.

## Краткая памятка

```text
логический порядок
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

алиас из SELECT: в WHERE нельзя, в ORDER BY можно
агрегат: в WHERE нельзя, в HAVING можно
```

```text
NULL = неизвестно

NULL = NULL       → NULL
проверка          → IS NULL / IS NOT NULL
NOT IN + NULL     → пустой результат
агрегаты          → игнорируют NULL, кроме COUNT(*)
GROUP BY          → все NULL в одну группу
```

```text
INNER → только совпадения
LEFT  → все левые + совпавшие правые
FULL  → все с обеих сторон
CROSS → декартово произведение

условие по правой таблице
в ON    → LEFT остаётся LEFT
в WHERE → LEFT становится INNER
```

```text
anti-join
NOT EXISTS  → безопасно, обычно быстрее
LEFT + IS NULL → работает
NOT IN      → ломается на NULL
```

```text
UNION     → с дедупликацией
UNION ALL → без, быстрее
```

```text
GROUP BY → строки схлопываются
OVER     → строки остаются

ROW_NUMBER → 1,2,3,4
RANK       → 1,2,2,4
DENSE_RANK → 1,2,2,3
```

## Краткий ответ для собеседования

Запрос выполняется не в том порядке, в котором записан: сначала `FROM` и
соединения, затем `WHERE`, `GROUP BY`, `HAVING`, потом `SELECT`, `DISTINCT`,
`ORDER BY` и `LIMIT`. Из этого следует, что алиас, объявленный в `SELECT`,
недоступен в `WHERE`, но доступен в `ORDER BY`, и что фильтровать по агрегату
можно только в `HAVING`.

`WHERE` фильтрует строки до группировки, `HAVING` — группы после. Условие,
которое можно поставить в `WHERE`, туда и ставят: оно уменьшает объём
группировки.

`NULL` означает неизвестное значение, поэтому любое сравнение с ним даёт `NULL`, а
не истину или ложь. Проверяют через `IS NULL`. Главная практическая ловушка —
`NOT IN` с подзапросом: единственный `NULL` внутри делает результат пустым, и
безопасной заменой служит `NOT EXISTS`. Агрегатные функции игнорируют `NULL`, кроме
`COUNT(*)`.

`INNER JOIN` оставляет только совпавшие строки, `LEFT JOIN` — все строки левой
таблицы. Важно, где стоит условие по правой таблице: в `ON` оно применяется при
соединении и внешний характер сохраняется, а в `WHERE` — после, и строки с `NULL`
отбрасываются, из-за чего `LEFT JOIN` превращается в `INNER`.

Оконные функции выполняют агрегацию, не схлопывая строки. Это позволяет считать
ранги, накопительные итоги и обращаться к соседним строкам. Типовая задача —
выбрать топ-N в каждой группе через `ROW_NUMBER()` с `PARTITION BY`, обернув
запрос, поскольку фильтровать по окну в `WHERE` нельзя.

## Вопросы на собеседовании

### 1. В каком порядке выполняется SQL-запрос?

**Ответ:** `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `DISTINCT`,
`ORDER BY`, `LIMIT`. Это логический порядок; физический план может отличаться.

### 2. Почему алиас из SELECT нельзя использовать в WHERE?

**Ответ:** `WHERE` выполняется раньше `SELECT`, алиас к этому моменту не
существует. В `ORDER BY` он доступен, поскольку тот идёт после.

### 3. Чем WHERE отличается от HAVING?

**Ответ:** `WHERE` фильтрует строки до группировки и не работает с агрегатами,
`HAVING` фильтрует группы после и с агрегатами работает.

### 4. Что означает NULL?

**Ответ:** неизвестное значение. Сравнение с ним даёт `NULL`, а не истину или
ложь, поэтому строка не попадает в результат. Проверяется через `IS NULL`.

### 5. Почему NOT IN с подзапросом опасен?

**Ответ:** если подзапрос вернёт `NULL`, всё условие станет `NULL` и результат
окажется пустым. Безопасная замена — `NOT EXISTS`.

### 6. Как агрегатные функции обходятся с NULL?

**Ответ:** игнорируют их. Исключение — `COUNT(*)`, который считает все строки.
Поэтому `AVG` делит на число не-`NULL` значений.

### 7. Есть ли разница между COUNT(*) и COUNT(1)?

**Ответ:** нет, оба считают строки. `COUNT(колонка)` отличается — он пропускает
`NULL`.

### 8. Чем INNER JOIN отличается от LEFT JOIN?

**Ответ:** `INNER` возвращает только строки с совпадением в обеих таблицах, `LEFT`
— все строки левой таблицы, подставляя `NULL` там, где пары нет.

### 9. Чем условие в ON отличается от условия в WHERE при LEFT JOIN?

**Ответ:** в `ON` оно применяется при соединении, и строки без пары сохраняются с
`NULL`. В `WHERE` — после соединения, и такие строки отбрасываются, из-за чего
`LEFT JOIN` фактически становится `INNER`.

### 10. Как найти строки, у которых нет связанных записей?

**Ответ:** через `NOT EXISTS` либо через `LEFT JOIN` с условием `IS NULL` по полю
правой таблицы. `NOT IN` для этого использовать не стоит из-за `NULL`.

### 11. Какое правило действует для полей в SELECT при GROUP BY?

**Ответ:** каждое поле должно быть либо в `GROUP BY`, либо под агрегатной
функцией. Иначе непонятно, какое из значений группы показать.

### 12. Чем UNION отличается от UNION ALL?

**Ответ:** `UNION` убирает дубликаты и потому требует сортировки или хеширования,
`UNION ALL` просто объединяет и работает быстрее.

### 13. Что такое CTE и зачем он нужен?

**Ответ:** именованный подзапрос, объявленный через `WITH`. Улучшает читаемость и
позволяет писать рекурсивные запросы для иерархий.

### 14. Материализуется ли CTE в PostgreSQL?

**Ответ:** до версии 12 всегда, и он служил барьером оптимизации. С 12 версии
нерекурсивный CTE, используемый один раз, встраивается в запрос; прежнее поведение
задаётся словом `MATERIALIZED`.

### 15. Чем оконные функции отличаются от GROUP BY?

**Ответ:** `GROUP BY` схлопывает строки в одну на группу, оконная функция
вычисляет агрегат, оставляя все строки на месте.

### 16. В чём разница между ROW_NUMBER, RANK и DENSE_RANK?

**Ответ:** `ROW_NUMBER` нумерует подряд без повторов. `RANK` даёт одинаковый ранг
равным значениям и пропускает следующие номера. `DENSE_RANK` тоже даёт одинаковый
ранг, но пропусков не делает.

### 17. Как выбрать по три самых высокооплачиваемых сотрудника в каждом отделе?

**Ответ:** `ROW_NUMBER()` с `PARTITION BY department ORDER BY salary DESC`, затем
обернуть запрос и отфильтровать по номеру. Обёртка нужна, поскольку в `WHERE`
оконная функция недоступна.

### 18. Что делает ORDER BY внутри OVER?

**Ответ:** превращает агрегат в накопительный: он считается от начала партиции до
текущей строки, а не по всей партиции целиком.

### 19. Когда DISTINCT — признак проблемы?

**Ответ:** когда дубликаты появились из-за соединения, размножившего строки.
Исправлять нужно соединение, а не прятать следствие.

### 20. Что такое коррелированный подзапрос?

**Ответ:** подзапрос, ссылающийся на колонки внешнего запроса и логически
выполняемый для каждой его строки. Оптимизатор часто переписывает его в
соединение, но план стоит проверять.
