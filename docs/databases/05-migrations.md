# Миграции схемы базы данных

## Зачем нужны

Код версионируется в Git, а схема базы — нет. Без отдельного механизма состояние
базы на машине разработчика, на тестовом стенде и в продакшене расходится, и
никто не может сказать, чем именно.

Миграции решают это тем, что схема описывается упорядоченным набором скриптов,
лежащих в том же репозитории, что и код. Инструмент хранит в служебной таблице,
какие скрипты уже применены, и накатывает недостающие при старте.

```text
скрипт → часть репозитория → та же версия, что и код
таблица истории → что уже применено на этой базе
```

---

## ddl-auto и почему его недостаточно

Hibernate умеет создавать схему сам:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

```text
none        → ничего не делает
validate    → проверяет соответствие схемы сущностям, не меняет её
update      → достраивает недостающее
create      → пересоздаёт при старте
create-drop → плюс удаляет при остановке
```

`update` выглядит удобным и потому опасен. Он умеет добавлять, но не умеет
переименовывать, удалять, менять тип, переносить данные и откатывать. Порядок
действий не определён, две версии приложения при постепенной выкладке будут
править схему одновременно, а что именно произошло с базой — нигде не записано.

Рабочая связка: схему меняют миграции, `ddl-auto: validate` служит страховкой,
которая уронит приложение на старте при расхождении сущностей и схемы.

```text
create / create-drop → только тесты
update               → только локальная песочница, никогда не прод
validate             → прод
```

## Flyway

```text
src/main/resources/db/migration/
├── V1__create_orders.sql
├── V2__add_status_to_orders.sql
└── V3__create_order_items.sql
```

Имя разбирается на части: префикс `V`, версия, два подчёркивания, описание.

```sql
-- V2__add_status_to_orders.sql
ALTER TABLE orders ADD COLUMN status VARCHAR(32);
UPDATE orders SET status = 'NEW' WHERE status IS NULL;
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
```

Spring Boot подхватывает Flyway автоматически при наличии зависимости и выполняет
миграции до создания `EntityManagerFactory`, то есть до проверки `validate`.

История хранится в таблице `flyway_schema_history`, где для каждого применённого
скрипта записана контрольная сумма.

```text
V   → versioned, применяется один раз в порядке версий
R   → repeatable, применяется заново при изменении контрольной суммы
U   → undo, только в платной версии
```

Повторяемые миграции (`R__create_views.sql`) удобны для представлений и функций:
их можно править на месте, инструмент сам переприменит.

## Liquibase

Тот же принцип, другой способ описания: журнал изменений из отдельных наборов.

```yaml
databaseChangeLog:
  - changeSet:
      id: 2
      author: dmitry
      changes:
        - addColumn:
            tableName: orders
            columns:
              - column:
                  name: status
                  type: varchar(32)
      rollback:
        - dropColumn:
            tableName: orders
            columnName: status
```

Формат может быть YAML, XML, JSON или обычный SQL.

## Что выбрать

```text
Flyway
+ обычный SQL, читается любым, кто знает базу
+ порог входа минимальный
− откат только в платной версии
− абстракции над диалектами нет

Liquibase
+ откат описывается явно и бесплатно
+ независимость от диалекта, если пользоваться абстракциями
+ контексты и метки: разные наборы для разных сред
− собственный формат, многословнее
− абстракция протекает, как только нужен специфичный SQL
```

Ответ на собеседовании, который честнее заученного: для типового проекта на одной
СУБД Flyway проще и потому чаще; Liquibase выигрывает там, где нужен
декларативный откат или поддержка нескольких СУБД.

## Правила работы с миграциями

### Применённая миграция неизменяема

Инструмент хранит контрольную сумму. Правка уже применённого файла даёт ошибку
проверки при следующем запуске — и это защита, а не помеха: на других стендах
скрипт уже выполнен в прежнем виде, и молча разъехавшаяся схема хуже падения.

Исправление делается новой миграцией. Команда `flyway repair` пересчитывает суммы,
но применять её нужно осознанно и редко.

### Одна миграция — одно логическое изменение

Так проще читать историю и понимать, какой скрипт что сломал.

### Миграции идут в том же коммите, что и код

Иначе выкладка разъезжается: код ждёт колонку, которой ещё нет.

### Номера версий и параллельные ветки

Две ветки с `V5__` дадут конфликт при слиянии. Распространённое решение — версия
по временной метке: `V20260917101500__add_status.sql`.

## Совместимость при постепенной выкладке

При rolling update две версии приложения какое-то время работают с одной схемой.
Значит, миграция должна быть совместима и со старым кодом тоже.

Приём называется expand/contract:

```text
релиз 1 (expand)
→ добавить новую колонку, nullable
→ код пишет в обе, читает из старой

релиз 2
→ перенести данные, код читает из новой

релиз 3 (contract)
→ удалить старую колонку
```

Переименование колонки одной командой ломает ещё не заменённые экземпляры, поэтому
разносится на три шага: добавить, синхронизировать, удалить.

## Опасные операции в PostgreSQL

Миграция берёт блокировки, и на живой базе это может означать простой.

```sql
ALTER TABLE orders ADD COLUMN status VARCHAR(32);
```

Добавление nullable-колонки без значения по умолчанию — операция на уровне
метаданных, быстрая. А вот так:

```sql
ALTER TABLE orders ADD COLUMN status VARCHAR(32) NOT NULL DEFAULT 'NEW';
```

В PostgreSQL 11 и новее это тоже быстро: значение по умолчанию хранится в
каталоге, таблица не переписывается. В более старых версиях перезаписывалась вся
таблица под эксклюзивной блокировкой.

Что действительно опасно:

```text
ALTER COLUMN TYPE          → переписывает таблицу под ACCESS EXCLUSIVE
CREATE INDEX               → блокирует запись на всё время построения
ADD CONSTRAINT ... CHECK   → полное сканирование под блокировкой
```

Обходные приёмы:

```sql
CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
```

Строит индекс без блокировки записи, но не может выполняться внутри транзакции —
в Flyway такая миграция помечается как нетранзакционная.

```sql
ALTER TABLE orders ADD CONSTRAINT chk_status CHECK (...) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT chk_status;
```

Сначала ограничение действует только для новых строк, затем проверка старых идёт
под слабой блокировкой.

Отдельный приём — `lock_timeout`:

```sql
SET lock_timeout = '3s';
```

Миграция, не получившая блокировку за три секунды, упадёт. Это лучше, чем очередь
из запросов, вставшая за ней: ожидающий `ALTER TABLE` блокирует и все обращения к
таблице, пришедшие после него.

## Данные и схема

Миграции данных тоже версионируются, но с оговорками. Массовое обновление в одной
транзакции блокирует строки и раздувает журнал, поэтому большие переносы делают
пакетами или отдельной задачей, а не скриптом при старте приложения.

Тестовые данные в миграции класть не стоит: они уедут в продакшен. Для них
существуют отдельные наборы — `spring.flyway.locations` с профилем или контексты
Liquibase.

## Тестирование

```java
@SpringBootTest
@Testcontainers
class MigrationTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");
}
```

Миграции выполняются на настоящей СУБД той же версии, что в продакшене, — это
единственный способ убедиться, что скрипт вообще применим. Подмена на H2 здесь
особенно бесполезна: именно в DDL диалекты расходятся сильнее всего.

Проверять стоит и накат на пустую базу, и накат поверх предыдущей версии схемы.

## Типичные ошибки

### Использовать ddl-auto: update в продакшене

Инструмент не умеет переименовывать, удалять и переносить данные, порядок действий
не определён, история изменений нигде не сохраняется.

### Править уже применённую миграцию

Контрольная сумма перестаёт совпадать, а на других стендах скрипт выполнен в
старом виде. Исправление — только новой миграцией.

### Класть миграцию отдельно от кода

Выкладка разъезжается: приложение ожидает колонку, которой ещё нет, или наоборот.

### Переименовывать колонку одной командой при rolling update

Старая версия приложения перестаёт работать. Нужен expand/contract в три релиза.

### Строить индекс без CONCURRENTLY на живой таблице

Запись блокируется на всё время построения.

### Не ограничивать lock_timeout

Ожидающая блокировки миграция выстраивает за собой очередь из всех запросов к
таблице, и сервис встаёт целиком.

### Делать массовое обновление данных одной транзакцией

Блокировки удерживаются, журнал растёт, старт приложения затягивается.

### Помещать тестовые данные в общие миграции

Они попадут в продакшен. Для этого есть отдельные наборы и профили.

### Нумеровать версии подряд в параллельных ветках

Слияние даёт конфликт версий. Временная метка в имени снимает проблему.

### Проверять миграции на H2

Диалекты DDL расходятся сильнее всего, и работающий на H2 скрипт может не
примениться на PostgreSQL.

## Краткая памятка

```text
схема версионируется так же, как код
таблица истории хранит применённые скрипты и их контрольные суммы
```

```text
ddl-auto
none / validate → прод
update          → локальная песочница
create-drop     → тесты
```

```text
Flyway    → V1__name.sql, обычный SQL, flyway_schema_history
            R__ повторяемые, U__ откат только в платной версии
Liquibase → changelog, откат описывается явно, независимость от диалекта
```

```text
применённая миграция неизменяема
исправление — новой миграцией
repair — осознанно и редко
версия по временной метке снимает конфликты веток
```

```text
expand / contract
1 добавить колонку nullable, писать в обе
2 перенести данные, читать из новой
3 удалить старую
```

```text
PostgreSQL
ADD COLUMN nullable         → быстро, метаданные
ALTER COLUMN TYPE           → переписывает таблицу
CREATE INDEX CONCURRENTLY   → без блокировки записи, вне транзакции
ADD CONSTRAINT NOT VALID + VALIDATE → в два шага
SET lock_timeout            → падать, а не выстраивать очередь
```

## Краткий ответ для собеседования

Схема базы версионируется набором скриптов, лежащих в репозитории рядом с кодом;
инструмент хранит в служебной таблице, какие из них уже применены, и накатывает
недостающие при старте. Это даёт воспроизводимость: на любой машине схема
приводится к состоянию, соответствующему версии кода.

Flyway описывает изменения обычным SQL с именами вида `V1__описание.sql` и хранит
историю в `flyway_schema_history`. Liquibase использует журнал изменений в YAML
или XML и умеет описывать откат явно. Для проекта на одной СУБД обычно берут
Flyway как более простой.

Механизм `ddl-auto: update` в Hibernate миграции не заменяет: он не умеет
переименовывать, удалять и переносить данные, а история изменений нигде не
сохраняется. В продакшене ставят `validate`, чтобы приложение падало при
расхождении схемы и сущностей.

Применённую миграцию нельзя править — контрольная сумма перестанет совпадать;
исправление оформляется новой миграцией.

При постепенной выкладке две версии приложения работают с одной схемой, поэтому
изменения делают совместимыми и разносят на релизы: сначала добавить, затем
перенести данные, затем удалить старое. На PostgreSQL отдельно следят за
блокировками: индекс строят с `CONCURRENTLY`, ограничение добавляют как
`NOT VALID` с последующей проверкой, а `lock_timeout` не даёт миграции выстроить
за собой очередь запросов.

## Вопросы на собеседовании

### 1. Зачем нужны миграции, если есть ddl-auto?

**Ответ:** `ddl-auto` умеет только достраивать. Он не переименовывает, не удаляет,
не переносит данные и не оставляет истории. Миграции дают воспроизводимое и
задокументированное состояние схемы.

### 2. Какое значение ddl-auto ставят в продакшене?

**Ответ:** `validate`. Оно ничего не меняет, но не даёт приложению стартовать, если
схема разошлась с сущностями.

### 3. Как Flyway понимает, что уже применено?

**Ответ:** по таблице `flyway_schema_history`, где для каждого скрипта хранится
версия и контрольная сумма.

### 4. Что произойдёт, если изменить применённую миграцию?

**Ответ:** контрольная сумма не совпадёт, и запуск завершится ошибкой. Это защита
от расхождения схем между стендами.

### 5. Чем versioned-миграция отличается от repeatable?

**Ответ:** первая применяется один раз в порядке версий, вторая — заново при любом
изменении её содержимого. Повторяемые удобны для представлений и функций.

### 6. Чем Flyway отличается от Liquibase?

**Ответ:** Flyway описывает изменения обычным SQL и не умеет бесплатно откатывать.
Liquibase использует собственный формат журнала, позволяет описать откат явно и
абстрагироваться от диалекта.

### 7. Когда выполняются миграции в Spring Boot?

**Ответ:** при старте контекста, до создания `EntityManagerFactory`, поэтому
проверка `validate` видит уже обновлённую схему.

### 8. Как избежать конфликта версий в параллельных ветках?

**Ответ:** нумеровать миграции временной меткой вместо последовательного числа.

### 9. Почему переименование колонки опасно при rolling update?

**Ответ:** старые экземпляры приложения ещё работают и обращаются к прежнему
имени. Нужен expand/contract: добавить, перенести, удалить в разных релизах.

### 10. Что такое expand/contract?

**Ответ:** разнесение несовместимого изменения на три шага — добавление нового
рядом со старым, перенос данных и удаление старого в следующем релизе.

### 11. Почему CREATE INDEX опасен на живой таблице?

**Ответ:** обычное построение блокирует запись на всё время. Нужен
`CREATE INDEX CONCURRENTLY`, который не выполняется внутри транзакции.

### 12. Зачем задавать lock_timeout в миграции?

**Ответ:** ожидающий блокировки `ALTER TABLE` блокирует все последующие обращения
к таблице. Лучше упасть через несколько секунд, чем остановить сервис.

### 13. Как добавить CHECK-ограничение без долгой блокировки?

**Ответ:** сначала как `NOT VALID`, затем отдельной командой `VALIDATE
CONSTRAINT`, которая проверяет существующие строки под слабой блокировкой.

### 14. Стоит ли класть тестовые данные в миграции?

**Ответ:** нет, они попадут в продакшен. Для них используют отдельные наборы,
подключаемые по профилю или контексту.

### 15. Как тестировать миграции?

**Ответ:** прогонять на настоящей СУБД в Testcontainers — и на пустой базе, и
поверх предыдущей версии схемы. На H2 диалект DDL отличается слишком сильно.
