# Индексы и планы запросов

## Зачем нужны индексы

Без индекса поиск строки означает чтение всей таблицы: база просматривает каждую
страницу и проверяет условие. На тысяче строк это незаметно, на десяти миллионах —
секунды.

Индекс — отдельная структура данных, которая хранит значения колонки в
упорядоченном виде вместе со ссылками на строки таблицы. Он позволяет найти нужные
строки, не читая всё остальное.

```text
без индекса → O(n), последовательное сканирование
B-tree      → O(log n), спуск по дереву
```

Цена — дополнительное место на диске и замедление записи: каждый `INSERT`,
`UPDATE` и `DELETE` обязан обновить все индексы таблицы.

---

## Как устроен B-tree

Основной тип индекса, который используется по умолчанию. Точнее — B+-дерево:
значения хранятся в листьях, внутренние узлы содержат только разделители.

```text
              [50 | 100]
             /     |     \
      [10|30]   [60|80]   [120|150]
        листья связаны в двусвязный список
```

Свойства, из которых следует всё остальное:

- дерево сбалансировано, глубина одинакова для любого значения;
- глубина растёт логарифмически: на миллионах строк это обычно 3–4 уровня;
- листья упорядочены и связаны между собой.

Последнее объясняет, почему B-tree поддерживает не только равенство:

```text
=            → спуск до значения
<, >, BETWEEN → спуск до границы, затем проход по листьям
ORDER BY      → чтение листьев по порядку, сортировка не нужна
LIKE 'abc%'   → префикс работает как диапазон
LIKE '%abc'   → не работает, начало строки неизвестно
IS NULL       → работает, NULL хранятся в индексе
```

Возможность отдать данные уже отсортированными — недооценённое свойство. Индекс
часто выбирают не ради фильтрации, а чтобы избежать сортировки при `ORDER BY` с
`LIMIT`.

## Селективность

Ключевая характеристика, определяющая пользу индекса. Селективность — доля строк,
которые остаются после фильтрации.

```text
WHERE email = 'a@b.c'      → одна строка из миллиона, высокая селективность
WHERE status = 'ACTIVE'    → половина таблицы, низкая селективность
WHERE gender = 'M'         → половина таблицы, индекс почти бесполезен
```

Здесь важно понять, почему при низкой селективности база сознательно игнорирует
индекс.

Чтение по индексу — случайный доступ: для каждой найденной записи нужно сходить в
таблицу за самой строкой. Последовательное чтение страниц идёт заметно быстрее.
Поэтому существует порог, после которого прочитать всю таблицу дешевле, чем
прыгать по ней. Обычно он находится в районе 5–10% строк, но точное значение
вычисляет планировщик на основе статистики.

Отсюда практический вывод: индекс на колонку с двумя-тремя различными значениями
почти всегда бесполезен — если только распределение не перекошено.

```sql
-- 99% строк имеют status = 'DONE', 1% — 'FAILED'
CREATE INDEX ON tasks (status) WHERE status = 'FAILED';
```

Частичный индекс на редкое значение — как раз тот случай, когда индекс по колонке
с низкой кардинальностью оправдан.

## Составные индексы

Индекс по нескольким колонкам. Порядок колонок в нём принципиален.

```sql
CREATE INDEX idx_orders ON orders (user_id, status, created_at);
```

### Правило левого префикса

Индекс работает, если условия покрывают колонки слева направо без пропусков.

```text
WHERE user_id = 1                                  → работает
WHERE user_id = 1 AND status = 'NEW'               → работает
WHERE user_id = 1 AND status = 'NEW' AND created_at > ... → работает

WHERE status = 'NEW'                               → префикс пропущен
WHERE created_at > ...                             → префикс пропущен
WHERE user_id = 1 AND created_at > ...             → частично: только user_id
```

Причина видна из устройства дерева: записи упорядочены сначала по `user_id`, внутри
одинакового `user_id` — по `status`, и лишь затем по `created_at`. Не зная
`user_id`, нельзя определить, где искать.

Аналогия — телефонный справочник, отсортированный по фамилии, затем по имени.
Найти всех Ивановых легко, найти всех Сергеев — только полным перебором.

### Диапазон обрывает индекс

Тонкость, которую спрашивают у тех, кто уверенно ответил про левый префикс.

```sql
WHERE user_id = 1 AND created_at > '2026-01-01' AND status = 'NEW'
```

С индексом `(user_id, status, created_at)` база использует `user_id` и `status`, а
диапазон по `created_at` применит последним. С индексом
`(user_id, created_at, status)` после диапазона по `created_at` колонка `status`
для поиска уже недоступна — внутри диапазона данные по ней не упорядочены.

```text
порядок колонок в составном индексе
1. колонки с равенством
2. колонка с диапазоном
3. колонки только для сортировки или выборки
```

### Порядок и сортировка

Составной индекс помогает и в `ORDER BY`, если направление совпадает:

```sql
CREATE INDEX ON orders (user_id, created_at DESC);

SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;
```

Сортировка не выполняется вовсе — данные уже лежат в нужном порядке.

## Стоимость записи

```text
таблица без индексов      → INSERT пишет одну структуру
таблица с пятью индексами → INSERT пишет шесть структур
```

Каждый индекс замедляет запись и занимает место. Отсюда обычные рекомендации:
индексировать то, что реально используется в запросах, и периодически удалять
неиспользуемые индексы.

В PostgreSQL найти их можно так:

```sql
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

Отдельный случай — `UPDATE`. В PostgreSQL обновление создаёт новую версию строки,
и она должна попасть во все индексы. Оптимизация HOT-update позволяет обойтись без
обновления индексов, но только если ни одна проиндексированная колонка не менялась
и на странице есть свободное место. Лишние индексы отбирают эту возможность.

## Когда индекс не используется

Частый вопрос: индекс создан, а план его игнорирует.

### Функция или выражение над колонкой

```sql
WHERE LOWER(email) = 'a@b.c'        -- индекс по email не подойдёт
WHERE created_at::date = '2026-01-01'
WHERE price * 2 > 100
```

Индекс хранит значения колонки, а не результат функции. Решения — индекс по
выражению либо переписывание условия:

```sql
CREATE INDEX ON users (LOWER(email));

WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
```

Второй вариант обычно предпочтительнее: диапазон работает с обычным индексом.

### Несовпадение типов

```sql
WHERE user_id = '123'    -- колонка bigint, литерал текстовый
```

Иногда приводится автоматически, иногда мешает использованию индекса. Особенно
заметно при сравнении `varchar` с числом.

### Поиск с ведущим шаблоном

```sql
WHERE name LIKE '%иван%'
```

Начало строки неизвестно, спуститься по дереву невозможно. Для полнотекстового
поиска нужен GIN, для поиска подстроки — расширение `pg_trgm`.

### Низкая селективность

Условие отбирает слишком много строк, и последовательное чтение дешевле.

### Маленькая таблица

На нескольких сотнях строк таблица помещается в пару страниц, и обращение к
индексу лишь добавит работы.

### Устаревшая статистика

Планировщик опирается на собранную статистику. Если она не отражает реальность,
оценки будут неверными.

```sql
ANALYZE orders;
```

Автовакуум обычно делает это сам, но после массовой загрузки данных стоит запустить
вручную.

### OR по разным колонкам

```sql
WHERE user_id = 1 OR email = 'a@b.c'
```

Иногда база строит bitmap-объединение двух индексов, иногда сваливается в
последовательное чтение. Надёжнее переписать через `UNION ALL`.

## Типы сканирования в PostgreSQL

```text
Seq Scan
→ последовательное чтение всей таблицы
→ оптимально, когда нужна большая часть строк

Index Scan
→ поиск по индексу, затем обращение к таблице за каждой строкой
→ оптимально при высокой селективности

Bitmap Index Scan + Bitmap Heap Scan
→ сначала собирается битовая карта нужных страниц
→ затем страницы читаются по порядку
→ промежуточный вариант: много строк, но не вся таблица
→ снижает случайный доступ

Index Only Scan
→ данные берутся прямо из индекса, к таблице обращения нет
→ возможно, если индекс содержит все нужные колонки
```

Bitmap-сканирование стоит понимать отдельно: это не «плохой индексный доступ», а
осознанный компромисс. База превращает множество случайных обращений в
последовательное чтение нужных страниц.

### Index Only Scan и видимость

Здесь особенность PostgreSQL, о которой полезно знать. Индекс не хранит информацию
о видимости версии строки для текущей транзакции — она лежит в самой таблице.
Поэтому Index Only Scan возможен только для страниц, помеченных в карте видимости
как полностью видимые.

```text
карта видимости актуальна → к таблице не обращаемся
страница помечена грязной → всё равно идём в таблицу
```

Карту обновляет `VACUUM`. Отсюда следствие: после массовых изменений Index Only
Scan может перестать работать, пока вакуум не отработает.

Расширить покрытие индекса можно, не увеличивая ключ:

```sql
CREATE INDEX ON orders (user_id) INCLUDE (total, created_at);
```

Колонки в `INCLUDE` хранятся только в листьях и не участвуют в поиске, но позволяют
обойтись без обращения к таблице.

## Другие типы индексов

```text
B-tree → универсальный, по умолчанию, поддерживает =, <, >, BETWEEN, сортировку

Hash   → только равенство, без сортировки и диапазонов
         с PostgreSQL 10 журналируется, но выигрыш перед B-tree невелик

GIN    → множественные значения в одном поле
         полнотекстовый поиск, jsonb, массивы

GiST   → геометрия, диапазоны, поиск ближайших соседей

BRIN   → очень компактный, хранит границы значений по блокам
         эффективен на больших таблицах с естественным порядком,
         например при вставке по возрастанию времени
```

Отдельно стоит знать про частичные индексы и индексы по выражению:

```sql
CREATE INDEX ON orders (created_at) WHERE status = 'PENDING';
CREATE INDEX ON users (LOWER(email));
```

Частичный индекс меньше, быстрее и дешевле в обслуживании, если запросы всегда
содержат то же условие.

## EXPLAIN

Показывает план, который планировщик собирается выполнить. Запрос при этом не
выполняется.

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```text
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=1 width=64)
  Index Cond: (user_id = 42)
```

Как читать:

```text
cost=0.43..8.45
→ 0.43  оценка стоимости получения первой строки
→ 8.45  оценка стоимости получения всех строк

rows=1
→ ожидаемое число строк

width=64
→ средний размер строки в байтах
```

Единицы стоимости условны — это не миллисекунды, а абстрактные величины, где за
единицу принято последовательное чтение одной страницы. Сравнивать их имеет смысл
только между планами одного запроса.

## EXPLAIN ANALYZE

Запрос действительно выполняется, и к оценкам добавляются фактические показатели.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
```

```text
Index Scan using idx_orders_user_id on orders
  (cost=0.43..8.45 rows=1 width=64)
  (actual time=0.021..0.023 rows=1 loops=1)
  Index Cond: (user_id = 42)
  Buffers: shared hit=4
Planning Time: 0.102 ms
Execution Time: 0.041 ms
```

Важное предупреждение: `EXPLAIN ANALYZE` для `UPDATE`, `DELETE` и `INSERT`
выполняет операцию по-настоящему. Проверять такие запросы нужно внутри транзакции с
последующим `ROLLBACK`.

### На что смотреть

**Расхождение `rows` и `actual rows`.** Главный диагностический признак. Если
планировщик ожидал 10 строк, а получил 500 000, план построен на неверных
предпосылках — и, скорее всего, выбран неудачно. Причина обычно в устаревшей
статистике или в корреляции между колонками, которую база не видит.

**`loops`.** Число повторов узла. Указанное время — среднее на одну итерацию, так
что реальные затраты равны `actual time × loops`. Большое значение `loops` внутри
Nested Loop часто и есть источник проблемы.

**`Buffers`.** `shared hit` — страницы, найденные в кеше, `shared read` — прочитанные
с диска. Показывает объём реальной работы лучше, чем время, которое зависит от
прогретости кеша.

**Узлы сортировки.** `Sort Method: external merge Disk: 24000kB` означает, что
сортировка не поместилась в `work_mem` и ушла на диск.

## Основные узлы плана

### Соединения

```text
Nested Loop
→ для каждой строки внешней таблицы ищем совпадения во внутренней
→ хорошо, когда внешних строк мало и есть индекс по внутренней
→ катастрофа, когда внешних строк много

Hash Join
→ по меньшей таблице строится хеш-таблица в памяти
→ по большей выполняется проход с проверкой
→ хорош для больших объёмов, требует памяти
→ только для равенства

Merge Join
→ обе стороны сортируются и сливаются
→ выгоден, когда данные уже отсортированы, например пришли из индекса
```

### Прочие

```text
Seq Scan        → полное чтение таблицы
Index Scan      → чтение по индексу с обращением к таблице
Index Only Scan → только индекс
Bitmap Scan     → битовая карта страниц
Sort            → сортировка
HashAggregate   → группировка через хеш-таблицу
GroupAggregate  → группировка по отсортированным данным
Limit           → ограничение
Materialize     → сохранение промежуточного результата
```

## Типичные ошибки

### Индексировать всё подряд

Каждый индекс замедляет запись, занимает место и мешает HOT-обновлениям.

### Ошибаться с порядком колонок в составном индексе

Индекс `(status, user_id)` не поможет запросу с условием только по `user_id`.

### Заводить отдельные индексы вместо составного

Три индекса по одной колонке не заменяют один составной. База может объединить их
через bitmap, но это дороже.

### Оборачивать колонку в функцию

`LOWER(email)` или `created_at::date` в условии отключают обычный индекс. Нужен
индекс по выражению или переписанное условие.

### Считать, что индекс всегда ускоряет

При низкой селективности последовательное чтение дешевле, и планировщик прав, когда
игнорирует индекс.

### Индексировать boolean или другую колонку с двумя значениями

Смысл появляется только при перекошенном распределении, и тогда лучше подходит
частичный индекс.

### Читать EXPLAIN без ANALYZE и делать выводы о времени

`EXPLAIN` показывает оценки, а не факты. Расхождение видно только с `ANALYZE`.

### Запускать EXPLAIN ANALYZE на модифицирующем запросе вне транзакции

Запрос выполнится по-настоящему.

### Принимать cost за миллисекунды

Это условные единицы, сопоставимые лишь в пределах одного запроса.

### Забывать про ANALYZE после массовой загрузки

Планировщик будет опираться на устаревшую статистику.

## Краткая памятка

```text
B-tree
→ =, <, >, BETWEEN, IS NULL, LIKE 'префикс%', ORDER BY
→ не работает: LIKE '%подстрока', функция над колонкой
```

```text
селективность
высокая → индекс полезен
низкая  → Seq Scan дешевле, порог около 5–10%
```

```text
составной индекс
→ правило левого префикса
→ порядок: равенства → диапазон → выборка
→ после диапазона следующие колонки для поиска недоступны
```

```text
типы сканирования
Seq Scan        вся таблица
Index Scan      индекс + обращение к таблице
Bitmap Scan     карта страниц, меньше случайного доступа
Index Only Scan только индекс, нужна актуальная карта видимости
```

```text
EXPLAIN         → план и оценки
EXPLAIN ANALYZE → фактическое выполнение
  rows vs actual rows → расхождение указывает на плохую статистику
  loops               → время умножается на число повторов
  Buffers             → hit из кеша, read с диска
```

```text
соединения
Nested Loop → мало внешних строк + индекс внутри
Hash Join   → большие объёмы, только равенство
Merge Join  → данные уже отсортированы
```

## Краткий ответ для собеседования

Индекс — отдельная упорядоченная структура со ссылками на строки таблицы, которая
позволяет находить данные без полного сканирования. По умолчанию используется
B-tree, где значения хранятся в листьях, а глубина растёт логарифмически. Помимо
равенства он поддерживает диапазоны, префиксный поиск и позволяет получить данные
уже отсортированными.

Польза индекса определяется селективностью — долей строк после фильтрации. Чтение
по индексу требует случайного доступа к таблице, поэтому при отборе большой части
строк последовательное сканирование оказывается дешевле, и планировщик сознательно
игнорирует индекс.

В составном индексе принципиален порядок колонок: действует правило левого
префикса, и условия должны покрывать колонки слева направо. Сначала ставят колонки
с равенством, затем колонку с диапазоном — после неё следующие колонки для поиска
уже недоступны, поскольку внутри диапазона данные по ним не упорядочены.

Индекс не используется, если колонка обёрнута в функцию, если шаблон поиска
начинается с подстановочного знака, при низкой селективности, на маленьких
таблицах и при устаревшей статистике.

`EXPLAIN` показывает план с оценками, `EXPLAIN ANALYZE` дополнительно выполняет
запрос и даёт фактические значения. Главный диагностический признак — расхождение
между ожидаемым и фактическим числом строк: оно означает, что план построен на
неверных предпосылках.

## Вопросы на собеседовании

### 1. Что такое индекс и какова его цена?

**Ответ:** упорядоченная структура со ссылками на строки, ускоряющая поиск. Цена —
дополнительное место и замедление записи, поскольку каждый `INSERT`, `UPDATE` и
`DELETE` обновляет все индексы таблицы.

### 2. Как устроен B-tree?

**Ответ:** сбалансированное дерево, где значения хранятся в листьях, а листья
связаны в список. Глубина одинакова для любого значения и растёт логарифмически.

### 3. Какие операции поддерживает B-tree?

**Ответ:** равенство, диапазоны, `BETWEEN`, `IS NULL`, префиксный `LIKE` и
сортировку. Не поддерживает поиск по подстроке с ведущим шаблоном.

### 4. Что такое селективность?

**Ответ:** доля строк, остающихся после фильтрации. Чем она выше, тем полезнее
индекс.

### 5. Почему база может проигнорировать индекс?

**Ответ:** при низкой селективности чтение по индексу требует случайного доступа к
таблице, и последовательное сканирование оказывается дешевле. Порог обычно в
районе 5–10% строк.

### 6. Что такое правило левого префикса?

**Ответ:** составной индекс работает, если условия покрывают его колонки слева
направо без пропусков. Запрос только по второй колонке индекс не задействует.

### 7. В каком порядке ставить колонки в составном индексе?

**Ответ:** сначала колонки с равенством, затем колонка с диапазоном, затем те, что
нужны только для сортировки или выборки.

### 8. Почему после диапазона остальные колонки индекса не работают для поиска?

**Ответ:** внутри диапазона значений первой колонки данные по следующим колонкам не
упорядочены, спуск по дереву по ним невозможен.

### 9. Почему условие с функцией отключает индекс?

**Ответ:** индекс хранит значения колонки, а не результат функции. Нужен индекс по
выражению либо переписывание условия в диапазон.

### 10. Почему LIKE '%текст%' не использует индекс?

**Ответ:** начало строки неизвестно, поэтому спуститься по дереву нельзя. Для
такого поиска применяют GIN с `pg_trgm`.

### 11. Чем Index Scan отличается от Bitmap Scan?

**Ответ:** `Index Scan` идёт в таблицу за каждой найденной строкой, создавая
случайный доступ. `Bitmap Scan` сначала собирает карту нужных страниц, затем
читает их по порядку, что выгоднее при большом числе строк.

### 12. Что такое Index Only Scan и когда он возможен?

**Ответ:** чтение данных прямо из индекса без обращения к таблице. Возможен, если
индекс содержит все нужные колонки и страницы помечены в карте видимости как
полностью видимые.

### 13. Зачем нужен INCLUDE в индексе?

**Ответ:** добавить колонки в листья индекса, не включая их в ключ поиска. Позволяет
получить Index Only Scan без увеличения размера ключа.

### 14. Что такое частичный индекс и когда он полезен?

**Ответ:** индекс с условием `WHERE`. Полезен, когда запросы всегда содержат то же
условие, например при поиске редкого статуса в перекошенном распределении.

### 15. Чем EXPLAIN отличается от EXPLAIN ANALYZE?

**Ответ:** `EXPLAIN` показывает план с оценками и не выполняет запрос.
`EXPLAIN ANALYZE` выполняет его и добавляет фактические значения.

### 16. Что означает cost в плане?

**Ответ:** условная оценка стоимости, где за единицу принято последовательное
чтение страницы. Не миллисекунды; сопоставима только между планами одного запроса.

### 17. На что смотреть в EXPLAIN ANALYZE в первую очередь?

**Ответ:** на расхождение между `rows` и `actual rows`. Большая разница означает,
что план построен на неверной оценке, обычно из-за устаревшей статистики.

### 18. Что означает loops в плане?

**Ответ:** число повторов узла. Указанное время относится к одной итерации, поэтому
общие затраты равны произведению времени на число повторов.

### 19. Какие есть способы соединения и когда что выбирается?

**Ответ:** `Nested Loop` — когда внешних строк мало и есть индекс по внутренней
таблице. `Hash Join` — для больших объёмов и только для равенства. `Merge Join` —
когда данные уже отсортированы.

### 20. Что делать, если после массовой загрузки запросы стали медленными?

**Ответ:** выполнить `ANALYZE`, чтобы обновить статистику. Планировщик мог
опираться на устаревшие данные о распределении значений.
