# Транзакции, изоляция и блокировки

## ACID

Четыре свойства, которые СУБД обещает транзакции.

### Atomicity

Транзакция выполняется целиком или не выполняется вовсе. Промежуточное состояние
снаружи не наблюдается.

Механизм — журнал упреждающей записи (WAL). Изменения сначала попадают в журнал, и
при откате или сбое база восстанавливает согласованное состояние по нему.

### Consistency

После завершения транзакции данные удовлетворяют всем ограничениям: первичным и
внешним ключам, `CHECK`, `NOT NULL`, уникальности.

Свойство отличается от остальных трёх: оно во многом на стороне приложения. База
следит только за объявленными ограничениями, а бизнес-инварианты вроде «сумма по
счетам не меняется при переводе» обеспечивает разработчик.

### Isolation

Параллельные транзакции не видят промежуточных результатов друг друга. Степень
изоляции регулируется уровнями — основная часть темы.

### Durability

После подтверждения `COMMIT` изменения переживут отключение питания. Обеспечивается
сбросом WAL на диск до подтверждения.

```text
Atomicity   → всё или ничего
Consistency → ограничения соблюдены
Isolation   → параллельные транзакции не мешают
Durability  → подтверждённое не теряется
```

## Аномалии

Уровни изоляции определяются тем, какие аномалии они допускают. Разбирать нужно
именно аномалии — уровни без них заучиваются как бессмысленная таблица.

### Dirty read

Транзакция читает данные, которые другая транзакция изменила, но ещё не
подтвердила.

```text
T1: UPDATE accounts SET balance = 0 WHERE id = 1
T2: SELECT balance FROM accounts WHERE id = 1   → 0
T1: ROLLBACK
```

`T2` приняла решение на основе значения, которого никогда не существовало.

### Non-repeatable read

Повторное чтение той же строки в одной транзакции даёт другое значение, потому что
между чтениями кто-то изменил и подтвердил её.

```text
T1: SELECT balance FROM accounts WHERE id = 1   → 100
T2: UPDATE accounts SET balance = 50 WHERE id = 1; COMMIT
T1: SELECT balance FROM accounts WHERE id = 1   → 50
```

### Phantom read

Повторное выполнение того же запроса возвращает **новые строки**, добавленные
другой транзакцией.

```text
T1: SELECT COUNT(*) FROM orders WHERE status = 'NEW'   → 5
T2: INSERT INTO orders (status) VALUES ('NEW'); COMMIT
T1: SELECT COUNT(*) FROM orders WHERE status = 'NEW'   → 6
```

Отличие от non-repeatable read: там менялась существующая строка, здесь меняется
состав выборки.

### Lost update

В стандарте не перечислен, но встречается чаще остальных.

```text
T1: SELECT quantity FROM products WHERE id = 1   → 10
T2: SELECT quantity FROM products WHERE id = 1   → 10
T1: UPDATE products SET quantity = 9  WHERE id = 1; COMMIT
T2: UPDATE products SET quantity = 9  WHERE id = 1; COMMIT
```

Продано два товара, списан один. Обновление `T1` потеряно.

Ключевая деталь: аномалия возникает из-за цикла «прочитал — посчитал в приложении —
записал». Если бы обе транзакции выполнили `UPDATE ... SET quantity = quantity - 1`,
проблемы бы не было — база взяла бы блокировку строки на время обновления.

### Write skew

Аномалия, которую устраняет только `SERIALIZABLE`. Транзакции читают пересекающиеся
данные, но пишут в разные строки, и вместе нарушают инвариант.

```text
Правило: хотя бы один врач должен оставаться на дежурстве.
Дежурят двое.

T1: проверяет, что дежурных двое → снимает себя
T2: проверяет, что дежурных двое → снимает себя
обе подтверждаются → дежурных нет
```

Каждая транзакция по отдельности корректна, конфликта записи нет — они изменили
разные строки. Нарушен именно инвариант, охватывающий несколько строк.

## Уровни изоляции

Стандарт SQL определяет четыре уровня через допустимые аномалии.

| Уровень | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| READ UNCOMMITTED | возможен | возможен | возможен |
| READ COMMITTED | нет | возможен | возможен |
| REPEATABLE READ | нет | нет | возможен |
| SERIALIZABLE | нет | нет | нет |

Это стандарт. Реальные СУБД от него отклоняются, и знание отклонений ценится выше
знания таблицы.

### Как это в PostgreSQL

```text
READ UNCOMMITTED
→ принимается синтаксически, но работает как READ COMMITTED
→ грязного чтения в PostgreSQL нет в принципе, оно невозможно из-за MVCC

READ COMMITTED
→ уровень по умолчанию
→ каждый оператор видит свой снимок данных
→ два SELECT в одной транзакции могут вернуть разное

REPEATABLE READ
→ снимок фиксируется на всю транзакцию
→ фантомов нет, вопреки стандартной таблице
→ это snapshot isolation
→ но write skew возможен
→ при конфликте записи транзакция падает с ошибкой 40001

SERIALIZABLE
→ поверх snapshot isolation добавлен контроль конфликтов (SSI)
→ устраняет и write skew
→ платой служат ошибки сериализации под нагрузкой
```

Два момента стоит проговаривать на собеседовании отдельно.

Первый: в PostgreSQL `REPEATABLE READ` не допускает фантомов, хотя стандартная
таблица их разрешает. Стандарт задаёт минимальные требования, а не точное
поведение.

Второй: `SERIALIZABLE` не выстраивает транзакции в очередь. Он выполняет их
параллельно и откатывает те, чей результат не соответствовал бы никакому
последовательному порядку. Поэтому приложение обязано уметь повторять транзакцию
после ошибки `40001` — иначе уровень бесполезен.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

## MVCC

Multiversion Concurrency Control — механизм, за счёт которого читающие транзакции
не блокируют пишущие и наоборот.

### Идея

Вместо изменения строки на месте база создаёт её новую версию. Старая остаётся,
пока её может видеть хоть какая-то транзакция.

```text
UPDATE
→ старая версия помечается устаревшей
→ создаётся новая версия
→ обе физически лежат в таблице
```

Каждая версия строки (в терминологии PostgreSQL — кортеж) хранит две служебные
колонки:

```text
xmin → номер транзакции, создавшей версию
xmax → номер транзакции, удалившей или заменившей версию
```

Видимость определяется сравнением с собственным снимком: транзакция видит версию,
если `xmin` уже подтверждён и виден ей, а `xmax` либо пуст, либо принадлежит
транзакции, которая для неё ещё не завершилась.

Отсюда прямо следует, почему грязное чтение в PostgreSQL невозможно: версия,
созданная неподтверждённой транзакцией, просто не проходит проверку видимости.

### Снимок

```text
READ COMMITTED  → новый снимок на каждый оператор
REPEATABLE READ → один снимок на всю транзакцию
```

Это и объясняет разницу между уровнями изнутри, а не через таблицу аномалий.

### Следствия

**Раздувание таблиц.** Старые версии занимают место, пока их не удалит `VACUUM`.
Таблица, которую часто обновляют, растёт, даже если число строк постоянно.

**Долгие транзакции опасны.** Пока открыта транзакция со старым снимком, вакуум не
может удалить версии, которые она теоретически способна увидеть, — во всей базе.
Одна забытая открытая транзакция раздувает всё.

```sql
SELECT pid, state, xact_start, query
FROM pg_stat_activity
WHERE state = 'idle in transaction';
```

Состояние `idle in transaction` — типичный симптом: приложение открыло транзакцию
и не закрыло. Отсюда практическое правило — держать транзакции короткими и не
выполнять внутри них обращения к внешним сервисам.

**`COUNT(*)` не мгновенный.** База обязана проверить видимость каждой версии,
поэтому точный подсчёт строк требует сканирования.

## Блокировки

MVCC решает конфликты чтения и записи, но конфликты записи с записью решают
блокировки.

### Уровень строки

```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
```

Блокирует строки до конца транзакции. Другая транзакция, пытающаяся обновить их
или взять ту же блокировку, будет ждать.

```text
FOR UPDATE       → полная блокировка строки
FOR NO KEY UPDATE → слабее, не мешает внешним ключам
FOR SHARE        → разделяемая, читать можно, менять нельзя
FOR KEY SHARE    → самая слабая, защищает только ключ
```

Обычный `UPDATE` берёт блокировку автоматически. Явный `FOR UPDATE` нужен, когда
между чтением и записью выполняется вычисление в приложении.

### NOWAIT и SKIP LOCKED

```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- ошибка сразу, если строка занята

SELECT * FROM jobs WHERE status = 'NEW' FOR UPDATE SKIP LOCKED LIMIT 10;
-- пропустить занятые строки
```

`SKIP LOCKED` — стандартный способ построить очередь задач поверх таблицы:
несколько обработчиков разбирают разные строки, не мешая друг другу.

### Уровень таблицы

Берутся автоматически. `SELECT` берёт `ACCESS SHARE`, `UPDATE` —
`ROW EXCLUSIVE`, а вот `ALTER TABLE` и `DROP TABLE` — `ACCESS EXCLUSIVE`, который
конфликтует со всем.

Практическое следствие для миграций: `ALTER TABLE` ждёт завершения всех
транзакций, работающих с таблицей, и одновременно блокирует все новые. Одна долгая
транзакция превращает быструю миграцию в остановку сервиса. Для этого существует
`lock_timeout`.

## Пессимистическая и оптимистическая блокировка

Два подхода к защите от потерянного обновления.

### Пессимистическая

Блокируем сразу, предполагая конфликт.

```sql
BEGIN;
SELECT quantity FROM products WHERE id = 1 FOR UPDATE;
-- вычисления в приложении
UPDATE products SET quantity = 9 WHERE id = 1;
COMMIT;
```

Надёжно, но строка заблокирована на всё время транзакции, а остальные ждут. При
высокой конкуренции превращается в узкое место.

### Оптимистическая

Не блокируем, но при записи проверяем, что данные не изменились. Обычно через
колонку версии.

```sql
UPDATE products
SET quantity = 9, version = version + 1
WHERE id = 1 AND version = 7;
```

Если обновлено ноль строк — кто-то опередил, и операцию нужно повторить.

```text
пессимистическая
→ блокируем заранее
→ конфликты редки → лишнее ожидание
→ конфликты часты → предсказуемо

оптимистическая
→ блокировок нет
→ конфликты редки → выигрыш
→ конфликты часты → много повторов
```

Это ровно тот же механизм, что `ETag` и `If-Match` в HTTP: там версия ресурса, тут
версия строки, и в обоих случаях несовпадение означает, что данные успели
измениться.

## Дедлоки

### Как возникает

Две транзакции берут одни и те же блокировки в разном порядке.

```text
T1: UPDATE accounts SET ... WHERE id = 1   → заблокировала строку 1
T2: UPDATE accounts SET ... WHERE id = 2   → заблокировала строку 2
T1: UPDATE accounts SET ... WHERE id = 2   → ждёт T2
T2: UPDATE accounts SET ... WHERE id = 1   → ждёт T1
```

Цикл ожидания замкнулся, сам он не разорвётся.

### Обнаружение

PostgreSQL находит дедлоки автоматически. Детектор запускается не сразу: сначала
транзакция ждёт `deadlock_timeout` (по умолчанию одна секунда), и только затем
строится граф ожиданий. Задержка сделана намеренно — построение графа стоит
дорого, а подавляющее большинство ожиданий разрешается само.

Обнаружив цикл, база выбирает жертву и откатывает её:

```text
ERROR: deadlock detected
SQLSTATE: 40P01
```

Вторая транзакция продолжает работу. Приложение должно быть готово повторить
откатанную.

### Как избегать

```text
единый порядок обращения к строкам
→ если все транзакции берут блокировки по возрастанию id, цикл невозможен

короткие транзакции
→ меньше окно, в котором держатся блокировки

брать блокировки одним запросом
→ SELECT ... WHERE id IN (1, 2) FOR UPDATE ORDER BY id

не обращаться к внешним сервисам внутри транзакции
→ HTTP-вызов с таймаутом в 30 секунд держит блокировки всё это время

NOWAIT или lock_timeout
→ лучше быстро упасть, чем ждать
```

Единый порядок — самое действенное средство. Если два счёта всегда блокируются в
порядке возрастания идентификатора, взаимного ожидания не возникнет в принципе.

### Дедлок на пуле соединений

Отдельный случай, который к базе отношения не имеет и потому дольше ищется.

```text
пул из 10 соединений
каждый поток берёт соединение, начинает транзакцию
и внутри просит второе соединение

10 потоков заняли все 10 соединений
все ждут одиннадцатое
```

База ничего не обнаружит — с её точки зрения дедлока нет, просто десять открытых
транзакций. Приложение зависнет до таймаута пула.

Причины обычно две: вложенные транзакции с `REQUIRES_NEW` и параллельные запросы
внутри транзакции.

## Savepoints

Точка внутри транзакции, к которой можно откатиться, не отменяя всё.

```sql
BEGIN;
INSERT INTO orders ...;
SAVEPOINT sp1;
INSERT INTO order_items ...;   -- ошибка
ROLLBACK TO sp1;
INSERT INTO order_items ...;   -- другой вариант
COMMIT;
```

Важная особенность PostgreSQL: после любой ошибки транзакция переходит в
нерабочее состояние, и все последующие операторы отклоняются до отката. Savepoint
— единственный способ продолжить работу после ошибки внутри транзакции.

На этом же механизме построена вложенность транзакций в Spring.

## Типичные ошибки

### Считать READ COMMITTED достаточным для чтения-изменения-записи

Между `SELECT` и `UPDATE` данные могут измениться. Нужна блокировка `FOR UPDATE`
или версионирование.

### Считать, что REPEATABLE READ в PostgreSQL допускает фантомы

Не допускает. Стандартная таблица описывает минимальные требования, а не реальное
поведение конкретной СУБД.

### Считать SERIALIZABLE очередью

Транзакции выполняются параллельно, конфликтующие откатываются с ошибкой `40001`.
Без логики повтора уровень бесполезен.

### Не обрабатывать ошибки сериализации и дедлока

`40001` и `40P01` — штатные ситуации при высоких уровнях изоляции, а не сбои.

### Держать транзакцию открытой долго

Блокирует вакуум во всей базе, раздувает таблицы и мешает миграциям.

### Вызывать внешние сервисы внутри транзакции

HTTP-запрос с большим таймаутом держит блокировки и соединение всё это время.

### Обновлять строки в разном порядке

Прямой путь к дедлоку. Порядок должен быть единым.

### Использовать READ UNCOMMITTED ради скорости

В PostgreSQL он и так работает как `READ COMMITTED`, выигрыша нет.

### Продолжать работу после ошибки внутри транзакции

Все последующие операторы будут отклонены. Нужен savepoint или откат.

### Полагаться на COUNT(*) как на мгновенную операцию

Из-за MVCC требуется проверка видимости каждой версии.

## Краткий ответ для собеседования

ACID — четыре свойства транзакции. Атомарность обеспечивается журналом
упреждающей записи и означает выполнение целиком или отсутствие эффекта.
Согласованность — соблюдение ограничений, причём бизнес-инварианты остаются на
стороне приложения. Изоляция определяет, насколько параллельные транзакции видят
друг друга. Долговечность гарантирует сохранность подтверждённых данных.

Уровни изоляции описываются через допустимые аномалии: грязное чтение,
неповторяемое чтение и фантомы. Стандартная таблица задаёт минимальные
требования, и реальные СУБД от неё отклоняются. В PostgreSQL грязного чтения нет
ни на одном уровне из-за MVCC, а `REPEATABLE READ` не допускает и фантомов, так
как фиксирует снимок на всю транзакцию. При этом на нём возможен write skew — его
устраняет только `SERIALIZABLE`.

MVCC означает, что обновление создаёт новую версию строки, а старая остаётся,
пока её может увидеть какая-либо транзакция. Видимость определяется служебными
полями `xmin` и `xmax`. Отсюда два практических следствия: старые версии
накапливаются и удаляются вакуумом, а долгая открытая транзакция мешает вакууму
во всей базе.

Конфликты записи решаются блокировками. Пессимистический подход берёт блокировку
заранее через `SELECT FOR UPDATE`, оптимистический не блокирует, но проверяет
версию строки при обновлении и повторяет операцию при несовпадении.

Дедлок возникает, когда транзакции берут блокировки в разном порядке. PostgreSQL
обнаруживает его по графу ожиданий после `deadlock_timeout` и откатывает одну из
транзакций с кодом `40P01`. Главное средство профилактики — единый порядок
обращения к строкам и короткие транзакции.

## Вопросы на собеседовании

### 1. Что такое ACID?

**Ответ:** атомарность, согласованность, изоляция и долговечность. Атомарность и
долговечность обеспечиваются журналом упреждающей записи, изоляция — уровнями,
согласованность частично лежит на приложении.

### 2. Чем non-repeatable read отличается от phantom read?

**Ответ:** в первом случае изменилось значение существующей строки, во втором
изменился состав выборки — появились новые строки.

### 3. Что такое lost update?

**Ответ:** две транзакции читают значение, вычисляют новое и записывают; результат
первой теряется. Возникает из-за цикла чтение-вычисление-запись на стороне
приложения.

### 4. Какой уровень изоляции используется в PostgreSQL по умолчанию?

**Ответ:** `READ COMMITTED`. Каждый оператор видит собственный снимок данных.

### 5. Возможно ли грязное чтение в PostgreSQL?

**Ответ:** нет, ни на одном уровне. `READ UNCOMMITTED` принимается синтаксически,
но работает как `READ COMMITTED`, а MVCC не даёт увидеть неподтверждённую версию.

### 6. Допускает ли REPEATABLE READ фантомы в PostgreSQL?

**Ответ:** нет. Снимок фиксируется на всю транзакцию, поэтому новые строки не
появятся. Стандарт задаёт минимальные требования, а реализация может быть строже.

### 7. Что не защищает REPEATABLE READ?

**Ответ:** write skew — ситуацию, когда транзакции читают пересекающиеся данные, но
пишут в разные строки и вместе нарушают инвариант.

### 8. Ставит ли SERIALIZABLE транзакции в очередь?

**Ответ:** нет. Они выполняются параллельно, а конфликтующие откатываются с ошибкой
`40001`. Приложение обязано уметь повторять транзакцию.

### 9. Что такое MVCC?

**Ответ:** механизм, при котором обновление создаёт новую версию строки, а старая
сохраняется, пока видна каким-либо транзакциям. Позволяет читателям не блокировать
писателей.

### 10. Что хранят xmin и xmax?

**Ответ:** номера транзакций, создавшей и удалившей версию строки. По ним
определяется видимость версии для конкретного снимка.

### 11. Чем опасна долгая открытая транзакция?

**Ответ:** вакуум не может удалить версии строк, которые она способна увидеть, — во
всей базе. Таблицы раздуваются, а `ALTER TABLE` не может получить блокировку.

### 12. Почему COUNT(*) в PostgreSQL не мгновенный?

**Ответ:** нужно проверить видимость каждой версии строки для текущего снимка,
поэтому требуется сканирование.

### 13. Зачем нужен SELECT FOR UPDATE?

**Ответ:** заблокировать строки до конца транзакции, когда между чтением и записью
выполняются вычисления в приложении. Обычный `UPDATE` берёт блокировку сам.

### 14. Для чего нужен SKIP LOCKED?

**Ответ:** пропускать заблокированные строки. Стандартный способ реализовать
очередь задач, где несколько обработчиков разбирают разные строки.

### 15. Чем оптимистическая блокировка отличается от пессимистической?

**Ответ:** пессимистическая блокирует заранее и заставляет остальных ждать.
Оптимистическая не блокирует, а проверяет версию при записи и повторяет операцию
при конфликте. Первая выгодна при частых конфликтах, вторая — при редких.

### 16. Как реализуется оптимистическая блокировка?

**Ответ:** колонкой версии, которая проверяется в `WHERE` и увеличивается при
обновлении. Ноль обновлённых строк означает, что данные успели измениться.

### 17. Как возникает дедлок?

**Ответ:** транзакции берут одни и те же блокировки в разном порядке, и цикл
ожидания замыкается.

### 18. Как PostgreSQL обнаруживает дедлок?

**Ответ:** после ожидания в `deadlock_timeout` строит граф ожиданий и при
обнаружении цикла откатывает одну из транзакций с кодом `40P01`. Задержка нужна,
потому что построение графа дорого, а большинство ожиданий разрешается само.

### 19. Как избежать дедлоков?

**Ответ:** обращаться к строкам в едином порядке, держать транзакции короткими, не
выполнять внутри них внешние вызовы, использовать `lock_timeout` или `NOWAIT`.

### 20. Может ли дедлок возникнуть без участия базы?

**Ответ:** да, на пуле соединений: транзакции удерживают все соединения и ждут
дополнительное. База такой ситуации не видит, приложение зависает до таймаута
пула.

### 21. Что происходит после ошибки внутри транзакции в PostgreSQL?

**Ответ:** транзакция переходит в нерабочее состояние, и все последующие операторы
отклоняются. Продолжить можно только откатом или возвратом к savepoint.
