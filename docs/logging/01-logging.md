# Логирование

## Зачем оно нужно

Отладчик доступен на своей машине. В продакшене его нет: приложение работает в
контейнере, воспроизвести ситуацию не получается, а ошибка возникла ночью у одного
пользователя из тысячи.

Логи — единственный способ узнать, что происходило.

```text
что случилось
когда
в каком порядке
с какими данными
в каком запросе
```

Отсюда критерий качества лога: по нему можно восстановить ход событий, не имея
доступа к работающей системе.

---

## Фасад и реализация

```text
SLF4J     → фасад, набор интерфейсов
Logback   → реализация, используется в Spring Boot по умолчанию
Log4j2    → альтернативная реализация
java.util.logging → встроенная в JDK, применяется редко
```

Код обращается только к фасаду:

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);
```

### Зачем нужен фасад

Причина не в том, что реализацию хочется менять — на практике её меняют редко.
Причина в библиотеках.

Приложение подключает десяток зависимостей, и каждая логирует по-своему. Если бы
все они писали в свою реализацию, приложение получило бы несколько независимых
систем логирования с разными настройками и разными файлами.

SLF4J решает это через мосты: библиотека пишет в свой API, мост перенаправляет
вызов в SLF4J, а тот — в единственную реализацию. Все логи приложения оказываются в
одном месте с общей конфигурацией.

```text
библиотека на JCL → jcl-over-slf4j ─┐
библиотека на JUL → jul-to-slf4j   ─┼→ SLF4J → Logback
библиотека на Log4j → log4j-over-slf4j ─┘
```

Spring Boot собирает эту конструкцию сам через `spring-boot-starter-logging`.
Практическое следствие: при подключении Log4j2 нужно исключить стандартный стартер,
иначе в classpath окажутся две реализации.

### Lombok

```java
@Slf4j
public class OrderService {
    // поле log создаётся автоматически
}
```

Один из немногих случаев, где Lombok в проекте с Spring уместен без оговорок.

## Уровни

```text
TRACE → подробности внутренней работы, в проде выключен
DEBUG → диагностическая информация для разработчика
INFO  → значимые события нормальной работы
WARN  → неожиданное, но не помешавшее работе
ERROR → операция не выполнена, требуется внимание
```

Разграничение на практике:

```java
log.trace("Проверка правила {} для заказа {}", rule, orderId);
log.debug("Загружено {} позиций заказа {}", items.size(), orderId);
log.info("Заказ {} создан, сумма {}", orderId, total);
log.warn("Повторная попытка {} из {} для платежа {}", attempt, max, paymentId);
log.error("Не удалось обработать заказ {}", orderId, exception);
```

Два вопроса, которые решаются неверно чаще всего.

**Что относить к INFO.** Не каждый шаг, а события, интересные при разборе инцидента:
создание заказа, смена статуса, старт и остановка приложения. Если INFO пишется на
каждый вызов метода, лог становится нечитаемым и дорогим.

**Когда WARN, а когда ERROR.** WARN — ситуация обработана, работа продолжается:
сработал повтор, значение взято из кеша, сервис деградировал. ERROR — операция не
выполнена и кто-то должен разобраться. Если по ERROR не нужно ничего предпринимать,
это не ERROR.

### Иерархия логгеров

Логгеры образуют дерево по именам пакетов, и уровень наследуется:

```yaml
logging:
  level:
    root: INFO
    com.example: DEBUG
    org.hibernate.SQL: DEBUG
    org.springframework.web: WARN
```

Уровни можно менять на работающем приложении через Actuator:

```text
POST /actuator/loggers/com.example
{"configuredLevel": "DEBUG"}
```

Это один из самых полезных приёмов в эксплуатации: включить подробности для
конкретного пакета, воспроизвести проблему, выключить обратно — без перезапуска.

## Параметризованные сообщения

```java
log.debug("Заказ {} обработан за {} мс", orderId, duration);
```

Не конкатенация и не форматирование строки. Причина техническая.

```java
log.debug("Заказ " + order + " обработан");
```

Здесь строка собирается **всегда**, даже если уровень DEBUG отключён. Вызывается
`toString()` объекта, выделяется память, склеиваются строки — и результат
отбрасывается.

С плейсхолдерами форматирование выполняется только после проверки уровня. Если
DEBUG выключен, ничего не происходит.

```text
конкатенация     → работа выполняется всегда
плейсхолдеры {}  → работа выполняется, только если уровень включён
```

Разница незаметна на редких вызовах и весьма заметна в цикле на миллион итераций,
особенно если `toString()` сущности тянет ленивые связи.

### Когда нужна явная проверка

```java
if (log.isDebugEnabled()) {
    log.debug("Состояние: {}", buildExpensiveReport());
}
```

Плейсхолдеры не спасают, если аргумент вычисляется дорогим методом — он будет
вызван до передачи в логгер. В таких случаях проверка уровня оправдана.

## Логирование исключений

```java
// правильно
log.error("Не удалось обработать заказ {}", orderId, e);
```

Исключение передаётся последним аргументом без плейсхолдера. SLF4J распознаёт его и
выводит полный стек.

```java
// неправильно
log.error("Ошибка: " + e.getMessage());     // стек потерян
log.error("Ошибка: {}", e.getMessage());    // стек потерян
e.printStackTrace();                        // мимо системы логирования
```

`getMessage()` без стека почти бесполезен: непонятно, откуда исключение пришло.
`printStackTrace()` пишет в системный поток вывода, минуя конфигурацию, — в файл
или в агрегатор это не попадёт.

### Не логировать и пробрасывать одновременно

```java
try {
    process(order);
} catch (Exception e) {
    log.error("Ошибка обработки", e);
    throw e;                             // будет залогировано ещё раз выше
}
```

Одно исключение попадёт в лог дважды или трижды, и при разборе инцидента возникнет
ощущение нескольких независимых сбоев.

Правило: логирует тот, кто обрабатывает. Если исключение пробрасывается дальше,
логировать его здесь не нужно — достаточно добавить контекст, обернув в другое
исключение.

## Что не должно попадать в логи

```text
пароли, токены, ключи API
номера карт, CVV
персональные данные: паспорта, адреса, телефоны
содержимое запросов и ответов целиком
```

Логи попадают в системы агрегации, к ним имеет доступ существенно больше людей, чем
к базе, и хранятся они долго. Утечка через логи — распространённый сценарий.

```java
// плохо
log.debug("Запрос: {}", request);           // внутри может быть что угодно

// лучше
log.debug("Создание заказа: клиент={}, позиций={}", customerId, items.size());
```

Отдельная опасность — логирование сущностей целиком. Метод `toString()`,
сгенерированный Lombok, включает все поля, а у сущности Hibernate ещё и обращается
к ленивым связям.

Если чувствительные данные всё же нужны для диагностики, их маскируют:
`4111********1111`.

## MDC и сквозной идентификатор

Проблема: в логе тысячи строк от параллельных запросов, и понять, какие относятся к
одному, невозможно.

Решение — Mapped Diagnostic Context: набор пар «ключ-значение», привязанный к
потоку и автоматически добавляемый в каждую запись.

```java
MDC.put("traceId", UUID.randomUUID().toString());
try {
    process(request);
} finally {
    MDC.clear();          // обязательно
}
```

```text
2026-09-06 12:00:01 INFO  [traceId=a1b2c3] Заказ 42 создан
2026-09-06 12:00:01 DEBUG [traceId=a1b2c3] Списание 1200 руб.
```

Теперь все записи одного запроса выбираются по одному фильтру.

Обычно идентификатор устанавливается в фильтре, а если приходит из заголовка
`X-Request-Id`, берётся оттуда — тогда след прослеживается через несколько
сервисов.

### MDC и потоки

Важная деталь: MDC реализован через `ThreadLocal`.

```text
переход в другой поток → контекст теряется
@Async, ExecutorService, parallelStream → MDC пуст
```

Это та же особенность, что и с транзакциями Spring: и то и другое привязано к
потоку. Решается копированием контекста при передаче задачи:

```java
Map<String, String> context = MDC.getCopyOfContextMap();

executor.submit(() -> {
    MDC.setContextMap(context);
    try {
        doWork();
    } finally {
        MDC.clear();
    }
});
```

Очистка обязательна: в пуле поток переиспользуется, и остатки контекста попадут в
логи следующей задачи.

Готовые решения — Micrometer Tracing и Spring Cloud Sleuth в старых версиях — делают
это автоматически и добавляют распространение идентификатора между сервисами.

## Структурированное логирование

Обычная строка удобна человеку и неудобна машине: чтобы отфильтровать записи по
идентификатору заказа, приходится разбирать текст регулярными выражениями.

Структурированный формат решает это:

```json
{
  "timestamp": "2026-09-06T12:00:01.123Z",
  "level": "INFO",
  "logger": "com.example.OrderService",
  "message": "Заказ создан",
  "traceId": "a1b2c3",
  "orderId": 42,
  "service": "order-service"
}
```

Поля индексируются в системе агрегации, и по ним строятся запросы и графики без
разбора текста.

Практический подход: в локальной разработке человекочитаемый формат, в
продакшене — JSON. Настраивается профилями.

## Appender-ы

```text
ConsoleAppender  → стандартный вывод
FileAppender     → файл
RollingFileAppender → файл с ротацией по размеру и времени
AsyncAppender    → буферизация и запись в отдельном потоке
```

Для контейнеров стандартом стал вывод в консоль: сбором и хранением занимается
инфраструктура, а не приложение. Запись в файл внутри контейнера обычно избыточна.

`AsyncAppender` полезен под нагрузкой — синхронная запись блокирует поток запроса.
Цена: при аварийном завершении часть буфера теряется, а при переполнении очереди
записи отбрасываются.

## Почему не System.out.println

```text
нет уровней          → нельзя приглушить в проде
нет времени и потока → непонятен порядок и источник
нет имени класса     → неизвестно, откуда запись
нет ротации          → файл растёт бесконечно
нет MDC              → нельзя связать записи запроса
не настраивается     → нельзя перенаправить или отключить
синхронный вывод     → блокирует поток
```

Единственное допустимое применение — короткие эксперименты, не попадающие в
репозиторий.

## Типичные ошибки

### Конкатенация вместо плейсхолдеров

Строка собирается независимо от уровня.

### Терять стек при логировании исключения

Исключение передаётся отдельным аргументом, а не через `getMessage()`.

### Логировать и пробрасывать

Одно исключение попадёт в лог несколько раз.

### Использовать printStackTrace

Вывод идёт мимо системы логирования и не попадает в агрегатор.

### Писать чувствительные данные

Логи доступнее базы и хранятся долго.

### Логировать сущности целиком

`toString()` может тянуть ленивые связи и раскрывать все поля.

### Ставить INFO на каждый шаг

Лог становится нечитаемым, а объём — дорогим.

### Использовать ERROR там, где действий не требуется

Обесценивает уровень и мониторинг на его основе.

### Забывать MDC.clear

В пуле поток переиспользуется, и контекст протечёт в чужие записи.

### Ожидать, что MDC переживёт переход в другой поток

Он привязан к потоку через `ThreadLocal`.

### Логировать в горячем цикле

Даже отключённый уровень стоит вызова метода, а включённый — записи.

## Краткий ответ для собеседования

SLF4J — фасад, Logback — реализация, используемая в Spring Boot по умолчанию.
Фасад нужен прежде всего для того, чтобы логи подключённых библиотек, написанных под
разные API, попадали в одну систему через мосты.

Уровни различаются назначением: TRACE и DEBUG — диагностика, INFO — значимые
события работы, WARN — обработанные отклонения, ERROR — невыполненная операция,
требующая внимания.

Сообщения пишутся с плейсхолдерами, а не конкатенацией: при конкатенации строка
собирается всегда, даже когда уровень отключён, тогда как форматирование с
плейсхолдерами выполняется только после проверки уровня.

Исключение передаётся отдельным последним аргументом — иначе теряется стек вызовов.
Логировать исключение и одновременно пробрасывать его не нужно: оно попадёт в лог
несколько раз.

В логи не должны попадать пароли, токены, номера карт и персональные данные,
поскольку логи доступнее базы и хранятся долго.

Для связывания записей одного запроса используется MDC — контекст, привязанный к
потоку и добавляемый в каждую запись. Поскольку он основан на `ThreadLocal`, при
передаче работы в другой поток контекст нужно копировать вручную.

В продакшене логи обычно пишут в консоль в формате JSON: структурированные поля
индексируются системой агрегации и позволяют строить запросы без разбора текста.

## Вопросы на собеседовании

### 1. Зачем нужен SLF4J, если есть Logback?

**Ответ:** чтобы логи всех библиотек попадали в одну систему. Библиотеки написаны
под разные API, и мосты перенаправляют их вызовы в SLF4J, а тот — в единственную
реализацию.

### 2. Какая реализация используется в Spring Boot по умолчанию?

**Ответ:** Logback, через `spring-boot-starter-logging`.

### 3. Какие есть уровни и когда какой применять?

**Ответ:** TRACE и DEBUG для диагностики, INFO для значимых событий, WARN для
обработанных отклонений, ERROR для невыполненных операций, требующих вмешательства.

### 4. Чем WARN отличается от ERROR?

**Ответ:** при WARN работа продолжается — сработал повтор или запасной путь. ERROR
означает, что операция не выполнена. Если по записи не нужно предпринимать
действий, это не ERROR.

### 5. Почему нельзя писать log.debug("текст " + value)?

**Ответ:** строка будет собрана всегда, даже если уровень отключён. С
плейсхолдерами форматирование происходит только после проверки уровня.

### 6. Когда нужна проверка isDebugEnabled?

**Ответ:** когда аргумент вычисляется дорогим методом — он будет вызван до передачи
в логгер, и плейсхолдеры от этого не спасут.

### 7. Как правильно логировать исключение?

**Ответ:** передать его последним аргументом без плейсхолдера, чтобы SLF4J вывел
полный стек. `getMessage()` без стека почти бесполезен.

### 8. Чем плох printStackTrace?

**Ответ:** вывод идёт в системный поток мимо конфигурации логирования, поэтому не
попадает в файл или агрегатор и не содержит контекста.

### 9. Почему не стоит логировать и пробрасывать исключение?

**Ответ:** оно будет записано несколько раз на разных уровнях стека, и при разборе
инцидента возникнет впечатление нескольких независимых сбоев.

### 10. Что нельзя писать в логи?

**Ответ:** пароли, токены, ключи, номера карт, персональные данные и тела запросов
целиком. Логи доступнее базы и хранятся долго.

### 11. Чем опасно логирование сущности целиком?

**Ответ:** сгенерированный `toString()` выводит все поля и может обращаться к
ленивым связям, вызывая дополнительные запросы или исключение.

### 12. Что такое MDC?

**Ответ:** контекст диагностики, набор пар «ключ-значение», привязанный к потоку и
добавляемый в каждую запись лога. Используется для сквозного идентификатора
запроса.

### 13. Что произойдёт с MDC при переходе в другой поток?

**Ответ:** контекст потеряется, поскольку основан на `ThreadLocal`. При передаче
задачи в пул его нужно копировать вручную.

### 14. Почему обязателен MDC.clear?

**Ответ:** потоки в пуле переиспользуются, и остатки контекста попадут в записи
следующей задачи.

### 15. Зачем нужен сквозной идентификатор запроса?

**Ответ:** чтобы выбрать все записи, относящиеся к одному запросу. Если он
приходит в заголовке, след прослеживается через несколько сервисов.

### 16. Что такое структурированное логирование?

**Ответ:** запись в машиночитаемом формате, обычно JSON, где поля индексируются
системой агрегации и доступны для запросов без разбора текста.

### 17. Куда писать логи в контейнере?

**Ответ:** в стандартный вывод. Сбором, хранением и ротацией занимается
инфраструктура, а не приложение.

### 18. Можно ли изменить уровень логирования без перезапуска?

**Ответ:** да, через эндпоинт Actuator `/actuator/loggers`. Это стандартный приём
при разборе проблемы в продакшене.

### 19. Чем плох System.out.println?

**Ответ:** нет уровней, времени, имени класса, ротации, MDC и возможности
настройки. Вывод синхронный и блокирует поток.

### 20. Зачем нужен AsyncAppender?

**Ответ:** чтобы запись не блокировала поток обработки запроса. Плата — потеря
части буфера при аварийном завершении и отбрасывание записей при переполнении
очереди.
